The big picture

One process, the controller (bbh super serve), is the only writer of one SQLite database. Every change is a command sent to it over a loopback socket. The controller asks the pure model to decide the command, which either refuses it or returns events. Then it folds each event into the state and writes the changed records, all in one transaction. Nothing else changes the state.

The state holds eight record kinds, listed in model.clj › entity-kinds: counters, threads, workers, asks, replies, outbox, tokens and router. The rest of this page covers the life of each one, plus the processes and files around them.

  • A thread is one piece of your work, with a handle such as T38. It has at most one live Worker at a time and keeps the ones that came before in :history. What it is doing (:execution) is derived from its latest Worker, never stored.
  • A Worker is a bbh agent session in its own jj workspace, driven by a wf run. It talks to you through asks, and you answer with replies.
  • Every message to a session goes through the outbox. The controller turns a row into a mailbox file, the session takes the file itself, and the row is :done once the file is gone.
  • The Router is one long-lived session that reads what you say when no thread is named. It starts threads and Workers for you, and cancels, steers or replaces them when a message of yours asks.

Measured at 1948e818: 28 commands with a decide* method, plus sweep! in the controller and 9 reads; 28 fold* methods, of which 26 fold events a command emits today and 2 (:thread-linked, :worker-attached) fold only old logs, plus 6 retired kinds that fold to nothing (model.clj › retired-events). The machines have 8 Worker states, 7 derived thread executions plus archived, 5 ask states, 2 reply states, 4 outbox states, 5 health classifications and 5 job states. Two Shepherd services run it.

Commands, events and the store

Every change follows one path, and the same path serves every surface, Worker and internal step.

  1. Request. A client sends {:command :args :id :token} as one EDN line to the controller's port. client.clj › call!
  2. Principal. The controller looks up the sha256 of the token among the unrevoked tokens. The principal is :owner, :router or [:worker "W32"]. With no match the answer is :unauthorized. super.clj › handle, principal-of
  3. Reads (:threads :thread :events :ask :reply :worker :health :projects :sections) are answered from memory and write nothing. super.clj › read-command
  4. Writes go through run!, which serializes on the database. It calls store/commit!, which opens one transaction. A command id that was seen before returns its stored result with :repeat? true, so every retry is safe. Otherwise model/decide authorizes the command and decides it, the events get :seq and :at and are appended, model/fold applies them, model/changed lists the records that differ and upsert! writes those, and the result is stored under the command id. A refusal rolls everything back. super.clj › run! store.clj › commit!, upsert! model.clj › decide, authorize, fold, changed
  5. Side effects (opening a workspace, starting a wf run, opening a buffer, landing, sending mail) happen in the controller around the commits, never inside the model. Each one is keyed so that a repeat after a crash reuses what already exists. Internal steps use fixed command ids such as running-W32, sent-o41, acked-o41 and dropped-o41. super.clj › launch!, dispatch!

The database has an append-only events table, a commands table (id → result), and one table per record kind that holds the folded records. store/replay refolds the events alone, so you can check that against store/load. store.clj › schema, record-ddl, load, replay

Threads

A thread is created by :thread! (:thread-created) and named T plus a counter. Its :execution is not stored: execution derives it from the thread's latest Worker, and every read of a thread adds it (thread-view). Archiving sets :resolved-at and is the only way a thread ends. Once archived, a thread refuses new Workers (:archived). A Worker that was already running carries on, but it no longer holds a slot. model.clj › execution, thread-view

What a finish does to the rest of the state

fold* :worker-finished sets the outcome and :reason (and :landed, the landed change id, for :done). It revokes the Worker's tokens and marks its still-open asks :superseded, because nobody is left to read an answer. If the Worker is still the thread's current one, the fold also clears :worker, appends it to :history and bumps :milestone-seq; the thread's execution follows from the outcome. From then on the Worker gets no mail: its pending and sent rows are dropped (see Outbox).

Launch

launch! runs these steps in order. Each is idempotent by the Worker's name. super.clj › launch!, launch-steps!

  1. workspace! creates or reuses the jj workspace <super>/workspaces/<thread>-<generation>. A repo that does not exist yet gets jj git init first.
  2. It creates conversations/super-<id>, and wf-start! starts the wf run with the brief as the task, unless the Worker already has one.
  3. worker-prepared! runs.
  4. open! calls eng/bbh-super-open in the Emacs daemon, which opens a bbh acp session in the workspace with BBH_SUPER_TOKEN and WF_RUN.
  5. worker-running! runs, with the brief row.

A step that throws fails the Worker with Launch failed: … and promotes the next one. The one exception is an Emacs error while the daemon is down: then the Worker stays :starting, and once Emacs is up and 30 s have passed since its start or the controller's boot, reconcile! issues it a new token and opens its buffer.

Slots

A Worker holds a slot under the cap when it is in :starting :working :waiting :cancelling, its session has not ended, and its thread is not archived. The cap is the only limit on starting Workers. model.clj › active-states, holds-slot?, session-ended?, blocked-by

Health, session ends and resume

reconcile! follows one rule: observe before acting. It runs under recovery-lock when a Worker is cancelling, at least every 2 minutes, and right after each cancel!. For every queued or active Worker it reads the conversation's agent.json (the live session, checked by pid and start time), its jobs, its wf status and whether its REPL answers an nREPL describe. From those it builds one classification. It commits :health! only when the health differs from the stored one in more than :at, and a commit that changes only when it was observed reloads no view. super.clj › reconcile!, repl-answering?, shown; inbox.clj › agent; model.clj › health-changed?, decide* :health!, fold* :health-observed

Acting on it

  • Starting, with a live session: worker-running! runs (see Launch).
  • Cancelling: see the cancel row above. A cancelling Worker whose session ended is cancelled at once, since there is no session to tell.
  • Starting, without a session: the Emacs-down case of Launch.
  • Session ended: nothing. The controller never relaunches a session or its jobs. The Worker waits for you, and the Inbox shows it under Needs attention.
  • Orphan jobs: jobs of Workers that ended :done or :failed are stopped on every pass.
  • Router: ensure-router! runs at the end of every pass.

Resume

You have three ways on: resume it (resume!, see the Workers table), cancel it (x), or tell the Router to replace it, which starts the thread's next generation with a fresh brief. A resumed Worker keeps its conversation and wf run. Its [Recovery] message tells it to continue the existing run, inspect its jobs before acting and not relaunch surviving ones. When the last health pass saw jobs in state :rebooted, the message names them as killed by a reboot, so the Worker neither waits on them nor reruns one it does not need. A job is :rebooted when its .boot names another boot id or, for an older job without one, its .cmd is older than the boot time read from /proc/stat. model.clj › decide* :resume!, rebooted-jobs; super/process.clj › jobs, boot, before-boot?

Jobs

observe-jobs! runs on every dispatcher pass. For each jobs/*.exit of a working or waiting Worker that it has not yet recorded, it commits job-exited! under the stable id job-exited-[W job]. It skips an exit that a running job-wait will report itself (.waiting). That gives :job-exited, which records the job and, unless the Worker already read the exit (.seen), queues [Job id exited with status n. Log: …] to the Worker. It never launches anything. super.clj › observe-jobs!; model.clj › decide* :job-exited!, fold* :job-exited

Asks and replies

An ask is how a Worker needs you: a question with options, an action for you to take, or a review of a revision. A reply is your answer, which can cover several asks of the thread at once. While you choose, your picks and note are the thread's draft. The reply travels to the Worker as an outbox row, its session takes it into a turn, and the Worker confirms it acted with super-answered!.

The outbox and mailbox delivery

A message to a session is never sent inside a command. Instead the command adds an outbox row (o plus a counter, holding the conversation and text) in the same transaction as the change that caused it. The dispatcher then delivers it. So a crash can delay a message but never lose it. super.clj › dispatch!

One dispatcher pass

  1. Router rows. When at least one pending Router row is not a summary, every pending Router row goes out as one mailbox message, oldest first. Each line except a summary is prefixed with its row id, such as o12 [emacs] …. Each row then gets outbox-sent!. A summary never wakes the Router alone.
  2. Dead letters. A pending or sent row for a conversation whose Workers have all finished gets outbox-dropped! (dropped-o…), and its mailbox file is deleted unread. A finished Worker gets no mail. model.clj › dead-letter?, decide* :outbox-dropped!
  3. Worker rows. Each other :pending row gets inbox/send!: a JSON file written atomically to <conversation>/mailbox/<message-id>.json, with kind steer for steering. Then outbox-sent! (sent-o…) records the message id.
  4. Taken. When a :sent row's file has left the mailbox, outbox-acked! (acked-o…) marks the row :done.

:outbox-sent only moves a :pending row, so a late repeat never moves one back. :outbox-acked and :outbox-dropped only move a pending or sent row, so neither undoes the other. model.clj › fold* :outbox-sent, :outbox-acked, :outbox-dropped

How a session takes a message

Delivery is at least once, and the session does it itself. take-mail! claims every waiting message that is not a cancel, oldest first, tagged [Mail id] or [Steering id]. It runs at the start of each input, before each model call of a running turn and ahead of each tool result, so steering reaches the model in the turn that is running. record! deletes a file once the transcript holds its tag, and that deletion is what the controller watches for. A message that was claimed but never recorded stays in the mailbox and is taken again. An idle session needs a nudge: its Emacs shell sends the prompt [mail] (mail-wake), which prompt! replaces with the waiting mail. The shell checks every second and after each turn, so a stuck shell delays mail but cannot lose it. A cancellation is no prompt: watch-controls! acts on it within 200 ms. session.clj › take-mail!, record!, mail-wake, prompt!, run-code!, watch-controls!; inbox.clj › send!, pending, ack!; agent-shell.el › eng/bbh-mail-watch, eng/bbh-mail-wake, eng/bbh-mail--on-event, eng/bbh-mail-waiting-p

A message stuck :sent means the session never recorded a turn that held it. T36 traced idle Workers that never took their mail to shells left busy in a deleted workspace directory. The fix, release-session!, moves the session out of the workspace before retire! deletes it. Past 30 minutes, health shows the stuck row as :needs-human.

The Router: say! and routing

Everything you type or dictate without a reply context enters as say! with an origin: :emacs, :phone, :voice or :herdr. model.clj › decide* :say!

  1. Handle. When the text starts with a handle (T38, t38, tee thirty eight), the handle is stripped and the rest goes to that thread's Worker as :worker-steered ([T38 from voice, dictated] …). If the thread has a Worker that is not :working or :waiting with a conversation, the result is :not-running. If the thread has no current Worker, the text goes to the Router as T38: …. An unknown handle is refused with :no-such-thread. Only a handle sends a message to a Worker. model.clj › parse-handle, deliverable?
  2. Otherwise it becomes :router-queued: an outbox row for the Router's conversation with the :origin recorded. With no Router registered the result is :no-router. model.clj › router-row

Each delivery to a Worker also queues a summary row for the Router, so the Router knows what went where without acting on it. There is no triage: the Router reads every message itself and leaves noise without a reply or action.

When your message asks for a change

When a message asks to cancel, steer or replace Workers, the Router acts only on what it asks and passes the message's row id: (super-cancel! w reason {:for "o66"}), (super-steer! w text {:for "o66"}), or, for a Worker whose session ended, (super-start-worker! {:for "o66" :thread id :replaces w …}). message-lease turns that id into the authority: a :lease-granted event with the row, its origin, the command and the Worker, written in the same commit. A live Worker is replaced by cancelling it and then starting one. model.clj › message-lease, replacement; super/sandbox.clj › bindings; init.clj › router-helpers

Registering and running the Router

register-router! (:router-registered) records the Router's conversation and revokes every earlier Router token. The controller does this by itself in ensure-router! when no session runs in the Router conversation, at most once per 30 s, and only while Emacs is up. Then open-router! opens the Router buffer and the Inbox. bbh super start-router does the same by hand. The Router's prompt tells it to answer questions in one line, start a thread and a Worker for each request with :for naming the message's row, ignore [routed to …] lines, and never default to a repository. super.clj › ensure-router!; client.clj › open-router!, start-router!; init.clj › router-helpers

Workflow (wf) runs, phases and gates

Every controller-launched Worker drives one wf run, which wf-start! starts at launch with the brief as its task. The run's id goes into the Worker's environment as WF_RUN. A run is a journal of events (journal.edn) under ~/.local/state/bbh/workflows/<id>/, with an evidence/ directory beside it. workflow.clj › start!, fold-event, replay; super.clj › wf-start!

Run status: :active → :done when the last phase passes. A run becomes :blocked when a phase would be entered more often than its :max-visits (default 3) or names an unknown phase, and :abandoned on wf abandon. workflow.clj › fold-event, enter, abandon!

  • wf attest runs every gate of the current phase itself. A command gate runs the run's :repro, :check or :bench with sh -c under a 600 s timeout and expects exit 0 (or nonzero), and its output is saved as evidence. An artifact gate needs a non-empty file in evidence/. A verdict gate needs a verdict recorded for this phase and visit. workflow.clj › attest!, run-gates, run-command, run-artifact, run-verdict
  • The outcome is :fail if any gate failed, else :pending if a verdict is missing, else :pass. Pending changes nothing. Pass enters :next, or :done when there is none. Fail enters :on-fail, or the same phase again with its visit count up. workflow.clj › outcome, decide
  • An attest is recorded only if the run is still at the phase and visit its gates ran for. Otherwise nothing is recorded (one of the races T25's model found). Verdicts come from wf review, which runs a fresh reviewer, or from wf verdict --human. workflow.clj › attest!, review!, verdict!

Where wf meets super

  • start-worker! refuses a workflow whose :requires flags are missing, and an unknown workflow. super.clj › start-worker*; model.clj › decide* :start-worker!
  • Health reads workflow/status. A missing run makes the Worker :needs-human. A resumed Worker continues the same run. super.clj › reconcile!
  • A :review ask binds to the evidence's sha256, and an approval is stale if the evidence changed. super.clj › evidence-sha
  • The super state does not track wf phases. A Worker calls super-done! when wf status says done.

Message flows, end to end

You to a Worker and back

You type T38 use docs/ into the Router composer in Emacs. The Worker later stops on a question, you answer it in the Inbox, and it finishes.

Steps 3, 10, 14 and 18 are single store/commit! transactions. Steps 4, 5, 8 and 15 run in the dispatcher thread, at most 500 ms apart. Step 6 happens inside the running turn, before its next model call; an idle Worker would first get the [mail] wake from its shell. Step 7 is the session deleting the file once its transcript holds the message. Step 11 is notify-views! poking each registered Inbox port. Step 12 writes the thread's draft, and step 13 sends it. The reply could also come from the phone (POST /api/super/threads/T38/reply), and it would take the same path from step 14 on.

A request the Router turns into a Worker

The Worker records the origin of row o12, and its brief says where the request came from. If the cap is full, it stays :queued after step 9 until promote! picks it. Steps 4 and 5 are the Router's own mail path: its shell wakes it, and the session takes the batch and deletes the file.

A Worker whose session ended

The machine reboots while W32 waits on job-wait. On the next health pass reconcile! finds no session, sees the job as :rebooted, and commits :session-ended; W32 frees its slot and T38 moves to Needs attention. You press u: resume! checks there is a free slot, commits :worker-resumed with a [Recovery] row that names the dead job, and resume* reopens the buffer with a new token. The dispatcher delivers the row like any other, and the session continues its wf run. Had you told the Router "restart T38 from scratch" instead, it would have run start-worker! with :replaces "W32" and :for your message: W32 fails as replaced and W33 starts as T38's next generation. super.clj › reconcile!, resume*; model.clj › decide* :resume!, replacement
