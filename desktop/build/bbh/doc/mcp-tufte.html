MCP, read off one wire

The Model Context Protocol, revision 2026-07-28, traced through Claude Code, bbh.mcp and a babashka REPL

A language model can only act through the tools its host program hands it. Before MCP every host wired every tool by hand. Three hosts and four tool providers meant twelve adapters, each with its own idea of how to list a capability, call it and report failure.Left, three hosts (squares) and four servers (circles) integrated pairwise, twelve adapters. Right, the same seven parties through one protocol, seven implementations. The cost grows as M×N on the left and M+N on the right.
 MCP replaces the pairs with one contract. A host implements the client side once, a tool provider implements the server side once, and any client talks to any server.

The idea is borrowed openly from the Language Server Protocol, which did the same for editors and programming languages.The specification says so in its overview, docs/specification/2026-07-28/index.mdx. LSP also supplied the wire format, JSON-RPC 2.0, and the habit of negotiating capabilities instead of assuming them. The protocol has moved quickly. Five dated revisions have shipped in twenty months (2024-11-05 to 2026-07-28, the current one in red), and the latest is the largest break so far. It removes the opening handshake that the four before it required.Every statement about the protocol on this page is checked against revision 2026-07-28, read from the spec repository modelcontextprotocol/modelcontextprotocol at commit 3c4d91b (2 November 2026). Where the older, stateful behavior matters, the page cites 2025-11-25, which is what the worked example actually speaks.

This page explains the protocol from one concrete deployment, the one running on this machine. bbh is a babashka program that starts Claude Code as its agent loop and gives the model a single tool, a Clojure REPL. The tool reaches the model through MCP. Every claim about that deployment comes either from its source, desktop/build/bbh/src/bbh/mcp.clj and claude.clj, or from a trace of real messages captured on 5 November 2026 and dissected in the last section.

Hosts, clients and servers

MCP names three roles. The host is the application the person uses, here Claude Code. It owns the model, the conversation and the permission prompts. Inside the host sit one or more clients, each holding exactly one connection to one server.The one-to-one rule keeps servers isolated. A server sees only its own connection, never the conversation or the other servers. The host decides what crosses between them. A server is a program that offers capabilities, and it may run as a local child process or as a remote web service.

Three flags in claude.clj make this server the model's whole world. --tools '' removes Claude Code's built-in tools, --strict-mcp-config ignores any other MCP configuration on disk, and --allowedTools mcp__bbh__clojure pre-approves the one tool that remains. The name shows the host's convention. Claude Code exposes a server's tool clojure from the server it calls bbh as mcp__bbh__clojure.bbh also sets MCP_TOOL_TIMEOUT=1800000, thirty minutes, because one REPL call may legitimately wait ten minutes on a background job. Timeouts are a host policy. The protocol only says that a sender should cancel a request it has given up on.

Transports

The protocol defines two standard transports and leaves room for custom ones. Both carry the same JSON-RPC messages, so a server's logic does not change with its transport.

stdio is the local transport. The client launches the server as a subprocess, writes messages to its standard input and reads messages from its standard output, one JSON object per line, with no embedded newlines. Anything else the server wants to say goes to standard error, which the client may show, log or ignore. Standard output must carry nothing but valid MCP messages.bbh.mcp answers tools/call on a future, so two calls can finish at once. Its send! takes a lock around println and flush, which keeps two replies from interleaving within a line. Without it the newline framing would break under load. Shutdown is equally plain. The client closes the server's input, waits, and escalates to SIGTERM and then SIGKILL if the process lingers.

Streamable HTTP serves remote servers from a single endpoint. Each client message is its own POST, and the server answers either with one application/json body or with a text/event-stream that carries progress notifications before the final result. Revision 2026-07-28 simplified this transport sharply. It dropped the Mcp-Session-Id header and protocol-level sessions, the standing GET stream, and stream resumption by Last-Event-ID. It added required MCP-Protocol-Version, Mcp-Method and Mcp-Name headers so that proxies can route a request without parsing its body.The original HTTP+SSE transport, two endpoints and a long-lived event stream, was replaced in 2025-03-26 and is formally Deprecated in 2026-07-28 (SEP-2596). Change notifications that used to ride the GET stream now flow on an explicit subscriptions/listen request.

JSON-RPC messages

Every MCP message is a JSON-RPC 2.0 object with "jsonrpc": "2.0". There are only four shapes, and a reader who can tell them apart can follow any MCP exchange.

Errors use the JSON-RPC codes for parse failures (−32700), invalid requests (−32600), unknown methods (−32601), bad parameters (−32602) and internal faults (−32603). Revision 2026-07-28 reserves −32020 to −32099 for the specification itself, for example −32022 for an unsupported protocol version, and leaves −32000 to −32019 to implementations.

A failing tool is not a protocol error. When the code a tool runs throws, the server still returns a normal result, with the message in its content and isError: true, so that the model can read the failure and try again. bbh.mcp follows this rule. Its call catches every exception and reports it as content prefixed bbh bridge:.

Any params or result object may also carry _meta, a map for data about the message rather than its payload. Keys under io.modelcontextprotocol/ belong to the specification; other prefixes belong to whoever defines them. The trace shows both kinds.

Lifecycle

Here the revisions part ways, and the figure below draws them side by side on the same scale.

Up to 2025-11-25 a connection is stateful. The client's first message must be initialize, carrying the newest protocol version it supports, its capabilities and its identity. The server replies with the same version if it supports it, or with another it does support, together with its own capabilities. The client then sends the notification notifications/initialized, and only then does ordinary traffic begin.Capabilities are declarations of what each side will handle. A server that declares tools promises tools/list and tools/call. Adding listChanged: true promises a notifications/tools/list_changed whenever the list changes. Neither side may use a feature the other did not declare. Everything negotiated holds until the connection ends.

Notifications fill the operation phase. A server reports progress on a long request with notifications/progress, keyed by the progressToken the client supplied. Either side withdraws a request with notifications/cancelled. A server whose tool list changes says so with notifications/tools/list_changed. Shutdown has no message of its own; the transport's end is the end.

Revision 2026-07-28 deletes the handshake, along with ping and logging/setLevel (SEP-2575). Every request now carries its protocol version and the client's capabilities in _meta, under io.modelcontextprotocol/protocolVersion and io.modelcontextprotocol/clientCapabilities. A server that cannot honor the version answers UnsupportedProtocolVersionError. A new method, server/discover, which every modern server must implement, returns the supported versions, capabilities and identity in one reply.Statelessness is what lets a remote server sit behind an ordinary load balancer. Any replica can answer any request, because nothing was negotiated on a connection that a different replica never saw. Every result also gains a resultType, which is "complete" for ordinary results. List results gain ttlMs and cacheScope, so clients can cache tool lists instead of polling.

Old and new must coexist for a while, and the specification says how. On stdio a client that speaks both eras should probe with server/discover first. A DiscoverResult means a modern server. A recognized modern error means a modern server that wants another version. Any other error, or silence, means a legacy server, and the client falls back to initialize. Claude Code 2.1.309 does exactly this, as the trace shows.

Primitives

A server offers three kinds of things, and a client offers three in return. They differ most in who decides when they are used.

primitiveoffered bywho decides to use itmethodsstatus in 2026-07-28in this setup
toolsserverthe modeltools/list, tools/callactivebbh.mcp offers one, clojure

Tools are functions the model may call, each described by a name, a description and a JSON Schema for its input.bbh's schema, as it crossed the wire, is {type: object, properties: {code: {type: string}}, required: [code]}. Revision 2026-07-28 allows any JSON Schema 2020-12 keyword here (SEP-2106). Resources are data addressed by URI, a file, a database row, a log, that the application chooses to put in front of the model. Prompts are templates the user picks on purpose, which many hosts surface as slash commands.

The client-side features let a server ask for something back. Sampling asks the host's model for a completion, roots asks which directories the server may work in, and elicitation asks the person for input, through a schema-checked form or, for anything sensitive such as a credential, a URL the person opens outside the client. In 2025-11-25 these were requests the server sent to the client. Revision 2026-07-28 replaces that with multi round-trip requests (MRTR, SEP-2322). The server answers the original request with resultType: "input_required" and a set of inputRequests, and the client retries the original request with inputResponses attached.The same revision deprecates sampling, roots and logging (SEP-2577). The suggested replacements are tool parameters or server configuration for roots, direct provider APIs for sampling, and stderr or OpenTelemetry for logs. Deprecated features keep working for at least twelve months. Nothing in that exchange needs state on the server.

To see the protocol rather than its description, a small script sat between Claude Code and the real bbh.mcp and copied every line to a log with a millisecond timestamp. The model was Haiku, to keep the run short, and the bbh session behind the loopback socket was a stub that evaluated the code with load-string. Probe

Message 1, at 5 ms. Claude Code opens with the 2026-07-28 probe. The version, its identity and its capabilities all ride in _meta, because modern requests carry their own context. The capabilities say what this host will handle, roots with change notifications, elicitation in both modes and the official tasks extension. Sampling is absent; this host will not lend its model to a server.The id is the string server-discover-probe-1. JSON-RPC permits string or integer ids, and Claude Code switches to integers from 0 once it has picked an era.

Message 2, at 48 ms. The reply took 43 ms because the line waited in the pipe while babashka started.Inferred, not measured. The tee logged the request when it wrote it to the pipe, and every later reply took at most 5 ms. bbh.mcp knows nothing of server/discover, and its catch-all answers any unknown request with an empty result. That reply is neither a DiscoverResult, since it has no supportedVersions, nor the error the specification expects from a legacy server. Claude Code read it as legacy anyway and fell back, which is the outcome bbh needs, though the specification does not promise it.A one-line change would make the probe unambiguous. The catch-all could return the error in Figure 3, −32601 Method not found, for any unknown request. Being a legacy server is legal. Answering the probe with an empty success is the questionable part.

Message 8, at 1190 ms. After 1.1 seconds of model time the call arrives. Two keys ride in _meta. progressToken invites progress notifications, which bbh.mcp never sends. claudecode/toolUseId is a vendor key, outside the io.modelcontextprotocol/ namespace, carrying the id of the model's tool-use block. bbh.mcp passes it on as the call's id inside the session, which is how a REPL evaluation is matched to its line in the conversation transcript.

Shutdown

Nothing more crossed the pipe. When claude -p finished it closed the server's standard input. line-seq in bbh.mcp ran out, -main returned and the process exited, which is the graceful path the stdio section prescribes.

The whole server is the dispatch below, plus a few helpers that forward calls to the session. Set against the trace, each branch accounts for one message, and the last branch is the one that answered the probe.

(defn -main [& _]
  (doseq [line (line-seq (io/reader System/in))]
    (let [{:keys [id method params]} (json/parse-string line true)]
      (case method
        "initialize" (send! {:id id :result {:protocolVersion (:protocolVersion params)
                                             :capabilities {:tools {}}
                                             :serverInfo {:name "bbh" :version "1"}}})
        "tools/list" (send! {:id id :result {:tools [{:name "clojure" …}]}})
        "tools/call" (future (call id params))
        (when id (send! {:id id :result {}}))))))

What the wire shows

  1. bbh's server speaks the stateful 2025-11-25 dialect. Claude Code 2.1.309 speaks both eras and chose the old one after one probe. Measured.
  2. The probe works by luck of interpretation. An empty result is not a valid reply to server/discover, and a stricter client could stop there instead of falling back. Inferred from the spec's stdio compatibility rules.
  3. Seven messages and 64 ms passed before the model could see its tool, most of it spent starting the server process. After that one tool call cost two messages and 282 bytes. Measured on one run.
  4. Of the six primitives, bbh uses one. The page's table shows what the rest would offer if bbh grew resources or prompts. Not tested here.
