bbh workflow engine

How pstack workflows run inside bbh, what the gates check, and how to drive a run from Pi or bbh.

The idea

A workflow is a small state machine for one task. Each phase names what the agent must do and the checks that prove it. The agent can claim it finished, but only the runner decides whether the phase advanced.

The split has three parts.

  • The agent reads the phase brief, does the work, writes evidence files, and attests.
  • The runner (wf, in bbh.workflow) runs every gate itself. It executes commands, checks files, and reads recorded verdicts. It then moves the phase or refuses.
  • You record verdicts for reviews that need judgment, and you answer when a run is blocked.

Flow

The bug-fix workflow is shown below. The other two workflows are linear.

What one attest does

  1. Read the run's journal and fold it into the current state: phase, visit count, and recorded verdicts.
  2. Run every gate of the current phase, in order. Command gates write their output to the evidence directory. Artifact gates check the file. Verdict gates look for a verdict recorded for this visit.
  3. Append an attest event with every gate result.
  4. Decide the next step from the results. A pending verdict changes nothing. A pass moves to the next phase. A fail moves to on-fail, or retries the same phase when there is none.
  5. Append the resulting events. The journal is append-only, so a run can be resumed from any process.

Gates

KindWhat the runner checksExample
:commandRuns the command with timeout and sh -c in the run's repo. Passes when the exit code matches :expect (default :zero). A timeout always fails. Output and a SHA-256 are recorded.{:kind :command :cmd :repro :expect :nonzero}
:artifactThe named file exists in the evidence directory and is not empty. This only proves that something was written.{:kind :artifact :path 'mechanism.md'}
:verdictA verdict was recorded for the current visit. Agents get one from wf review, which starts a fresh bbh conversation with the criteria and the evidence. The reviewer's reply must end with a VERDICT: pass or VERDICT: fail line, or the review fails. A person can record one with wf verdict --human NAME. Until a verdict exists the gate is pending. It passes only on :pass.{:kind :verdict :criteria '...'}

:cmd :repro and :cmd :check are placeholders. They resolve to the --repro and --check values given at start. A gate marked :optional true is skipped when its command was not given.

A failed gate outranks a pending one. So a missing artifact is reported as a failure even while a verdict is still waiting.

A command gate also has a timeout. It defaults to 600 seconds and can be set per gate with :timeout. A timeout always fails the gate, even when a nonzero exit was expected.

Visits and caps

Each entry into a phase counts as a visit. A failed attest that retries the same phase also counts. Every phase has a cap, :max-visits, which defaults to 3. Going past the cap blocks the run.

bug-fix, verify fails three times in a row:
  implement  visit 1  -> verify 1  -> fail -> implement 2
  implement  visit 2  -> verify 2  -> fail -> implement 3
  implement  visit 3  -> verify 3  -> fail -> implement 4   (4 > 3)
  status: blocked, "phase implement exceeded 3 visits"

A blocked run refuses further attests. Only you can unblock it, by starting a new run.

Each phase carries a short brief. wf status prints the brief for the current phase. The briefs live in the workflow EDN files in desktop/build/bbh/src/bbh/workflows/. There is no separate playbook text.

Commands

CommandEffect
wf start <workflow> --task T [--repro CMD] [--check CMD] [--cwd DIR]Creates a run and prints its status and brief.
wf status [RUN]Phase, visit, status, brief, and evidence directory. RUN defaults to the latest run.
wf attest [RUN] --claim TEXTRuns the gates for the current phase and prints each result.
wf review [RUN]Starts a fresh reviewer for the current verdict gate, records its verdict, and prints it with the reason.
wf verdict [RUN] --human NAME --verdict pass|fail [--note TEXT]Records a verdict from a person. Agents are told not to use it.
wf session-dir [WORKSPACE] [DIR]Prints Pi's session directory for a workspace. Used by the recall, reflect, and show-me-your-work skills.

From Pi, run these in bash. From bbh, use (sh "wf status") in the clojure tool. Runs and evidence live under ~/.local/state/bbh/workflows/, outside the repo.

Example

This transcript is from the first version, when the verdict was typed by hand with wf verdict. The model-driven runs under the current rules are covered in their own section.

This is a real run from a toy project. Its calc.clj computed (- a b) for add. The repro script checked (= 5 (add 2 3)). Some lines are shortened.

$ wf start bug-fix --task 'add returns the difference' --repro 'sh repro.sh'
run 20261023-224248-284-bug-fix
workflow bug-fix  phase reproduce  visit 1  status active

$ wf attest --claim 'repro fails'
attest: pass
  [ok] `sh repro.sh` exited 1, output in .../evidence/reproduce-1-0.txt

$ wf attest --claim 'mechanism, no evidence'
attest: fail
  [FAIL] artifact .../evidence/mechanism.md
  [wait] verdict pending: The evidence causally supports the mechanism...
workflow bug-fix  phase diagnose  visit 2  status active

$ wf attest --claim 'mechanism written'          # after writing mechanism.md
attest: pending
  [ok] artifact .../evidence/mechanism.md
  [wait] verdict pending: The evidence causally supports the mechanism...

$ wf verdict --reviewer fresh-review --verdict pass --note 'line 3 is the mechanism'
$ wf attest --claim 'mechanism accepted'
attest: pass
workflow bug-fix  phase implement  visit 1  status active

$ wf attest --claim 'premature: claims done'     # implement has no gates
attest: pass
workflow bug-fix  phase verify  visit 1  status active

# calc.clj fixed here
$ wf attest --claim 'fixed the minus'
attest: pass
  [ok] `sh repro.sh` exited 0, output in .../evidence/verify-1-0.txt
  [ok] optional check skipped, none given at start
workflow bug-fix  phase finish  visit 1  status active

$ wf attest --claim 'reported'
workflow bug-fix  phase finish  visit 1  status done

$ wf attest --claim 'after done'
run is done

Two details to notice. The premature claim at implement passed, because that phase has no gates by design. Its harm is limited, because verify still needs the repro to pass. And the verdict ran against visit 2, the visit that wrote the evidence. A verdict recorded earlier would not have counted.

Journal and state

Each run lives in ~/.local/state/bbh/workflows/<run-id>/. It holds journal.edn and an evidence/ directory. The journal is an append-only list of EDN maps. The current state is recomputed from it on every call. Here are the first three events of the run above, trimmed.

{:type :start, :workflow :bug-fix, :phase :reproduce, :repro "sh repro.sh", :cwd "/tmp/...", :id "20261023-224248-284-bug-fix"}
{:type :attest, :phase :reproduce, :visit 1, :claim "repro fails", :outcome :pass,
 :gates [{:kind :command, :cmd "sh repro.sh", :exit 1, :evidence "...reproduce-1-0.txt", :sha256 "e3b0...", :pass? true}]}
{:type :enter, :phase :diagnose, :visit 1}

Replaying the journal gives the state, so a crashed or restarted process resumes where the run left off. Re-running a command gate in the same visit overwrites that visit's evidence file and appends a new event. Earlier events are never edited.

Each event is one append. A crash mid-write can leave a partial last line. Reads drop a partial last line and rewrite the file without it. The dropped event was never committed, so the run continues from the state before it. A bad line anywhere else means corruption, and reads stop with the line number.

Routes and where they live

Jev classifies a new task into a route, and each route maps to a workflow. The route list appears in three places.

  • desktop/build/bbh/src/bbh/workflows/*.edn, under :routes. This is the mapping to workflows.
  • desktop/configs/bbh/init.clj, the routes map that bbh passes to Jev.
  • desktop/pi/agent/extensions/jev-pstack.ts, the same list for Pi.

The test routes-match-the-jev-classifiers fails when the two classifier lists differ from the workflow routes plus the manual list. The manual routes are pr_workflow, skill_work, and other. pr_workflow stays manual on purpose, since there are no pull requests. A manual route has no workflow, so the agent does the work directly and says so.

Tests

Run with cd desktop/build/bbh && bb test:workflow. The suite has 15 tests and 44 assertions. They cover:

  • The bug-fix path from start to done, with a pending verdict, a fail, a retry, and a fix.
  • A premature fixed claim, which stays at reproduce.
  • Repeated verify failures, which block the run with the exact reason.
  • The change workflow refusing to start without --check.
  • A hanging repro, which fails even when a nonzero exit was expected.
  • An unknown run ID, which gives a clean error.
  • The decision function on its own, with literal expected events.
  • Route agreement across the workflows, Jev in Pi, and Jev in bbh.
  • The Pi session directory rule, including the explicit-directory override.
  • A torn last journal line, which is dropped, and a corrupt line in the middle, which stops reads.
  • A review that runs a fresh conversation and records its verdict, and a review with no VERDICT line, which fails. These use a scripted model, so they cost nothing.
  • performance refusing to start without --bench.

The full bbh suite also passes (bb test, 44 tests). The end-to-end run above went through the real wf launcher on a real project.

Model-driven runs

A model was given a real bug in a toy project and the prompt calc/add returns the difference, but it should return the sum. Fix it. Run it with bb eval:workflow [MODEL] [OUTPUT-DIR] from desktop/build/bbh. It runs a real bbh conversation, with the poteto-mode skill injected on the first prompt, and it records what the run did.

Three findings came out of these runs.

  • Advisory rules get skipped. Run 1 read the skill, called its own work a one-line change, and went around it. The fix was to make the rule mandatory and to say that size does not exempt a task. Runs 2 to 4 all started the run before their first edit.
  • The reviewer has to be stronger than the agent. In run 2, the haiku reviewer passed a mechanism note that said wait see output above. A direct probe showed Sonnet rejects that note and passes a note that names the line and the repro output. The default reviewer is now Sonnet, and WF_REVIEW_MODEL overrides it.
  • Gates re-run commands, but artifacts stay weak. The agents wrote their own repro output and their own mechanism notes. The command gates ran the repro again, so a faked output could not pass. Nothing checks that a mechanism note is true, and only the reviewer judges it.

The eval runs wrote to the real state directory, so their runs appear in wf status history. Isolating the eval's state needs an environment variable set for the REPL, and that is not done yet.

Limits

  • Reviewer independence is by construction, not by proof. wf review gives the reviewer a fresh conversation and only the criteria, the task, and the evidence paths. A determined agent can still run wf verdict --human. The CLI requires that flag, and the rules forbid it, but nothing else stops it.
  • Artifact gates are weak. They check existence and size, not content. Command gates carry the real checks.
  • The implement phase is ungated. That is deliberate. The verify phase is the check that matters.
  • Commands run in the repo as the current user. A repro that writes files or hits the network will do so for real.
  • No parallel runs. Two agents on one run would interleave journal events. Use separate runs.
  • Manual routes. pr_workflow, skill_work, and other still have no workflow.
