bbh workflow engine

How pstack workflows run inside bbh, what the gates check, how to drive a run from Pi or bbh, and how this compares with upstream pstack. Updated 2026-10-26.

The idea

A workflow is a small state machine for one task. Each phase names what the agent must do and the checks that prove it. The agent can claim it finished, but only the runner decides whether the phase advanced.

The split has three parts.

  • The agent reads the phase brief, does the work, writes evidence files, and attests.
  • The runner (wf, in bbh.workflow) runs every gate itself. It executes commands, checks files, and reads recorded verdicts. It then moves the phase or refuses.
  • You record verdicts for reviews that need judgment, and you answer when a run is blocked.

Flow

The bug-fix workflow is shown below. Every workflow is a chain along :next. Some phases also name an :on-fail phase to go back to. These are verify in bug-fix, review in change, measure and review in performance, answer in prototype, and review in large-project.

What one attest does

  1. Read the run's journal and fold it into the current state. That is the phase, the visit count, the recorded verdicts, and the workflow definition the run started with.
  2. Run every gate of the current phase, in order. Command gates write their output to the evidence directory. Artifact gates check the file. Verdict gates look for a verdict recorded for this visit.
  3. Append an attest event with every gate result.
  4. Decide the next step from the results. A pending verdict changes nothing. A pass moves to the next phase. A fail moves to on-fail, or retries the same phase when there is none.
  5. Append the resulting events. The journal is append-only, so a run can be resumed from any process.

Gates

KindWhat the runner checksExample
:commandRuns the command with timeout and sh -c in the run's repo. Passes when the exit code matches :expect (default :zero). A timeout always fails. Output and a SHA-256 are recorded.{:kind :command :cmd :repro :expect :nonzero}
:artifactThe named file exists in the evidence directory and is not empty. This only proves that something was written.{:kind :artifact :path 'mechanism.md'}
:verdictA verdict was recorded for the current visit. Agents get one from wf review, which starts a fresh bbh conversation with the criteria and the evidence. The reviewer model defaults to claude/opus, and WF_REVIEW_MODEL overrides it. If the reply has no VERDICT: pass or VERDICT: fail line, the reviewer is asked for it up to two more times, then the review fails. A person can record one with wf verdict --human NAME. Until a verdict exists the gate is pending. It passes only on :pass.{:kind :verdict :criteria '...'}

:cmd :repro and :cmd :check are placeholders. They resolve to the --repro and --check values given at start, or later with wf set. wf abandon retires a run so it stops being the default. A gate marked :optional true is skipped when its command was not given.

A failed gate outranks a pending one. So a missing artifact is reported as a failure even while a verdict is still waiting.

:cmd :bench works the same way with --bench. A workflow's :requires list names flags that wf start refuses to go without. change requires --check and performance requires --bench.

A command gate also has a timeout. It defaults to 600 seconds and can be set per gate with :timeout. A timeout always fails the gate, even when a nonzero exit was expected.

Visits and caps

Each entry into a phase counts as a visit. A failed attest that retries the same phase also counts. Every phase has a cap, :max-visits, which defaults to 3. Going past the cap blocks the run.

bug-fix, verify fails three times in a row:
  implement  visit 1  -> verify 1  -> fail -> implement 2
  implement  visit 2  -> verify 2  -> fail -> implement 3
  implement  visit 3  -> verify 3  -> fail -> implement 4   (4 > 3)
  status: blocked, "phase implement exceeded 3 visits"

A blocked run refuses further attests. Only you can unblock it, by starting a new run. Entering a phase the definition does not have also blocks the run, instead of finishing it.

Workflow files are validated when they load, and every problem is reported at once. A run stores the definition it started with, so editing a workflow file never changes a run in progress.

Each phase carries a short brief. wf status prints the brief for the current phase. The briefs live in the workflow EDN files in desktop/build/bbh/src/bbh/workflows/. There is no separate playbook text.

A phase can also list :principles, such as ["fix-root-causes" "attack-the-premise"] on bug-fix's diagnose phase. Each name is a pstack principle skill, desktop/pi/agent/skills/pstack/principle-<name>/SKILL.md. Those skills are hidden from the skill list, so this is how a run reaches them. wf status prints each one in full after the brief, without its YAML header and with its links made absolute. wf review gives the reviewer the same text. A name with no skill file fails validation when the workflow loads. A run journals the names with its definition, but the text is read fresh each time.

Commands

CommandEffect
wf start <workflow> --task T [--repro CMD] [--check CMD] [--bench CMD] [--cwd DIR]Creates a run and prints its status and brief.
wf status [RUN] [--json]Phase, visit, status, brief, and evidence directory. --json prints every phase with its brief, visits and gates, for the Emacs panel. It writes nothing.
wf attest [RUN] --claim TEXTRuns the gates for the current phase and prints each result.
wf set [RUN] [--repro CMD] [--check CMD] [--bench CMD]Replaces run commands on an active run. The next wf attest uses them.
wf abandon [RUN] [--reason T]Retires an active or blocked run. An abandoned run stops being the default for its directory or conversation.
wf review [RUN]Starts a fresh reviewer for the current verdict gate, records its verdict, and prints it with the reason.
wf verdict [RUN] --human NAME --verdict pass|fail [--note TEXT]Records a verdict from a person. It needs a terminal and asks you to type the run ID to confirm, so an agent's shell cannot use it.
wf session-dir [WORKSPACE] [DIR]Prints Pi's session directory for a workspace. Used by the recall, reflect, and show-me-your-work skills.

When RUN is omitted, wf uses $WF_RUN. Otherwise it uses the run this bbh conversation started, recorded in a workflow-run file beside the conversation's repl.port. Otherwise it uses the newest run started for the current directory or one containing it. Runs from other repositories never qualify.

From Pi, run these in bash. From bbh, use (sh "wf status") in the clojure tool. Runs and evidence live under $XDG_STATE_HOME/bbh/workflows/, which defaults to ~/.local/state/bbh/workflows/, outside the repo.

Example

This transcript is from the first version, when the verdict was typed by hand with wf verdict --reviewer. That flag is now --human, and agents run wf review instead. The model-driven runs under the current rules are covered in their own section.

This is a real run from a toy project. Its calc.clj computed (- a b) for add. The repro script checked (= 5 (add 2 3)). Some lines are shortened.

$ wf start bug-fix --task 'add returns the difference' --repro 'sh repro.sh'
run 20261023-224248-284-bug-fix
workflow bug-fix  phase reproduce  visit 1  status active

$ wf attest --claim 'repro fails'
attest: pass
  [ok] `sh repro.sh` exited 1, output in .../evidence/reproduce-1-0.txt

$ wf attest --claim 'mechanism, no evidence'
attest: fail
  [FAIL] artifact .../evidence/mechanism.md
  [wait] verdict pending: The evidence causally supports the mechanism...
workflow bug-fix  phase diagnose  visit 2  status active

$ wf attest --claim 'mechanism written'          # after writing mechanism.md
attest: pending
  [ok] artifact .../evidence/mechanism.md
  [wait] verdict pending: The evidence causally supports the mechanism...

$ wf verdict --reviewer fresh-review --verdict pass --note 'line 3 is the mechanism'
$ wf attest --claim 'mechanism accepted'
attest: pass
workflow bug-fix  phase implement  visit 1  status active

$ wf attest --claim 'premature: claims done'     # implement has no gates
attest: pass
workflow bug-fix  phase verify  visit 1  status active

# calc.clj fixed here
$ wf attest --claim 'fixed the minus'
attest: pass
  [ok] `sh repro.sh` exited 0, output in .../evidence/verify-1-0.txt
  [ok] optional check skipped, none given at start
workflow bug-fix  phase finish  visit 1  status active

$ wf attest --claim 'reported'
workflow bug-fix  phase finish  visit 1  status done

$ wf attest --claim 'after done'
run is done

Two details to notice. The premature claim at implement passed, because that phase has no gates by design. Its harm is limited, because verify still needs the repro to pass. And the verdict ran against visit 2, the visit that wrote the evidence. A verdict recorded earlier would not have counted.

Journal and state

Each run lives in ~/.local/state/bbh/workflows/<run-id>/. It holds journal.edn and an evidence/ directory. The journal is an append-only list of EDN maps. The current state is recomputed from it on every call. Here are the first three events of the run above, trimmed.

{:type :start, :workflow :bug-fix, :phase :reproduce, :repro "sh repro.sh", :cwd "/tmp/...", :id "20261023-224248-284-bug-fix"}
;; current runs also store :definition, the whole workflow map, in the start event
{:type :attest, :phase :reproduce, :visit 1, :claim "repro fails", :outcome :pass,
 :gates [{:kind :command, :cmd "sh repro.sh", :exit 1, :evidence "...reproduce-1-0.txt", :sha256 "e3b0...", :pass? true}]}
{:type :enter, :phase :diagnose, :visit 1}

Replaying the journal gives the state, so a crashed or restarted process resumes where the run left off. Re-running a command gate in the same visit overwrites that visit's evidence file and appends a new event. Earlier events are never edited.

Each event is one append. A crash mid-write can leave a partial last line. Reads drop a partial last line and rewrite the file without it. The dropped event was never committed, so the run continues from the state before it. A bad line anywhere else means corruption, and reads stop with the line number.

Routes and where they live

Jev classifies a new task into a route, and each route maps to a workflow. The route list appears in three places.

  • desktop/build/bbh/src/bbh/workflows/*.edn, under :routes. This is the mapping to workflows.
  • desktop/configs/bbh/init.clj, the routes map that bbh passes to Jev.
  • desktop/pi/agent/extensions/jev-pstack.ts, the same list for Pi.

The test routes-match-the-jev-classifiers fails when the two classifier lists differ from the workflow routes plus the manual list. The manual routes are pr_workflow, skill_work, and other. pr_workflow stays manual on purpose, since there are no pull requests. A manual route has no workflow, so the agent does the work directly and says so.

Emacs panel

Opening a bbh conversation in Doom's agent-shell also opens a *bbh workflow* buffer (desktop/configs/doom/agent-shell.el). It reads wf status --json for that conversation's run and lists the phases in run order with their briefs, visits and gates. j and k move the selection and g refreshes. The panel is read-only. Moving the selection changes only what it shows. The composer status line also shows the run as workflow: phase.

Tests

Run with cd desktop/build/bbh && bb test:workflow. The suite has 22 tests and 78 assertions. They cover:

  • The bug-fix path from start to done, with a pending verdict, a fail, a retry, and a fix.
  • A premature fixed claim, which stays at reproduce.
  • Repeated verify failures, which block the run with the exact reason.
  • The change workflow refusing to start without --check.
  • A hanging repro, which fails even when a nonzero exit was expected.
  • An unknown run ID, which gives a clean error.
  • The decision function on its own, with literal expected events.
  • Route agreement across the workflows, Jev in Pi, and Jev in bbh.
  • The Pi session directory rule, including the explicit-directory override.
  • A torn last journal line, which is dropped, and a corrupt line in the middle, which stops reads.
  • A review that runs a fresh conversation and records its verdict, and a review with no VERDICT line, which fails. These use a scripted model, so they cost nothing.
  • performance refusing to start without --bench.
  • The default run, which belongs to the current directory and never to another repository.
  • status --json listing phases in run order.
  • Validation. Every shipped workflow is valid, and an invalid one is rejected with every problem listed.
  • An unknown phase, which blocks the run instead of finishing it.
  • A run keeping the definition it started with after the file changes.
  • A property test. Random gate outcomes only ever enter real phases, and a run finishes only from a passing terminal phase.

The full bbh suite also passes (bb test, 83 tests and 243 assertions on 2026-10-26). The end-to-end run above went through the real wf launcher on a real project.

Model-driven runs

A model was given a real bug in a toy project and the prompt calc/add returns the difference, but it should return the sum. Fix it. Run it with bb -m bbh.workflow-eval [MODEL] [OUTPUT-DIR] from desktop/build/bbh. The eval:workflow task was removed from bb.edn, but the namespace is still on the classpath. It spends model credits. It runs a real bbh conversation, with the poteto-mode skill injected on the first prompt, and it records what the run did.

RunRule in the skillReviewerwf callsPathResult
1Advisory: "pick the workflow"none0Skipped the workflow, edited the file directly.Bypassed the workflow entirely.
2Mandatory: runs before any edit, size does not exempthaiku11Full path. Jev, start, repro, diagnosis, review, fix, verify, finish.Done. Fixed. Repro exit 0.
3Samehaiku9Full path.Done. Fixed. Repro exit 0.
4Samesonnet9Full path.Done. Fixed. Repro exit 0.

Three findings came out of these runs.

  • Advisory rules get skipped. Run 1 read the skill, called its own work a one-line change, and went around it. The fix was to make the rule mandatory and to say that size does not exempt a task. Runs 2 to 4 all started the run before their first edit.
  • The reviewer has to be stronger than the agent. In run 2, the haiku reviewer passed a mechanism note that said wait see output above. A direct probe showed Sonnet rejects that note and passes a note that names the line and the repro output. The default reviewer became Sonnet, and is now Opus, because the agents doing the work include Opus. WF_REVIEW_MODEL overrides it.
  • Gates re-run commands, but artifacts stay weak. The agents wrote their own repro output and their own mechanism notes. The command gates ran the repro again, so a faked output could not pass. Nothing checks that a mechanism note is true, and only the reviewer judges it.

The eval runs wrote to the real state directory, so their runs appear in wf status history. The state root now honors XDG_STATE_HOME, but the eval does not set it yet.

Compared with upstream pstack

The workflows adapt pstack's poteto-mode playbooks from cursor/plugins. Upstream was at 0.15.32, commit e73df47, on 2026-10-26. The vendored bundle in desktop/pi/agent/skills/pstack/ records 0.15.13, commit 2cbf585, in UPSTREAM.md. 64 upstream commits touch pstack/ since that baseline.

pstack's playbooks carry judgment the one-line briefs drop. Examples are seeding hypotheses with how and why, committing the failing repro before the fix, and the benchmark noise checklist. The sibling skills are still in the bundle, but only change points to one, architect. Whether gates beat prose on outcomes has not been measured. eval/RESULTS.md compares harnesses, not workflow systems.

Limits

  • Reviewer independence is by construction, not by proof. wf review gives the reviewer a fresh conversation and only the criteria, the task, and the evidence paths. wf verdict needs a terminal and a typed run ID, which an agent's shell lacks. An agent that can drive a real terminal, for example through Herdr, could still get past that.
  • Artifact gates are weak. They check existence and size, not content. Command gates carry the real checks. investigation, handoff, and the first three phases of prototype have only artifact gates, so a placeholder file passes them.
  • The implement phase is ungated. That is deliberate. The verify phase is the check that matters.
  • Commands run in the repo as the current user. A repro that writes files or hits the network will do so for real.
  • No parallel runs. Two agents on one run would interleave journal events. Use separate runs.
  • Manual routes. pr_workflow, skill_work, and other still have no workflow.
  • Vendored pstack is behind. The bundle tracks 0.15.13 while upstream is at 0.15.32.
