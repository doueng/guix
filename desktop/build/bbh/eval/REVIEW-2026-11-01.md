# bbh harness review, 2026-11-01

An overnight evaluation of bbh against Pi, with new eval arms, a pass over every real conversation, and a list of what to change. Each claim is measured unless marked inferred or guess. Raw artifacts are under `~/.cache/bbh-eval/2026-11-01/`, with the analysis scripts, tables and logs in its `report/` directory, and labels are in `~/.local/share/bbh/eval/labels.jsonl`.

## Verdict

On short coding tasks bbh is as reliable as any Pi configuration, with the fewest tool errors on Gemini and the fewest context tokens on DeepSeek. The weaknesses are in long real sessions, not in task completion. A quarter of all production tool steps are polling, because the 120 s evaluation budget turns every long command into a loop of `job-wait` calls that each cost a model request at about 130k tokens. Context grows faster than in Pi on the same multi-turn task. The model still guesses helpers that do not exist, and `edit!` mismatches are now the largest single error class. The eval tooling undercounted failures by 38 percent until tonight's fix, nobody has labeled a trace by hand, and the comparison runs a different engine (the OpenRouter loop) than production (Claude Code).

What the numbers mean, and what bounds them:

- Pass rate is saturated for three arms on both models, so it says nothing about which harness is better at these tasks. It does say bbh did not regress since the 2026-10-30 cohort.
- bbh's 11 DeepSeek tool errors are 5 expected `FileNotFoundException`s on the deliberately missing path, plus 6 guessed names such as `(pwd)` and a `**/*` glob that the ACP client marks failed but the old linter did not count (`errors-deepseek.txt`). The `root-blind-glob` assertion hit 6 of 20 DeepSeek traces and 2 of 12 Gemini traces even though the init prompt warns against it.
- pi-sci's Gemini failures are one cause: Gemini calls the SCI tool wrappers with positional or misnamed arguments and gets `Validation failed for tool write: path must have required properties` repeatedly (`errors-gemini.txt`, 19 of 25 errors). bbh's plain Clojure surface does not have that failure mode, which is the clearest harness-level difference tonight.
- Output tokens are not comparable across arms. Pi runs with `--thinking off` and reports `reasoning 0`; bbh's OpenRouter requests leave reasoning on, and its Gemini runs log 37 to 106 thinking tokens per request. bbh's higher reported Gemini cost ($0.027 vs $0.019 per trial) follows from that, so it is an untuned-side artifact, not a harness cost.
- Reported cost uses each harness's own price table and is kept as a diagnostic only. For the same reason no latency claim is made.
- Spread: the 2026-10-18 and 2026-10-30 cohorts put Pi/SCI at 58, 65 and 60 calls over 12 trials with no code change, so call-count gaps under about 10 per 12 trials are noise (inferred from those three runs).

- bbh defined at least one `defn` helper in 6 of 8 DeepSeek trials, usually one or two, and none in the other 2, where it re-derived the parsing inline each turn. Nothing in the prompt asks the model to keep helpers, so whether the persistent REPL's main feature is used depends on the model's mood.

- pi-codemode used its `store()`/`load()` globals in all three trials, three stores and three loads each, to carry the function body between calls. Pi's built-in codemode therefore does spontaneously what bbh's REPL is for.

- bbh sent the model 2.5 to 9 times more tool-result text than plain Pi on the same task and reached 10.9k context tokens by request 17 against Pi's 3.6k by request 12 (per-request usage in `events.jsonl` and `runs.jsonl`). The cause is what the model chose to print, whole CSVs and intermediate maps, which bbh returns verbatim up to its 30k cap. Pi's bash results were under 1k each.

## A command longer than the budget (slow-command)

`sh check.sh` sleeps 150 s and prints one line, longer than bbh's 120 s evaluation budget. DeepSeek, 3 reps (`slow-table.txt`).

| profile | passed | top-level calls per trial | requests per trial | wall s per trial | how it waited |
|---|---|---|---|---|---|
| bbh | 2/3 | 5, 5, 7 | 6, 6, 8 | 153, 124, 157 | `job` then 2 or 3 `job-wait` calls of 60 s |
| pi | 3/3 | 2, 4, 4 | 3, 5, 5 | 151, 152, 152 | bash with a long timeout, one blocking call |
| pi-codemode | 3/3 | 2, 2, 2 | 3, 3, 3 | 152, 151, 302 | `tools.bash` with `timeout 900` inside one script |
| pi-sci | 3/3 | 3, 2, 4 | 4, 3, 5 | 303, 151, 454 | same, with one or two wrapper errors first |

- bbh used the job helpers correctly in every trial and never lost its REPL, but each wait is a tool call and a model request, so it took twice the requests of built-in codemode for one command. This is the eval-scale version of the production polling tax.
- The failed bbh trial is a harness defect, not a model one. After two text-free rounds the session appended `[bbh] The user hasn't heard from you in a while. Say in a few words what you're doing, then continue.` to the tool result. The model answered with a sentence and no tool call, which ends the turn in the loop engine, so the job finished with nobody waiting and answer.txt was never written. The third trial got the same reminder and happened to continue. A reminder that can end the turn is worse than no reminder.
- Every bbh trial wrote `(job-wait id 60000)`, a positional argument the helper does not document (it takes `:ms`). It worked only because SCI tolerated the stray argument and the default is 60 s.

## Production use

### bbh, 93 conversations since 2026-10-17 (`analyze-real.txt`, `polling.txt`, `big-steps.txt`)

Engine in production is Claude Code with claude-opus-5-5 (42 of 44 turns since runs.jsonl began on 10-30), not the OpenRouter loop that the comparison exercises.

- 3828 tool steps, 274 turns, 8 steps per turn at the median, 36 at p90, 94 at most.
- 142 failed steps (3.7 percent) after the classifier fix: 34 REPL restarts, 28 `ExceptionInfo` (24 are `edit!` "Expected one match"), 15 `FileNotFoundException`, 13 unresolved symbols, 10 `ArityException`, 10 `StringIndexOutOfBoundsException`, 6 `IllegalArgumentException`, 6 `IllegalStateException`, and a tail.
- Polling: 902 of 3791 steps (23.8 percent) call `job-wait`, `job-status`, `Thread/sleep` or `deref`. 505 steps start a `job`. Since 10-30, 170 timed `job-wait` runs waited 121 minutes in total, and 68 tool runs took 60 s or longer, 59 of them `job-wait`. Every such step ends in a model request; the mean request since 10-30 is 129.8k input tokens, 121.9k of them cache reads (94 percent cached).
- Restarts: of 32 restarts with a following step, the next step errored twice and redefined something 12 times. The code that hit the deadline was mostly waiting: `(deref job 280000)`, `(Thread/sleep 180000)`, `job-wait` at 108 to 110 s, or a long `sh` such as `make doom-check`.
- Context: llm requests carry 107.7k input tokens at the median, 303k at p95, 350.7k at most, right under the 350k rollover. Tool results are 1000 chars at the median, 660 exceed 4k, 117 hit the 30k cap, 10.0M chars in total.
- Cost and time: 44 turns since 10-30 cost $65.80, $1.06 per turn at the median, $3.02 at p90, $8.52 at most. A turn takes 173 s at the median and 637 s at p90. Tool runs are 0.9 s at the median and 100 s at p95.
- Judge on 15 recent conversations: 13 good, 2 bad. The bad critiques: a conclusion stated as "measured by reading all five diffs" when the steps fetched five files and a stat; and a turn that ended at step 120 with no final reply and an unfinished workflow run. Both match the `no-final-answer` assertion, which hits 9 real traces.
- The workflow engine works end to end on a real model: the toy bug-fix run went reproduce, diagnose with review, implement, verify, finish, with Jev used and the fix verified by its repro, for $0.18.
- `bb test` passes 140 tests with 481 assertions and `make lint` passes.

### Pi in this repo, 144 sessions from 2026-09-24 to 10-26 (`pi-sessions.txt`, `pi-errors.txt`)

- 547 prompts, 8095 requests, 8873 tool calls: codemode 4795, bash 1996, read 1334, edit 572, write 143. 11 requests per prompt at the median, 31 at p90.
- 553 failed tool executions (6.2 percent). Pi's bash counts a nonzero exit as an error, which bbh's `sh` does not, so this is not the same quantity as bbh's 3.7 percent. Of the 296 codemode failures, 68 are timeouts and the largest remaining group is `Unable to resolve symbol` in SCI.
- Context per request is 104k at the median, 286k at p90, 348k at p95, 728k at most. The Pi sessions therefore ran as large as bbh's, and sometimes twice as large. Cost is not recorded by the Claude bridge (every usage has cost 0).

So on the two things a user feels most, context size and requests per prompt, the two harnesses in real use are alike: 104k vs 108k median context, 11 vs 8 steps per prompt. The difference is in where the requests go. In bbh a quarter of them are waiting.

## Strengths

1. Correctness parity at a small surface. 112 of 112 live trials passed on two models, including Gemini, where SCI codemode lost 5 of 12. One tool, plain Clojure, no wrapper schemas for a model to get wrong.
2. Cheapest short tasks in context terms. 6.2k tokens per DeepSeek trial against 11.0k for plain Pi, 12.3k for built-in codemode and 19.9k for SCI, with the smallest system prompt (995 tokens) of the four arms.
3. Observability. Every conversation is a trace with `runs.jsonl`, and `eval:lint`, `stats`, `runs:metrics`, `eval:show` and the judge all worked on tonight's data without changes. Few harnesses can answer "what fraction of my steps are polling" from existing logs.
4. The workflow engine holds on a real model. Gates ran, the reviewer disagreed twice tonight with real reasons (a nested `let`, unrelated README hunks) and was right both times.
5. Prompt caching in production is 94 percent of input, which is what keeps a $1 median turn from being $5.
6. Engine independence. The same transcript format drives Claude Code and the OpenRouter loop, and Gemini worked through bbh on the first try.

## Weaknesses

1. The 120 s budget creates a polling tax. 24 percent of production steps wait, 121 minutes of waiting since 10-30 ended in 170 model requests at about 130k tokens each, and 34 turns lost their REPL to the deadline while waiting. Estimated share of production spend: 170 of 498 requests, so roughly a third of $65.80 (inferred from the mean request; per-request cost varies with cache state).
2. Context grows faster than Pi's on the same work. On monthly-reports bbh carried 2.3 times Pi's context by its 12th request. In production 117 results hit the 30k cap and p95 requests are 303k tokens, so rollover at 350k is being approached routinely.
3. The helper surface still invites guesses. 13 unresolved symbols (`pwd`, `slurp-safe`, `read-lines-str`, `sh-raw`, `wf-status`, `sleep-ms`), 10 arity errors (mostly `(sh "cmd" "arg")`), 10 `subs` out-of-bounds errors, and 24 `edit!` mismatches, after the signatures experiment already cut arity errors in the eval.
4. Persistence is not used. Two of three session trials defined no helper. The prompt never says to.
5. Turns that end without a reply. 9 real traces, both judge-bad traces, and the linter cannot yet tell an interrupt from a model that stopped.
6. The quiet-turn reminder can end a turn. Appended to a tool result after two silent rounds, it asks the model to "say what you are doing, then continue", and a model that answers in text only has ended its turn with the work undone. That is how bbh lost 1 of 3 slow-command trials.
7. The eval checks a different engine than production uses. Production is Claude Code; the comparison runs the OpenRouter loop with reasoning left on. No human labels exist, so the judge's 13/2 is unvalidated. Cost is not normalized.

## Eval tooling

- Fixed tonight: `error-of` only matched class names ending in `Exception` or `Error`, so `clojure.lang.ExceptionInfo` and class-less SCI errors were not failures. 40 of 106 real `err:` results were invisible, and `unresolved-symbol` reported 1 hit where there were 13. The fix is committed with a test; lint tables in this report use it.
- `no-final-answer` conflates interrupted turns with turns the model ended on a tool call. 20261028-155715-472 ends on a tool call with no tool result, which is an interrupt.
- `eval:lint`'s cohort table has no spread column, so a reader cannot tell 6 of 20 from noise.
- Pi usage events repeat each `usage` block three times (start, update, end); the cohort script counts `message_end` only. Anyone grepping `events.jsonl` will triple-count.

## Improvements, in order of expected value

1. Make waiting free. Let `job-wait` (and nothing else) extend the evaluation deadline, since a wait holds no REPL state worth protecting, or have the session poll the job itself and return when it finishes. Either removes most of the 170 poll requests and the 34 restarts. Measure with `polling.clj` before and after; target under 5 percent polling steps.
2. Cap what the model sees. Lower the inline result cap from 30k to about 8k with the rest spilled to a file as now, and trim tool outputs from earlier turns once a conversation passes 100k tokens. Measure p95 request tokens (303k today) and session-cohort context (191k today).
3. Close the guessed-helper gap. Make `sh` accept extra arguments (10 arity errors), expose the private `clip` (10 `subs` errors), add `pwd`, and on `Unable to resolve symbol` append the three nearest helper names to the error. Rerun `missed-errors.clj`; target zero arity and unresolved hits in a week of traces.
4. Tell the model to keep helpers. One line in `helper-reference`: define `defn` helpers for work you will repeat; they persist. Measure with `BBH_EVAL_TASKS=monthly-reports`: defn steps per trial and calls in prompts 2 to 4.
5. Fix the reminder, then guard the final reply. Make the quiet-turn reminder ask for the status text inside the same message as the next tool call, and if a reminded model answers with text only while a job is still running, re-prompt it once instead of ending the turn. Then, when a turn ends on a tool call, send one nudge for a reply. Measure with `BBH_EVAL_TASKS=slow-command` and `no-final-answer` on real traces.
6. Eval the production engine. Add a `bbh-claude` profile that runs `BBH_MODEL=claude/...` and a Pi arm on the claude bridge, set bbh's OpenRouter reasoning to match Pi's `--thinking off`, and normalize cost from tokens with one price table. Then label 25 to 50 traces with `bb eval:review` so `eval:agreement` can say whether the judge is usable.
7. `edit!` diagnostics. On "Expected one match, found 0", print the closest line by edit distance. 24 failures in 93 conversations, each one a wasted request.

## Attention

Self-reviewed, except the three code changes, which passed `wf review`. DeepSeek and Gemini are cheap models; the user's production model is Opus through Claude Code and was only observed in traces, not in a controlled run. The live tasks are small and all arms pass them, so they measure friction, not capability. No speed claim is made. Reported costs come from two different price tables. The judge has no human labels behind it.
