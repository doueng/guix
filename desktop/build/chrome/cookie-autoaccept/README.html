Cookie autoaccept

What it does: when a page shows a cookie consent popup, the extension answers it for you. By default it clicks accept. You can switch to reject, and you can turn it off for single sites. It does the work locally and sends nothing anywhere.

Prior art

I don't care about cookies and Consent-O-Matic already do this; Consent-O-Matic can also reject. This extension is a thin shell around DuckDuckGo's autoconsent rules: about 1600 rules covering OneTrust, Cookiebot, Didomi, Quantcast, TrustArc, Usercentrics, Sourcepoint, the IAB TCF CMPs and many single sites. autoconsent is MPL-2.0, not MIT. MPL-2.0 is per-file copyleft, so the vendored files stay unmodified and keep their LICENSE, and our own files are unaffected.

Install in the flatpak Chrome

The Chrome flatpak cannot read ~/projects by default. It can read ~/Downloads and ~/Documents. Pick one of the two options below.

A. Let Chrome read the repo, read-only (recommended)

flatpak override --user \
  --filesystem=/home/engstrand/projects/cookie-autoaccept:ro \
  com.google.Chrome
  1. Quit Chrome completely, then start it again.
  2. Open chrome://extensions and switch on Developer mode (top right).
  3. Click Load unpacked and choose /home/engstrand/projects/cookie-autoaccept.
  4. Pin the cookie icon from the puzzle-piece menu if you want to see the badge.

B. Copy it somewhere Chrome can already read

rsync -a --delete \
  --exclude .jj --exclude .git --exclude test \
  /home/engstrand/projects/cookie-autoaccept/ \
  ~/Documents/cookie-autoaccept/

Then do steps 2 and 3 above, choosing ~/Documents/cookie-autoaccept.

Update

  • Our code: after a change lands in the repo (rerun the rsync if you use option B), click the reload arrow on the extension's card in chrome://extensions, then reload any open tabs.
  • autoconsent rules: run scripts/update-autoconsent.sh 18.6.0 (or whatever version you want). It is the only step that uses the network. It checks the npm sha512, copies the four files and rewrites vendor/autoconsent/VERSION. Then run npm test && npm run e2e, commit with jj, and reload the extension.

Using it

Click the toolbar icon to open the popup. It shows what happened on the current site, for example Accepted cookies (Onetrust), Hid 1 cookie banner (generic) or No cookie popup seen. It also has two controls:

  • On for this site: unticking it stops the extension on that hostname (a leading www. is ignored).
  • Accept / Reject cookies: one global choice for every site.

Changing either control reloads the tab. A ✓ badge means the extension handled the popup on that tab. When a CMP rule says it answered, the popup shows Found X, checking... until the fallback has looked at the page after that answer (at most about 3 s), because some rules report success and leave the banner up.

How it works

  • At document_start, a one-line script in the top frame tells the service worker a new page began, so the tab's report starts fresh before any iframe exists. An iframe's CMP can then finish before the top frame is idle without its result being lost.
  • At document_idle, every frame (including iframes and about:blank frames) runs the unmodified autoconsent content bundle. It asks the service worker for rules. The worker sends only the rules that can apply to that frame: about 430 KB for a top frame and much less for an iframe.
  • autoconsent detects the CMP, including inside open shadow roots, and watches for banners that appear late. Then it clicks accept (optIn) or reject (optOut). Some CMPs need page JavaScript, such as Cookiebot or UC_UI. For those, the worker runs one of autoconsent's own snippet functions in the page. It never runs a code string.
  • Generic fallback: 3 s after the page is idle (again at 7 s and 12 s, and on page changes for 30 s), a small script looks for a visible fixed or sticky element, or dialog, that talks about cookies or consent and has a button. It looks in the page, in open shadow roots, and in small consent iframes. In accept mode it clicks the best accept button (Accept all, Allow all, Alle akzeptieren, Tout accepter, Acepto, OK and so on). It never clicks a button that mentions subscribing, paying, settings, rejecting or necessary-only. If no such button exists, or in reject mode, it hides the banner instead, and then also hides an empty full-screen backdrop left behind it and lifts a scroll lock. It skips anything with a text field, such as an email sign-up that asks for your consent to mail you. It waits while autoconsent is working on a popup. It also runs after autoconsent reports success, because some upstream accept rules click buttons that are gone and leave the banner up.
  • In reject mode, autoconsent's heuristic also clicks reject buttons it has no rule for. In accept mode that heuristic is off, because upstream has no heuristic accept. DuckDuckGo ships opt-out only, so upstream's accept steps are less maintained than its reject steps; the generic fallback covers that gap.

Permissions and privacy

  • storage holds your settings. The per-tab status is kept in memory only and is gone when the browser closes.
  • scripting plus host access to all sites is needed to run the snippet functions in the page. This is the same reach the all-sites content script already has, so the install warning is unchanged.
  • No tabs, cookies or webNavigation permission, no remote code, no network requests and no telemetry.

Tests

npm test          # 27 unit tests (node --test)
npm run e2e       # 14 checks, headless flatpak Chrome, ~45 s
npm run bombadil  # Bombadil explores the fixtures for 5 min; not part of npm test

The e2e run starts flatpak run com.google.Chrome --headless=new with a throwaway profile and read-only access to the repo. It loads the extension over the DevTools pipe (Extensions.loadUnpacked), because branded Chrome ignores --load-extension. Then it opens the fixture pages in test/fixtures. The fixtures are small rebuilds of each CMP's DOM and API, not saved copies of live pages: OneTrust, Cookiebot (old and current template), Didomi, Quantcast, TrustArc, Usercentrics in shadow DOM, Sourcepoint in a cross-origin iframe, an unknown pay-or-consent iframe, and home-made banners. The run checks that:

  • the accept button is the one pressed;
  • reject mode presses reject, and with no rule it hides rather than accepts;
  • a banner added late in shadow DOM is caught;
  • a newsletter box stays;
  • a disabled site is left alone.
Set CHROME=/path/to/chromium to use another browser.

Bombadil

npm run bombadil runs Bombadil 0.7.10 against one headless Chrome with the extension loaded, over the fixture site served on localhost and 127.0.0.1 with no network. Bombadil clicks, scrolls, goes back and forward, reloads and waits. Through the harness it also opens the real popup, reads it, toggles the site and switches accept or reject. After every step it checks these properties:

  • on an enabled site a consent banner is gone within 15 s (a pay-or-consent wall in reject mode is exempt);
  • on a disabled site the extension clicks, decides and hides nothing;
  • in reject mode it never clicks accept;
  • it clicks only inside consent UI, never a link that navigates or a form button;
  • once the banner is gone, no overlay or scroll lock blocks the page for more than 3 s;
  • non-consent boxes (newsletter, mail sign-up) stay;
  • the popup's status line is true of what the page saw.

Options: npm run bombadil -- --time 600 sets the budget in seconds (default 300); --page modal-lock.html keeps it on one fixture; --seed N picks the starting settings. A failure prints the property, the seed and the trace directory, and --reproduce DIR replays that trace from the same settings. Bombadil 0.7.10 has no seed of its own; its trace is the replay. It needs bombadil on PATH, $BOMBADIL, or the pinned Guix package in ~/guix (T174), which the script builds on demand. Files: bombadil/run.mjs (harness), spec.ts (properties and actions) and probe.js (injected into each fixture page to see what the extension did).

Chrome: Guix has ungoogled-chromium but no aarch64 substitute (on 14 November 2026 it would build Chromium and clang from source), so the harness uses the flatpak Chrome headless with a throwaway profile, like the e2e run. Set CHROME=/path/to/chromium to use another browser. The report of the first runs is docs/bombadil-report.html.

Live check

On 14 November 2026 I ran the extension in headless Chrome on seven live sites: the Guardian, Le Monde, cookiebot.com, Spiegel, the BBC, Marca and IKEA Sweden. After 12 s, none of them showed a consent banner or wall. IKEA was handled by autoconsent's OneTrust rule and cookiebot.com by the fallback after the stale Cookiebot rule. The Guardian and Spiegel were handled by the fallback inside their consent frames, and Le Monde and Marca by the fallback on their pay-or-consent walls. The BBC page was clear at the end of the run. Before the fallback could click, none of the first four was handled. Stack Overflow and Zeit served bot checks to headless Chrome, so they tell us nothing.

Known limits

  • The fallback stops watching for new banners 30 s after the page is idle, so a banner added later stays.
  • Running at document_idle (as asked) can briefly show a banner before it is handled. Upstream runs at document_start to hide banners before they paint.
  • When the fallback hides a banner instead of clicking it, no choice is recorded, so that site may ask again on the next visit.
  • The fallback picks buttons by their text. A banner with an unusual accept label is hidden instead of accepted. If it ever presses the wrong button on a site, turn that site off from the popup.
  • A site that never loads a known CMP and uses an unusual layout will still show its banner. You can turn the site off, or report it upstream.
