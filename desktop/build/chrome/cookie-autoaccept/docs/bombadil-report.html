Bombadil on cookie-autoaccept

T178 · W199 · 14 November 2026 · cookie-autoaccept with Bombadil 0.7.10, headless flatpak Chrome 157 on aarch64 Guix

Result. Bombadil found four real bugs in the extension during its first runs. All four are fixed, and each has a unit test that fails on the old code. After the fixes: a 10-minute run over the whole fixture site passed, as did a 45 s focused run on each of the 19 fixtures. Three bugs injected on purpose were each caught within 5 to 23 s. measured

Specs

These properties are checked on every state. Each one reads facts that a probe script gathers inside every fixture page and frame: untrusted clicks (an extension's el.click()), consent choices made through the fixture's handler, marks the fallback left, autoconsent's style elements, whether the consent UI is visible, and what blocks the page.

PropertyRule
bannerGoesAwayOn an enabled site, a visible consent banner is gone within 15 s of being seen. A pay-or-consent wall is exempt in reject mode, since it can only be paid or accepted.
disabledSiteUntouchedOn a disabled site: no script clicks or decisions, no fallback marks, no autoconsent styles, and no consent UI hidden without the user's choice.
rejectNeverAcceptsIn reject mode, no script click on an accept button and no script accepted decision, including inside frames.
clicksStayInConsentUiEvery script click lands inside consent UI and never on a link that navigates or on a form's submit button. No script form submit.

nonConsentUiStaysThe newsletter box and the mail sign-up stay visible.
popupTellsTheTruthWhen the real popup is opened, its status line matches the page: Off exactly when disabled; Accepted only in accept mode with evidence; Rejected only in reject mode with no accept; Hid N equals the hidden marks; No cookie popup seen only if nothing was done.

Actions: in-page clicks, link clicks, scrolling, back, forward, reload and wait. Dwells of 2 to 4.5 s, weighted up while a page is younger than 12 s, give late banners and the fallback's retries time to happen. The harness opens the real popup through chrome.action.openPopup to read it, toggle the site, or switch accept and reject; these choices are weighted so that disabled sites get re-enabled.

Fixtures

Nineteen top-level pages and two frame pages are served on localhost and 127.0.0.1 with no network: OneTrust, OneTrust loaded 6 s late, Cookiebot (old and current template), Didomi, Quantcast, TrustArc, Usercentrics in shadow DOM, Sourcepoint in a cross-origin frame, an unknown TCF v2 CMP with __tcfapi, a pay-or-consent frame, generic banners (plain, late in shadow DOM, late in light DOM at 9 s), two modals with a backdrop and scroll lock, a newsletter box, a mail sign-up form, and a page with no banner. Seven of these are new; the rest are the e2e fixtures, now marked with data-consent-ui or data-keep.

Run time and cost

  • Final 10-minute run: 363 states, 93 page loads, 16 of the 19 top-level fixtures, all four mode and site combinations, and 23 popup reads. measured
  • About one action per 1.6 s, because dwells dominate. One Chrome runs at a time, plus Bombadil, a 14 MB static binary.
  • npm run bombadil defaults to 300 s. It is not part of npm test or the e2e run.

Chromium on aarch64 Guix

ungoogled-chromium 156 is in Guix, but no substitute server had it for aarch64. guix build --dry-run would build Chromium and clang 23 from source, which takes many hours on this machine. measured The harness therefore runs the flatpak Chrome headless with a throwaway profile and read-only access to the repo. It loads the extension over the DevTools pipe (Extensions.loadUnpacked) and gives Bombadil a debugging port. Your daily Chrome profile is not touched. CHROME=/path/to/chromium switches to any Chromium binary.

Reproducing

npm run bombadil                          # 300 s over the whole site
npm run bombadil -- --time 600 --seed 7   # starts in reject mode with localhost disabled
npm run bombadil -- --page sourcepoint.html
npm run bombadil -- --reproduce /tmp/cookie-autoaccept-trace-XXXX

On failure the harness prints the violated property with the page facts, the seed and the trace directory. Bombadil 0.7.10 has no seed of its own: its trace is the replay, and the seed fixes the starting settings. The replay of finding 4's trace passed once the fix was in.

Limits

  • Exploration is random, so a short run can miss a combination. The sweep runs, 45 s per fixture with --page, are what covered every page.
  • The probe sees only open shadow roots, and frames only through what they post to their parent.
  • Bombadil cuts a custom action off at about 5 s, so a long stay is several dwells in a row.
