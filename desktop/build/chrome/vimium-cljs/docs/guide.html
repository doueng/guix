Vimium (cljs): load, use, test

Vimium (cljs) is your own Vimium, rewritten in ClojureScript as a Chrome Manifest V3 extension. It reads your Vimium export, keeps your key mappings, and runs in the flatpak Chrome next to Vimium or instead of it.

Load it in the flatpak Chrome

  1. Build it once (needs Java from guix):
    cd /home/engstrand/projects/vimium-cljs
npm install
npm run build      # = guix shell openjdk@25:jdk node -- npx shadow-cljs release bg content ui options
    ./check.sh runs the build, the unit tests and the e2e suite in one go.
  2. Let the flatpak see the extension folder (once, read-only):
    flatpak override --user --filesystem=/home/engstrand/projects/vimium-cljs/ext:ro com.google.Chrome
    Restart Chrome after this. T178 did the same for the cookie extension.
  3. Open chrome://extensions, turn on Developer mode (top right), click Load unpacked and pick /home/engstrand/projects/vimium-cljs/ext. The extension is called Vimium (cljs), version 0.1.0. Its options page opens on first install.
  4. On the options page, choose your export, /home/engstrand/Downloads/vimium-options.json, under Import from Vimium. The flatpak can read Downloads. The import only parses the JSON: it lists what it took, drops the duplicate typelit.io rule and notes options it does not use.
  5. After a rebuild, click the reload arrow on the extension's card in chrome://extensions, then reload open tabs.

Next to Vimium or instead of it

Both extensions listen for the same keys, so running both on one page makes each command fire twice. Choose one of these:

  • Instead of Vimium: switch Vimium off with its toggle in chrome://extensions. Its settings stay, so switching back is one click.
  • Side by side: keep Vimium in your main profile and load Vimium (cljs) in a second Chrome profile (profile menu → Add). Each profile has its own extensions.
  • Per site: add an exclusion rule in one extension for the sites where the other should run.

Your guix repo's Vimium aliases (/home/engstrand/guix/desktop/configs/vimium/keybindings.txt: g? gb g/ gh gl) are not in the export. To use them, paste those lines into Custom key mappings.

What it does

KeysAction
i gifocus the first text field (a count picks the nth; Tab cycles)
w e Ctrl+oprevious tab, next tab, last-visited tab (your mappings)
h l H Lback, forward (your mappings plus the defaults)
p Tsearch open tabs
j k d u gg Gscroll; counts work, as in 5j
f F yf Alt+flink hints: open, new tab, copy URL, open several
/ n * #find; every match is highlighted. N goes to the page, since you unmapped it.
o O b B ge gEVomnibar: history, bookmarks, tabs, search, edit URL
v Vvisual mode: h j k l w b e 0 $ gg G, o swaps ends, y yanks
mx, `xset or jump to a mark (capital letters work across tabs; `` goes back)
t x X yt g0 g$ << >> W zi zotab commands, as in Vimium
?help: every command with your current keys

Keys typed in inputs, textareas, contenteditable areas and inputs inside shadow DOM always go to the page. Esc leaves the field. go.dev and typelit.io are excluded, as in your Vimium. grabBackFocus is on, so pages can't grab focus on load.

Key clashes: none. Kanata turns Cmd chords into Ctrl ones and Cmd+hjkl into arrows, and Hyprland takes Alt+digits, Alt+W and Alt+Space. Nothing sends Ctrl+O, Alt+F, Alt+P or Alt+M, so those reach the page. Extensions can't run on chrome:// pages or the Web Store, so there the global key guide (Cmd+/) still applies.

Not ported

Filtered (type-the-link-text) hints, the : command Vomnibar, setZoom, download and incognito hint modes, Vimium's new-tab page, the toolbar popup that edits exclusions, search-engine completion, and find history. Your config uses none of them.

How it is built

There is one shadow-cljs :browser build per entry point, each released with :advanced into ext/js/: bg (the service worker), content (every frame, at document_start), ui (the Vomnibar, help and offscreen clipboard pages) and options. MV3 forbids eval, and shadow-cljs dev builds load code through eval, so the extension only runs release builds. check.sh fails if any bundle contains eval. Pure logic (keys, mappings, hints, exclusions, import, ranking) lives in plain namespaces that npm test runs on node. T178's cookie extension can use the same pattern.

Hints across frames work as in Vimium. Every frame counts its visible clickable elements, the service worker hands out one set of unique hint strings, and each frame draws its own markers in a closed shadow root that the page can't style or read.

Tests

  • npm test: 20 cljs.test tests (key parsing, your mappings, the key state machine, hint strings, exclusions, the import, ranking and typed URLs).
  • npm run e2e: 11 checks in one headless flatpak Chrome over local fixture pages, about 30 s. Split by stage: e2e:content, e2e:worker and e2e:ui.
  • npm run bombadil: Bombadil explores the fixture site with random clicks, scrolls and key presses, and checks on every state that hints cover every visible link (including the shadow DOM and both iframes), that keys typed into fields never fire commands, that j and k scroll, and that find highlights every match. Its first runs found three bugs, all fixed with tests: Escape racing a hint start, a cross-origin frame left in hint mode, and j scrolling a blurred textarea.
