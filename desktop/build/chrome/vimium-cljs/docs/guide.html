Vimium (cljs): load, use, test

Vimium (cljs) is your own Vimium, rewritten in ClojureScript as a Chrome Manifest V3 extension. Your settings from your Vimium export are compiled in from one source file, and it runs in the flatpak Chrome next to Vimium or instead of it.

Load it in the flatpak Chrome

  1. Load it once, from the guix repo:
    ext-reload load vimium-cljs
    It builds the extension (bb build in /home/engstrand/guix/desktop/build/chrome/vimium-cljs/; Java and node come from guix), opens chrome://extensions (with Developer mode on, top right), asks you to Remove any copy loaded from an old folder, then puts /home/engstrand/guix/desktop/build/chrome/vimium-cljs/ext on the clipboard: click Load unpacked, type Ctrl+L, Ctrl+V and Enter. Pick the ext folder, not the folder above it, which has no manifest.json: Chrome then says Manifest file is missing or unreadable. The extension is called Vimium (cljs), version 0.1.0. Its manifest key fixes its id (ceeiidnmpnfgpgccdchgcladeoldljem) wherever it is loaded from. The compiled scripts in ext/js/ are build output and not in the repo, so an unbuilt ext/ fails with Could not load background script. Guix Home grants the flatpak /home/engstrand/guix/desktop/build/chrome read-only (flatpak override), which Chrome sees from its next start; before that the file chooser hands Chrome the folder through the document portal, which works as well.
  2. For Ctrl+L: open chrome://extensions/shortcuts, find Vimium (cljs), Open the Vomnibar, click the pencil and press Ctrl+L. Chrome will not hand an extension a key that one of its own shortcuts uses until you do this once. Ctrl+Shift+K (tab search) and Ctrl+Shift+E (the side-panel tab list, Alt+E in Hyprland) are suggested keys, so a fresh load gets them.
  3. After a change, ext-reload vimium-cljs rebuilds it, has Chrome reread it and reloads open tabs. bb test in the folder runs the unit tests, the release builds, the load check in a headless flatpak Chrome and this guide's check; make lint in the guix repo runs it whenever the folder changed.

Next to Vimium or instead of it

Both extensions listen for the same keys, so running both on one page makes each command fire twice. Choose one of these:

  • Instead of Vimium: switch Vimium off with its toggle in chrome://extensions. Its settings stay, so switching back is one click.
  • Side by side: keep Vimium in your main profile and load Vimium (cljs) in a second Chrome profile (profile menu → Add). Each profile has its own extensions.
  • Per site: add an exclusion rule (Vimium's options page, or exclusions in the config file below) for the sites where the other should run.

Change keys and settings

There is no options page. Every setting is plain ClojureScript data in /home/engstrand/guix/desktop/build/chrome/vimium-cljs/src/vimium_cljs/config.cljs: your key mappings, link-hint characters, search engines, exclusions, scrolling and the rest, as your Vimium export had them. Edit it, then run ext-reload vimium-cljs. A mapping is ["w" "previousTab"]; ["N" nil] unmaps a key; ? on a page lists every command name. npm test checks that the file is well formed.

Your guix repo's Vimium aliases (/home/engstrand/guix/desktop/configs/vimium/keybindings.txt: g? gb g/ gh gl) were not in the export, so they are not in the config. Add them as mappings to use them.

Ctrl+L opens the Vomnibar

Once Ctrl+L is set at chrome://extensions/shortcuts, it opens the Vomnibar instead of focusing the address bar, from the page, from the address bar itself and from chrome:// pages. Chrome sends it to the extension's service worker, so no page script and no desktop remap is involved, and Ctrl+L in every other application is unchanged. When the page can't take the keyboard (focus is in the address bar, or the page is a chrome:// page or the Web Store, where extensions can't run), the Vomnibar opens in a small popup window that acts on the tab you were in; it fills that window edge to edge in the same colours as the in-page one, with the input focused. Esc closes it. Cmd+L stays the right arrow; Alt+d still focuses the address bar.

Cmd+Space b b searches open tabs

As Doom's SPC b b switches buffers, the desktop leader's Cmd+Space b b opens the Vomnibar on your open tabs when Chrome is focused. Hyprland takes Cmd+Space before Chrome sees it, so the leader sends Ctrl+Shift+K, the suggested key of the extension's Search open tabs command; it works from the address bar and chrome:// pages too. In other windows b b still picks a window.

Keys typed in inputs, textareas, contenteditable areas and inputs inside shadow DOM always go to the page. Esc leaves the field. go.dev and typelit.io are excluded, as in your Vimium. grabBackFocus is on, so pages can't grab focus on load.

Key clashes: none. Kanata turns Cmd chords into Ctrl ones and Cmd+hjkl into arrows, and Hyprland takes Alt+digits, Alt+W and Alt+Space. Nothing sends Ctrl+O, Alt+F, Alt+P or Alt+M, so those reach the page. Extensions can't run on chrome:// pages or the Web Store, so there only Ctrl+L works and the global key guide (Cmd+/) still applies.

The Vomnibar

One list across open tabs, history and bookmarks, in your system's light or dark theme, with favicons, the matched text highlighted and a badge saying what each row is. Each word you type matches the title or the URL: as text, as initials (hn finds Hacker News), as letters in order, or one typo away (vimuim finds vimium). Rows rank by how well they match, then by how often and how lately you used them, and pages you picked before for the same text come first. A page that is already open in a tab switches to that tab instead of opening twice.

A new tab (t or Ctrl+T) is the Vomnibar: the extension replaces Chrome's new tab page, so you type at once and what you pick opens in that tab; Esc clears the text. Chrome puts a new tab page's keyboard focus in the address bar, so the replacement steps aside for an ordinary extension page in the same place, and its address reads ui.html?newtab. Keys you type while the Vomnibar is still opening are kept and land in it, never in the page. The page reads your tabs, history and bookmarks once when it opens and ranks them itself on each keystroke, in a few milliseconds over 3000 history entries; there is no scrollbar, and the selected row stays in view.

Not ported

Filtered (type-the-link-text) hints, the : command Vomnibar, setZoom, download and incognito hint modes, Vimium's new-tab page, the toolbar popup that edits exclusions, search-engine completion, and find history. Your config uses none of them.

How it is built

There is one shadow-cljs :browser build per entry point, each released with :advanced into ext/js/: bg (the service worker), content (every frame, at document_start), ui (the Vomnibar, help and offscreen clipboard pages). MV3 forbids eval, and shadow-cljs dev builds load code through eval, so the extension only runs release builds. bb test fails if any bundle contains eval. Pure logic (keys, mappings, the config, hints, exclusions, ranking, which element a scroll moves) lives in plain namespaces that npm test runs on node. T178's cookie extension can use the same pattern.

Hints across frames work as in Vimium. Every frame counts its visible clickable elements, the service worker hands out one set of unique hint strings, and each frame draws its own markers in a closed shadow root that the page can't style or read.

Tests

  • npm test: 35 cljs.test tests (key parsing, your mappings, that the config is well formed and matches your export, the key state machine, hint strings, exclusions, Vomnibar matching, ranking, its speed over 3000 history entries, that the faster typo matcher and the per-keystroke cache give the same rows, what the Vomnibar lists in each mode, typed URLs, and choosing the scroll target).
  • npm run e2e: 14 checks, including the Ctrl+L command run from the worker (DevTools keys never reach Chrome's own shortcuts), in one headless flatpak Chrome over local fixture pages, about 40 s. test/fixtures/tube.html mimics YouTube's subscriptions feed (web components, a fixed scrolling guide) for the scroll-target checks. node test/e2e/youtube.mjs runs the same kind of check on the real YouTube. Split by stage: e2e:content, e2e:worker and e2e:ui.
  • npm run bombadil: Bombadil explores the fixture site with random clicks, scrolls and key presses, and checks on every state that hints cover every visible link (including the shadow DOM and both iframes), that keys typed into fields never fire commands, that j and k scroll, that find highlights every match, and for the Vomnibar that it opens focused within 750 ms, keeps every key typed at full speed, keeps keys away from the page, closes on Escape with focus back where it was, ranks an open page's exact title or URL first, switches to an open tab instead of opening a second one, shows rows for the typed text within 150 ms, shows no scrollbar and keeps the selected row in view in a tab search longer than ten rows, and keeps keys typed right after o or p, before it has loaded (also from inside an iframe). scripts/vomnibar-perf.mjs times opening and every keystroke over 5000 history entries and 60 tabs; scripts/vomnibar-live.mjs screenshots a headed Chrome on an Xvfb (the in-page Vomnibar, the new tab page, the popup) while xdotool types at once. scripts/vomnibar-lab.mjs takes screenshots over a seeded profile and scripts/vomnibar-keys.mjs counts keystrokes for common tasks. Its runs found four bugs, all fixed with tests: Escape racing a hint start, a cross-origin frame left in hint mode, j scrolling a blurred textarea, and the first key typed into a just-opened Vomnibar getting lost.
