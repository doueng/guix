Vimium (cljs): load, use, test

Vimium (cljs) is your own Vimium, rewritten in ClojureScript as a Chrome Manifest V3 extension. Your settings from your Vimium export are compiled in from one source file, and it runs in the flatpak Chrome next to Vimium or instead of it.

Load it in the flatpak Chrome

  1. Load it once, from the guix repo:
    ext-reload load vimium-cljs
    It builds the extension (bb build in /home/engstrand/guix/desktop/build/chrome/vimium-cljs/; Java and node come from guix), opens chrome://extensions (with Developer mode on, top right), asks you to Remove any copy loaded from an old folder, then puts /home/engstrand/guix/desktop/build/chrome/vimium-cljs/ext on the clipboard: click Load unpacked, type Ctrl+L, Ctrl+V and Enter. Pick the ext folder, not the folder above it, which has no manifest.json: Chrome then says Manifest file is missing or unreadable. The extension is called Vimium (cljs), version 0.1.0. Its manifest key fixes its id (ceeiidnmpnfgpgccdchgcladeoldljem) wherever it is loaded from. The compiled scripts in ext/js/ are build output and not in the repo, so an unbuilt ext/ fails with Could not load background script. Guix Home grants the flatpak /home/engstrand/guix/desktop/build/chrome read-only (flatpak override), which Chrome sees from its next start; before that the file chooser hands Chrome the folder through the document portal, which works as well.
  2. Nothing to set by hand: Ctrl+Shift+H (the Vomnibar, Ctrl+L in Hyprland), Ctrl+Shift+K (tab search), Ctrl+Shift+Y (new-tab mode, Cmd+T in Hyprland) and Ctrl+Shift+E (the side-panel tab list, Alt+E in Hyprland) are suggested keys, so a fresh load gets them.
  3. After a change, ext-reload vimium-cljs rebuilds it, has Chrome reread it and reloads open tabs. bb test in the folder runs the unit tests, the release builds, the load check in a headless flatpak Chrome and this guide's check; make lint in the guix repo runs it whenever the folder changed.

Next to Vimium or instead of it

Both extensions listen for the same keys, so running both on one page makes each command fire twice. Choose one of these:

  • Instead of Vimium: switch Vimium off with its toggle in chrome://extensions. Its settings stay, so switching back is one click.
  • Side by side: keep Vimium in your main profile and load Vimium (cljs) in a second Chrome profile (profile menu → Add). Each profile has its own extensions.
  • Per site: add an exclusion rule (Vimium's options page, or exclusions in the config file below) for the sites where the other should run.

Change keys and settings

There is no options page. Every setting is plain ClojureScript data in /home/engstrand/guix/desktop/build/chrome/vimium-cljs/src/vimium_cljs/config.cljs: your key mappings, link-hint characters, search engines, exclusions, scrolling and the rest, as your Vimium export had them. Edit it, then run ext-reload vimium-cljs. A mapping is ["w" "previousTab"]; ["N" nil] unmaps a key; ? on a page lists every command name. npm test checks that the file is well formed.

Your guix repo's Vimium aliases (/home/engstrand/guix/desktop/configs/vimium/keybindings.txt: g? gb g/ gh gl) were not in the export, so they are not in the config. Add them as mappings to use them.

Ctrl+L opens the Vomnibar

Ctrl+L opens the Vomnibar instead of focusing the address bar, and the pick opens in the same tab. Chrome never gives an extension Ctrl+L, so Hyprland sends the vomnibar command's key Ctrl+Shift+H when Chrome is focused. It works from the page, from the address bar itself and from chrome:// pages. Chrome sends it to the extension's service worker, so no page script is involved, and Hyprland passes Ctrl+L through unchanged to every other application. When the page can't take the keyboard (focus is in the address bar, or the page is a chrome:// page or the Web Store, where extensions can't run), the Vomnibar opens in a small popup window that acts on the tab you were in; it fills that window edge to edge in the same colours as the in-page one, with the input focused. Esc closes it. Cmd+L stays the right arrow; Alt+d still focuses the address bar.

Cmd+Space b b searches open tabs

As Doom's SPC b b switches buffers, the desktop leader's Cmd+Space b b opens the Vomnibar on your open tabs when Chrome is focused. Hyprland takes Cmd+Space before Chrome sees it, so the leader sends Ctrl+Shift+K, the suggested key of the extension's Search open tabs command; it works from the address bar and chrome:// pages too. In other windows b b still picks a window.

Mode badge

A small badge in a bottom corner of every page names the mode your keys are in: NORMAL, INSERT (keys type text: a field, or the Docs and Sheets editors), HINTS, VISUAL, VOMNIBAR, PASS KEY or MARK; the find bar stands in for FIND. It takes no clicks, sits in the bottom left unless something clickable is there (the Sheets add-sheet button), then the bottom right, and fades while the pointer comes near. A click on the page closes the Vomnibar, as in Vimium.

Google Docs and Sheets

Docs draws the document itself and reads your keys from a hidden editor in a 1px frame, which always has focus while you are in the document. Sheets reads them from a cell editor it keeps above the page until you edit a cell. So, as Phil Crosby's SheetKeys does for Sheets, the extension keeps its own mode there, and the badge in a bottom corner names it (INSERT while keys type, NORMAL after Esc):

  • When a doc or sheet opens, and whenever you click in it, you are typing: every key goes to the document, or starts editing the selected cell. grabBackFocus leaves that hidden editor alone.
  • While you edit a cell or the formula bar, Esc is the sheet's: it cancels the edit and you are back on the grid, still typing (arrows move the selection, letters start an edit). The next Esc gives normal mode.
  • Esc switches to normal mode without taking Docs' focus away (a HUD says so); a second Esc goes to Docs, which closes its menus and dialogs. In normal mode j k d u gg G scroll the document or the grid, f hints the menus, toolbar buttons, sheet tabs and the items of an open menu, and o, ? and find open over the page. Keys that would type, and are not mapped, go nowhere, so nothing lands in the document by accident. Ctrl and Alt chords (Ctrl+B, Ctrl+Z) and the arrow keys still reach Docs.
  • i or a click types again. Docs taking the focus back after a menu, a toolbar button or its own Escape does not: you stay in normal mode.
  • Alt+E (Ctrl+Shift+E, the side-panel tab list) is a Chrome command, so Chrome takes it before Docs' own Ctrl+Shift+E (center align).

test/fixtures/docs.html and sheets.html reproduce those structures for the e2e and Bombadil checks below. npm run gdocs <url> runs the Docs checks on a real Doc in headless Chrome, and scripts/gdocs-live.mjs runs Docs and Sheets in a real Chrome window on the test display, typing with wtype and taking screenshots. Both type into the document: give them a scratch Doc and Sheet of your own that anyone with the link can edit, never someone else's (a public Doc that allows suggestions keeps the keys as anonymous suggestions).

Key clashes: none. Kanata turns Cmd chords into Ctrl ones and Cmd+hjkl into arrows, and Hyprland takes Alt+digits, Alt+W and Alt+Space. Nothing sends Ctrl+O, Alt+F, Alt+P or Alt+M, so those reach the page. Extensions can't run on chrome:// pages or the Web Store, so there only Ctrl+L works and the global key guide (Cmd+/) still applies.

The Vomnibar

One list across open tabs, history and bookmarks, in your system's light or dark theme, with favicons, the matched text highlighted and a badge saying what each row is. Each word you type matches the title or the URL: as text, as initials (hn finds Hacker News), as letters in order, or one typo away (vimuim finds vimium). Rows rank by how well they match, then by how often and how lately you used them, and pages you picked before for the same text come first. A page that is already open in a tab switches to that tab instead of opening twice.

On the guix desktop, Cmd+T (or Ctrl+T) in Chrome opens the Vomnibar over the page in new-tab mode: what you pick opens in a new tab, and Esc opens nothing. Hyprland sends the extension's vomnibar-new-tab key Ctrl+Shift+Y for it, since Chrome gives no extension Ctrl+T.

A new tab (t) is the Vomnibar: the extension replaces Chrome's new tab page, so you type at once and what you pick opens in that tab; Esc clears the text. Chrome puts a new tab page's keyboard focus in the address bar, so the replacement steps aside for an ordinary extension page in the same place, and its address reads ui.html?newtab. It is also your home page, since Chrome's home page is the new tab page. Keys you type while the Vomnibar is still opening are kept and land in it, never in the page. The page reads your tabs, history and bookmarks once when it opens and ranks them itself on each keystroke, in a few milliseconds over 3000 history entries; there is no scrollbar, and the selected row stays in view.

Incognito windows work the same: Ctrl+Shift+N and type, and it goes to the Vomnibar; keys work on pages there too. Chrome never lets an extension replace the incognito new tab page, so the extension's incognito half (the manifest's split incognito mode) swaps it for ui.html?newtab as it opens, in about a quarter of a second for a new window. Chrome needs Allow in Incognito on once, at chrome://extensions/?id=ceeiidnmpnfgpgccdchgcladeoldljem; it keeps that for the extension's fixed id, and ext-reload says so when it is off.

Not ported

Filtered (type-the-link-text) hints, the : command Vomnibar, setZoom, download and incognito hint modes, Vimium's new-tab page, the toolbar popup that edits exclusions, search-engine completion, and find history. Your config uses none of them.

How it is built

There is one shadow-cljs :browser build per entry point, each released with :advanced into ext/js/: bg (the service worker), content (every frame, at document_start), ui (the Vomnibar, help and offscreen clipboard pages). MV3 forbids eval, and shadow-cljs dev builds load code through eval, so the extension only runs release builds. bb test fails if any bundle contains eval. Pure logic (keys, mappings, the config, hints, exclusions, ranking, which element a scroll moves) lives in plain namespaces that npm test runs on node. T178's cookie extension can use the same pattern.

Hints across frames work as in Vimium. Every frame counts its visible clickable elements, the service worker hands out one set of unique hint strings, and each frame draws its own markers in a closed shadow root that the page can't style or read.

  • npm run e2e: checks including the Ctrl+L command run from the worker (DevTools keys never reach Chrome's own shortcuts), in one headless flatpak Chrome over local fixture pages, about 40 s. test/fixtures/tube.html mimics YouTube's subscriptions feed (web components, a fixed scrolling guide) for the scroll-target checks. node test/e2e/youtube.mjs runs the same kind of check on the real YouTube. test/e2e/select.mjs records every redraw after a pick, on the new tab page and in a page. test/e2e/incognito.mjs (npm run e2e:incognito) opens an incognito window and checks that it shows the Vomnibar, takes typing, and that j and gg work on a page there; scripts/incognito-live.mjs does it with real keys on an Xvfb and takes screenshots. Split by stage: e2e:content, e2e:worker and e2e:ui. npm run e2e:docs runs the Google Docs checks on test/fixtures/docs.html: the editor keeps its focus and gets typing, Escape then j scrolls the document and q types nothing, i and a click type again, hints open a menu and pick its item, Escape out of hints and the Vomnibar stays in normal mode; and the Sheets checks on test/fixtures/sheets.html: the cell editor keeps its focus and typing fills cells, Escape then j scrolls the grid while q edits nothing and arrows move, Escape in a cell or the formula bar is the sheet's and a second one gives normal mode, hints reach menus, the toolbar and sheet tabs, and a click on a cell types again.
  • npm run bombadil: Bombadil explores the fixture site with random clicks, scrolls and key presses, and checks on every state that hints cover every visible link (including the shadow DOM and both iframes), that keys typed into fields never fire commands, that j and k scroll, that find highlights every match, and for the Vomnibar that it opens focused within 750 ms, keeps every key typed at full speed, keeps keys away from the page, closes on Escape with focus back where it was, ranks an open page's exact title or URL first, switches to an open tab instead of opening a second one, shows rows for the typed text within 150 ms, shows no scrollbar and keeps the selected row in view in a tab search longer than ten rows, and keeps keys typed right after o or p, before it has loaded (also from inside an iframe); that the rows are for the typed text, and that nothing is drawn after Enter or Escape, in a page or on a new tab page. scripts/vomnibar-perf.mjs times opening and every keystroke over 5000 history entries and 60 tabs; scripts/vomnibar-live.mjs screenshots a headed Chrome on an Xvfb (the in-page Vomnibar, the new tab page, the popup) while xdotool types at once. scripts/vomnibar-lab.mjs takes screenshots over a seeded profile and scripts/vomnibar-keys.mjs counts keystrokes for common tasks. Its runs found four bugs, all fixed with tests: Escape racing a hint start, a cross-origin frame left in hint mode, j scrolling a blurred textarea, and the first key typed into a just-opened Vomnibar getting lost. A fifth, the new tab page showing every row again after a pick, is caught by its new-tab-page action. npm run bombadil:docs and npm run bombadil:sheets start on the Docs or Sheets fixture and add random key runs there: with no Escape while typing every key lands in the document, while in normal mode none does, and a run ending in Escape (two in a Sheets cell) ends in normal mode. On every state the mode badge must agree, within a second, with the mode and focus the page shows, and at once after each action; while it says INSERT plain keys land in the document or cell, while it says NORMAL they type nothing, and it says VOMNIBAR while the Vomnibar is open. Their runs found four bugs, fixed: v in Docs left the page in a visual mode no key could leave, the Docs editor lost its focus when the Vomnibar closed so nothing typed until a click, a Vomnibar left open after a click on the page kept its keys, and a badge report from the Docs editor frame could land after the focus had moved. bb e2e runs both for BOMBADIL_TIME each (90 s by default) after the e2e tests.
