Rex instead of Herdr, with our own Rust client?

T194, revised by W230 on 2026-11-16. The first version (W229, commit vtlzprnt) assumed we would package rexy. This one assumes we write our own client in Rust and use rexy only as a reference.

Goal: decide whether to replace Herdr with Rex if we write our own Linux client in Rust, rather than packaging rexy.

Recommendation: still wait, but the gate is now smaller. changed Writing our own client removes every blocker that came from rexy: it has no license, needs Rust 1.100 and has no floating panes. Two spikes showed the hard part works on this machine. The blockers that remain are all in the Rex server: no stable release, no license, no session restore, and an API that changed revision in a few days. Owning the client does not fix any of these, and it adds about 4 to 6 weeks of work plus upkeep each time Rex changes. So keep Herdr for now. When Rex ships a stable, licensed release, build our own client (working name rexmux) instead of packaging rexy, starting from the milestones in section 12.

Each claim has a tag: measured means I ran it or read it in code, inferred means I reasoned from what I read, and guess means an estimate. changed marks a finding that differs from the first version, and unchanged marks one that still holds.

1. Short answer

  • Feasible, and the risky core is proven. In a 65-line throwaway Rust program, our own code connected to a real Rex preview.19 server over its Unix socket, negotiated API revision 14, got a data ticket from session.bootstrap, opened the pane's data stream, and restored the pane's screen from Rex's Ghostty snapshot with libghostty-vt. The restored screen read RED spike-marker and the next three lines exactly. measured changed The first version called this the reason a client was hard to build; it is now shown to be about a day of work.
  • It builds here. libghostty-vt from libghostty-rs builds on this aarch64 Asahi machine with Guix's rust-1.96, which has substitutes, and the repo's own zig-0.17. A clean build took 2 min 19 s. rexy needs Rust 1.100, which Guix does not have. measured changed
  • Much lighter than rexy. A terminal-UI client (tokio, tokio-tungstenite, serde_json, crossterm, ratatui, libghostty-vt) locks 129 crates, 18 of them Windows or WASM only. rexy locks 422. measured changed
  • Design: a terminal UI inside Ghostty, like Herdr, not a GUI window like rexy. That keeps the Ghostty window class trick, kanata's terminal layer and Hyprland focus as they are, and it skips fonts and GPU rendering, which are most of rexy's code. inferred
  • Size: about 5,000 to 6,500 lines of Rust and 4 to 6 focused weeks, including Guix packaging and porting our scripts. guess
  • Still blocked by the server: no stable release, no license, no session restore, and it moves quickly (API revision 13 to 14 in days, preview builds about daily). measured unchanged

4. What Rex is unchanged, re-checked today

Re-checked on 2026-11-16: the stable channel still answers No Rex stable release is available, preview.19 from 2026-11-13 is still the newest, and rexy still has no license. measured

  • Rex is the multiplexer for all work from Superlogical. One server owns sessions, windows and blocks (panes), and clients attach to it. The macOS app is the main client and has a local server. iOS, Linux and Windows clients exist but are not in public testing. measured, from the installation page
  • The server and CLI are one 44 MB Go binary for x86-64 and ARM64, on glibc 2.26 or later or musl. Releases are public at https://blob.superlogical.com/api/releases/rex/preview with sha256 sums. Three channels exist, and stable is empty. Snapshots ship about daily, and preview.19 is from 2026-11-13. measured
  • Telemetry: none, and no license or account checks. The Linux server only listens on Unix sockets by default, with optional SSH, Tailscale or WebSocket access. measured, from the privacy and remote-access docs
  • Restarting the server ends every program in its sessions. Only the login-server mode keeps sessions across upgrades, and nothing survives a reboot. Herdr resumes agents on restore. measured, from the docs
  • Automation is strong: a self-describing API (74 methods in API revision 14), rex api call, rex events --json, server-side Lua (init.lua, rex.bind, key sequences, key modes, custom actions, event hooks), and an agent skill. measured

7. Architecture

The dashed arrow carries view events: layout changes go from the control task to the compositor.

  • A terminal UI, not a GUI. rexmux runs in a Ghostty window, as Herdr does, so the outer Ghostty does fonts, GPU, ligatures, clipboard and IME. rexy's egui interface alone is 6,526 of its 12,710 lines, before its notification, theme and Wayland code; none of that has a counterpart. measured The cost is that pane graphics such as Kitty images have to be passed through, which we can leave out at first. inferred
  • Tasks. A tokio runtime runs one control task, which owns the socket, gives each request an id and a reply channel, and turns events into messages for the UI, plus one data task per visible pane, which counts bytes, splits off the rex1 messages and forwards the rest. inferred
  • Terminals on one thread. libghostty-vt terminals are FFI handles; rexy keeps them on a dedicated thread too. The thread restores the snapshot, feeds bytes and produces a render state for the compositor. measured in rexy's terminal.rs
  • Compositor. Turns session.view into rectangles, copies each pane's cells and styles from the libghostty-vt render state into a ratatui buffer, draws borders, the tab bar, status dots and floating layers, and lets ratatui write only changed cells. Repaints are batched to the display rate. inferred
  • Input. crossterm enables the kitty keyboard protocol flags (disambiguate, event types, alternate keys, all keys as escapes, associated text), which Ghostty supports. Each key becomes a client.key. Physical key names come from the base layout key. Mouse clicks focus panes, the wheel scrolls, and pastes become terminal.write. inferred
  • State. The server is the source of truth. The client keeps a cache rebuilt from session.view and its events, so a reconnect or restart of rexmux loses nothing. inferred

10. Guix packaging on aarch64 Asahi

  1. libghostty-vt. A package built with zig-0.17 from Ghostty at the commit libghostty-rs pins, with -Demit-lib-vt=true, which installs the library and pkg-config files. It reuses ghostty.scm's zig-environment and dependency fetching, but needs its own list of Zig dependencies for that commit. The build fetches nothing when --system points at prefetched dependencies. About 1 day. inferred from build.rs and ghostty.scm
  2. rex. The release binary with patchelf, like herdr.scm, plus a Home shepherd service for rex server run. Half a day. measured that patchelf is needed
  3. rexmux. cargo-build-system with #:rust rust-1.96, the libghostty-vt-sys pkg-config feature so build.rs doesn't fetch Ghostty, and crate sources generated with guix import crate --lockfile into a channel-local crates module. Guix's rust-crates.scm already defines 10,633 crate sources, so most of the roughly 110 Linux crates may already be there; the git dependency on libghostty-rs needs an origin of its own. 1 to 2 days, including the first Rust check rules in checks.edn. inferred

The dependency burden is now small: 129 crates locked, about 110 of them for Linux, about a quarter of rexy's 422, and no toolchain package of our own. A from-scratch build of rexmux should take a few minutes, most of it the Zig build. measured for the counts and the spike's build time, guess for the package build time

14. Go, wait or no-go

Wait. changed reasons, same call Owning the client changes the call's reasons, but not the call itself.

  • Removed by owning the code: rexy's missing license, its Rust 1.100 toolchain, its missing floating panes, its single-author churn, and its 422-crate build. measured
  • Not removed: the Rex server's missing license and stable release, no restore, and protocol churn. Churn now costs more, because it lands on us. measured status, inferred cost
  • Cost against benefit: about 4 to 6 weeks plus upkeep, to get native OSC 7501, a Lua keymap and a cleaner API in place of a Herdr setup that works today. That is worth it on a stable, licensed server, but not on a closed beta. inferred
  • Not no-go: the fit is good, and the spikes removed the main technical doubt. measured

Gate to start, smaller than before

  1. https://blob.superlogical.com/api/releases/rex/stable returns a release.
  2. Rex publishes a license that allows private use and packaging.
  3. The API revision holds still for a few weeks, or Rex states a compatibility policy.

Dropped from the first version's gate: a licensed Linux client with floating panes, and a Guix rust that meets rexy's rust-version. changed

Migration once the gate opens

  1. Package libghostty-vt, rex and rexmux under new names, and add a feature-rex beside feature-familiar-herdr.
  2. Build M1 to M4 in the repo, using the side-by-side window class.
  3. Put a desktop/lib/mux.clj adapter behind keyleader and the pickers, with Herdr and Rex backends chosen by window class. unchanged
  4. Move the bbh-super Emacs frames first, then the popups, then make Rex the default.
  5. Fallback: Herdr stays installed and Super+B still opens it. Switching back is a one-line change of the default backend; no data moves, because bbh state lives in bbh. unchanged

If you want to start before the gate opens, the cheapest step that keeps value is M1 as a private experiment, which would show daily-use latency and key handling. I would not start M2 or later before the gate. guess
