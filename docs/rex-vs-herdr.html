Rex instead of Herdr?

Goal: decide whether to replace Herdr with Rex, given that on Linux we would have to supply the client ourselves.

Recommendation: wait. Don't migrate now. Look again when Rex has a stable release and a published license, and when a Linux client has floating panes, a license and a few months of history. Spend at most an afternoon on a side-by-side trial. Herdr stays as it is in the meantime.

Each claim has a tag: measured means I ran it or read it in code, inferred means I reasoned from what I read, and guess means an estimate.

1. Short answer

  • The Rex server works on this machine. The arm64 preview.19 binary is a Go program linked against glibc. Once patchelf points it at Guix's loader, rex server start, sessions, send, capture, events and OSC 7501 status reads all worked on the 16K-page Asahi kernel. measured
  • Rex itself is closed source and pre-release. There is no stable release yet: the stable channel returns No Rex stable release is available. Linux is server-only and marked in testing, and no license is published. The download is public, though the install docs are behind Discord. measured
  • rexy is a native GUI window (egui and libghostty), not a TUI that runs inside Ghostty. It was started on 2026-11-13 and has 57 commits by one author over three days. It has no license, so all rights are reserved by default. It needs Rust 1.100, while Guix has 1.93, plus Zig 0.17. It has no floating panes. measured
  • Herdr is Apache-2.0, is at release 0.9.5, and is already packaged and well integrated here. measured Herdr features that Rex plus rexy lack today: popups, which five of your bindings use, session and agent resume after a restart, and the plugins. inferred
  • A client of our own in bb or Emacs Lisp is not realistic. A client has to be a terminal emulator that reads Ghostty's snapshot format over a WebSocket, and the CLI shortcut rex block stream answers not implemented. measured The practical route is to package rexy or rex-rune in Guix and port our scripts to the rex CLI and Lua.

3. What Rex is

  • Rex is the multiplexer for all work from Superlogical. One server owns sessions, windows and blocks (panes), and clients attach to it. The macOS app is the main client and has a local server. iOS, Linux and Windows clients exist but are not in public testing. measured, from the installation page
  • The server and CLI are one 44 MB Go binary for x86-64 and ARM64, on glibc 2.26 or later or musl. Releases are public at https://blob.superlogical.com/api/releases/rex/preview with sha256 sums. Three channels exist, and stable is empty. Snapshots ship about daily, and preview.19 is from 2026-11-13. measured
  • Telemetry: none, and no license or account checks. The Linux server only listens on Unix sockets by default, with optional SSH, Tailscale or WebSocket access. measured, from the privacy and remote-access docs
  • Restarting the server ends every program in its sessions. Only the login-server mode keeps sessions across upgrades, and nothing survives a reboot. Herdr resumes agents on restore. measured, from the docs
  • Automation is strong: a self-describing API (74 methods in API revision 14), rex api call, rex events --json, server-side Lua (init.lua, rex.bind, key sequences, key modes, custom actions, event hooks), and an agent skill. measured

4. What a client has to implement

  • Control: a WebSocket at /api/control with subprotocol rex.control.v1. The client sends a JSON hello within 5 s, negotiates the API revision and gets a reconnect token, then makes requests and receives events tagged with sequence numbers and revisions. measured, from the server's /llms.txt
  • Data: per pane, data.connect issues a ticket. The client opens a WebSocket at /api/data, sends a 17-byte binary HELLO, and gets a WELCOME or REJECT. After that comes a snapshot in Ghostty's snapshot format, then the raw program output with APC rex1;nonce;json messages (resize, theme, child_exited) mixed in. Resuming means counting the exact number of bytes received. Input goes back on the control connection through client.key or the terminal's write. measured
  • So a client must embed a terminal emulator that can restore Ghostty snapshots: libghostty-vt in practice. rexy's Cargo.toml says no libghostty-rs release can restore a snapshot yet, so it pins a commit. measured Emacs vterm uses libvterm, which cannot read this format. inferred
  • The CLI does not offer a dumb terminal attach. It has no attach command, and rex block stream answers Error: command "rex block stream" is not implemented. measured

8. Migration sketch with fallback

  1. Gate. Wait for all of these: a Rex stable release with a license, a licensed Linux client (rexy or rex-rune) with floating panes, and a Guix rust that meets its rust-version, or a client that relaxes it.
  2. Side by side. Package Rex and the client under new names and add feature-rex without touching feature-familiar-herdr. Run the Rex server as a Home shepherd service.
  3. Thin adapter. Add desktop/lib/mux.clj behind keyleader and the pickers, with a Herdr backend and a Rex backend, so bindings choose the backend by window class.
  4. Move one workflow, such as the bbh-super Emacs frames, which only needs OSC 7501. Move the popups last.
  5. Fallback. Herdr stays installed and Super+B still opens it. Switching back means a one-line change of the default backend, with no data to migrate, because bbh state lives in bbh and not in the multiplexer.

9. Why wait rather than no-go

Rex's design suits this setup. OSC 7501 is the protocol bbh already speaks. The self-describing API and the Lua keymap are cleaner than Herdr's CLI plus socket. Built-in Tailscale and SSH access could later serve the phone path. inferred What blocks a move today is maturity and licensing, not fit: a closed beta server with no stable release and no restore, and a three-day-old client with no license and no popups. Signals to re-check: https://blob.superlogical.com/api/releases/rex/stable returns a release, and https://github.com/haydn-jones/rexy gains a LICENSE and floating panes.
