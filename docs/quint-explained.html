1. The bug that tests miss

Two workers share a counter that starts at 0. Each one adds 1. The answer should be 2.

But a computer adds in two steps. First the worker reads the counter into its own memory. Then it writes back what it read, plus 1.

Now let both workers run at once. One possible order:

Both read 0 before either wrote. One update is lost.

Why does a test not catch this? Because a read and a write take a few nanoseconds. Almost every time you run the test, A finishes before B starts, and you get 2. The bad order needs B to slip into a tiny gap. It happens once in a million runs, on a busy day, in production.

And it gets worse fast. Count the possible orders (programmers say interleavings):

WorkersSteps eachPossible orders
226
25252
35756,756
4511,732,745,024

A test runs one of them. The machine picks which, and it nearly always picks the same easy one. Code that talks over a network is the same story: messages arrive late, twice, or in a different order, and a server can die between any two steps.

So: concurrent code has far more possible orders than any test will ever see, and the bugs hide in the rare ones.

2. A system is a state plus actions

To check every order, we first need a simple way to describe the system. Two ideas are enough.

The state is a handful of variables: everything you need to know about the system right now. For our counter, three things:

  • x, the counter,
  • pc, where each worker is: about to Read, about to Write, or Done,
  • tmp, what each worker read.

An action is one thing that can happen, as one step. It has two parts:

  • a condition: when it is allowed. A can only write if A has read.
  • an effect: the new values of the variables after the step.

Our actions: read(A), write(A), read(B), write(B). That is the whole system.

Notice what we left out: the CPU, threads, memory, timing. We keep only what matters for the question we ask. That is called a model.

So: a model is a few variables (the state) and a few actions, each with a condition for when it can happen and an effect on the variables.

3. A behaviour is a list of states

Start in the first state. Pick any action whose condition holds. Apply it. You get a new state. Repeat.

The list of states you walk through is one behaviour: one possible history of the system. The lost update from step 1 is this behaviour:

Different choices give different behaviours. All of them together are everything the system can ever do. Every order from the table in step 1 is one behaviour.

So: run the model by picking allowed actions one after another; each path you can take is a behaviour, and the set of all paths is everything that can happen.

4. Writing it down in Quint

Quint is a language for writing exactly this: variables and actions. It looks like a programming language, but nothing in it runs on your computer as a program. It is a description that tools can explore.

Here is the counter, from /home/engstrand/guix/docs/quint-explained/race.qnt (trimmed):

module race {
  type Pc = Read | Write | Done

  var x: int            // the shared counter
  var pc: str -> Pc     // where each worker is
  var tmp: str -> int   // what each worker read

  val workers = Set("A", "B")

  action init = all {
    x' = 0,
    pc' = workers.mapBy(w => Read),
    tmp' = workers.mapBy(w => 0),
  }

  action read(w: str): bool = all {
    pc.get(w) == Read,          // condition
    tmp' = tmp.set(w, x),       // effect
    pc' = pc.set(w, Write),
    x' = x,
  }

  action write(w: str): bool = all {
    pc.get(w) == Write,
    x' = tmp.get(w) + 1,
    pc' = pc.set(w, Done),
    tmp' = tmp,
  }
}

Read it slowly. The small stuff first: type Pc = Read | Write | Done makes a type with three possible values, val gives a name to a value, w => Read is a tiny function, and mapBy, get and set build, read and update a map. Then five new things that matter:

  • var declares a state variable and its type. str -> Pc is a map: from a worker's name to where it is.
  • x' (x with a tick, said “x prime”) means x in the next state. So x' = x means “x stays the same”, and x' = tmp.get(w) + 1 means “next, x is what w read, plus 1”.
  • all { … } means all of these together, in one step.
  • A line with no tick, like pc.get(w) == Read, is the condition. If it is false, the whole action cannot happen right now.
  • init is the action that makes the first state. It has no condition; it just sets every variable.

One rule to remember: every action must say the next value of every variable, even the ones it leaves alone. That is why read says x' = x. Check this by eye: the type checker only notices a missing one when two branches of an any (step 5) disagree.

quint typecheck docs/quint-explained/race.qnt

No output means it is fine.

So: in Quint, var is a piece of state, x' is its next value, and an action is an all { } of a condition and the next value of every variable.

5. Choice: any and nondet

We have actions. Now we must say which one happens next. The honest answer is: we do not know. Either worker might go. That is the whole point.

Quint says “one of these, we don't know which” with two words:

  • any { a, b, c }: one of these actions happens, any one whose condition holds.
  • nondet w = workers.oneOf(): pick some value from a set, any one, and call it w.

Together they make the action called step, which is every possible next move:

  action step = any {
    { nondet w = workers.oneOf() any { read(w), write(w) } },
    finished,
  }

In words: pick a worker, any worker, and let it read or write, if it may. Or, if both are done, finished (it changes nothing; step 9 says why it is there).

“Nondeterministic” is just the long word for this: the model does not decide. The tools do. A simulator flips a coin. A model checker tries every option. That is how one short step stands for every order in the table from step 1.

So: step lists every move that could come next, with any and nondet, and leaves the choice open; the tools then explore the choices for you.

6. Invariants: true in every state

Now say what “correct” means. The simplest kind of rule is an invariant: something that must be true in every state the system can reach, no matter which path led there.

  // When both are done, the counter is 2.
  val bothCounted = workers.forall(w => pc.get(w) == Done) implies x == 2

val names a value computed from the current state. A implies B means “if A, then B” (when A is false, there is nothing to check).

Reachable matters. A state like “x = 7” is allowed by the types, but no path gets there, so nobody cares about it. We only ask about states you can actually walk to from init by taking steps.

And one bad state is enough. If even one reachable state breaks the rule, the rule is broken, and the path that leads there is the proof.

So: an invariant is a yes/no question about one state, and it must say yes in every state some path can reach.

7. quint run: try lots of random paths

The first tool is a simulator. It does what step 3 described, by flipping coins: start at init, pick a random allowed move from step, check the invariant, repeat. By default it walks 20 steps per path and tries up to 10,000 paths. It stops at the first state that breaks the rule.

cd /home/engstrand/guix
quint run docs/quint-explained/race.qnt --invariant=bothCounted
An example execution:

[State 0]
{ pc: Map("A" -> Read, "B" -> Read), tmp: Map("A" -> 0, "B" -> 0), x: 0 }

[State 1]
{ pc: Map("A" -> Read, "B" -> Write), tmp: Map("A" -> 0, "B" -> 0), x: 0 }

[State 2]
{ pc: Map("A" -> Write, "B" -> Write), tmp: Map("A" -> 0, "B" -> 0), x: 0 }

[State 3]
{ pc: Map("A" -> Write, "B" -> Done), tmp: Map("A" -> 0, "B" -> 0), x: 1 }

[State 4]
{ pc: Map("A" -> Done, "B" -> Done), tmp: Map("A" -> 0, "B" -> 0), x: 1 }

[violation] Found an issue (12ms at 2000 traces/second).
  ❌ bothCounted
Use --seed=0x918485aa67f7b133 --backend=rust to reproduce.
error: Invariant violated

Twelve milliseconds. The race that a real test would hit once in a million runs, the simulator found at once, because it does not care how small the gap is: “B goes now” is just another coin flip.

The --seed line is the coin's starting point. Pass it back and you get the same paths again, so a failure is never a ghost you cannot repeat.

But notice the limit. If no random path hits the bad state, quint run says [ok] No violation found, and that only means it did not find one. It is a very good test, not a proof.

So: quint run walks thousands of random paths in seconds and is great at finding bugs, but “ok” from it means “not found”, not “not there”.

8. Reading a counterexample

The output above is a counterexample (also called a trace): a real path from the start to a state that breaks the rule. Read it as a story, one state at a time, and ask “what changed?”:

Statepc Apc BxWhat happened
0ReadRead0start
1ReadWrite0B read 0
2WriteWrite0A read 0 too: now it is too late
3WriteDone1B wrote 0+1
4DoneDone1A wrote 0+1 over it

The trace never names the action; you see it from what changed. (The REPL in step 10 shows the changes with arrows.) Three tips:

  • Look at the last state first: that is what is wrong. Then walk back to find the first state where it was already doomed (here, state 2).
  • Bugs in a model usually need only a few steps, so the story is usually five to twenty lines, not a thousand. A model checker gives the shortest one; a random run's can be longer.
  • Each line is a real situation your code can be in. To fix the bug, change the model so that the doomed step can no longer happen, and run again.
So: a counterexample is a step-by-step story of how the bug happens; read the last state, then find where it went wrong.

9. quint verify: try every path

Here is the surprising part. You do not need to walk every path to check every state. Many paths lead to the same state: “A reads, then B reads” and “B reads, then A reads” end in the same place. So eleven billion orders can shrink to a few thousand states. A model checker is a tool that uses tricks like this to cover all of them, instead of a random sample.

Our counter has 13 reachable states in total. A model checker visits all 13 and checks the rule in each. If it says ok, the rule holds everywhere. That is a proof, for this model.

Quint comes with two model checkers:

  • Apalache, the default for quint verify. It does not list states. It turns “is there a path of at most N steps that breaks the rule?” into one big logic puzzle and hands it to a solver. That makes it bounded: it checks paths up to --max-steps (default 10), not longer.
  • TLC, the classic one from TLA+ (step 15). It keeps a list of the states it has seen, never explores one twice, and so visits every reachable state, with no bound on path length. It needs a model small enough to list, and it can also check the “eventually” rules of step 13.
quint verify docs/quint-explained/race.qnt --invariant=bothCounted

It starts Apalache (a Java program), which prints a page of log lines. The answer is at the bottom: the same story as in step 8, then

[violation] Found an issue (3630ms).
  ❌ bothCounted
error: found a counterexample

Now fix the bug. The file has a second step, stepFixed, where a worker reads and writes in one action (add), so nobody can come in between. That is what a lock, or an atomic add, gives you in real code:

quint verify docs/quint-explained/race.qnt --step=stepFixed --invariant=bothCounted
[ok] No violation found (3461ms).
You may increase --max-steps.

Read “You may increase --max-steps” honestly: Apalache checked every path of up to 10 steps. For this model that is everything (after two adds both workers are done and nothing changes), but in general it is a bound.

About finished from step 5. A model checker also complains when the system gets stuck: a state where no action is allowed, called a deadlock. Without finished, “both done” is such a state, and quint verify answers error: reached a deadlock. In a real system a deadlock is often a bug, so that complaint is a feature. Here being done is fine, so finished says so.

So: a model checker covers every case instead of a sample, so “ok” really means ok: Apalache every path up to a length, TLC every reachable state with no limit.

10. quint test and the REPL

Two smaller tools help while you write a spec.

quint test runs paths you write down by hand. A run chains actions with .then and checks with .expect. If an action is not allowed at that point, the test fails. This one replays the bad order on purpose:

  run lostUpdateTest =
    init
      .then(read("A")).then(read("B"))
      .then(write("A")).then(write("B"))
      .expect(x == 1)
quint test docs/quint-explained/race.qnt

  race
    ok lostUpdateTest passed 1 test(s)

  1 passing (12ms)

Tests are how you check that the model does what you think it does, before you trust the model checker's “ok”.

The REPL lets you take steps by hand and look around. Load the module, then type actions and expressions (output trimmed):

quint -r docs/quint-explained/race.qnt::race
>>> init
true
{ pc: Map("A" -> Read, "B" -> Read), tmp: Map("A" -> 0, "B" -> 0), x: 0 }
>>> read("A")
true
{ pc: Map("A" -> Read => Write, "B" -> Read), tmp: Map("A" -> 0, "B" -> 0), x: 0 }
>>> read("B")
true
>>> write("A")
true
{ …, x: 0 => 1 }
>>> write("B")
true
>>> bothCounted
false
>>> write("A")
false

true means the action happened, and Read => Write shows what it changed. The last false means write("A") is not allowed now (A is already done), so nothing changed. Type .exit to leave.

So: quint test checks paths you choose; the REPL lets you take steps by hand and look at any value.

11. The real thing: Rexmux's connection

Now the same ideas on a spec that guards real code: /home/engstrand/guix/desktop/build/rexmux/verify/quint/rexmux.qnt

The story it models. ghostty-rex (your terminal window) keeps a connection to the Rex server. That sounds simple. It is not, because:

  • the server can be down, can stop, and can drop the connection at any moment;
  • the client retries, and may start a local server itself;
  • each try is an attempt with a number, and every answer (connected, failed, closed) names its attempt, but answers arrive in any order, late, or for an attempt the client gave up on.

That is step 1's problem again, with more workers and more steps. The state (trimmed):

  type Conn = Down | Connecting | Up
  type Kind = Connected | Failed | Closed
  type Ctrl = {
    srvUp: bool,               // the Rex server answers
    conn: Conn,                // what the client thinks
    gen: int,                  // the attempt it is waiting for
    live: int,                 // the attempt it adopted
    inflight: Set[int],        // attempts the server has not answered yet
    open: Set[int],            // attempts whose socket is open
    answers: Set[(Kind, int)], // answers queued for the client
    …
  }

The actions are the things that can happen: tryConnect (start attempt gen), answer(g) (the server answers attempt g), late (an attempt the client stopped waiting for connects anyway), connected(g), connectFailed(g) and closed(g) (the client handles an answer), timer (the retry timer fires), startLocal, hangup, serverStops, serverStarts. step is any of them, with nondet g = ids.oneOf() choosing which attempt an answer is for.

Notice that answers is a set, not a queue. Any answer in it can be handled next. That one choice of data type is what says “answers come in any order”.

The rules, as invariants, in plain words:

NameMeans
neverStrandedWhen down, something will try again. When connecting, an answer is coming.
upIsLiveThe client says Up exactly when it adopted the attempt it waits for, and that socket is open (or its close is on the way).
noLeakEvery open socket is the live one, or still waiting for the client's verdict. No socket is forgotten.

A spec needs limits so a checker can finish: here the connection is lost at most 3 times (MaxLosses), attempt numbers go up to 2 and are reused (MaxGen), and one late answer may happen (MaxLates). The module connect at the bottom of the file sets them. Bugs almost always show up with small numbers, so small limits catch them.

T220 moved this spec from TLA+ (Rexmux.tla) to Quint. The proof that nothing was lost in the move: both versions have exactly 3034 reachable states. Your bb tasks run it (W288 wrote the Babashka side, /home/engstrand/guix/desktop/build/quint/README.md):

The first is the quick check that make test runs when Rexmux changes: steps 7 and 10. The second is the full model check (step 9), which make verify runs. The 3034 is pinned in /home/engstrand/guix/desktop/build/rexmux/verify/quint/checks.edn, so a change that grows or shrinks the state space shows up.

So: the real spec is the counter again, bigger: a record of state, a dozen actions, answers in a set so any order is possible, and three invariants checked in all 3034 states.

12. The bug the review found, caught again

Before T211, a code review found this race in ghostty-rex. Two attempts both connected. The client kept one and closed the extra one, which is right. But closing a socket produces a :closed answer, and when that stale :closed came back, the client treated it as “my connection closed”. It dropped its live connection and forgot it, while that socket stayed open.

The fix was the attempt number: closed(g) only counts if g is the attempt the client is on. In the spec it is this line:

    control(if (current(ctrl, g, Up) or current(ctrl, g, Connecting)) { ...failed(c), live: noConn } else c),

Take the fix out and ask Quint. Copy the spec and make closed ignore which attempt the close is for:

cd /home/engstrand/guix
cp desktop/build/rexmux/verify/quint/rexmux.qnt /tmp/broken.qnt
chmod u+w /tmp/broken.qnt
sed -i 's/current(ctrl, g, Up) or current(ctrl, g, Connecting)/ctrl.conn == Up or ctrl.conn == Connecting/' /tmp/broken.qnt
quint run /tmp/broken.qnt --main=connect --invariant=noLeak
[violation] Found an issue (65ms at 1323 traces/second).
  ❌ noLeak
error: Invariant violated

Under a tenth of a second. The full model checker gives the shortest story. In a bbh REPL, where quint names that Babashka runner, (quint/model-check "/tmp/broken.qnt" "connect" {:invariants ["noLeak"]}) returns it as data; here it is as a table:

#connliveopenanswersWhat happened
0Downnone{}{}start, server up
1Connectingnone{}{}tryConnect: attempt 1
2Connectingnone{1}(Connected, 1)server accepts 1
3Up1{1}{}client adopts 1
4Up1{0, 1}(Connected, 0)an old attempt connects late
5Up1{1}(Closed, 0)client closes the extra one: right
6Downnone{1}{}the stale close drops the live one

Read the last row first (step 8): socket 1 is open, but the client is Down and has no live attempt. Nobody will ever close socket 1. That is the leak. Walk back: row 5 was fine, and row 6 is the doomed step, a close for attempt 0 acted on as if it were for attempt 1. That is exactly the review's finding, rebuilt in six steps from a one-line change.

Put the line back and the same checks say ok in all 3034 states. That is the deal Quint offers: the review found this bug once, by luck and skill; the spec now finds it every time anyone brings it back.

So: remove one guard from the real spec and Quint rebuilds the review's stale-close race as a six-step story in under a second.

13. Eventually: properties about the future

Invariants say “nothing bad ever happens”. That is called safety. But a client that never connects at all breaks no invariant: being Down forever is safe. We also want “something good eventually happens”. That is called liveness.

For that, Quint has two words that talk about a whole behaviour (step 3), not one state:

  • always(P): P is true in every state of the behaviour, from here on. An invariant is just always of a state rule.
  • eventually(P): P is true in some state, now or later.

Put together, they say a lot. From the Rexmux spec:

  temporal serverUpAttaches = fairness implies
    always((ctrl.conn != Up and ctrl.srvUp) implies eventually(ctrl.conn == Up or not(ctrl.srvUp)))

In words: at any moment when the client is not connected but the server is up, sooner or later the client is connected, or the server went down again. Ignore fairness implies for one more step.

A liveness counterexample looks different. A safety bug is a finite story ending in a bad state. A liveness bug is a story that goes on forever without the good thing: either it ends in a loop that comes back around, or it ends in a state where the system just sits still forever.

Which tools can check these? quint run cannot: a random walk of 20 steps cannot show “forever”. Apalache has only partial support. TLC can, because it has the whole map of states and can look for loops in it. That is why your repo runs liveness with TLC, in bb verify:quint-mc.

So: safety is “nothing bad, ever” (always); liveness is “something good, eventually” (eventually), and its counterexample is an endless path, a loop or a stop, that never gets there.

14. Fairness: things that can happen, do

There is a catch. In a model, “nothing happens” is always allowed: the system can just pause forever, even while actions are allowed. This is called stuttering. It is not a deadlock (step 9), where nothing can happen; here something could, but nothing does. Then every eventually fails, for a silly reason: the timer is set, but the model never lets it fire.

Fairness rules out these silly paths. It is an assumption you add, in plain words: “this action does not wait forever”.

  • weakFair(A, vars): if A stays allowed, it eventually happens. A retry timer that is set does fire.
  • strongFair(A, vars): if A is allowed again and again, even with gaps, it eventually happens. Used for startLocal(true): if starting the local server keeps being tried, one try eventually works.

The spec lists these assumptions in temporal fairness, and each liveness rule starts with fairness implies: “assuming nothing waits forever, …”.

See what one missing line does. Take weakFair(timer, ctrl) out of the list and check serverUpAttaches again with TLC. It fails, after all 3034 states, with this story (trimmed):

#srvUpconntryWhat happened
0falseDownToConnectstart, server down
1falseConnectingNothingattempt 1
2falseConnectingNothingit fails
3trueConnectingNothingthe server starts
4–5trueConnectingNothinga late attempt connects and is closed
6trueDownToAfterthe failure is handled: wait for the timer
7trueDownToAfterthe stale close is ignored, as it should be
8Stuttering: nothing happens, forever

The server is up, the client is down and waiting for its timer, and the timer never fires. TLC even prints a warning that this kind of answer usually means a missing fairness rule. Put the line back: ok.

Fairness is a promise about the world, so only promise what is true. A real timer fires; that is fair to assume. “The network never drops” is not, and the spec does not assume it.

So: fairness says which actions cannot wait forever; without it, “nothing ever happens” breaks every liveness rule.

15. Quint and TLA+

Everything above comes from TLA+, the language Leslie Lamport built on his Temporal Logic of Actions. Quint uses the same logic, so it can say and check the same things. What changes is how it reads:

IdeaQuintTLA+
state variablevar x: intVARIABLE x
next valuex' = x + 1x' = x + 1
all at onceall { a, b }a /\ b
one ofany { a, b }a \/ b
pick a valuenondet v = S.oneOf()\E v \in S:
always, eventuallyalways(P), eventually(P)[]P, <>P
fairnessweakFair(A, v)WF_v(A)

Beyond looks, Quint builds in types, a type checker, tests, a REPL and a fast simulator; for TLA+ these are separate or optional tools, or missing. It drops a few rarely used TLA+ features; for example there is no CHOOSE, which is why rexmux.qnt picks the least element of a set with fold. And quint compile turns a Quint spec into TLA+, which is how the TLC checks here run at all.

For you, T220 was this move: Rexmux, bbh super and the wf runs went from TLA+ to Quint, with the same state counts as proof. Details are in /home/engstrand/guix/docs/quint.html

So: Quint is TLA+'s logic with programmer syntax, types, tests and a REPL, and it compiles to TLA+ when a TLA+ tool is needed.

16. The whole picture, and what to type

Tests see only the orders the machine happens to pick (1). So describe the system as a state and actions (2), where each path is a behaviour (3), write it in Quint (4) and leave the choices open with any and nondet (5). Say what must always hold (6). quint run tries random paths fast (7) and hands you a story when it finds a bug (8); a model checker visits every state, so its ok is a proof for the model (9). Tests and the REPL check that the model means what you think (10). Your Rexmux spec does all of this in 3034 states (11), and rebuilds the review's stale-close race from a one-line change (12). eventually adds liveness (13), fairness keeps it honest (14), and all of it is TLA+'s logic in friendlier clothes (15).
