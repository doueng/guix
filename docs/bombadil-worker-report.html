Outcome

Goal: extend the Bombadil tests of the bbh Emacs UI from the Inbox to the Worker view: the Router and Worker transcripts, the composer, mailbox wakes and session state. Scrolling large transcripts gets time bounds and a hang watchdog. Result: make bombadil now runs the Inbox and then the Worker view. The Worker view drives a real Router and two Workers on a churning controller, over a 5 MB transcript made from anonymized real conversations. It found eight real bugs, all fixed, each with an ERT regression test that fails without its fix. Scrolling stays far under its budget: the slowest scroll step in the final 10-minute run took 121 ms against a 1 s bound, and the longest stall between commands was 795 ms. measured
Not fixed, by choice: C-n while a restarted session is still starting says Starting agent, please wait and keeps the draft, so you press C-n again. The spec accepts that as a stated refusal. Queueing the draft instead would be a design change in agent-shell's send path.

How it runs

  • Same harness as the Inbox (W191): Bombadil 0.7.10 in a 140x40 PTY, Emacs -Q -nw with evil and this checkout's agent-shell.el and bbh-super.el, a temp HOME, the heavy-job slot, and a memory cap. bb test:bombadil --view worker picks this view.
  • Real sessions: a real controller opens a Router and Workers through emacsclient on the run's own Emacs server. They are real bbh acp processes answering from a script model. A script step can now stream its text in chunks (bbh.models), so output lands mid-scroll as with a real model.
  • Churn: mail to Workers and the Router, asks, notes, finishes, and SIGKILLs of Workers (the T162 restart path). A seeded share of turn ends throws, the T163 fault: a 10-minute run injects about 150–270 of them.
  • Large transcripts: the first Worker gets a 5 MB replay of real conversations, anonymized per run: every word is replaced by a pseudo-word of the same length, keeping the shapes of code blocks, tables and long lines. A second Worker gets 2.5 MB.
  • What the spec sees: worker.el tags the composer's status line [T1 N F TOP CHECK]: thread, evil state, follows the end or scrolled, transcript at its first line, and whether any Emacs-side check failed.

Properties

Screen properties, worker.ts

  • C-n sends from the composer in normal and insert state; the draft leaves, or the echo area says why not. C-c C-c never sends.
  • A word typed in insert state lands in the composer within a second, unless it was sent first; the transcript shows only words that were sent.
  • The composer stays on screen unless a key left the view; no refusal shows as bbh super: x x.
  • Working ends within 90 s (T163); no error repeats on consecutive lines (T162); a thread the Inbox shows done is not Working in its view.
  • After G the transcript ends on its bottom rows, unless it is short enough to show from its first line.

Emacs-side checks, worker.el

  • Time bounds: every command plus its redisplay under 1 s; no stall over 1 s between commands, measured from a 0.5 s heartbeat timer; a watchdog that SIGUSR2s Emacs for a backtrace and fails the run after 15 s without timers.
  • Windows after each command: point visible, start inside the buffer, no blank rows below the end.
  • Output: a window following the end still follows; a scrolled-up window keeps its point and start, through the edit and the redisplay after it.
  • State: a selected transcript or thread list is never in insert state.

What the spec had to learn

A terminal screen can lag Emacs by a key or two, and Emacs can lag the keys. Each of these first showed up as a false violation: inferred

  • A slow keystroke's redraw lands a state late, so typed words get a second to show, and words typed but not yet drawn count as sent.
  • ESC can still show insert state for a moment, so a word only counts as typed in insert state after a key that cannot change the state.
  • A sample can land mid-redraw while output streams, so the bottom of the transcript gets a second to settle after G.
  • Emacs skips redisplay while typed-ahead keys wait, so worker.el redisplays before it checks the windows. Output can land inside a command, as while gg waits for its second key, so a window that command moves is not blamed on the output.
  • The Inbox's refusals flash in the echo area until the next key, so inbox.el now counts them in the mode line, which the spec reads.
  • Typing inside a word, as vim's i after ESC does, only splits it, so C-c C-c counts as sending only if the composer also got shorter.

Open finding

Blank rows after re-entering the Router view. Once in about 40 minutes of runs: C-c r from the Router's own composer left its 19-row transcript window on a start that fits only 11 rows, with 8 blank rows below the end. The post-command clamp should pull such a start back, and the next command did. A replay of the same keys on a small transcript in the TTY test did not reproduce it, so it stays open, not guessed at. Evidence: open-finding/ in the wf evidence, from seed 600333. measured

Use it

make bombadil                        # Inbox, then Worker view, 120 s each
make bombadil VIEW=worker BOMBADIL_TIME=600
cd desktop/build/bbh && bb test:bombadil --view worker --seed N --reproduce DIR --keep

A failure prints the property, the screen, and a reproduce line. With --keep the temp root holds steps.log (every command's time, state and buffer), checks.log, messages.log, faults.log and the trace.
