nixpkgs-bridge

Design for using cache.nixos.org binaries on this Guix System laptop (M1 MacBook Air, aarch64-linux, Asahi kernel with 16 KiB pages). Written 2026-10-13 against Guix 6754acb and nixpkgs 8edc0c72.

Each claim carries an evidence tag. measured means I ran it on this laptop. source means I read it in Guix, guix-transfer, or cache.nixos.org output. background means general knowledge of the two projects that I did not check here. guess means an untested prediction.

Recommendation. Do not translate nixpkgs derivations. Copy built nixpkgs outputs into /gnu/store instead. Rewrite the 10-byte prefix /nix/store to /gnu/store, which is also 10 bytes, and keep the 32-character hash. The rewritten bytes have the same layout, so ELF interpreters, RPATHs, shebangs and symlinks keep working. Rewrite every occurrence of the prefix, not only the hash parts.

As built, make nixpkgs-import does the rewriting and signs the result with a local key that the daemon trusts, then pipes it to guix archive --import. A Guix package wrapper makes the items installable from home.scm. Section 11 describes the built system. Sections 4 to 9 are the original proposal, which used a substitute server instead.

A spike on this laptop rewrote the closures of hello, python3, git, fd, ripgrep and jq (93 store items, 454 MiB on disk) from cache.nixos.org. All six ran from /gnu/store measured.

1. Goal and constraints

  • Install nixpkgs packages on this machine without building them, using the binaries Hydra already built for aarch64-linux.
  • Keep one store, one daemon and one garbage collector. Packages from nixpkgs should sit in the same Guix Home profile as Guix packages.
  • The machine runs a 16 KiB page kernel (getconf PAGESIZE prints 16384) measured. nixpkgs aarch64 binaries assume nothing about page size in general. jemalloc builds that hard-code 4 KiB pages are the usual failure. fd, which nixpkgs links against jemalloc, ran fine measured.
  • No secrets, firmware or machine backups go in the repository (from AGENTS.md). A public signing key may go in. The secret key stays on the machine.

2. What guix-transfer does, and why its mirror image misses the goal

guix-transfer walks a Guix .drv graph bottom-up. It rewrites every /gnu/store reference to the already translated /nix/store path and registers each derivation with nix derivation add, which recomputes the output paths source. It must recompute paths because the store directory is an input to the output path hash, in both systems (guix-transfer DESIGN.md section 6) source.

That is the reason a mirror image cannot use the nixpkgs cache. A translated nixpkgs derivation gets a new /gnu/store output path that no cache has ever built, so the Guix daemon must build it. guix-transfer says so itself. Realising hello recompiles Guix's whole source bootstrap and takes hours source. The reverse would rebuild nixpkgs from its bootstrap tools in the same way. Only fixed-output sources would come from a cache.

So the unit that crosses over must be the built output (a NAR), not the derivation. The question becomes how to make a binary built for /nix/store run from /gnu/store.

The trick that makes it cheap

/nix/store and /gnu/store are both 10 bytes. Replacing one with the other in place keeps every string length, ELF offset and NAR length field intact. If the bridge also keeps the 32-character hash part, the whole mapping from nixpkgs paths to Guix paths is one pure function:

/nix/store/0xy6jlccm8kfpwmhkxabz3638lchyi74-hello-2.12.3
/gnu/store/0xy6jlccm8kfpwmhkxabz3638lchyi74-hello-2.12.3

guix-transfer needs a growing map from Guix paths to Nix paths and must process the graph in order. Here there is no map and no ordering, because a reference's new name never depends on its content. Self-references, such as glibc pointing into its own lib/, are no special case. Guix's grafting does a similar same-length rewrite of store references, which shows that such rewrites hold up in practice background.

C2 beats C1 because the user never holds a key that can inject arbitrary store items. Lowering a package only asks the daemon to ensure-path. It is the right choice if you want nixpkgs tools such as nix shell, flakes or home-manager rather than nixpkgs binaries.

5.1 Data shapes

Path mapping. A function, not a table. (nix->gnu "/nix/store/X") = "/gnu/store/X". Because of this, the bridge, the lock and the Guix module never have to agree on a translation table.

Lock file (desktop/nixpkgs.lock, an s-expression so Guile reads it without a JSON dependency). It is the single source of truth. The lock writer produces it and nothing else edits it.

(nixpkgs-lock
 (revision "8edc0c72e3a38faf5434e40d1f19431125fe4b30")
 (system "aarch64-linux")
 (packages
  ("jq" (version "1.8.2")
        (install "bin" "man")
        (outputs ("bin" "/nix/store/kr5py0dcqc9f3l9148qd1axh0z77lld3-jq-1.8.2-bin")
                 ("man" "/nix/store/3dk5p8ydxv92px9q2y5vgq3gzl26vdxy-jq-1.8.2-man"))))
 (closure "/nix/store/hx9wvdx2l59iahwf9nmrx7rwkm6cymgs-glibc-2.44-25" ...))

closure is the union of the runtime closures of every installed output, from narinfo References. The bridge uses it as its allowlist. The lock writer refuses to write the lock if any closure member lacks a narinfo on cache.nixos.org. A missing narinfo means Hydra did not build it for aarch64, and the bridge must never fall back to building.

Rewritten narinfo, the bridge's answer. Example for hello:

StorePath: /gnu/store/0xy6jlccm8kfpwmhkxabz3638lchyi74-hello-2.12.3
URL: nar/zstd/0xy6jlccm8kfpwmhkxabz3638lchyi74-hello-2.12.3
Compression: zstd
NarHash: sha256:<hash of the rewritten NAR>
NarSize: 294360
References: 0xy6jlccm8kfpwmhkxabz3638lchyi74-hello-2.12.3 hx9wvdx2l59iahwf9nmrx7rwkm6cymgs-glibc-2.44-25
System: aarch64-linux
Signature: 1;localhost;<canonical sexp signed by the bridge key>

NarSize and References carry over unchanged in length and hash parts. The nixpkgs Deriver is dropped because no such .drv exists in /gnu/store.

5.3 The Guix side

A G-expression compiler turns a locked nixpkgs path into a source input. lower-inputs in guix/gexp.scm:952 treats any lowered value that is a store path string as a source source. The daemon registers sources as references of the derivation, and through it of the profile. That puts bridged items under normal Guix garbage collection.

(define-record-type <nixpkgs-item>
  (nixpkgs-item path)
  nixpkgs-item?
  (path nixpkgs-item-path))

(define-gexp-compiler (nixpkgs-item-compiler (item <nixpkgs-item>) system target)
  (let ((path (nix->gnu (nixpkgs-item-path item))))
    (mbegin %store-monad
      ((store-lift ensure-path) path)   ; the daemon substitutes it from the bridge
      (return path))))

(define (nixpkgs-package attr)
  (match (lock-package attr)
    (($ <locked-package> attr version install-paths)
     (package
       (name (string-append "nixpkgs-" attr))
       (version version)
       (source #f)
       (build-system trivial-build-system)
       (arguments
        (list #:modules '((guix build union))
              #:builder
              #~(begin
                  (use-modules (guix build union))
                  (union-build #$output
                               (list #$@(map nixpkgs-item install-paths))))))
       (synopsis (string-append "nixpkgs " attr " from cache.nixos.org"))
       (description "Binary output of nixpkgs, rewritten into /gnu/store.")
       (home-page "https://search.nixos.org")
       (license #f)))))

In home.scm, (map nixpkgs-package '("jq" "ripgrep")) joins the package list. The nixpkgs- prefix keeps names apart from Guix packages in guix package -I and in profile conflict messages.

6. Trust

  • The bridge key can sign anything, so it is as powerful as the bordeaux key in /etc/guix/acl. It lives only with the nixpkgs-bridge service account. Revoking it means removing one entry from authorized-keys.
  • The bridge signs only after it has checked the cache.nixos.org signature and the original NarHash. So the chain of trust is cache.nixos.org, then a fixed byte rewrite anyone can repeat, then the local key. The spike already checks NarHash and fails on a mismatch measured. Checking Sig is still to do.
  • The allowlist keeps the bridge silent for every other hash. Otherwise each Guix substitute lookup would leak a /gnu/store hash to cache.nixos.org and add a round trip.
  • A collision between a bridged path and a future Guix output path would need two different 160-bit truncated SHA-256 values to match. I treat it as impossible.

8. Spike evidence

The spike store paths come from Hydra's latest finished nixpkgs/unstable aarch64 builds. hello, jq and ripgrep match revision 8edc0c72 exactly measured. The spike fetched narinfos and NARs from cache.nixos.org, checked NarHash, swapped the prefix and unpacked the result into a directory. 9. Implementation plan

The riskiest unknown comes first. Each phase ends in a check run on the real system.

  1. Daemon acceptance. Generate the bridge key and authorize it with a reconfigure. Serve the hello narinfo and NAR from a throwaway server, then run guix build /gnu/store/0xy6…-hello-2.12.3. Done means the item is valid, guix gc --verify=contents passes, and guix gc -R lists glibc.
  2. Lock writer. make nixpkgs-lock writes desktop/nixpkgs.lock for the wanted list. Done means the lock for hello, jq and ripgrep matches the paths in section 8, and an attribute missing on aarch64 makes the writer fail.
  3. Bridge service. Add the allowlist, the Sig check, rewrite, signing and the cache. Done means phase 1 passes against the service, and a hash outside the allowlist gets 404 with no outbound request.
  4. Guix module. Add nixpkgs-package and the G-expression compiler. Done means make home-build builds a Home containing nixpkgs-jq.
  5. Home integration and checks. Add make nixpkgs-check. Done means every locked package runs from ~/.guix-home/profile/bin after make home-apply, and guix gc keeps bridged items while the profile references them.
  6. Optional. Add an OpenGL driver link and a locale archive, if you want GUI apps.

10. Open decisions

  • Channel: nixpkgs-unstable (used here, revision 8edc0c72) or a stable nixos-YY.MM branch, which gets fewer updates but holds versions still for six months.
  • Scope: CLI tools only, or GUI apps too, which adds the OpenGL work in phase 6.
  • If you would rather run nixpkgs tooling itself (flakes, nix shell, home-manager), choose option A instead. It costs a second store but no code.

11. As built

The first implementation differs from section 5 in five ways.

  • File locations. The wanted list is modules/engstrand/nixpkgs/packages.sexp and the lock is modules/engstrand/nixpkgs/lock.sexp, beside the module that reads them, rather than desktop/nixpkgs.scm and desktop/nixpkgs.lock. The make targets run the command-line entry point desktop/build/nixpkgs/bridge.scm.
  • No substitute server. make nixpkgs-import signs an export stream with a key in ~/.config/guix/nixpkgs-bridge/ and pipes it to guix archive --import. The daemon trusts the key through authorized-keys in modules/engstrand/system/asahi.scm. The key is held by the user account rather than a service account. On this single-user laptop that account already has sudo, so the gain from a separate service did not pay for an HTTP server and a Shepherd service.
  • The lock holds every narinfo. modules/engstrand/nixpkgs/lock.sexp records URL, compression, NAR hash, size and references for each closure item. The lock writer checks each cache.nixos.org signature. The importer then needs only the lock, and refuses any NAR whose hash or size differs.
  • Graphics. The nixpkgs ghostty, run from the rewritten store, loaded OpenGL 4.6 through nixpkgs Mesa 26.2.4 measured. nixpkgs-system-services links /run/opengl-driver to that Mesa and installs /etc/fonts/fonts.conf. Those are the default paths nixpkgs libglvnd and fontconfig search, and Guix programs read neither measured. A first version set the Mesa variables in a ghostty wrapper instead, and every shell ghostty started inherited them, along with any Guix GUI program run from that shell.
  • Locales. Home sets LOCALE_ARCHIVE to nixpkgs glibcLocalesUtf8. Guix's glibc 2.41 has no reference to that variable measured, so only nixpkgs programs read it.

Before the key was trusted, a throwaway script checked the archive writer without root. It imported a content-addressed test item through the real daemon and verified the signature with guix authenticate against a temporary ACL. Now the real import and make nixpkgs-verify cover the same ground. Verify reads each item back from /gnu/store, maps /gnu/store/ back to /nix/store/, and compares the NAR hash with the one cache.nixos.org signed.
