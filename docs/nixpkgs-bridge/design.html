nixpkgs-bridge

How this laptop uses binaries that nixpkgs already built, inside a Guix system. Updated 2026-10-19. Target: aarch64-linux on an M1 MacBook Air with the Asahi kernel. Written so that you can read it top to bottom without knowing Nix.

In one sentence. The bridge copies packages that Hydra already built for nixpkgs from cache.nixos.org into /gnu/store, so nothing gets compiled, and it does this with one trick: swap the store directory name inside each file, from /nix/store to /gnu/store, which has exactly the same length.

1. The problem: binaries remember where they were built

Both Guix and Nix keep installed software in a store: one directory where every package lives under its own name. Guix uses /gnu/store. Nix uses /nix/store. The two systems do not share a store, so a Nix package cannot be installed directly into Guix.

Nixpkgs builds packages for aarch64-linux and uploads the results to cache.nixos.org, so this machine could skip compiling them. The obstacle is that a built binary carries its own location. Here is the ELF header of the fd binary from the cache, which we will return to in section 6:

$ readelf -l -d bin/fd
  [Requesting program interpreter: /nix/store/hx9wvdx2l59iahwf9nmrx7rwkm6cymgs-glibc-2.44-25/lib/ld-linux-aarch64.so.1]
 0x000000000000001d (RUNPATH)  Library runpath: [/nix/store/hx9wvdx2l59iahwf9nmrx7rwkm6cymgs-glibc-2.44-25/lib:/nix/store/na9inwswsrgxxqpqrz3ms78qn7pyxg44-gcc-16.2.0-lib/lib]

Linux does not search for the program's dynamic loader or its libraries. It reads these absolute strings and opens exactly those files. If the file is moved to /gnu/store without changing the strings, it fails at startup, because /nix/store/... does not exist on this machine. measured

So the bridge has one real job: make these strings point at the place where the file actually lives, without changing anything else.

2. Vocabulary you need

The rest of the page uses these words. Each one appears again in the pipeline.

Store path
A directory under the store with a name made of a hash and a label, such as /nix/store/09w3qz2zfj2libm9x42w65wpa6syzdgn-fd-10.5.0. The 32-character hash identifies the build. The label is for people.
Store prefix
The part before the hash: /nix/store in Nix, /gnu/store in Guix. Both are 10 characters long.
Closure
A package together with everything it needs at run time, found by following references from one store path to the next. The fd closure contains glibc and the gcc runtime library, among others.
ELF interpreter and RUNPATH
Two fields in an ELF binary. The interpreter is the dynamic loader the kernel starts. The RUNPATH is the list of directories the loader searches for shared libraries.
NAR
The Nix archive format. It is a deterministic serialization of one store item, such as a directory tree with its files, links and permissions. Two identical trees always produce identical NARs. Guix uses the same format for its exports.
NarHash
The SHA-256 of a NAR. It identifies the exact bytes of a store item.
narinfo
A small text file that the cache serves next to each NAR. It records the store path, the NAR URL, the NarHash and size, the references, and a signature.
Signature
An Ed25519 signature that cache.nixos.org makes over a summary of each narinfo. It proves that the cache published the record. It does not prove that the bytes are safe to run, but it lets us check that they are the bytes Hydra built.

3. Why not build the nixpkgs packages in Guix?

A store path is computed from a description of the build, and the store directory is part of that description. A nixpkgs recipe translated to /gnu/store therefore gets a new path that no cache has ever built. Guix would have to compile it, and compiling means rebuilding Guix's whole bootstrap first, which took hours in the guix-transfer project. source

The useful thing that already exists is the built output, the bytes Hydra produced. So the bridge moves outputs, not recipes. The problem becomes: how do we make a finished output from /nix/store run from /gnu/store?

4. The trick: same length, same layout

Both prefixes are 10 characters, so replacing one with the other inside a file does not move any byte. Every offset, every string table entry and every length field in the ELF header stays where it was. Only the letters change:

/nix/store/09w3qz2zfj2libm9x42w65wpa6syzdgn-fd-10.5.0
/gnu/store/09w3qz2zfj2libm9x42w65wpa6syzdgn-fd-10.5.0
            ^^^ only these three letters change: nix -> gnu

The bridge keeps the 32-character hash too. That is a deliberate choice. The hash is what makes the rewritten path recognizable as the same build, and it means the rewrite is a plain function from one path to the other, with no table to keep in sync:

(define (nix->gnu path)
  (string-append "/gnu/store/" (substring path 11)))   ; conceptually

Why this works in practice. A NAR stores each file's length before its contents, so if the length does not change, the rest of the archive keeps its meaning. The bridge's rewriter, rewrite-port in modules/engstrand/nixpkgs/bridge.scm, streams the NAR in 1 MiB chunks and keeps a small carry-over at each chunk boundary so that a prefix split across two chunks is still found.

The trick only works for references written as plain bytes. A reference hidden inside compressed data, such as a gzip-compressed man page, is not rewritten. Section 8 covers that.

5. NARs, narinfo and signatures

A NAR is a sequence of tokens. Each string is written as an 8-byte little-endian length, the bytes themselves, and zero padding up to a multiple of 8. A directory is the token sequence (, type, directory, then one entry per child, then ). This is why a NAR can be parsed without ever touching a real filesystem, and why the bridge can unpack one into a scratch directory to inspect it.

The cache publishes two things per store path: the NAR itself, served compressed, and a narinfo with its hash, size, references and signature. The bridge uses the narinfo as the source of truth. It checks the signature, downloads the NAR, and checks the NarHash and size against the narinfo before it rewrites anything.

Rewriting changes the bytes, so the NAR's hash changes too. The bridge handles this by keeping the cache's original hash in the lock and checking the reverse direction later: verify maps /gnu/store back to /nix/store while it streams the NAR, and compares the result with the hash that the cache signed. The rewrite is reversible, so the signed hash still proves the content. measured

6. The pipeline, one make target at a time

Each step below is a make target. Read them in order: each one needs the output of the one before.

Step 1. make nixpkgs-lock resolves the wanted list. The input is modules/engstrand/nixpkgs/packages.sexp, which holds attribute names such as "fd". The lock writer evaluates them against the pinned nixpkgs revision with nix eval, which runs through guix shell nix so no Nix daemon is needed. It then walks the narinfos from cache.nixos.org to collect the whole closure. For each item it checks the cache's Ed25519 signature. The result is lock.sexp, the single file that says which bytes we intend to use.

Step 2. make nixpkgs-key runs once. It creates a signing key pair in ~/.config/guix/nixpkgs-bridge/. The secret half never leaves the machine. The public half is copied to modules/engstrand/nixpkgs/signing-key.pub, so it can be committed.

Step 3. make nixpkgs-authorize runs once, with sudo. It runs guix archive --authorize so that the running daemon accepts imports signed by our key. For later system switches, authorized-keys in modules/engstrand/system/asahi.scm lists the same public key.

Step 4. make nixpkgs-import does the work. For every lock item that is not yet valid in /gnu/store, it:

  1. downloads the NAR, eight at a time, and checks its size and NarHash against the lock;
  2. rewrites /nix/store/ to /gnu/store/ while streaming;
  3. writes an export stream, signed with the local key, in the order that the references require; and
  4. pipes the stream into guix archive --import, which hands it to the daemon.

Items already in the store are skipped, so running it again costs nothing. A file lock on the cache directory makes concurrent runs wait for each other.

Step 5. make nixpkgs-verify is the audit. For every imported item it reads the file back from /gnu/store, maps the prefix back to /nix/store, and compares the NarHash with the cache's signed value. It prints all locked items match cache.nixos.org, or lists each mismatch and exits with status 1.

Step 6. Use it from Guile. nixpkgs-package in modules/engstrand/nixpkgs.scm turns a locked package into an ordinary Guix package whose files come from the imported store items. Home and system modules use it, for example (nixpkgs-package "jujutsu") in the herdr feature, or (nixpkgs-package "ghostty" ...) in the desktop feature.

7. Worked example: fd 10.5.0 from start to finish

This is the smallest useful case, and every number below comes from a real run on this laptop. measured

  1. Lock. The cache's narinfo for 09w3qz2zfj2libm9x42w65wpa6syzdgn-fd-10.5.0 lists the NAR as nar/1phyayz9...x6.nar.zst, zstd-compressed (1,483,034 bytes), with an uncompressed NAR of 4,093,568 bytes. Its references are glibc 2.44-25 and gcc-16.2.0-lib.
  2. Download and check. Downloading the NAR and decompressing it gives 4,093,568 bytes. That matches the narinfo's NarSize, and the NarHash matches too.
  3. Unpack and inspect. A small NAR parser unpacks the archive into a scratch directory. It consumes all 4,093,568 bytes exactly and produces 5 files in 11 directories, namely bin/fd, the bash, fish and zsh completions, and the man page share/man/man1/fd.1.gz.
  4. Find absolute paths. Only one file contains /nix/store/ as plain bytes: bin/fd, with three occurrences, all in the ELF header (the interpreter and the RUNPATH). The completions contain none, and the compressed man page contains none after decompression.
  5. Rewrite. The three occurrences become /gnu/store/.... Every other byte of the 4,093,568-byte file stays the same.
  6. Import. The rewritten item is signed with the local key and handed to guix archive --import. The item appears as /gnu/store/09w3qz2zfj2libm9x42w65wpa6syzdgn-fd-10.5.0, with the same hash as the cache, which is what section 4 promised.

What this tells us. For a small program like fd, the entire translation is three strings in one ELF header. A larger package with scripts, wrappers, or config files that embed paths would have more hits. The check in section 8 tells you which case you have.

8. Trust: who can put what into the store

There is a chain of checks, and each link is only as strong as the one before it:

  • Hydra and cache.nixos.org built the bytes. The lock writer checks their Ed25519 signature over each narinfo.
  • The NarHash check confirms that the downloaded NAR is the one the signed narinfo describes.
  • The rewrite is fixed and reversible, so verify can prove that nothing else changed.
  • The local key signs the rewritten items. The daemon accepts only items signed by keys that authorized-keys or guix archive --authorize lists.

The local key is the sensitive part. Anyone who has it can add arbitrary store items, just like the Guix substitute key. So the secret stays in ~/.config/guix/nixpkgs-bridge/ with mode 0600, and only the public half is committed. The lock limits the scope too: only items listed in lock.sexp can enter the store through the bridge.

9. Limits and what the spikes found

These come from the spikes on this laptop, from reading the code, and from the risks I could not yet test.

10. Related idea: relocatable binaries

On 2026-10-17 Farid Zakaria wrote One store, two frontends. It argues that a Nix closure should be a shape, a tree with relative paths, rather than a location fixed at /nix/store. Once every path is relative, the same bytes can live under /, under a build tool's output directory, or in a remote worker's input root. The three places where paths are baked in are:

  • RUNPATH. The loader already expands $ORIGIN, so a relative RUNPATH works today if nixpkgs builds with it.
  • PT_INTERP. The article uses a BPF binfmt_misc handler, which needs Linux 7.3.
  • Wrapper scripts. The cc-wrapper and bintools-wrapper scripts embed absolute paths in shell, which the article suggests deriving from $(dirname "$0").

How it relates to the bridge. The bridge does the same job after the fact. Instead of relocating nixpkgs at build time, it rewrites the bytes at import time. The article's shape is the goal, and the bridge's same-length swap is a way to reach it today with cache binaries that were not built relocatable.

Could we use it now? Not to drop the rewrite. Our measurement of fd shows the cache's binary still has an absolute interpreter and an absolute RUNPATH. measured The RUNPATH could become relative once nixpkgs builds that way (the article links opt-in PR #534339), which would leave the interpreter. The interpreter needs the Linux 7.3 handler, and this laptop runs 7.1.13-asahi, so the interpreter line still needs rewriting here.

What would change if it lands. Items whose binaries are fully relative would import without touching their ELF headers, so verify would compare the cache's own NarHash directly. Items that still have text references would keep the rewrite. The bridge would not need a new design, but it would rewrite fewer bytes.

Proposed, not built. The useful next step is a per-item report: count the absolute store references in each locked package, grouped as ELF interpreter, ELF RUNPATH, and plain text. That tells us which items are already shape-only, and which ones block the change. This is the nixpkgs-check idea from the earlier design, and nothing in the Makefile implements it yet.

11. Status: built, planned, open

Built

  • The wanted list, packages.sexp, and the lock, lock.sexp, for the current package set, with cache signatures checked at lock time.
  • The key, authorization and import flow, with make nixpkgs-key, nixpkgs-authorize and nixpkgs-import.
  • make nixpkgs-verify, which reads each item back and compares it with the signed hash.
  • Home and system integration through nixpkgs-package, nixpkgs-locale-archive and nixpkgs-system-services.

Changed from the first design

  • No substitute server. The first design planned a local HTTP service that the daemon would query. The as-built version imports through guix archive --import instead. On this single-user laptop, the account that runs the import already has sudo, so a separate service was not worth the extra moving parts.
  • The lock holds the closure. URL, compression, NarHash, size and references for every item are in lock.sexp. The importer does not need to talk to the cache.

Planned

  • The per-item report from section 10.
  • A check that a locked binary runs from the real Home profile after make home-apply.

Open decisions

  • Channel. nixpkgs-unstable (revision 8edc0c72 is locked now) gets updates quickly. A stable nixos-YY.MM branch gets fewer updates but holds versions still for months.
  • Scope. Command-line tools only, or GUI apps too. GUI apps are already covered for ghostty, through the OpenGL and fontconfig links in section 9.
  • Alternative. If you want the nixpkgs tooling itself, such as flakes, nix shell or home-manager, a separate Nix install would give you a second store but no bridge code to maintain.
