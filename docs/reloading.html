What needs reloading after a change

After a change in ~/guix, run make status. It lists every component that runs old code or config, says why, and names the command that refreshes it. make refresh runs the refreshes that are safe unattended and lists the rest. make switch and make home now end with that refresh, so the summary prints after every switch.

How it decides

One script, desktop/bin/stale, reads the running system into one map of facts. A pure function in desktop/lib/stale.clj turns that map into rows. Four rules cover almost every component:

  1. Store rule. A process is stale when its executable or an argument names a /gnu/store item that the current system and Home no longer hold.
  2. Source rule. A process running code from the checkout is stale when a source file changed after it started, or after the last refresh, which leaves a stamp in $XDG_RUNTIME_DIR/stale.
  3. Boot rule. When the kernel, initrd or kernel arguments of the current system differ from the booted one, the machine needs a reboot.
  4. Config rule. When modules/, desktop/*.scm, kanata.kbd or channels.scm changed after the newest system generation, you need make switch.

Status always reads the checkout that Home links to (~/guix), even when it runs from a Worker's workspace. STALE_REPO overrides that.

What is automatic now

  • Hyprland reloads its config itself. A nested Hyprland 0.55.4 test showed autoreload picks up edits to hyprland.lua and to files it requires, through the stow symlinks, and when a file is replaced by rename. So no Hyprland config step remains. make mux lost its hyprctl reload; the refresh after make home reloads Hyprland when the mux file changed.
  • kanata reloads after every switch. The hyprkan reload line in make switch is gone. The refresh at the end reloads kanata when /etc/kanata changed and records that.
  • Shepherd services restart when their code changed. After a switch or make home, the refresh restarts each home service and each sudo-allowed system service whose store path or script changed. Shepherd's own "replacement pending" flag is not used, since Guix sets it on every service at every reconfigure.
  • The ghostty-rex client reloads in every refresh where its code changed, so after each switch and make home, on the same session, through the existing mx.client.reload. Between switches, run make refresh after editing it.
  • Chrome extensions already reload themselves when their manifest.json changes (lint enforces it, T197). The refresh rebuilds and reloads an extension whose source changed.
  • Doom's env file now also leaves out EMACSLOADPATH and Rex's pane variables. The live one had saved REX_SESSION, REX_BLOCK and TERM_PROGRAM, the same kind of leak as T216's signature.

What still needs you

A reboot for a new kernel or initrd. Logging out and back in for Hyprland or the home Shepherd. Restarting Emacs, and running doom sync first after init.el, packages.el or cli.el changed (Doom 3 writes its env file in doom sync; doom env no longer does). Restarting the super-agent, which runs the Router and the Workers. Stopping the Rex or Herdr server, which closes their sessions. Any system service that sudo would ask a password for. make status prints each of these with its command.

The Makefile, before and after

It had 68 targets and 374 lines. Now it has 13 workflows in 163 lines. Tests live in desktop/build/checks/checks.edn as commands. make test runs the ones covering your change, ONLY=rule picks rules by name prefix, and make verify adds the slow and live ones.

Found along the way

  • The kanata simulator in ~/.cache/kanata-sim fails to load libgcc_s.so.1, so the kanata chord tests fail before this change too.
  • leader-test.clj and review-test.clj fail in ~/guix as well, in their Herdr navigation cases.
  • A nested or crashed Hyprland leaves its sockets in $XDG_RUNTIME_DIR/hypr. session/wayland-env picked such a dead one, so a respawned hyprkan exited at once. It now requires the pid in hyprland.lock to be alive.
