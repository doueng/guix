1. A terminal draws a grid of letters

A terminal is just a program with a window. The window shows a grid: say 50 rows by 120 columns. Each square holds one letter, with a colour. That is all the terminal shows. No buttons, no pictures (mostly).

Someone has to tell it what to put in the squares. That someone sends it a stream of bytes. Most bytes are plain letters: h, i. The terminal puts each one in the next square and moves the cursor on.

Some bytes are orders instead. They start with the Escape byte. ESC [ 31 m means “red from now on”. ESC [ 5 ; 10 H means “jump to row 5, column 10”. ESC [ ?25 l means “hide the cursor”. These orders are called escape codes. The part of a terminal that reads them and updates the grid is called the VT parser (VT after old DEC terminals).

So: a terminal turns a stream of bytes, letters plus escape codes, into a grid of coloured letters.

2. The shell sits on the other end of a pty

Where do the bytes come from? From a program, like fish, Vim or pi. The terminal and the program are two separate programs. They talk through a pty, a “pseudo-terminal”. Think of it as a two-way pipe the kernel provides.

  • The program writes bytes into its end. The terminal reads them and draws.
  • You press a key. The terminal turns it into bytes (a, or ESC [ A for Up) and writes them into its end. The program reads them.

The key fact: whoever holds the terminal end of the pty keeps the program alive. If that holder quits, the kernel tells the program “your terminal hung up”, and the program usually exits.

Try it. In any shell, tty prints your pty, like /dev/pts/7.

So: the terminal and the program are two programs joined by a pty, and the program lives only as long as someone holds the other end.

3. Ghostty, alone

Ghostty is a terminal (step 1) that is fast and accurate. It draws with the graphics card, it understands nearly every escape code, and it has extras such as the Kitty keyboard protocol (keys like Ctrl+Enter arrive whole) and pictures in the terminal.

Ghostty also has its own tabs and splits. Each tab or split opens its own pty and starts its own shell. Ghostty holds every one of those ptys.

That is “plain Ghostty”. It is simple: one program, nothing in between. A key goes from Ghostty straight into the pty.

The catch follows from step 2. Ghostty holds the ptys, so when the window closes, every shell in it hangs up. Ghostty crashes, you quit it, you log out, a new Ghostty build wants a restart: your pi session, your long test run and your Emacs frames all go. Nothing can reattach later, because nothing kept them.

So: plain Ghostty is the shortest path from key to program, but the window and the programs live and die together.

4. A multiplexer moves the shells out of the window

A multiplexer fixes that with one idea. Let a different program hold the ptys. A quiet background program, a server, that no window owns.

The window is now just a viewer, called a client. It connects to the server, shows what the programs print, and passes your keys on. Leaving a server like this is called detaching. Connecting again is attaching.

Four things fall out of that one idea:

  1. Sessions outlive the window. Close the window. The server still holds the ptys, so nothing hangs up.
  2. Reattach. Open a new window, connect, and everything is where you left it.
  3. Panes and tabs drawn inside one terminal. The client can draw several programs side by side in one grid, with a tab bar and borders made of letters. The terminal does not need its own tabs at all.
  4. Remote. The server can run on another machine. You connect over the network, and your work there survives a dropped Wi-Fi link.

tmux and screen are old multiplexers. Herdr and Rex are newer ones, built with coding agents in mind.

So: a multiplexer splits “holding the programs” (server) from “showing them” (client), so the window becomes disposable.

5. Why you want that

  • Agents run for hours. pi and the bbh agent shells work while you do other things. A window crash must not kill them.
  • bbh lives in a tab. The bbh tab runs emacs-bbh, a terminal frame of the bbh-super Emacs, where Workers report and you answer.
  • You need to know who is waiting. With ten agents, you want a list: blocked, failed, done. Only something that sees every pane can make it.
  • Upgrades. make home brings new builds. You want to restart the viewer to pick up its new code, without restarting your work.
  • The phone. Honest note: today the phone reaches your agents through bbh web (/home/engstrand/guix/desktop/build/bbh/src/bbh/web.clj), not through any multiplexer. measured A multiplexer would matter for the phone only if you wanted to see the actual panes from it.
So: long-lived agents and a status list are the real reasons; the window must be cheap to lose.

6. How Herdr does it

Herdr is one program, herdr, from the herdrdev project (Apache-2.0). We install their ready-built release, 0.9.5. measured

  • The first herdr you run starts a server in the background. It holds every pane's pty (step 4).
  • The same herdr, running inside a Ghostty window, is the client. It draws everything as letters in Ghostty's grid: the tab bar, the borders, each pane, the popups.
  • To draw a pane, Herdr must understand that pane's escape codes. So Herdr has its own VT parser per pane (step 1), and Ghostty only shows the finished, combined grid.

Herdr knows about agents by itself. It sees pi or Claude in a pane, tracks idle, working, blocked and done, and can resume them after a restart. Your Emacs tells it about bbh with herdr pane report-agent. It also does remote out of the box: herdr --remote HOST or herdr machine add over SSH.

Your additions are on the outside: a Ctrl+b prefix in /home/engstrand/guix/desktop/configs/herdr/config.toml, Hyprland sending Alt+Space as Ctrl+b Space, and three small Babashka plugins (sesh, tiny-fingers, jjui) packaged in /home/engstrand/guix/modules/engstrand/packages/herdr.scm

So: Herdr is a ready-made server plus a text-drawing client; you configure it and add plugins, but its core is someone else's compiled program.

7. How Rex does it

Rex is a multiplexer from Superlogical. It is one program, rex, a Go binary. It is a preview build (0.1.0-preview.21) with no published license, so it is for private use. measured

Rex uses its own words for the same things:

Rex saysHerdr saysMeans
sessionworkspacea set of tabs, like your main
windowtabone screenful of panes
blockpaneone pty with one program

The server, rex server run, holds every block. It does one extra thing: it keeps its own copy of each block's screen, with its own VT parser. That copy lets it do two useful things:

  • Answer programs. Some programs ask the terminal “where is the cursor?” or “what colour is the background?”. Rex answers, so the answer never depends on which window is open.
  • Snapshots. When a client connects to a block, Rex first sends a picture of the current screen, then the live bytes. So attaching is instant: no blank pane, no replay of hours of output.

Clients talk to the server through a socket file, /run/user/1000/rex/server.sock, in two kinds of connection:

  • One control connection: requests (“split this block”, “rename this tab”), replies, and events (“a block's program exited”, “pi is now blocked”).
  • One data stream per visible block: the snapshot, then the program's output bytes.

Agents report their state by printing a special escape code, OSC 7501, into their own pane, for example state=working:app=bbh. Rex stores it on the block and announces it as an event.

The catch: Rex's main client is a macOS app. Its Linux client is not public. measured So on Linux, Rex is a server with no screen. You have to bring the viewer. That is what ghostty-rex is.

Try: rex server status (version, pid, log), rex session list (you have main, personal-site, quiet-tundra), rex api list (about 99 methods you can call).

So: Rex is a server that keeps a live copy of every screen and speaks a clean API, but on Linux it ships no viewer, so you wrote one.

8. Your ghostty-rex, piece by piece

Now the viewer you built. It has six pieces. Here is the trick that makes it click: inside the Ghostty window, the “program” is not a shell. It is your client. Ghostty's pty connects to a Babashka program, and that program connects to Rex.

a. The Ghostty window

A normal Ghostty, started with its own class, dev.engstrand.Rex, and an extra config, /home/engstrand/guix/desktop/configs/ghostty-rex/ghostty, whose keybind = clear removes Ghostty's tab and split keys. It keeps only copy, paste, font size and config reload. Every other key goes through to the client. Ghostty's job here is to show a grid and send keys. Nothing more.

b. bb attach, the brain

desktop/bin/ghostty-rex attach starts bb … attach from /home/engstrand/guix/desktop/build/ghostty-rex/src/rexg/ (about 1,900 lines of Clojure). It runs straight from the checkout, so an edit needs no build. It reads your keys, talks to Rex over the control connection, opens a data stream per visible pane, and decides the layout, the tab bar, the status line and where the cursor goes. It does not draw.

c. rexg-render, the painter

A small C program, /home/engstrand/guix/desktop/build/ghostty-rex/csrc/rexg-render.c (about 700 lines). It uses libghostty-vt, the VT parser from inside Ghostty, packaged on its own. It keeps one little terminal per visible pane, feeds each one that pane's bytes, then glues them into one big grid with the borders and bars bb asked for. It writes only the squares that changed to Ghostty.

Why C and not Clojure? Parsing every byte of every pane is the hot loop. Babashka has no way to call a C library, so the parser runs in its own process and bb sends it short text lines. inferred from /home/engstrand/guix/docs/rex-client-languages.html

d. The sidecar, the command layer

Loaded into the same bb process from /home/engstrand/guix/desktop/build/rexmux/sidecar/ (about 1,200 lines). It owns M-x, the leader keys, the agent list and the bbh commands. It runs one child, rex events --all --json, to hear every agent report, ranks them (blocked first, then error, then unseen done), and sends desktop notifications such as “bbh needs you”.

e. The Alt+Space keys

Alt+Space is your one prefix. Hyprland checks /home/engstrand/guix/desktop/configs/keybindings/leader.edn: for the class dev.engstrand.Rex it says :pass, so the key goes to the window. bb then reads the next keys from the same file: w v splits right, t r renames the tab, u jumps to the next blocked agent, i floats the bbh inbox. A menu shows what can follow. Ctrl+b is free again for fish and Emacs.

f. The Cmd+Space launcher

Cmd+Space runs ~/.local/bin/palette. When the Rex window has focus, it asks Rex what the client offers and what program runs in the focused pane, then lists that program's entries, the leader rows (with their Alt+Space keys, so you learn them), and every M-x command. Picking one runs rex -C ghostty-rex do ACTION: Rex passes it to your client, which does it. Cmd+Return, E, D and G switch tabs the same way.

So: Ghostty shows, bb decides, rexg-render paints, the sidecar runs commands and watches agents, and Rex holds the programs.

9. A keypress, start to finish

Blue: your key going down. Green: the program's output coming back up. Dashed: bb telling rexg-render what to draw around the panes. Step 5 physically passes through a reader thread in the bb process, which hands the bytes straight to rexg-render without looking at them.

You type l in the fish pane:

  1. Hyprland has nothing bound to it, so the key goes to the focused window.
  2. Ghostty turns it into bytes (Kitty keyboard protocol) and writes them into its pty. On the other end sits bb.
  3. bb decodes the key. Is it Alt+Space, the start of a leader sequence? Ctrl+h/j/k/l to move between panes? No. So it sends client.key for the focused block over the control connection.
  4. Rex turns the key into the bytes that program expects and writes them into fish's pty.
  5. fish reads l.

If you had typed Alt+Space w v instead, step 3 would find the leader sequence, and the sidecar would ask Rex to split the pane. Rex does it and sends an event. bb learns the new layout and tells rexg-render.

So: a key makes three hops (Ghostty, bb, Rex) before the program gets it; plain Ghostty makes one.

10. Output, start to finish

  1. fish prints l (its echo) into its pty.
  2. Rex reads it, updates its own copy of the screen, and sends it on that block's data stream.
  3. bb's reader thread for that stream passes the bytes straight to rexg-render, tagged with the pane ID. Output never waits behind keys.
  4. rexg-render feeds them to that pane's libghostty-vt terminal, works out which squares of the big grid changed, and writes just those as escape codes to Ghostty.
  5. Ghostty parses those escape codes and draws.

Count the VT parsers one byte meets. Plain Ghostty: one (Ghostty). Herdr: two (Herdr's, then Ghostty's). ghostty-rex: three (Rex's copy, rexg-render's, then Ghostty's). Each is fast, but each is also a place where two parsers can disagree about something small, like where the cursor is.

So: output climbs back the same chain, parsed three times, and bb only steers; it never touches the bytes.

12. The recent bugs, now easy to explain

Every bug of the last week lands on one of the pieces above. That is the payoff of knowing them.

Red “local not connected”. The control connection (step 7) is bb's lifeline to Rex. When the server stops, for example when a new rex replaces it after make home, the line drops. The client shows the red line, tries again after 0.25 s, doubling up to every 4 s, starts the server if needed, and reattaches the same session. That part is by design. The bug was different: two tries could both succeed. The client kept one and closed the other, but the “closed” notice from the spare one was taken to mean the live one had closed, so the client dropped a working connection. T211 gave each try an id so stale notices change nothing, and T220 model-checked it: /home/engstrand/guix/docs/quint-explained.html rebuilds this exact race in step 12.
Stale processes after make switch or make home. Guix puts new builds in new folders, and a running process keeps the old one (see Guix, from the ground up). ghostty-rex has five long-running processes instead of one, so there is more that can be stale. make status names each one, and make refresh reloads the bb client in place, on the same session, through mx.client.reload (T218). The Rex server is yours to restart, since stopping it ends its programs. Rex then brings each tab back as bare bash, and the client starts fish or the tab's program again, such as pi --continue (T210). A related one, T219: a server the client started got a trimmed environment without SSL_CERT_FILE, so git and curl in panes failed. It now gets the whole session environment, and make status flags a server without it.
Cursor weirdness. In plain Ghostty, the program moves Ghostty's cursor directly. In ghostty-rex, bb decides where the one visible cursor goes (in the focused pane, in the M-x prompt, or hidden) and tells rexg-render. So every cursor case is your code, and three parsers must agree (step 10). One fixed case: a pane that hid its cursor with ESC [ ?25 l still showed one. T210 fixed it and added an end-to-end check.
Slow project switch. Switching to the pi tab took about 10 seconds. The cause was the snapshot (step 7): pi's screen history held 51 MB of inline images, and rexg-render read it one byte per system call, 46 million calls, drawing nothing until it was done. Now it reads in large chunks without blocking, paints the visible screen first, and fills in history after. A test requires a pi tab with a 24 MB image to paint within 300 ms (T210). measured by the commit and its test

Notice the pattern. None of these could happen in plain Ghostty, which has no connection, one process, one parser and no snapshots. Herdr has the same kinds of parts, but they are inside a program someone else has run for longer, so you see its bugs less and fix them never.

So: the bugs come from the extra parts and from the code being one week old; each was fixed with a test, but more of that kind will come.

When to pick which

Plain Ghostty when nothing in the window must outlive it: a quick throwaway terminal, or debugging the multiplexer itself. You already have this: a plain ghostty runs beside the Rex window, and Alt+Space passes straight to it.
Ghostty + Herdr when you want it to just work and do not want to own a terminal client: a busy week, a trip where you need SSH remote sessions, or whenever ghostty-rex breaks in a way you do not want to fix now. make mux MUX=herdr switches; Rex keeps its sessions meanwhile.
ghostty-rex when the agent workflow is the point: the attention list, bbh in the window, Cmd+Space that knows the pane, and changing behaviour in Clojure the same afternoon. It is what you run now, and it is the right default as long as you are willing to fix what breaks. inferred

The honest risk is Rex, not your code. Your client is small, tested and yours. The server is a preview with no license and a moving API, and you cannot fix it. If Rex stalls or changes its terms, Herdr is the fallback, and it is still installed.

So: keep ghostty-rex as the daily driver, keep Herdr one command away, and treat a red line or a stale process as something step 7 or step 12 already explains.

The whole thing in one breath

A terminal draws a grid from bytes (1) that a program sends through a pty (2). Plain Ghostty holds those ptys, so they die with the window (3). A multiplexer's server holds them instead, and the window becomes a viewer that can come and go (4), which long-running agents need (5). Herdr is a ready-made server and viewer (6). Rex is a server with a live screen copy, snapshots and a clean API, but no Linux viewer (7). So you built one: Ghostty shows, bb decides, rexg-render paints, the sidecar runs commands and watches agents (8). Keys go down three hops (9), output comes back up through three parsers (10), every piece shows in ps and rex (11), and each recent bug sits on one of those pieces (12).
