Outcome

Goal: black-box property tests of the bbh Emacs Inbox in a real terminal, per the review. Result: the prototype works on this Asahi machine and paid off. In its first hour it found two real bugs in the split Inbox, both now fixed with ERT regression tests. After the fixes, two 10-minute runs passed with about 4,200 screens each. It is a separate target, make verify ONLY=bbh-bombadil (or bb test:bombadil), with a time budget. It is not part of bb test or make verify. measured
Reported, not fixed: four smaller issues: an i/send race, cryptic refusal messages, “Sent” for an empty send, and a stray “Process … finished” echo. See Findings.

How it runs

  • Binary: Bombadil 0.7.10, the static aarch64 release, as the Guix package (engstrand packages bombadil), pinned by hash. It is not in the home profile; the runner builds it with guix build -L modules on demand.
  • Isolation (T75, T163): HOME and the XDG dirs are a temp root. BBH_ and WF_ session variables are dropped, and BBH_EMACS_SERVER names a daemon that does not exist, so the controller's sweep fails harmlessly instead of reaching bbh-super. The runner checks all of this before it starts. It holds the heavy-job slot, refuses to start under 2.5 GB MemAvailable, and runs Emacs under a soft 1.5 GB address-space cap that the bbh it spawns lifts for itself, since babashka cannot start under it.
  • Fixture: bbh.super/start! with a stub launch, which needs no Emacs and no jj. A churn thread, seeded, makes threads and Workers, asks with unique texts q<n> <word>?, notes, and finishes Workers about every 0.8–2.5 s. It also takes the mailbox for them.
  • Screen: 140×40, so the list sits beside the thread. The pushed-reload idle delay is 0.05 s instead of 0.5 s. Bombadil types about every 130 ms, so with 0.5 s no push would ever reload, and the shorter delay keeps pushes racing keys.

Findings

1. Fixed: the thread list could hide the thread that needs you. eng/bbh-inbox--draw-list kept the selected row on the same screen line after every reload. When a thread sorted above the selection, for example because its Worker just asked, the window started below it. The header said “1 need you”, no ● row was visible, and up to 30 blank lines sat under the list. Now the window never starts lower than the point that puts the list's end at its bottom, so a list that fits starts at the top. A long list still keeps its screen line. Regression tests: bbh-inbox-split-reload-fills-the-window-before-hiding-rows-above and bbh-inbox-split-reload-keeps-a-long-lists-screen-line, plus the old test now expects the new row to show. All three fail on the old code.
2. Fixed: C-c C-c in the Inbox opened org's Tags prompt. On a heading, org-ctrl-c-ctrl-c asked “Tags:” in the minibuffer. Reloads stopped drawing until C-g, and the existing test only checked that C-c C-c was not send. It is now undefined in normal and insert state, as in the composer (T125's rule). bbh-inbox-and-thread-list-keys-under-evil asserts it.
3. Reported: i right after a send can strand insert state. Press C-n, then i before the send returns. The refresh that follows removes the Answer you entered, and you stay in insert state on read-only text (“Text is read-only”). Nothing is lost, since the pick already answered that ask. A fix would leave insert state when a render removes the Answer under point. Seed 769318. measured
4. Reported: refusal messages are cryptic, and an empty send says “Sent”. A send refused because the asks changed since the pick echoes bbh inbox: stale: stale. A closed ask gives no-such-ask: no-such-ask. Neither says what to do (C-c C-k discards the draft, then pick again). Separately, bbh inbox send with nothing in the draft sends nothing but exits 0, so the Inbox echoes “Sent T5”. The log showed that repeatedly. inferred from /home/engstrand/guix/desktop/build/bbh/src/bbh/super/pane.clj send! and the messages log. Owner: T125 (C-n send).
5. Reported: a stray echo. “Process bbh-inbox-cmd stderr finished” sometimes reaches the echo area. eng/bbh-inbox--run's sentinel kills the stderr buffer before that pipe's own default sentinel runs. Cosmetic. inferred
Not a bug: pushed reloads wait for idleness. With a key every 130 ms, the 0.5 s idle reload never ran, and the view stayed stale for many seconds (a finished Worker's asks still showed). That is the design (none runs while you type), so the test shortens the delay instead.

Use it

make verify ONLY=bbh-bombadil                         # 120 s, random seed
make verify ONLY=bbh-bombadil BOMBADIL_TIME=600 SEED=767157
cd desktop/build/bbh && bb test:bombadil --time 60 --keep
bb test:bombadil --seed N --reproduce /tmp/bbh-bombadil…/trace --keep

Every run prints the keys it sent. A failure also prints the property, the screen it judged, the seed, the trace directory, and the exact reproduce command. --reproduce replays the trace's keys against a fixture churned from the same seed. Replay is best effort: the fixture's timing is not replayed, but the bug above reproduced on its first try. Limits

  • Emacs runs with -Q plus evil and the bbh code, not Doom, so Doom keymap interactions such as SPC, evil-org and corfu are not covered.
  • This page covers the split Inbox. The Router and Worker view has its own spec, run by the same target: bombadil-worker-report.html.
  • Bombadil's shrink is still experimental and unused. Traces are big, and failing roots stay in /tmp until you delete them.
  • It is not in make verify. checks.edn lists it under :slow for the bbh Emacs files, so make test LIST=1 suggests it.
