Hyprland signature in Emacs shells

Choice

Keep hyprctl calls plain and stop Emacs handing out a saved Hyprland signature. Two small Doom config changes, plus a one-line warning in hyprkan. The instance-discovery code from W280 (hypr.ctl, session/hypr-signature and its callers, and the 120-line hyprkan test) is reverted.

Root cause

Doom's envvar file (~/.config/emacs/.local/etc/@/init.d/05-doom-env.load.el, dated 2026-11-12) is a snapshot of the shell that ran doom sync. Every Emacs loads it over the environment it inherited. Shells started from Emacs (vterm, compile, make switch) then got that login's HYPRLAND_INSTANCE_SIGNATURE. The file also held HERDR_PANE_ID, GHOSTTY_*, HL_INITIAL_WORKSPACE_TOKEN and TERM_PROGRAM from the herdr pane it ran in. Doom's own deny list already leaves out WAYLAND_DISPLAY, XDG_SESSION_* and *SOCK for this reason, but it does not cover Hyprland's variables.

The fix

  1. desktop/configs/doom/cli.el adds ^HYPRLAND_ ^HL_ ^HERDR_ ^GHOSTTY_ ^TERM_PROGRAM ^TERMINFO$ ^DESKTOP_SESSION$ ^XDG_SEAT ^fish_ to doom-env-deny. This is Doom's documented setting for this, and bin/doom loads cli.el.
  2. desktop/configs/doom/session-env.el covers the bbh-super daemon. The home Shepherd starts it outside Hyprland, so it has no signature of its own. emacsclient passes its environment to each new frame, but Emacs subprocesses read only process-environment, never the frame's (callproc.c copies only DISPLAY from the frame). An after-make-frame-functions hook copies HYPRLAND_INSTANCE_SIGNATURE and WAYLAND_DISPLAY from the client as the frame is made, before the client's --eval runs. bbh super opens its frame with emacsclient -t --eval, and server-after-make-frame-hook would run only after that eval. Each new frame carries the current login's values.
  3. hyprkan checks hyprctl's exit status and prints one line, such as hyprkan: hyprctl failed: Couldn't connect to …, instead of a JSON stack trace. The kanata reload still runs.
  4. W280's rexg change stays (rex server start --env HYPRLAND_INSTANCE_SIGNATURE). That was a separate cause: Rex's env allowlist dropped the variable. It is a plain pass-through, not discovery.

Options considered

  • Drop doom env (doom sync --no-env). This is the most Guix-like option, since the snapshot also pins /gnu/store paths such as glibc-locales and emacs-31.1's lisp dir, which go stale after upgrades. But Hyprland's PATH lacks ~/.local/bin and ~/.config/emacs/bin, which Emacs gets only from the snapshot today. Doing this first needs those directories added through a Guix Home environment-variables service. It is worth a follow-up, but it is larger than this bug.
  • Find the live instance in every caller (W280). This works, but every hyprctl caller has to route through it, and it treats the symptom.
  • systemd / uwsm import-environment. Hyprland pushes its variables into the systemd and D-Bus activation environments, and uwsm manages that for whole sessions. Shepherd has no equivalent, which is why the frame hook is needed here.

What you run

  1. After this lands, run doom sync from any shell. It rewrites the envvar file with the new deny list, and the shell's own Hyprland variables are left out.
  2. Restart Emacs: the GUI Emacs and herd restart bbh-emacs. Running Emacsen keep the stale value in process-environment, and shells already open in them keep it until reopened.

Test

make doom-env-test runs desktop/build/doom/session-env-test.el in batch Emacs. It checks that the deny list covers the session variables but not PATH or SHELL, that a client frame's signature replaces a stale one for subprocesses, and that a frame with no client changes nothing.
