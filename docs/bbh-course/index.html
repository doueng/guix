bbh internals

A course on how bbh works and why it is built the way it is. Source: desktop/build/bbh, as of 2026-10-20.

bbh is a coding agent harness written in babashka. It lets a language model work in a persistent Clojure REPL through one tool, and it runs the same conversation from a terminal or from Emacs. This course walks through the code layer by layer. Each lesson starts from a question, shows the code that answers it, and ends with a check you can open.

How to use this course

  • Read the lessons in order. Later ones assume the vocabulary and the diagrams of earlier ones.
  • Open the source file named in each lesson beside this page. The course quotes function names exactly, so you can search for them.
  • Each lesson has a Try it box with commands to run. The commands are read-only unless marked.
  • Click Check yourself to reveal answers. Try the question first.
  • Evidence matters here. Where a claim comes from the design log (decisions.tsv) or from a test, the lesson says so. Where it is only my reading of the code, the lesson says that too.

0. Orientation

Learning goals. Name the main parts of bbh. Draw the path from a keystroke to a model and back. Find the file that owns each responsibility.

The one-sentence design

Every conversation gets its own babashka REPL process. The model has exactly one tool, clojure, which evaluates code in that REPL. Because the REPL lives as long as the conversation, the model can define helpers once and reuse them, and it can change its own environment by redefining bbh.env/manifest.

1. The model owns a REPL

Learning goals. Explain why bbh exposes one tool instead of many. State what persists between turns, and what the tradeoff costs.

Why one tool that evaluates code

Most coding agents give the model many tools: read a file, run a shell command, edit a file. bbh gives it one, clojure. Babashka is a small Clojure that starts quickly and ships many libraries, so one evaluator can already read files, run processes, parse JSON and make HTTP requests. The model writes a small program instead of choosing among tools.

The design log records the consequence. A model that could not find the jev-classify-task helper spent about fifteen rounds hunting for it. After the helper was referred into user, it was called in the first tool call. decisions.tsv, 2026-10-17 env

What persists

  • Definitions. Every def and defn stays in the REPL until the process restarts. The model can build a helper once and call it in later turns. The live test in the decisions log defined 41 in one turn and evaluated 42 in the next. measured
  • The environment. The model can redefine bbh.env/manifest, and bbh re-reads it before every request. The model can change its own system prompt and its own limits.
  • Not the transcript alone. The transcript is what bbh saves on disk. The REPL state is in memory and is lost when the process restarts.

The tradeoff

GainsCosts
Helpers survive across turns, so the model spends fewer calls rebuilding them.A restart, a timeout or an interrupt loses every definition. bbh reloads init.clj and tells the model.
One tool means one schema and no tool-choice confusion.A mistaken (delete-file ...) is final. The REPL runs with your permissions and is not a sandbox.
The model can change its environment through ordinary code.A bad manifest is possible. bbh validates it and falls back to defaults (lesson 6).

Try it. Open src/bbh/repl.clj and find manifest and validate. Then find the call site in src/bbh/session.clj (system-prompt!).

Check yourself

If the model redefines bbh.env/manifest with :deadline-ms 5000 during a turn, when does the change take effect? Answer: system-prompt! re-reads the manifest before every model request, and run-code! reads :deadline-ms from the stored manifest each time it evaluates. So the new deadline applies from the next evaluation after the next request refreshes the manifest.

2. Conversations on disk

Learning goals. Name the files a conversation writes and what each one is for. Explain why the transcript is plain chat messages.

Layout

Each conversation is a directory under ~/.local/share/bbh/conversations/<id>/, where id is a timestamp such as 20261020-101530-245. The Emacs front end creates its ids the same way. main.clj, acp.clj

FileWritten byPurpose
messages.jsonltranscript/append!The append-only transcript, one chat message per line.
compactions.jsonltranscript/append-compaction!Each compaction: where the kept suffix starts, and the summary.
repl.portrepl/start!The nREPL port of the live REPL, for CIDER.
repl.logrepl/start!Stdout and stderr of the REPL process.
claude-sessionclaude.cljThe Claude Code session id, so a later process can resume it.
claude.logclaude.cljStderr of the Claude Code process.

Why the transcript is plain chat messages

Each line of messages.jsonl is an OpenAI-style message: role, content, and optionally tool_calls or a tool_call_id. The design log says the transcript should stay plain chat messages so the eval tools and the Claude adapter can read it. The summary and trimming are a view computed on top of the transcript, not a change to it. decisions.tsv, 2026-10-18 context

Resume

bbh --resume last picks the lexically largest directory under conversations/. Timestamp ids make that the newest one. It starts a fresh REPL, and the notes list tells the model that earlier definitions are gone.

Try it. Look at the newest conversation without changing it:

d=$(ls -d ~/.local/share/bbh/conversations/* | sort | tail -1)
ls -la "$d"
jq -c '{role, content: ((.content // "") | tostring | .[0:80])}' "$d/messages.jsonl" | head -20
Check yourself

Why does append-compaction! not rewrite messages.jsonl? Answer: the transcript is the durable record. A compaction only records where the model's view starts and what the summary says, so the original messages stay available for eval tools and for display.

3. The session and the turn loop

Learning goals. List the state a session holds. Trace what happens between a user's Enter and the next model request.

The session is one atom

session/new-session returns an atom holding everything about one conversation. The important keys are:

KeyMeaning
:dir, :cwd, :initWhere the transcript lives, where the REPL runs, and the init file it loads.
:model, :engine, :make-engineThe model id, the engine built from it, and the factory used to rebuild it on /model.
:messages, :compactionThe transcript loaded from disk, and the latest compaction.
:repl, :manifestThe live REPL connection, and the last manifest that passed validation.
:cancel, :interrupted, :evaluatingWhat to call to abort the current model request, and flags that tell the loop why it stopped.
:spent, :limits, :notesSession cost, the latest Claude rate-limit windows, and messages the model should see on its next turn.
:code-lockSerializes evaluations, so two tool calls never run at once in one REPL.

From input to model

The terminal and ACP both call session/prompt!. It does four things in order:

  1. Commands. If the input starts with / and names a built-in command (/help, /model, /compact, /usage, /restart, /port), bbh runs it without the model.
  2. Env expansion. Otherwise expand asks bbh.env/expand-prompt in the REPL. The env may return a rewritten prompt, or a {:reply ...} that answers without the model. This is how /skill:NAME and /poteto-mode-off work.
  3. Record. The user's message is appended to the transcript. Any pending notes, such as “the REPL restarted”, are prefixed as a [bbh] line.
  4. Turn. turn! dispatches on the engine's :kind. It is a multimethod with two methods: :loop (in session.clj) and :claude (in claude.clj).

The loop engine

For :loop engines, turn! repeats rounds until the model stops calling tools or the round limit of 100 is reached. Each round does this:

round n
  system     = system-prompt!          ; re-reads bbh.env/manifest, validates it
  if tokens(context) > :compact-at-tokens  -> compact!
  result     = sample!                 ; one streamed request; on-text emits events
  if overflow -> compact! once, then retry the round
  record assistant message             ; only if it has text or tool calls
  add-usage!                           ; tokens and cost, as an event
  for each tool call:
      record tool message = run-code!  ; evaluates, emits call and result
  no tool calls -> the turn ends
  interrupted   -> the turn ends and partial tool calls are dropped

Two details matter. First, the assistant's message is recorded before its tool results, so the transcript reads in the order the model produced it. Second, a cancelled request drops its partial tool_calls, so the transcript never shows a call that did not run.

Try it. Run the session tests. They drive prompt! through scripted replies:

cd desktop/build/bbh
bb -cp src:test -e "(require 'bbh.session-test) (clojure.test/run-tests 'bbh.session-test)"

Then open test/bbh/session_test.clj and read definitions-survive-across-turns. It is the shortest complete example of a turn.

Check yourself

What happens if the model asks for a tool call and the user presses Ctrl-C during the evaluation? Answer: interrupt! sets :interrupted. Since :evaluating is true, it also kills the REPL. run-code! then returns the failure text, and the REPL is restarted with a fresh init. The loop sees :interrupted and ends the turn without another round.

4. One event stream

Learning goals. Name the four event types. Explain why bbh has one stream instead of callbacks for each front end.

The events

The session never prints or sends anything itself. It calls emit! with a map that has a :type:

TypeFieldsSent when
:text:textA chunk of model text, or a [bbh] note such as a retry.
:tool-call:id, :codeBefore an evaluation starts.
:tool-result:id, :code, :text, :statusAfter it finishes, with :completed or :failed.
:usage:used, :size, :spentAfter each model sample, with prompt tokens and total session cost.

Three consumers

  • Terminal: print-event in main.clj prints text as it arrives, shows the code in dim text, and shows at most 15 lines of each result.
  • ACP: event->update in acp.clj turns each event into a session/update notification.
  • Tests: the session tests collect events and assert on them.

The design log records the change that introduced this. The four UI callbacks were replaced with one event stream, and the tests passed afterward. ACP and the terminal both consume the same text, tool-call, tool-result and usage events. decisions.tsv, 2026-10-17 events

A consequence for ACP

Agent-shell collapses each tool call into one line. By default that line showed only the word clojure, so a waiting call was invisible. The fix is in acp.clj: the tool block's title is the first line of the code, cut at 72 characters and marked with an ellipsis when more code follows. The result block repeats the code above its output, so output is never mistaken for coming from different code. decisions.tsv, 2026-10-17 acp

Try it. In src/bbh/acp.clj, find title and trace how one :tool-call event becomes a tool_call update. Then find the same event in main.clj's print-event.

Check yourself

Why doesn't the session know whether the terminal or ACP is listening? Answer: new-session takes an :emit function. Each front end passes its own, so the session stays unaware of presentation.

5. The REPL process

Learning goals. Explain how bbh starts a REPL, talks to it, and recovers from a timeout. Explain why bbh kills the process instead of interrupting it.

Starting it

repl/start! launches bb -e with a short bootstrap program. The bootstrap starts babashka's nREPL server on a free port, writes the port into the file named by BBH_PORT_FILE, and then waits forever. bbh polls that file, opens a socket, and starts a reader thread. The process's output goes to repl.log.

Then bbh clones two sessions from the server:

  • The user session runs the model's code. Its *ns* and its definitions belong to the model.
  • The control session runs bbh's own questions, such as reading the manifest or calling bbh.env/expand-prompt. It does not change the model's *ns*, so repl/call can ask questions without disturbing the model's state.

Talking to it

nREPL speaks bencode. request! writes a message with a fresh id, and a reader thread routes each reply to a queue by that id. The request ends at a reply whose status includes done, when the deadline passes, or when the connection closes. The result map is {:out :err :value :error?}, plus :timeout or :died when no complete reply arrived.

Why kill rather than interrupt

Babashka cannot interrupt a thread that is busy in user code. So when a deadline passes or the user interrupts an evaluation, bbh destroys the whole process tree with p/destroy-tree, starts a new REPL, and reloads init.clj. The transcript survives, but the definitions do not. The model is told so in the same tool result that reports the timeout.

The session tests cover this path. deadline-kills-the-repl-and-reloads-init checks that a timed-out evaluation restarts the REPL and reloads init. test/bbh/session_test.clj

Try it. Start a REPL by hand and talk to it through bbh's own functions, without a model. This writes only a scratch directory under /tmp:

cd desktop/build/bbh
bb -cp src -e "(require '[bbh.repl :as r])
(def c (r/start! {:dir "/tmp/bbh-course-repl" :cwd "."}))
(prn (r/eval! c "(def x 41) (inc x)" 5000))
(prn (r/eval! c "x" 5000))
(r/kill! c)"

The second evaluation returns 41, which shows the definition survived between requests.

Check yourself

Why does the manifest read use the control session? Answer: the model's code could have changed *ns* or bound a variable that bbh's own question depends on. The control session keeps bbh's questions separate from the model's state.

Observation. On a timeout, run-code! restarts the REPL and reports the failure in one result. The model then has to rebuild every helper it had. This is the largest reliability cost of the design. The eval assertion repl-restart counts how often it happens (lesson 13).

6. The environment and the manifest

Learning goals. Explain what the env controls, how bbh reads it, and how bbh stays usable when the model breaks it.

What the env is

~/.config/bbh/init.clj is the environment. In the repository it is desktop/configs/bbh/init.clj, which is stowed to the home directory. start-repl! loads it with load-file into every new REPL. session.clj The BBH_INIT variable overrides the path, which the tests use.

The file defines four things the rest of bbh reads by name:

VarRead byEffect
bbh.env/manifestrepl/manifest, before every requestSupplies the system prompt, the tool description and the limits.
bbh.env/expand-promptsession/expand, for every user inputRewrites the prompt, answers without the model, or passes it through.
bbh.env/commandsacp/commands-updateExtra slash commands offered for completion in agent-shell.
bbh.env/jev-classify-taskThe model, through the user namespaceA helper that routes a task with TypeSafe Jev. It is referred into user so the model can call it directly.

How the manifest is read and checked

The manifest may be a map, or a function that returns one. repl/manifest asks the control session for it, with a 10-second timeout. The result goes through validate, which checks each known key against a predicate:

:system, :tool-description     must be strings
:deadline-ms                   positive integer  (default 120000)
:max-output-chars              positive integer  (default 30000)
:compact-at-tokens             positive integer  (default 200000)
:keep-recent-tokens            positive integer  (default 20000)
:trim-tool-chars               positive integer  (default 4000)

A key that fails its check falls back to its default, and the failure is recorded as a problem. If the whole manifest is not a map, every default applies. system-prompt! then appends a [bbh] paragraph to the system prompt that lists the problems, so the model knows its own edit did not take effect.

Observation. validate only looks at keys in its checks table. A misspelled key such as :max-output-char is ignored without a problem message. A typo in a limit fails silently. Adding a check for unknown keys is a small, useful change.

Why the model may edit its own env

The design log records the decision that the env, not the controller, owns skills and poteto-mode. The model can change how its own input is expanded, the same way it changes everything else in the REPL. Expansion runs in the control session with a 10-second timeout, and an error in expand-prompt is reported as a [bbh] line before the original prompt goes to the model. decisions.tsv, 2026-10-17 env

Expansion, in practice

When the user types /skill:NAME look at the diff, the env's expand-prompt finds the skill file and returns the prompt with the skill's body inlined. Typing a plain sentence in a new conversation prefixes it with /skill:poteto-mode while poteto-mode is on. A {:reply ...} answers without the model, which is how /poteto-mode-off works.

Try it. Read the env's expansion function and the test that pins it down:

cd desktop/build/bbh
grep -n 'expand-prompt' ~/.config/bbh/init.clj test/bbh/session_test.clj
Check yourself

The model sets :deadline-ms to the string "slow". What does the next request use? Answer: the default of 120000 ms. The check fails, the problem is recorded, and system-prompt! tells the model that the defaults apply. The rest of the manifest still applies.

7. Engine one: OpenRouter

Learning goals. Explain how bbh streams a chat completion, accumulates tool calls, retries transient failures, and cancels cleanly.

The request

llm/openrouter returns a sample function for a model id. It posts to openrouter.ai/api/v1/chat/completions with stream set to true and usage.include set to true, so the final chunk carries token counts and cost. The tools list is sent only when there is one.

Reading the stream

The body is server-sent events. chunks keeps lines that start with data:, stops at [DONE], and parses each JSON payload. step folds each chunk into an accumulator. Text deltas are concatenated. Tool calls arrive in fragments: each fragment has an index, and its id, name and argument text are appended to the call at that index. finish sorts the calls by index and returns the message and usage.

Each text delta is also passed to on-text immediately, which is how the terminal and ACP show text as it arrives.

Retries

post! retries three kinds of failure: a thrown I/O exception, HTTP 429, and HTTP 5xx. The waits are 1, 2, 4, 8 and 16 seconds. A Retry-After header, in seconds, replaces the wait and is capped at 60 seconds. Each retry reports a note through on-retry, which the session turns into a [bbh] line. The wait polls the cancellation flag every 50 ms, so Ctrl-C stops a retry at once. decisions.tsv, 2026-10-18 retry

Other errors are not retried. A 400 whose body mentions a context limit gets :overflow true in its ex-data, and the session uses that to compact and try once more.

Cancellation

The sample function creates a cancelled atom and gives the session a function that sets it and closes the response body. If the stream breaks after cancellation, llm/openrouter returns the partial text with :interrupted true and no tool calls. A break without cancellation throws, so a network failure is an error, not a silent success. decisions.tsv, 2026-10-18 streaming

Try it. The retry and stream tests use stubbed HTTP responses, so they run offline:

cd desktop/build/bbh
bb -cp src:test -e "(require 'bbh.llm-test) (clojure.test/run-tests 'bbh.llm-test)"

Read rate-limits-and-server-errors-are-retried, and note what the test does not cover: the decision log says no live 429 was observed.

Check yourself

A stream delivers half a tool call and then the connection drops, and the user did not cancel. What happens? Answer: the IOException is rethrown, because cancelled is false. The session records no partial tool call, and the error ends the turn. The user sees the error, not a half-finished call.

8. Engine two: Claude Code

Learning goals. Explain why Claude Code runs the loop, how the tool gets back into the session, and how the transcript and the process stay in step.

Why

The design log records the decision to run Claude Code as the agent loop. It keeps the Claude subscription path that Pi's bridge already used. The CLI already owns sampling, retries and caching, so bbh does not reimplement them for Claude. decisions.tsv, 2026-10-17 claude

Starting the process

start-claude! runs claude in print mode with stream-json input and output and partial messages. The flags carry the design:

FlagWhy it is there
--tools ""Turns off Claude Code's built-in tools, so the model's only tool is bbh's.
--strict-mcp-config --mcp-config ...Loads exactly one MCP server, bbh's, and ignores any others the user has configured.
--allowedTools mcp__bbh__clojurePermits that one tool without asking.
--setting-sources ""Ignores the user's and project's Claude settings, so the run is reproducible.
--system-promptThe manifest's system prompt, read at start.
--resumeThe session id saved in claude-session, if there is one.

A reader thread parses each stdout line into a queue. When stdout closes, it puts a sentinel on the queue so the turn fails cleanly instead of waiting forever.

The tool, through MCP and back

This is the part to understand carefully. Claude Code starts mcp.clj as a child process, and that child speaks MCP over stdio. It does not run code itself. It forwards every call to the bbh session:

Claude Code  --MCP tools/call-->  mcp.clj (bb -m bbh.mcp)
                                     |  one JSON line over a loopback socket,
                                     |  with the session's random token
                                     v
                          claude.clj serve-bridge
                                     |
                                     v
                          session/run-code!  (the same path as the loop engine)
                                     |
                          REPL evaluates, events are emitted, result returned

The bridge listens on 127.0.0.1 with a random port, and every request must carry the token that bbh generated for this session. The token is passed to the MCP child in its environment. The describe operation returns the tool description from the manifest, so the description the model sees is the same one the loop engine uses.

Because the call goes through run-code!, a Claude tool call produces the same events and the same REPL state as an OpenRouter one. Claude's own tool results are recorded when the stream reports them, in record-tool-results!.

Turns, in order

  1. system-prompt! refreshes the manifest.
  2. ensure-claude! starts the bridge once, and starts a Claude process if none is running or the system prompt changed. A new system prompt needs a new process, because --system-prompt is fixed at start.
  3. If the process is new and the transcript already has assistant turns, the prompt is prefixed with the earlier transcript as text. This covers a Claude session that joins a conversation late, such as after --resume in another front end.
  4. The user message goes to stdin as one JSON line. The interrupt action sends a control_request on the same stdin.
  5. The loop takes events from the queue. Text deltas are emitted. message_start gives input tokens, including cache reads and writes. assistant and user messages are recorded. system init saves the session id. rate_limit_event updates the limits for /usage. result adds the cost and throws if the result is an error.

Observation. In the streaming path, separate text blocks are joined with a blank line for display. In record-assistant!, the stored text is the blocks joined with no separator. A transcript replayed later can therefore run two sentences together that the user saw on separate lines. It is a small inconsistency between what is shown and what is saved.

Try it. The Claude adapter is tested against a fake CLI, test/fake-claude.clj, so the tests need no subscription. Run them:

cd desktop/build/bbh
bb -cp src:test -e "(require 'bbh.claude-test) (clojure.test/run-tests 'bbh.claude-test)"
Check yourself

Why does changing the manifest's system prompt restart the Claude process, while changing the tool description does not? Answer: --system-prompt is passed when the process starts, so a new system prompt needs a new process. The tool description is fetched through describe each time the MCP server lists tools, so it can change without a restart.

9. Context, trimming and compaction

Learning goals. Explain the difference between the transcript and the context. Explain why bbh trims tool output only from earlier turns, and how a compaction cut point is chosen.

Two views of one conversation

The transcript keeps every message forever. The context is what the model sees. context/view builds it from the transcript and the latest compaction:

  1. If there is a compaction, a user message with the summary comes first, under a header that says earlier messages were compacted.
  2. Messages from the first kept index up to the start of the current turn come next. Tool output in them is cut to :trim-tool-chars, 4000 by default. The cut keeps the head and the tail and says how many characters it removed.
  3. The current turn is included in full, so the model always sees its own latest tool results at full size.

Why only earlier turns

The design log says why. Trimming old output once per turn keeps the prompt-cache prefix stable within a turn. A provider caches the start of a request, so if bbh changed earlier messages on every round, the cache would miss on every round. Trimming only at the turn boundary means each turn costs at most one rewrite of the prefix. decisions.tsv, 2026-10-18 context

When compaction runs

Before each round, turn! checks whether the context has passed :compact-at-tokens, 200000 by default. A provider overflow error also triggers one compaction and one retry. The user can ask for one with /compact, and the text after the command becomes the focus of the summary. Tokens are estimated as one quarter of the JSON character count. That is a rough figure, and the design says so.

Where the cut goes

cut-point picks the message index where the kept suffix begins. It considers only indices after the previous cut and never a tool message, because a tool result must stay with the call that asked for it. It takes the earliest candidate whose suffix fits within :keep-recent-tokens, 20000 by default. If none fits, it takes the latest candidate. If nothing lies before the cut, there is nothing to compact.

The summary request asks a model for a fixed set of Markdown sections: goal, constraints, progress, decisions, next steps and critical context. It tells the model to keep the user's words, to name every file and value, and to record the REPL helpers that still exist. The new summary replaces the previous one, which is included in the request.

The compaction is recorded in compactions.jsonl as {first-kept, summary}. The transcript is not changed, so an earlier compaction can always be reconstructed.

Try it. Compute a cut point on a small transcript without a model. The first argument is the list of messages, the second is the index to start from, and the third is the token budget for the kept suffix:

cd desktop/build/bbh
bb -cp src -e "(require '[bbh.context :as c])
(def msgs (vec (for [i (range 10)] {:role (if (even? i) "user" "assistant") :content (apply str (repeat 400 "x"))})))
(prn (c/cut-point msgs 0 300))
(prn (c/cut-point msgs 0 100000))"

The first call prints 8: with a 300-token budget only the last two messages fit, so eight messages are summarized. The second prints 1: with a generous budget the earliest candidate fits, so only the first message would be summarized. Both outputs match what the function's rule says.

Check yourself

A transcript ends with an assistant message that has a tool call, then a tool result, and the suffix budget would cut right before the tool result. What does cut-point do? Answer: tool messages are never candidates, so it moves the cut to an earlier user or assistant message, keeping the call and its result together.

10. Front ends: terminal and ACP

Learning goals. Describe both front ends, show how each one drives the same session, and list the rules ACP enforces.

The terminal

main.clj is the entry point. bbh with no arguments starts a terminal session. It builds a conversation directory, starts the session, and reads lines with a JLine reader that keeps history in ~/.local/share/bbh/history. Each line goes to session/prompt!. A Ctrl-C handler calls interrupt!, and /quit leaves. The terminal prints events as they arrive, with the code of each call in dim text and at most 15 lines of each result.

ACP

bbh acp runs the Agent Client Protocol over stdin and stdout. Each line is a JSON-RPC request. The methods are:

MethodWhat bbh does
initializeAnswers protocol version 1. Declares that bbh cannot load sessions and accepts text prompts only.
session/newCreates a session with a timestamp id, starts its REPL, lists the available models, and sends the command list, which includes bbh.env/commands.
session/promptRejects anything but a non-empty list of text blocks. Refuses a second prompt while one is running. Runs prompt! in a future and answers with end_turn or cancelled.
session/set_modelChanges the model, unless a turn is running.
session/cancelCalls interrupt!.

Malformed JSON gets error -32700. A request that is not an object with a method gets -32600. Unknown methods get -32601. Errors inside a request are answered with that request's id, so one bad call never ends the process. decisions.tsv, 2026-10-17 reliability

The ACP front end also turns events into agent-shell updates. Tool blocks are titled with the first line of their code, which fixed the invisible-call problem described in lesson 4.

Observations. The session id is a timestamp with millisecond resolution, so two sessions created in the same millisecond would collide. This is unlikely for one user. A separate point is that loadSession is false, so agent-shell cannot restore an ACP session after Emacs restarts. Resume works only from the terminal with --resume.

Try it. Send ACP requests by hand and watch the replies. This starts a session, which creates a scratch REPL under the data directory:

cd desktop/build/bbh
printf '%s\n' '{"id":1,"method":"initialize","params":{}}' '{"id":2,"method":"nope"}' | BBH_MODEL=script/test/script.edn bb -cp src -m bbh.acp 2>/dev/null

The first reply reports protocol version 1. The second is an error, -32601, because nope is not a method.

Check yourself

Why does the ACP front end run prompt! in a future rather than inline? Answer: the reader thread must keep reading. If it blocked during a turn, a session/cancel request could not be read, so the user could not stop the turn.

11. Models and credentials

Learning goals. Explain how a model id selects an engine, and where credentials come from.

Model ids

A model id is PROVIDER/MODEL. The split happens at the first slash, so openrouter/deepseek/deepseek-v4.1-flash means provider openrouter and model deepseek/deepseek-v4.1-flash. models/engine maps the provider to an engine:

ProviderEngineNotes
claude:claudeClaude Code as the loop, on the subscription.
openrouter:loop with llm/openrouterbbh's own loop against any OpenRouter model.
script:loop with a scripted samplerFor tests and demos. Replies come from an EDN file, where a string is an answer and {:code ...} is a tool call.

The default is claude/haiku, and BBH_MODEL overrides it. The model list offered in ACP is fixed in models/available. Any other provider stops with an error that names the three valid ones.

Credentials

auth.clj shares credentials with Pi and Claude Code instead of storing its own:

  • API keys come from an environment variable first, such as OPENROUTER_API_KEY. Otherwise they come from the provider's entry in Pi's auth.json.
  • Key values follow Pi's convention. A value that begins with ! is a shell command whose output is the key. A value that names a set environment variable reads that variable. Anything else is the key itself.
  • OAuth tokens for Codex come from Pi's file, and only while they are unexpired.
  • The Claude subscription comes from Claude Code's own credentials file, which the CLI refreshes. bbh reads it only for /usage.

Try it. Check which provider keys bbh can see, without printing them:

cd desktop/build/bbh
bb -cp src -e "(require '[bbh.auth :as a]) (prn (boolean (a/api-key "OPENROUTER_API_KEY" "openrouter")))"

The output is true or false. The key itself is never printed.

Check yourself

An auth.json entry has the key !pass show openrouter. What does bbh do with it? Answer: resolve-key runs that command through bash and uses its trimmed output as the key. The key is never stored in bbh.

Design choices in the tests

  • Scripted models. models/script replays a fixed list of replies. A test that depends on the model's choices would be flaky, and this one is deterministic.

  • Startup tests must not overwrite the saved workspace. The Doom startup test isolates its history and workspace writes, because an earlier version could overwrite the user's saved layout. decisions.tsv, 2026-10-18 verification
  • Tests for bugs seen in use. Several regressions began as a symptom in a live run: dropped whitespace in ACP chunks, a leaked MCP listener, a broken stream reported as success, and a helper that was not found. Each has a test that fails on the old behavior.

13. Evaluation from traces

Learning goals. Explain the two evaluation tools, the assertion registry, the label and judge loop, and why the reported results are provisional.

Every conversation is a trace

A trace is one conversation directory with a messages.jsonl. Because the transcript is plain chat messages (lesson 2), the eval tools can read every real conversation, and every archived comparison run, without any extra logging. This is the payoff of that early decision.

Cheap assertions from observed failures

The design follows Hamel Husain's advice to start with cheap assertions taken from failures you have actually seen. eval/bbh/traces.clj holds the registry. Each assertion is a function over a trace:

AssertionHit when
guessed-arityA step raised ArityException, usually a guessed helper signature.
unresolved-symbolA step named a function or namespace the REPL does not have.
pi-idiomThe code used Pi codemode conventions such as await, tools/..., fs/read or fs/list.
root-blind-globThe code used a **/ glob, which skips root-level files.
repl-restartAn evaluation timed out or died, and the REPL lost its definitions.
error-streakThree or more failed evaluations ran in a row.
no-final-answerA turn ended without assistant text after its last tool call.

A cohort is one comparison run and profile, or one day of real conversations. bb eval:lint counts, for each cohort, how many traces hit each assertion. That is how a change can be shown to make a failure rarer. The signature prompt change is the worked example: the root-blind glob hit 10 of 12 first-iteration traces, and none of the final ones. decisions.tsv, 2026-10-18 eval-traces

Labels and a judge

Labels are binary, good or bad, and each carries a critique. They are appended to one file, so the history is never rewritten. An LLM judge reads a trace without the grader's verdict, using eval/judge.md as its system prompt. Its labeler name includes a hash of judge.md, so an edited prompt starts a new labeler and old verdicts remain comparable.

eval:agreement reports precision and recall with bad as the positive class. Raw agreement is not reported, because when most traces are good it misleads. The command prints every disagreement with both critiques, which is what you use to edit the judge. The stated rule is to trust the judge on unlabeled traces only after its precision and recall hold on 25 to 50 of your labels, and to keep sampling afterward.

Comparisons

eval:compare runs fixed tasks through three profiles: Pi with its native tools, Pi with the production SCI extension, and bbh. The tasks give the same generated projects to every profile. eval:contracts checks the protocol with a scripted provider and makes no model calls.

The results are small and should be read that way. The first live cohort was Pi 12 of 12, Pi with SCI 12 of 12, and bbh 11 of 12, and the log records no performance verdict. The signature cohort moved bbh from 70 calls with 16 errors to 48 calls with 3 errors, against Pi with SCI at 65 calls and 6 errors. These are four tasks, three repetitions, and profiles that differ in prompts and tools, so the log does not declare a winner. decisions.tsv, 2026-10-18 eval-live, eval-review

Try it. Run the lint over the archived traces. It makes no model calls:

cd desktop/build/bbh
bb eval:lint

Pick one cohort in the output, then render one of its traces with bb eval:show DIR.

Check yourself

Why does the judge get the trace without the grader's verdict? Answer: the verdict is the answer key. If the judge saw it, agreement with the labels would measure copying, not judgment.

14. Design decisions

Learning goals. Explain the main design choices, the alternatives they replaced, and what each one cost. Use the decision log as the evidence.

The project keeps a decision log, decisions.tsv, with one row per decision. It records the time, the phase, the decision, why, the evidence and the result. The table below gathers the decisions that shape the internals. Open items are listed in lesson 15.

DecisionWhyWhat it cost or what it bought
One tool, clojure, evaluated in a persistent REPLThe model can keep helpers and change its environment through ordinary code.Restarts lose state. The REPL is not a sandbox.
Claude Code runs the loop for claude/...Keeps the subscription path. The CLI owns sampling, retries and caching.Two engines with two code paths. The tool must cross an MCP bridge.
One event stream, not UI callbacksACP and the terminal consume the same events, and the tests can check them.Front ends must translate events. The ACP title fix came from that translation.
The env owns expand-prompt and skillsThe model can change how its own input is expanded.The env can break input handling, so expansion errors are reported in the transcript.
Transcript is plain chat messages; the context is a viewThe eval tools and the Claude adapter read the same files, and compaction never rewrites history.Every turn recomputes the view. Trimming and summaries must be pure functions.
Trim tool output only from earlier turnsThe provider's prompt cache stays valid within a turn.Old tool output is shortened once per turn, not on every round.
Compact at a token threshold and on overflowThe budget controls cost and focus, and overflow recovery covers smaller context windows.Token counts are estimates. The live check compacted twice and still answered correctly.

Reading the log. Each row carries its evidence: a test name, a live run, or a measured number. Some rows are marked open or unverified. Those are the honest limits of the design, and they are the next place to look.

15. Limits and open questions

Learning goals. Separate what the design guarantees from what it only hopes for. Know where to look before trusting a behavior.

Open in the decision log

  • Provider cost semantics. Cumulative cost from Claude Code's result events was not verified against a real subscription run.
  • Live Claude restart with a new system prompt. The fake-CLI test covers the restart logic. A live restart was not checked, because real quota was deliberately not spent.
  • ACP resume. bbh does not load ACP sessions, so there is no resume in Emacs yet.
  • The doom-check PATH warning. make doom-check still reports an environment PATH warning. The log chose not to hide it by changing the env file or the baseline. decisions.tsv, 2026-10-17 doom
  • Judge trust. Two labels prove the pipeline, not alignment. The judge needs 25 to 50 labels before its verdicts can stand in for yours.
  • Persistent helpers and queued prompts. The eval contracts list these scenarios as untested.

Limits you will meet in use

  • No rollback and no branching. The transcript only grows. You can compact or restart, but you cannot undo a turn.
  • The REPL is not a sandbox. Model code runs with your permissions. Everything the REPL can reach, bbh can reach.
  • Restarts lose definitions. A deadline, an interrupt or /restart resets the REPL. The transcript and the init file survive, and nothing else does.
  • Estimated tokens. One quarter of the JSON character count is a rough guide. Compaction thresholds inherit that error.
  • Round limit. A turn stops after 100 tool rounds, and the model is told so in a note. It is a fixed constant, not a manifest key.

Observations from reading the code

These are not in the decision log. They come from reading the source for this course, and each one can be checked with a small test:

  • validate ignores keys it does not know, so a misspelled limit fails silently (lesson 6).
  • record-assistant! joins text blocks with no separator, while the display separates them (lesson 8).
  • ACP session ids have millisecond resolution, so ids could collide if two sessions start in the same millisecond (lesson 10).

16. Exercises

Learning goals. Apply what you learned by making a small, verifiable change to bbh.

  1. Trace one turn. Write a scripted reply file with one text step and one code step, then run the terminal with BBH_MODEL=script/PATH. Name each event you see, and which function emitted it.
  2. Reject unknown manifest keys. Extend repl/validate so an unknown key produces a problem line. Write a test in env_test.clj that fails before your change and passes after it. Consider whether the fallback text should name the valid keys.
  3. Add a built-in command. Add /tokens to session/commands, which reports the current context/tokens estimate. Make sure it runs without the model, and add a test in session_test.clj modelled on commands-run-without-the-model.
  4. Find the cut. Using cut-point, construct a transcript where the earliest fitting cut would land on a tool message. Show that the function moves the cut and explain why in one paragraph.
  5. Add an assertion. Follow the README's instructions to add an assertion to traces.clj for a failure you have seen in a trace. Add a test in eval_test.clj that builds a conversation with the failure, then run bb eval:lint over it.
  6. Settle a question. Verify or refute the observation about joined text blocks. Write the test that shows the difference between display and storage, and propose the change that makes them agree.

Glossary

ACP
Agent Client Protocol. JSON-RPC over stdio, used by Emacs agent-shell to talk to bbh.
Cohort
A set of eval traces grouped by comparison run and profile, or by day for real conversations.
Compaction
Replacing older messages in the model's view with a summary. The transcript itself is not changed.
Control session
The nREPL session bbh uses for its own questions, which leaves the model's namespace alone.
Cut point
The message index where the kept suffix begins during compaction. Never a tool message.
Engine
The thing that runs a turn: :loop for OpenRouter and scripts, or :claude for Claude Code.
Env
The init file and the vars it defines, which bbh reads by name: manifest, expand-prompt and commands.
Event
A map with a :type that the session emits and a front end renders.
Judge
An LLM that labels traces good or bad, using judge.md. Checked against your labels before its verdicts count.
Label
A binary good or bad verdict with a critique, appended to labels.jsonl.
Manifest
bbh.env/manifest: the system prompt, tool description and limits, read before every request.
MCP
Model Context Protocol. How Claude Code calls bbh's tool, through mcp.clj.
nREPL
The network REPL protocol, spoken in bencode, that bbh uses to talk to the REPL process.
Poteto-mode
A workflow that starts each new conversation with a skill that routes tasks through Jev. Turned off with /poteto-mode-off.
Skill
A SKILL.md file that the env can inline into a prompt with /skill:NAME.
Trace
One conversation directory, read by the eval tools.
Transcript
messages.jsonl: the durable, append-only record of a conversation.
Trimming
Shortening tool output from earlier turns in the context view, with head and tail kept.
Turn
One user prompt and the model's full response, including any tool rounds.
User session
The nREPL session that runs the model's code and keeps its definitions.
