1The store and derivations

The StoreDerivationsguix gcguix graphguix hash

A derivation is the only thing the daemon knows how to build. It is a small text file in the store that names a program to run, its arguments and environment, the store items that must exist first, and the paths the build must fill. Packages, services, your whole system: all of it is lowered to derivations before anything is built. The explorer below holds the real ones behind your zoxide, a package defined in /home/engstrand/guix/modules/engstrand/packages/zoxide.scm

Anatomy of a .drv real

This is /gnu/store/hckkwxvn…-zoxide-0.10.0.drv, field by field. The file is one Derive(…) term with seven positions, in the format Guix inherited from Nix.

1. outputs("out", "/gnu/store/ywp06qxj…-zoxide-0.10.0", "", "")
Name, path, and two empty slots for a hash algorithm and hash. The path is known before the build, because it is computed from the derivation itself. The empty slots mean this is an ordinary, input-addressed derivation. 2. input derivations26 entries such as ("…-patchelf-0.18.0.drv", ["out"]) and ("…-glibc-2.41.drv", ["out","static"])
Other derivations whose named outputs must be realised first. This list is the edge set of the derivation graph. 3. input sources…-module-import, …-zoxide-0.10.0-builder
Plain store files that already exist: here the build script and a directory of Guile modules. The client added them to the store while computing the derivation. 4. systemaarch64-linux
Which kind of machine may run the builder. The daemon refuses or offloads when it cannot. 5. builder/gnu/store/b83lyndh…-guile-3.0.9/bin/guile
The program to execute. In Guix it is almost always Guile; in Nixpkgs it is almost always bash. 6. arguments--no-auto-compile -L …-module-import -C …-module-import-compiled …-zoxide-0.10.0-builder
Load path for build-side modules, then the builder script. 7. environmentLC_CTYPE=C.UTF-8, out=/gnu/store/ywp06qxj…-zoxide-0.10.0
The whole environment of the build. Nothing from your shell leaks in.

How a store path gets its hash

The 32 characters are 160 bits in a base-32 alphabet without e o t u. There are three recipes, and which one applies decides when a path changes. I reproduced the second and third in babashka against the real paths on this machine before writing them down.

KindHash coversChanges when
Source file
…-zoxide-0.10.0-builder, plain-file, local-file		The file's own content (and for text files, the store paths it mentions).The content changes.
Fixed-output derivation
…-zoxide-0.10.0-…-musl.tar.gz		The declared content hash and the name. Not the URL, not the downloader.You change sha256 or the file name.
Ordinary derivation output
…-zoxide-0.10.0		The whole .drv with output paths blanked and each input derivation replaced by its hash, recursively.Anything in the build recipe or in any dependency's recipe changes.

So an ordinary path is input-addressed: it names the recipe, not the result. Two machines agree on the path without building anything, which is what lets a client ask a server "do you have ywp06qxj…?". The cost is the rebuild cascade: touch glibc and every path downstream changes, even if the rebuilt bytes would be identical. (Grafts, section 5, are the escape hatch.)

A fixed-output derivation (FOD) is the one place the network is allowed, because the result is pinned: the daemon hashes what the build produced and rejects it unless it matches. When an FOD appears as someone's input, the hash that stands in for it is made from its output path and content hash only. That is why moving a tarball to another mirror rebuilds nothing.

You change only the download URL of a package's source to a mirror, keeping the same sha256. What gets rebuilt?

The source is a fixed-output derivation. Its output path is computed from the content hash and name, and that path plus hash is all that dependents see of it. The .drv file of the source does change (the URL is in its environment), but no output path does. Try it in the calculator: there is no URL field to edit.

Why can Guix print the output path of a package before building it?

Ordinary outputs are input-addressed. The client hashes the derivation with output paths blanked and inputs replaced by their own hashes. Nothing has to be built or downloaded to know the name, which is what makes substitutes a simple lookup by path.

2The daemon and build isolation

guix-daemonBuild Environment Setupguix build--check, --rounds

Guix is two programs. The client, guix, is Guile code running as you: it evaluates Scheme and produces derivations. The daemon, guix-daemon, is a C++ program descended from Nix's that runs as root and owns /gnu/store and the database /var/guix/db/db.sqlite (which paths are valid, what each refers to, which derivation made it). They talk over the socket /var/guix/daemon-socket/socket. The client can ask for only a few things: add this text or file to the store, build these derivations, is this path valid, collect garbage. It can never write a store item directly, which is why an unprivileged user can install software safely.

What a build may see

A build runs as one of the guixbuilder users inside a chroot with its own PID, mount, network, IPC and UTS namespaces. Per the manual, the chroot holds only: the store items in the derivation's input closure, a minimal /dev, /proc showing only the build's processes, an /etc/passwd and /etc/group with the build user and nobody, an /etc/hosts mapping localhost, and a writable /tmp. HOME is /homeless-shelter, which does not exist. There is no network, except for fixed-output derivations. After the build, timestamps in the output are reset to the epoch and permissions canonicalised, so that those cannot differ between machines.

Isolation gives hermetic builds, not automatically bit-identical ones: a build can still embed the time, the CPU count or a random number. guix build --check PKG rebuilds and compares with what is in the store, and --rounds=2 does it up front.

3G-expressions and staging

G-ExpressionsThe Store MonadBuild Phases

Guix code runs at two different times. Host-side code runs now, in the guix process, with your modules loaded: it decides what to build. Build-side code runs later, somewhere else: in the build sandbox, in Shepherd (PID 1), in an activation script at boot, in a cron job. It is a different Guile process that knows nothing of your variables.

A G-expression is how host code writes build-side code. #~ quotes an expression for later, like quasiquote. #$ escapes back to the host to drop a value in, like unquote. The difference from plain quoting is the point: when the value is a package or another file-like object, the gexp remembers it as a dependency, and when the gexp is lowered it is replaced by its store path. You never write a store path, and you cannot forget an input.

SyntaxMeaning
#~expBuild-side code (gexp). Not evaluated now.
#$objEvaluate obj on the host and insert it (ungexp). A package becomes the path of its out; a string or number becomes a literal.
#$obj:lib, (gexp-input gcc "lib")A specific output.
#$@listSplice a host-side list in (ungexp-splicing).
#+objLike #$, but when cross-compiling, the version built for the build machine (ungexp-native): a tool you run, not a library you link.
#$outputThe derivation's own output directory. Lowered to (getenv "out"), since the path is not known while the builder script is being written.
(with-imported-modules '((guix build utils)) #~…)Make host-side Guile modules available to the build side. They become the module-import source input you saw in the .drv.

Mistakes staging makes impossible, and ones it does not

  • Forgotten dependency: impossible. If the lowered script names a store path, that path came from a #$, so it is an input of the derivation. Compare a shell script with /usr/bin/patchelf typed into it.
  • Using a host variable without #$: possible. #~(display my-config) lowers to code that refers to an unbound variable my-config, and fails only when it runs.
  • Joining paths on the wrong side: harmless but different. (string-append #$glibc "/lib") inside a gexp joins at build time; #$(file-append glibc "/lib") joins on the host. Both work. The second is a single file-like value you can pass to things that expect one.
  • Side effects on the host: possible. Anything outside #~ runs every time the config is evaluated, including for --dry-run.

In #~(invoke #$(file-append git "/bin/git") "init" (string-append home "/guix.git")) from your builder's activation gexp, when is (string-append home "/guix.git") evaluated?

It is inside #~ and not under a #$, so it is build-side code, copied as-is into the activation script. Only (file-append git "/bin/git") runs on the host, where it becomes a string like "/gnu/store/…-git-2.x/bin/git" and makes git a dependency of the system. home is bound by a let inside the same gexp.

Why does #$output lower to (getenv "out") instead of a literal path?

The builder script is a source input of the derivation, and the output path is a hash over the derivation including that script. Writing the path into the script would be circular. The daemon passes it through the environment instead: you saw out=… as the last field of the .drv.

4Packages, inheritance and transformations

Defining PackagesPackage VariantsTransformation OptionsBuild SystemsBuild Phases

A package is an ordinary Scheme record value. It is not a name in a registry: the name is just a field, two packages may share one, and anything that takes a package takes whichever value you hand it. Three consequences run through your config.

Lowering: package, bag, derivation

The build-system field turns a package into a bag: the package's own inputs plus the build system's implicit ones. That is where zoxide's 26 input derivations came from, though zoxide.scm declares none. copy-build-system rests on gnu-build-system, which adds tar, gzip, coreutils, gcc, glibc, binutils and friends (open the root node in the explorer and count). The bag is then lowered to the derivation, with the phases and arguments spliced into the builder script as a gexp. Fields such as inputs are delayed until needed, so modules may refer to each other in a cycle.

Packages from functions real

Because a package is a value, a function can return one. release-binary in /home/engstrand/guix/modules/engstrand/packages/release-binary.scm is that: zoxide, fd, fzf and ten more are each a single call. Nix does the same with functions such as mkDerivation; the difference is only that here the function, the record and the build phases are all one language.

The result is a new, unrelated value. Nothing that used base now uses the copy: other packages hold a reference to the old value in their inputs. This is the big behavioural difference from Nixpkgs overlays, which rebind a name in a fixed point so that every user sees the new one.

To change dependents, rewrite their inputs (package-input-rewriting, --with-input=openssl=my-openssl), or, for a binary-compatible security fix, set the replacement field so they are grafted (next section).

5Grafts

Security Updates--no-grafts

Input addressing makes a fix to a low-level library expensive: patch glibc and all 30,000 packages get new hashes and must be rebuilt. A graft avoids that for fixes that keep the ABI. The maintainer leaves the package as it is and points its replacement field at a fixed variant:

(define bash
  (package
    (name "bash")
    ;; …
    (replacement bash-fixed)))

Nothing is rebuilt. Instead, for each thing you ask for whose run-time closure contains the original, Guix adds one cheap derivation that copies the built output and rewrites every occurrence of the original's store path to the replacement's. The copy lands under a new hash; things that referred to it are grafted in turn. It takes seconds per package and runs wherever builds run.

  • Grafting needs the ungrafted output first, because only its references say whether it uses the replaced package at all. With substitutes that is a download.
  • The replacement must be binary-compatible with the same SONAME, since programs are not relinked. The rewrite swaps the 32-character hash in place, so no file changes size.
  • guix build bash --no-grafts prints the original path, plain guix build bash the grafted one. Substitute servers serve ungrafted builds; the graft itself is done on your side.
  • Grafts are meant to be temporary: the next large rebuild cycle folds the fix into the package and removes the replacement.

The overview page has the graft diagram: guix-explainer.html, Grafts. Nixpkgs has no equivalent in normal use; a security fix to a core library there goes through a full rebuild on the staging branches. uncertain Nixpkgs does ship a lesser-used system.replaceDependencies option with a similar idea.

A grafted package and its ungrafted original: how do their store paths relate?

The store is immutable, so a graft is a new derivation with a new output. The original stays until garbage collection. This is also why a command that mixes grafted and ungrafted paths (for instance comparing guix build output with a path from a substitute server's listing) can look inconsistent.

What is trusted, exactly

  • The daemon accepts a narinfo only if its signature verifies against a key in /etc/guix/acl. On Guix System that file is generated from the authorized-keys of the guix service; yours holds the keys for ci, bordeaux, the Asahi farm and guix-builder.
  • The signature covers the narinfo, and the narinfo names the nar's hash. So the archive itself can come from anywhere, over plain HTTP, from a mirror: it is checked against the signed hash.
  • Servers are asked in the order given. The manual adds a subtlety: a substitute from a server whose key you have not authorized is still accepted when an authorized server signs a narinfo for the same path with the same hash.
  • What the signature does not say is that the binary is what the source builds to. You are trusting the key's owner to have run the derivation honestly on an uncompromised machine.

Checking instead of trusting

Since a derivation is an exact recipe, anyone can rebuild and compare. guix challenge zoxide compares your local build's hash with what each server advertises. guix weather reports how much of a package set a server has. The project runs two independent farms, ci.guix.gnu.org and bordeaux.guix.gnu.org, so that one can be checked against the other. Your builder is a third for the things only you build.

On the serving side, your builder runs guix publish (system/builder.scm): port 8080, zstd level 9, a cache in /var/cache/guix/publish, narinfos advertised for 30 days, and a 60 second negative TTL so that a "don't have it" answer is retried soon after a prebuild.

Your laptop downloads a nar over plain HTTP from the builder. What stops someone on the path from swapping the archive?

Authenticity comes from the signature on the narinfo plus the NarHash check, not from the transport. The tailnet matters for a different reason: it keeps the builder's ports off the public internet.

A substitute's signature verifies. What have you learned?

A signature is a claim by a key holder, nothing more. Correspondence to source needs a rebuild and comparison (guix challenge, guix build --check), and that comparison only means something when the build is deterministic.

7Channels, guix pull, inferiors and time-machine

A channel is a Git repository of Guile modules. The guix channel is special only in that it also contains the guix command itself: the tool and the package collection are one repository at one commit. That is the key structural fact. There is no separate "Guix version" and "package set version" to keep in step.

Your own modules are not a channel: the Makefile passes -L modules, so they are loaded straight from the working tree, uncompiled and unauthenticated. That is the usual choice for a personal config, since changes take effect without a pull.

What guix pull does

  1. Fetch each channel into ~/.cache/guix/checkouts at the commit in channels.scm.
  2. Authenticate. Each channel entry carries an introduction: a commit and the OpenPGP fingerprint that signed it. From there every commit must be signed by a key listed in the .guix-authorizations file of its parent commit. Pull also refuses to move to a commit that is not a descendant of the current one, which blocks downgrade attacks. So trust comes from the introduction in your file, not from the hosting site.
  3. Build Guix with Guix. The currently installed guix computes a derivation that compiles all channels' modules together, and the daemon builds or substitutes it. This is why pull is slow without substitutes, and why your prebuild does it on the builder first.
  4. New generation of the profile ~/.config/guix/current. Yours is current-guix-8-link, with generation 7 still there to roll back to (guix pull --roll-back).

guix describe -f channels prints the channels of the running guix in the same form as channels.scm. Your make channels-current compares the two and stops make switch when they differ, so the system is never built by a Guix other than the pinned one.

Time travel

guix time-machine -C channels.scm -- CMD runs guix CMD as the Guix described by that file, building and caching that Guix first if needed, without touching your profile. With commits pinned, it is the reproducibility primitive: the same channels file gives the same derivations on any machine, today or in three years (subject to sources still being downloadable; Software Heritage is the fallback). Your make repro-build is this.

An inferior is the same mechanism as a library: a second Guix, at another revision, running as a subprocess that your config can ask for packages. It lets one manifest mix today's packages with one from last year:

(use-modules (guix inferior) (guix channels) (srfi srfi-1))
(define old
  (inferior-for-channels
   (list (channel (name 'guix)
                  (url "https://codeberg.org/guix/guix")
                  (commit "…an older commit…")))))
(packages->manifest
 (list (first (lookup-inferior-packages old "guile"))
       (specification->package "emacs")))

A channel can declare dependencies on other channels in a .guix-channel file; pull fetches them too. Channel Dependencies

Someone takes over the Codeberg account hosting a channel and pushes a commit. What does guix pull do?

Authentication is a chain from the introduction commit in your channels.scm: each commit must be signed by a key its parent authorizes. Control of the hosting account gives no signing key. This is a real difference from Nix flakes, whose lock file pins content hashes but does not check who authored the commits.

You run guix time-machine -C channels.scm -- build hello twice on two machines of the same architecture. What is guaranteed to match?

Pinned channels fix the code that computes derivations, so the .drv and the output path are identical regardless of what either machine had pulled. Bit-identical output additionally needs a deterministic build, which most but not all packages have.

Four profiles, one mechanism. NAME-N-link is generation N; the bare NAME link points at the current one. Switching generation is replacing one symlink, which is atomic, so a crash leaves you on the old or the new and never between. Systems 90 to 99 are on disk now.

  • Search paths. A profile's etc/profile sets variables such as PATH, GUILE_LOAD_PATH or EMACSLOADPATH, but only those that some package in the profile declares it consumes.
  • Collisions. Two packages providing the same file make the profile build fail or pick one with a warning; propagated inputs are the usual cause.

Your day-to-day packages come from the Home and system profiles, both declared in Scheme. ~/.guix-profile, the imperative guix install profile, exists at generation 2 and is the one place state can drift from the repo.

Every derivation graph must end somewhere. To build GCC you need a C compiler; to build that one, another. The leaves of the graph are binaries that were not built by the graph: the bootstrap seeds. They are the part of the system you cannot audit by reading source, and a compiler seed could in principle carry a self-propagating backdoor (the "trusting trust" attack). The smaller the seeds, the less you take on faith.

12guix shell and containers

guix shellguix packguix system container, vm

guix shell builds a temporary profile and runs a command or shell with it. Nothing is installed; the profile is an ordinary store item, cached so that the second run is instant, and collectable when unused.

guix shell python python-numpy -- python3 script.py   # ad hoc tools
guix shell -D zoxide -L modules     # the inputs needed to *build* zoxide
guix shell -m manifest.scm          # a declared set
guix shell                          # loads ./guix.scm or ./manifest.scm, if authorized
guix shell --pure …                 # clear the environment first
guix shell -C --network -F …        # container, with network, FHS layout
  • Auto-loading is opt-in per directory. Bare guix shell loads guix.scm or manifest.scm only when the directory is listed in ~/.config/guix/shell-authorized-directories, since loading the file runs its code.
  • --pure is not isolation. It only unsets environment variables; the program still sees all your files.
  • --container (-C) is. It uses unprivileged user namespaces, the same kernel features as the build sandbox: a fresh mount namespace containing the profile's closure and the current directory, no network unless --network, no home unless shared. --expose=DIR mounts read-only, --share=DIR read-write.
  • --emulate-fhs (-F) adds /bin, /lib and the rest inside the container for programs that assume them, such as pre-built binaries.
  • Reproducible when pinned. guix time-machine -C channels.scm -- shell -m manifest.scm gives the same environment anywhere.

The same container code backs guix system container (a whole OS in namespaces) and guix home container (try a Home config without touching yours). guix pack goes the other way: it exports a profile's closure as a tarball, Docker image, squashfs or relocatable binary for machines without Guix.

You run an untrusted build script with guix shell --pure gcc make -- make. Can it read ~/.ssh?

--pure cleans environment variables and nothing else. --container gives a new mount namespace in which only the store closure and the current directory exist.

Both move store items between machines over SSH, and both depend on the same two facts: a derivation means the same thing everywhere, and store items are signed when exported. The remote builder page covers your setup's operation; this is the mechanism.

Offload: borrow another machine's CPU

Offloading is decided by the daemon, per derivation, through a build hook. /etc/guix/machines.scm lists candidates. Yours is generated from asahi.scm and holds one real:

(build-machine
  (name "guix-builder.tailbf68ad.ts.net")
  (systems '("aarch64-linux"))
  (port 2222) (user "offload")
  (host-key "ssh-ed25519 …")
  (private-key "/etc/guix/offload/id_ed25519")
  (parallel-builds 1)
  (overload-threshold 0.8))
  1. The daemon needs to build a derivation. The hook picks a machine whose systems match and whose load is under the threshold.
  2. It opens SSH as offload and copies over the .drv and any inputs the builder lacks. The builder imports them only because they are signed by the laptop's key, which is in the builder's ACL (laptop-signing.pub in builder.scm).
  3. The builder's own daemon runs the build in its sandbox.
  4. The output comes back signed by the builder's key, which is in the laptop's ACL. The laptop's daemon registers it as if it had built it.

So offload needs trust in both directions, and guix offload test checks each leg. With --max-jobs=0 offload is not an optimisation here but the only way anything gets built.

Why must the laptop's signing key be in the builder's ACL for offloading to work?

SSH keys authenticate the connection; store signing keys authenticate the items. Inputs travel laptop to builder and outputs travel back, so each side's ACL must hold the other's public key. They are different key pairs from the SSH ones.

Guix began as Nix with Scheme in place of the Nix language, and the manual says so plainly: "Guix is based on the Nix package manager" (Acknowledgments). The store, derivations, the .drv format, the daemon, the sandbox, profiles, generations and garbage collection are the same ideas and in places the same code; everything in sections 1, 2 and 8 transfers. A channel is a Git repository of Guile modules added to one shared module namespace; guix pull compiles them and they become your Guix, per user. A flake is a repository with a flake.nix that declares inputs and a schema of named outputs; it is per project, and its inputs are passed in as function arguments, so two versions of Nixpkgs can coexist in one evaluation without an inferior. Flakes compose better as a project format and are the de facto standard, yet upstream Nix still lists them as an experimental feature; classic nix-channel is the older, unpinned mechanism and is not the equivalent of Guix channels despite the name.

The model is the same: fetch a signed .narinfo by store hash, check the signature against locally trusted Ed25519 keys, download the nar, verify its hash. The formats differ (Guix signs with an S-expression carrying the public key; Nix uses name:base64 signatures over a fingerprint of path, nar hash, size and references), and so does what surrounds it. Guix has two independently operated official farms and a built-in guix challenge to compare any server against a local build or against another server. Nix has one official cache, cache.nixos.org, and a large ecosystem of third-party caches (Cachix, Attic); nix build --rebuild is the analogue of guix build --check. Why it matters: in both, adding a key means letting its holder put arbitrary binaries on your machine under any store path, so the list should be short. Coverage is the practical difference: Nix's cache has nearly everything for x86_64 and aarch64, while Guix on aarch64 has gaps, which is the reason your builder exists. Nix also has an experimental content-addressed store model that reduces how much a signature must be trusted.

Nixpkgs is one of the largest and freshest package collections of any distribution; Guix is roughly a quarter of its size by Repology's count, with a smaller contributor base. Why it matters: on Nix the package you want very likely exists and is recent. On Guix you will sometimes package it yourself, which this repo does about 25 times in modules/engstrand/packages and automates with latest.scm and the updates tooling. What Guix offers in return is coherence: one language from package to service to build script, one repository for tool and packages, authenticated history, and a small system you can read. uncertain Governance and release cadence are from general knowledge, not from the manuals.

Nix-side statements describe upstream Nix, Nixpkgs and NixOS as documented in late 2026; forks such as Lix and Determinate Nix differ in places (flakes are marked stable in Determinate Nix, for one).

Which of these is the same in Guix and Nix?

Both lower everything to derivations in the same file format and name outputs by hashing the recipe. Above that line they differ: Scheme and gexps against the Nix language and bash, Shepherd against systemd.

You want hello built with a patch, and every package depending on it to use the patched one. What is the idiomatic tool on each side?

Guix packages hold direct references to their inputs, so dependents change only when the graph is rewritten. Nixpkgs is a fixed point over a set of names, so an overlay that rebinds hello is seen by everything that takes hello as an argument. inherit and overrideAttrs on their own each produce one new package and change no dependents.
