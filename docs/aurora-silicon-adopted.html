Aurora Silicon parts adopted: speaker limiter, video decode, camera denoise

Goal

Take the two parts of aurora-silicon you picked from the survey (/home/engstrand/guix/docs/aurora-silicon.html): (1) Aurora's speaker limiter for the M1 Air, and (2) hardware video decode on the Apple Video Decoder (AVD) plus the camera denoiser. Userspace only, with no kernel change. Nothing was switched or rebooted.

Outcome

  • Speakers: the J313 graph now ends with Aurora's true-peak limiter. In an offline render, peaks that reached +6 dBFS now stop at −1.00 dBFS. Quiet audio comes out bit-identical, only 7.6 ms later.
  • Video decode: the open AVD firmware, the VA-API driver Aurora ships and the wiring all build on guix-builder. The driver loads both on the host and inside the flatpak Chrome's runtime. It decodes only after the firmware loads, which needs a module reload or a reboot. It stays opt-in: nothing uses it until you start mpv or Chrome with the flags below.
  • Camera: camera-denoise runs as a Home service. A 4-second live test published a denoised “FaceTime HD Camera” node beside the raw one, without opening the camera.
  • guix system build (Home included) and make lint pass, and check-kernel.bb shows the kernel unchanged.

1. Speaker limiter

This is Aurora's asahi-audio commit b30c50a by Ryan Murray, J313 hunk only. It is MIT, the same licence and copyright holders as asahi-audio, and the patch header credits it. It adds an LSP limiter_stereo after woofer_lim, set to −1 dBFS with 5 ms lookahead, true-peak 24-bit oversampling and no gain boost. It only lowers peaks. speakersafetyd still sits after the graph, unchanged.

Offline test, measured. Each graph ran in a private PipeWire daemon with no ALSA, so no sound reached a speaker. The plugins were your running lsp-plugins 1.2.25 and bankstown. The harness is Aurora's tests/speaker-graph-clips.py, plus a quiet −30 dBFS signal. The old graph is your current asahi-audio and the new one is the patched build.

The level (RMS) on the kick and bass mix stayed at −12.6 dB. On the pink noise it went from −8.3 to −9.3 dB, and on the sweep from −5.3 to −7.6 dB. The −30 dBFS signal came out identical sample by sample.The old RMS counts energy above full scale that the amps would have squared off anyway. So the louder old numbers on the sweep are distortion, not lost bass. Data: /home/engstrand/.local/state/bbh/workflows/20261122-130738-704-change/evidence/limiter-render.txt

What to listen for after switching. Use music you know with deep kicks or synth bass, at your usual loud level. You don't need to go to full volume. The crackle or pop on bass hits should be gone. Normal-level listening should sound the same. Very loud sustained bass may sound slightly less punchy, by up to about 1 dB. To check that the limiter is live, run pw-dump | grep -c woofer_peak, which should print 1 or more.

2. Video decode on the AVD

  • Firmware: Asahi's own avd-fw 0.2 (MIT), not Aurora's fork. Aurora's fork speaks the queue ABI of Aurora's kernel and has no config block, which your asahi-7.2.15 apple_avd driver requires. The build has H.264, HEVC and VP9 enabled. Asahi turns H.264 and HEVC off by default for patent reasons, and that would leave the M1 with VP9 only. I checked the image: the AVDc block at 0x400 has the capability mask 1111.
  • VA-API driver: libva-v4l2_request 1.3.r11 (GPL-3.0+), the commit nixos-aurora pins. A link named asahi_drv_video.so lets libva pick it from the GPU's DRM driver name. 226 of its 228 offline tests pass. I dropped the other two: they are self-tests of its test harness and need a TSan runtime and timing the build container lacks.
  • Wiring: the firmware goes through firmware-service-type, and LIBVA_DRIVERS_PATH is set in Home. A flatpak override lets Chrome see the driver's store path and sets the same variable inside its sandbox. vainfo comes from libva-utils.

Measured now: on the host and inside Chrome's runtime (freedesktop 25.08, libva 2.22), libva opens the driver and finds __vaDriverInit_1_22. It then stops with no V4L2 Request API decoder found, which is expected while the firmware is missing.

Risk, as you accepted (opt-in). The stock 7.2.15 AVD driver lacks 15 fixes from iconidentify/omarchy-m1-video. They include a job-completion race that can oops the kernel and lock /dev/video until a reboot. A bad video can therefore need a reboot.

Try it without rebooting, after the switch: save your work and close any video, then run sudo modprobe -r apple_avd && sudo modprobe apple_avd. Then check:

  • sudo dmesg | grep -i avd shows no failed to load firmware
  • ls /dev/video* now shows a second node
  • vainfo --display drm lists the H264, HEVC and VP9 profiles

If it fails, the reboot after the switch loads the firmware anyway.

mpv: guix shell mpv -- mpv --hwdec=vaapi --gpu-api=opengl FILE. mpv stays out of the profile because it propagates a lua that clashes. Look for Using hardware decoding (vaapi). Vulkan output shows a ghost picture on Asahi, so use OpenGL.

Chrome: quit Chrome completely, then start it with CHROME_UNIFIED_ARGS='--enable-features=AcceleratedVideoDecodeLinuxGL,VaapiIgnoreDriverChecks' chrome-unified. Chrome accepts only Intel and Mesa VA-API drivers unless VaapiIgnoreDriverChecks is set, so that flag is the opt-in. Two checks while a video plays:

  • chrome://gpu shows Video Decode: Hardware accelerated
  • chrome://media-internals names VaapiVideoDecoder

If chrome://gpu still says software, add --ignore-gpu-blocklist. I could not run Chrome against the decoder before the firmware loads, so these flags are untested here. They come from the Chrome and omarchy-m1-video docs.

3. Camera denoise

Aurora's camera-denoise (MIT) is built from main at 6ae2f1d and runs as the Home Shepherd service camera-denoise, after PipeWire and WirePlumber. The M1 has no board data, so you get the CPU temporal filter only. Aurora reports about 3 ms per 1080p frame, less at 720p.

  • Apps see FaceTime HD Camera (denoised) and FaceTime HD Camera (V4L2) (raw).
  • Settings go in ~/.config/aurora-camera-denoise/denoise.conf; mode = off passes frames through unchanged.
  • To stop it for this session, run herd stop camera-denoise.

Switch and roll back

  1. make pull first: the pulled Guix still lists the asahi channel that T212 dropped, so make switch refuses to run until then.
  2. make switch
  3. Restart the sound services so PipeWire loads the new graph: herd restart wireplumber; herd restart pipewire, or log out and in. Then herd start camera-denoise.
  4. Roll back with sudo guix system roll-back, or pick the previous generation in GRUB.
  5. Undo the Chrome override with flatpak override --user --unset-env=LIBVA_DRIVERS_PATH com.google.Chrome.
  6. If the AVD misbehaves at boot, add module_blacklist=apple_avd to the kernel line in GRUB.
