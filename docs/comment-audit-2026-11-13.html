Workaround plan

Each group is ranked by value, then by risk.

Delete: the cause is gone

1. Drop the Guix channel hold

Where: desktop/bin/updates line 59 (channel-holds)

Why: Guix is held at 704ad8ce because rde's node packages used node-bootstrap, which Guix removed. rde 7d7cdce2 (2026-11-08) reworked them, and the pinned rde 9300ace7 no longer names node-bootstrap anywhere (git grep found no matches).

Do: Delete the entry, run updates apply for guix and make prebuild. The builder checks whether rde evaluates against the Guix head.

Value: High: unblocks Guix updates, which have been pinned since 2026-10-26. Risk: Medium: the symbol is gone (verified), but whether nothing else breaks is inferred until the builder evaluates it.

2. Remove reload shims for Emacs state from before 2026-11-09

Where: desktop/configs/doom/agent-shell.el line 1283 (the evil C-c C-c clearing only), line 1389 (workflow side panel cleanup); desktop/configs/doom/bbh-super.el line 1380, line 1459 (preview kill and the non-org Inbox branch); their tests in desktop/build/bbh/test/agent-shell-test.el lines 71, 388 and 993

Why: They upgrade buffers that older code built: the side panel was removed 2026-11-06, C-c C-c stopped sending 2026-11-09 (T125), and the Inbox became org 2026-11-08. The live bbh-super daemon started 2026-11-13 09:41, so it holds none of those buffers.

Do: Delete the shims, their comments and the three test cases. Keep the generic reload code that brings live buffers up to the current code.

Value: Medium: about 30 lines of code and 3 tests. Risk: Low. A GUI Emacs still running since before 2026-11-09 would keep a stale C-c C-c until restart (inferred that none is running).

3. Drop the folds for retired super events

Where: desktop/build/bbh/src/bbh/super/model.clj line 889 (:thread-linked) and line 893 (:worker-attached)

Do: Delete both defmethods and their comments. First confirm that replay never reads past the newest snapshot, and update the tests that build old logs (super_test, super_store_test).

Value: Low to medium. Risk: Low to medium: tests and fixtures may still use these events.

Refactor

1. Replace the T137 flatpak desktop-entry copy with FLATPAK_BINARY

Where: modules/engstrand/features/desktop.scm line 84 (%home-flatpak-desktop-entries, about 40 lines of activation)

Why: Flatpak 1.18.4 reads FLATPAK_BINARY when it writes the Exec line of an exported entry (the string sits next to its %s run --branch format in .flatpak-real and libflatpak). If FLATPAK_BINARY points at /run/current-system/profile/bin/flatpak, flatpak writes stable paths itself, and Home no longer needs to shadow its entries.

Do: Set FLATPAK_BINARY for user installs (Home environment) and for the D-Bus-activated flatpak-system-helper (system installs). Re-export with flatpak update, check Exec=, then delete the activation copy and its copies under ~/.local/share/applications.

Value: Medium: removes a stateful activation hack. Risk: Medium: whether the system helper sees the variable is inferred. Keep the copy until Exec= is verified after a guix gc.

2. Retire the bbh super version 1 store migration

Where: desktop/build/bbh/src/bbh/super/store.clj lines 36-77, model.clj line 852 (the [:snapshot 1] upcast)

Why: The live store is at user_version 2, and its only snapshot is the version 1 one written by the migration, so the upcast still runs on every replay. Writing a fresh version 2 snapshot would make both the migration and the upcast dead code.

Do: Write a version 2 snapshot (store/snapshot!), confirm that the replay matches, then delete v1-tables, v1-state, migrate-v1!, the upcast entry and the v1 tests. Archive super.db.v1.bak (11.9 MB) outside the data directory.

Value: Medium: about 60 lines and a class of tests. Risk: Medium: this is the controller's source of truth. Take a backup and stop the controller during the snapshot.

3. One kernel rebuild for three kernel workarounds

Where: modules/engstrand/system/bootloader.scm line 17 (keyd name), modules/engstrand/features/tailscale.scm line 29 (legacy iptables), modules/engstrand/system/asahi.scm line 164 (LZO-only zram)

Why: The running 7.2.15-asahi kernel has CONFIG_NF_TABLES_INET unset and only CONFIG_ZRAM_BACKEND_LZO (read from /proc/config.gz). The kernel is already customized for uinput, and renaming it rebuilds it anyway.

Do: In the same customize-linux call, rename asahi-linux-keyd, enable NF_TABLES_INET (with nft for tailscale) and ZRAM_BACKEND_ZSTD. Then drop TS_DEBUG_FIREWALL_MODE=iptables and the lzo zram setting, together with their comments.

Value: Medium: three workarounds, one build. Risk: Medium to high: a kernel rebuild on the builder and a reboot, with the old generation as fallback. That the options build cleanly on the Asahi tree is inferred.

4. Consolidate the reload-into-live-buffers blocks

Where: desktop/configs/doom/agent-shell.el lines 1072 and 1416, desktop/configs/doom/bbh-super.el line 1458

Why: Three top-level blocks re-run setup in live buffers on a Doom reload, and each carries its own comment. One-off migrations were mixed into them, which is how the dead shims above accumulated.

Do: Put them in one eng/bbh-refresh-live-buffers function with one comment, called at the end of bbh-super.el. Put any future one-off migration there with a remove-after date.

Value: Low to medium. Risk: Low: agent-shell-test.el covers reloads.

5. Share one procfs reader

Where: desktop/build/bbh/src/bbh/super/process.clj line 24, desktop/build/bbh/src/bbh/super/sessions.clj line 17

Why: Both explain that slurp reads procfs as empty, and both work around it in their own way.

Do: Use one proc-bytes helper with one comment, called from both.

Value: Low. Risk: Low.

6. dusk on a newer Rust and GPUI (defer)

Where: desktop/build/dusk/Cargo.toml line 9, desktop/build/dusk/src/core.rs line 349

Why: GPUI is pinned to the last Zed revision that built with Guix's rust 1.93. The pinned Guix now also has rust-1.96, though the default rust is still 1.93 (verified in gnu/packages/rust.scm). A newer GPUI may fix the Wayland resize panic that core.rs works around (inferred).

Do: Only when you want GPUI fixes: point dusk's manifest at rust-1.96, move the Zed rev forward, and retest the resize workaround.

Value: Low now. Risk: High: GPUI API churn.
