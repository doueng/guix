Answer

Goal: a Rex client you can change and rerun in seconds, without Rust's compile times.

1. Babashka and a Chrome app window running xterm.js, over a tiny native core. I built a spike that streams a real Rex pane into xterm.js. bb holds the Rex connections, a 45-line C filter uses libghostty-vt to turn Rex's Ghostty snapshot into plain VT, and the page is 41 lines of JS. A key takes 16.6 ms (median) to show up on screen, and 200,000 lines render in 0.59 s measured. Changes reload with no build: bb starts in about 12 ms, and a JS edit takes a page reload. The C core compiles in 0.7 s and should rarely change measured. rexmux's bb sidecar moves in as it is. Only the rules in model.rs need porting.
2. Clojure on the JVM, as the same design without the C. Java's FFM API calls libghostty-vt directly from Clojure (0.42 s for the whole run, 26 ms of it decoding and formatting) measured. It's the fallback if the bb process ever needs libghostty in-process. Most bb code runs on it unchanged.
3. Emacs, with eat panes. It works with the same pane process. Keys take 12–27 ms and 200k lines take 3.4 s, about 6× slower than xterm.js measured. It is the most hot-reloadable option and gets M-x and which-key for free. But it would put a busy terminal on Emacs's single thread, and its terminal fidelity is lower.
Not now: Jolt. Its FFI did call libghostty-vt here and produced the same output, but a run took 7.9 s in source mode measured. It still has no Unix sockets and no GUI path, and no Linux aarch64 release (T201, inferred). Guile was the surprise: its FFI ran the same decode in 28 ms total measured. But Guile has no terminal widget, so the renderer would be yours to write.

On compile time: today a one-line Rust change costs 12–14 s to rebuild, and a clean build or a GPUI bump costs 7 min 47 s measured. The recommended hybrid's only native piece is the 45-line C file, at 0.7 s, plus libghostty-vt.so, which Guix would build once per Ghostty bump. So it saves essentially all of the compile time, not just most of it.

What actually needs native code

Rex's API is JSON over a WebSocket on a Unix socket. Any language with sockets can speak it: bb did, with a 64-line hand-written WebSocket client (rexws.clj) measured. The one hard part is the pane data stream. It starts with a Ghostty snapshot, which Rex's docs say is meant for terminal emulators built on Ghostty (/llms.txt, The Terminal Stream). After the snapshot it's ordinary VT plus ESC _ rex1;nonce;json ESC \ messages. So a client needs libghostty-vt in one of three ways:

  • A filter process: rex-vt decodes the snapshot, writes it back out with libghostty's own VT formatter (screen, palette, modes, cursor), then passes the stream through. Any terminal can then draw the pane: xterm.js, eat, vterm, even Ghostty itself measured.
  • FFI to libghostty-vt.so: measured working from the JVM (FFM), Guile and Jolt measured. SBCL, Racket and Janet have comparable FFIs inferred. bb has none.
  • WASM: libghostty-vt ships a wasm.h API, and ghostty-web 0.4.0 (coder, updated 2026-11-18) is an xterm.js-compatible terminal built on it measured (npm view). It could decode snapshots in the page and drop the C filter. Its snapshot support is untested guess.

Rex can also listen on TCP (--extra-listen http://127.0.0.1:PORT). But a plain TCP listener needs --allow-anonymous, which gives every local connection full access. So the browser should not talk to Rex directly. Keep the Unix socket, with its peer-credential check, and let bb bridge to it inferred.

Ranking

  1. bb + Chrome app window + xterm.js, with rex-vt on a Guix-built libghostty-vt. Fastest loop, the best measured rendering, the most reuse, and Bombadil's native target (web and terminal UIs). Swap in ghostty-web later to get Ghostty's own emulation in the page.
  2. The same on Clojure JVM with FFM, if bb hits a wall, such as needing libghostty's render state in-process for selection or search.
  3. Emacs + eat as a second front end on the same pane process, for the 'Rex inside Emacs' workflow. Not as the main window.
  4. Guile, then SBCL: good FFI and live coding, but you'd write a terminal renderer.
  5. Neovim/Fennel, Racket, Janet: viable, but nothing here favours them.
  6. Jolt: track it. Revisit when it ships aarch64 builds, Unix sockets and a GUI or webview story.

Migration from rexmux

  1. Package libghostty-vt in Guix next to modules/engstrand/packages/ghostty.scm (it already builds Ghostty with zig-0.17). Then add rex-vt as a small package. Both come from substitutes after that.
  2. Grow the sidecar into the client process. The bb process opens Rex itself (rexws replaces the per-call rex api call CLI in sidecar/rexmux/rex.clj) and serves the page. The EDN-lines link to Rust goes away, and so does the link part of Rexmux.tla. The streams and agents parts stay.
  3. Port model.rs (1447 lines with tests) to Clojure, as pure functions from keys and events to effects, as it already is in Rust. Keep a text renderer like screen.rs, so the Bombadil tty specs keep working while you add a Bombadil web spec.
  4. Page: one xterm.js per visible block, layout from session.view in CSS grid, minibuffer and which-key in HTML, fit addon for resize, search addon for copy-mode search. Port tiny fingers' regexes from hints.rs.
  5. Ship it as a third mux value (make mux MUX=rexweb), with Herdr staying the default. Walk docs/rex-parity.html item by item. Retire the Rust window once it matches.
  6. Later: try ghostty-web for in-page snapshot decoding and drop rex-vt.

Risks and open questions

  • Browser keys: Ctrl+W/T/N reached the shell in an app window measured. Ctrl+Shift+I, Ctrl+L, F11 and Alt menus are untested guess. Hyprland or kanata can remap any that leak.
  • Two languages: the page is JS. Scittle or squint keep it Clojure without a build inferred, or keep the page a dumb renderer and put all logic in bb.
  • Chrome is a flatpak here. A Guix ungoogled-chromium or WebKitGTK window would make it reproducible. Each needs a check of its WebGL and latency guess.
  • Fidelity: xterm.js isn't Ghostty. Kitty keyboard protocol and graphics differ, which matters for pi and jjui inferred. ghostty-web is the way out.
  • Data connection reuse: Rex allows one data connection per client per block. A bridge must close the Rex stream when its page goes away; the spike didn't, and a second page got nothing measured.
