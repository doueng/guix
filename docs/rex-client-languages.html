Answer

Goal: a Rex client you can change and rerun in seconds, without Rust's compile times.

Updated by W258. You asked why xterm.js and why not Ghostty. Measured, Ghostty wins, so the first pick changed. See Why xterm.js, and why not Ghostty?

1. Babashka with Ghostty itself as the window. Each Ghostty tab runs rex-attach, which attaches to one Rex block through rex-vt (libghostty-vt). A bb sidecar opens tabs with ghostty +new-tab over D-Bus and draws hints and menus in-band. Ghostty is 78 MB and about 1% CPU at idle. Keys reach the pty in 0.8–2.4 ms, and Ghostty renders the pane fully, with true colour, ligatures and Kitty protocols measured. There's no GUI code of our own, so every edit is bb or Ghostty config.
2. Emacs with Ghostel, if you want the client's UI in Emacs. Ghostel puts libghostty-vt in Emacs. With the same rex-attach it measured 3.8–6.6 ms per key and 200k lines in 0.15 s, at about 104 MB measured. You get which-key, M-x and windows for free. It needs a GUI Emacs for images, since yours is emacs-no-x.
3. rexmux with its GPUI core frozen. It already matches Herdr. Moving model.rs into bb would leave Rust only for new kinds of UI.
Demoted: bb + a Chrome app window + xterm.js (W256's first pick). It works and the loop is fast, but a Chrome instance costs 400–430 MB and 6–8% of a core at idle measured. xterm.js itself is only 289 KB. ghostty-web doesn't help: same Chrome, and 33–37% of a core at idle. Clojure JVM with FFM is still the fallback if libghostty is ever needed in-process. Jolt: not yet.

On compile time: today a one-line Rust change costs 12–14 s to rebuild, and a clean build or a GPUI bump costs 7 min 47 s measured. Options 1 and 2 have one native piece, rex-vt.c, which compiles in 0.2–0.7 s, plus libghostty-vt.so, which Guix builds once per Ghostty bump. So they save essentially all of the compile time.

Why xterm.js, and why not Ghostty?

Added by W258 after you asked this. Every number below comes from a spike outside the repo: a throwaway Rex server (0.1.0-preview.21), one bash block, each frontend on the hidden test display, three runs each unless noted. Raw data and code are in the W258 evidence directory listed under Sources.

The honest reason

W256 was asked which language to use, and bb has neither a GUI toolkit nor an FFI. A Chrome app window running xterm.js was the quickest way to give bb a window with no build step. Weight was not a criterion, and nobody measured it. I have now. The heaviness you suspected is real, but it comes from Chrome, not from xterm.js:

  • xterm.js itself is small: a 289 KB bundle plus 5.5 KB of CSS, and 10–12 MB of JS heap after the bench measured.
  • Chrome is the cost: one Chrome app instance is 23 processes and 402–429 MB of PSS (1.56 GB of RSS, much of it shared). It uses 6–8% of a core while the pane sits idle measured. Each run used a fresh profile, so this is a cold start. Opening the window in a Chrome you already have running would add only a renderer. I didn't test that, because it would mean touching your own Chrome guess.
  • Startup: 0.53–0.91 s from launch to the first painted pane measured.
  • Latency is fine: a key reaches the next painted frame in 16.3–16.5 ms (median), the same as before. That number is limited by the frame rate: the fastest samples are 3.2–5.9 ms, so the data path itself is a few ms measured.
  • The bb bridge adds about 51 MB and rex-vt about 7 MB. rex-vt was 73 MB in W256's spike because it never freed the decoded snapshot. Freeing it takes three lines measured.

Each bar counts the frontend's processes (PSS, which splits shared pages fairly) plus the Rex glue it needs. rexmux's glue is its bb sidecar and a rex child. Herdr today, for reference: its Ghostty window is 15 MB and herdr is 26 MB. Part of both is swapped out, so the real figures are higher measured.

The options

(a) The Ghostty app as the frontend: the best fit. In this spike, Ghostty runs rex-attach, a 70-line bb script, in each tab. It attaches to one Rex block, sends the stream through rex-vt to stdout, and sends Ghostty's keys to Rex. There is no GUI code of our own.
  • Asahi Guix: already installed and running Herdr. OpenGL 4.6 on Mesa measured.
  • Fidelity: you get Ghostty itself. The screenshot shows true colour, bold, italic and ligatures (-> != ===) through Rex measured. The pane's bytes pass through untouched, so Kitty graphics and the Kitty keyboard protocol reach Ghostty, and rex-vt's formatter restores the keyboard flags on attach inferred. Images already on screen when you attach are not re-sent, because the formatter has no image extra inferred.
  • Edit-to-run loop: all bb plus Ghostty config. Rerunning an attach costs about 0.4 s, and reload_config applies new keybinds live. Recompiling rex-vt takes 0.19 s measured.
  • Rex control: ghostty +new-tab --class=… --title=… -e rex-attach … opens a titled tab over D-Bus in 36 ms, in a private Ghostty instance that leaves your normal Ghostty alone measured. One catch: the instance must start with --command, since -e turns single-instance off (Config.zig) measured. Ghostty has no command for opening splits or switching tabs from outside, only +new-window and +new-tab. So Super+Return/E/D/G go through Ghostty keybinds such as goto_tab, reached with Hyprland's sendshortcut inferred.
  • Herdr parity: startup tabs work through +new-tab measured. Agent status can go in tab titles (OSC 2), and desktop notifications through OSC 9/777 inferred. Copy, search, selection and mouse are Ghostty's own inferred. Tiny fingers, which-key and the minibuffer would be drawn by rex-attach on the alternate screen: read the screen, draw the labels, take the key, then reattach for a fresh snapshot. That's bb work, maybe a few days guess. Ghostty's 1.4 key tables (activate_key_table) can hold the Ctrl+b leader. Splits are the weak spot. Ghostty makes a split from a keybind, and the new split's command can ask the sidecar for a fresh Rex split. But nothing can rebuild a split layout from outside, so after a reboot splits would come back as tabs inferred.
  • Work and costs: each tab here runs its own bb, at about 51 MB. One bb sidecar daemon plus a small C relay per tab (rex-vt with a socket, about 7 MB) fixes that inferred. Terminal queries also need filtering. With Ghostty attached, a device-attributes query got two replies (\E[?62;22c\E[?62;22;52c), one from Rex's terminal and one from Ghostty, and the Kitty keyboard query got two as well measured. The xterm.js and Ghostel designs share this problem, since every passthrough frontend answers queries too inferred.
(b) libghostty-vt through FFI from a dynamic language. Guile's FFI ran the snapshot decode in 28 ms (W256), and Guix has guile-sdl2, guile-gi, sbcl-cffi, sbcl-sdl2, sbcl-cl-cffi-gtk and janet for aarch64 measured (guix package -A). But libghostty-vt only hands you render state: render.h (27 calls) gives you rows, cells and colours, and kitty_graphics.h (17) gives you images. The font shaping that makes ligatures, the glyph atlas, the cursor, selection, IME and image placement are all yours to write. That's weeks before it matches Ghostty guess. Jolt still lacks sockets and a GUI.
Except Emacs, where it's already done: Ghostel is an Emacs terminal built on libghostty-vt, with Kitty keyboard and graphics according to its README. It is on MELPA and ships a prebuilt aarch64 Linux module. Running rex-attach in it measured 3.8–6.6 ms per key, 200k lines in 0.14–0.19 s and about 104 MB for the whole Emacs. That's the fastest key path here, 20× eat's throughput, and idle at about 0% measured. Emacs gives you which-key, M-x, a minibuffer, tab-bar and windows for free. Tiny fingers could be avy over the buffer text inferred. The catches: your Emacs is emacs-no-x running inside a terminal, so images need a separate pgtk Emacs, and a busy pane shares Emacs's single thread measured (running processes) / inferred.
(c) ghostty-web instead of xterm.js: not now. It's a drop-in replacement: the same page needed only a few changed lines. It renders the same 200k lines a little faster and with Ghostty's parser. But it uses a third of a core while idle, still needs all of Chrome, and its WASM has no snapshot decoder, so rex-vt stays measured. Its renderer is Canvas 2D, and its type definitions show no image API inferred. It removes none of the weight you objected to.
(d) Freeze rexmux's GPUI core and move the behaviour into bb. It already has Herdr parity (docs/rex-parity.html) and runs at 128–136 MB plus a 62 MB sidecar measured. To freeze it, model.rs (1447 lines) would move into bb, and the Rust side would keep only panes and a generic overlay protocol: one more Rust refactor, after which most edits are bb reloads inferred. Any new kind of UI still costs a 12–14 s rebuild, and a GPUI bump costs 7 min 47 s. Its renderer draws cells as GPUI text runs (gui.rs), with no image code, so fidelity stays below Ghostty's inferred.

So

For your setup, Ghostty is the lighter and better frontend. With rex-attach it is 5× smaller than Chrome, effectively idle, as fast or faster, and fully faithful, and it's already installed. What it lacks is room for our own drawing. Hints, which-key and the minibuffer have to be drawn in-band, and splits can't be rebuilt from outside. The language answer doesn't change: everything you edit is still bb, plus Ghostty config.

What actually needs native code

Rex's API is JSON over a WebSocket on a Unix socket. Any language with sockets can speak it: bb did, with a 64-line hand-written WebSocket client (rexws.clj) measured. The one hard part is the pane data stream. It starts with a Ghostty snapshot, which Rex's docs say is meant for terminal emulators built on Ghostty (/llms.txt, The Terminal Stream). After the snapshot it's ordinary VT plus ESC _ rex1;nonce;json ESC \ messages. So a client needs libghostty-vt in one of three ways:

  • A filter process: rex-vt decodes the snapshot, writes it back out with libghostty's own VT formatter (screen, palette, modes, cursor), then passes the stream through. Any terminal can then draw the pane: xterm.js, eat, vterm, even Ghostty itself measured.
  • FFI to libghostty-vt.so: measured working from the JVM (FFM), Guile and Jolt measured. SBCL, Racket and Janet have comparable FFIs inferred. bb has none.
  • WASM: libghostty-vt ships a wasm.h API, and ghostty-web 0.4.0 (coder, updated 2026-11-18) is an xterm.js-compatible terminal built on it measured (npm view). It could decode snapshots in the page and drop the C filter. Its snapshot support is untested guess.

Rex can also listen on TCP (--extra-listen http://127.0.0.1:PORT). But a plain TCP listener needs --allow-anonymous, which gives every local connection full access. So the browser should not talk to Rex directly. Keep the Unix socket, with its peer-credential check, and let bb bridge to it inferred.

Ranking

  1. bb + the Ghostty app (rex-attach per tab, a bb sidecar daemon, ghostty +new-tab, Ghostty key tables), with rex-vt on a Guix-built libghostty-vt. It has the lightest footprint of the GUI options, full Ghostty fidelity, no GUI code, and it's already installed.
  2. Emacs + Ghostel on the same rex-attach: the fastest measured key path, with Emacs UI for free. Use it as a second frontend, or as the main one if you move to a GUI Emacs.
  3. rexmux with the GPUI core frozen and its behaviour in bb: the safe fallback that already has parity.
  4. bb + Chrome app + xterm.js: only if you want a web UI. ghostty-web: not until it stops redrawing every frame.
  5. Clojure JVM with FFM, if libghostty is ever needed in-process. Guile, then SBCL: good FFI, but you'd write a renderer.
  6. Jolt: track it. Revisit when it ships aarch64 builds, Unix sockets and a GUI or webview story.

Migration from rexmux

  1. Package libghostty-vt in Guix next to modules/engstrand/packages/ghostty.scm, which already builds Ghostty with zig-0.17. Then add rex-vt as a small package, freeing the snapshot once it's written out (73 → 7 MB).
  2. Grow the sidecar into a daemon that holds the Rex connections (rexws replaces the per-call rex api call CLI in sidecar/rexmux/rex.clj). Port model.rs (1447 lines with tests) to Clojure as pure functions from keys and events to effects.
  3. rex-attach: a small relay per tab that the daemon feeds (rex-vt with a socket), so tabs don't each pay for a bb process. It must drop the frontend's replies to terminal queries, because Rex's terminal already answers them.
  4. Ghostty config for a private class (say dev.engstrand.Rex, started with --command): key tables for the Ctrl+b leader, goto_tab keys for Super+Return/E/D/G, and a command for new splits that asks the daemon for a Rex split. Startup tabs come from ghostty +new-tab --title.
  5. In-band UI: tiny fingers, which-key and the minibuffer drawn by rex-attach on the alternate screen, reusing the regexes from hints.rs. Agent status goes in tab titles, and attention in OSC 9/777 notifications.
  6. Ship it as a third mux value (make mux MUX=rexghostty), with Herdr staying the default. Walk docs/rex-parity.html item by item. Retire the Rust window once it matches. Ghostel can attach to the same daemon whenever you want Rex inside Emacs.

Risks and open questions

  • Double replies to queries: every passthrough frontend (Ghostty, xterm.js, Ghostel) answers queries that Rex's terminal also answers. With Ghostty attached, a DA query got two replies measured. rex-attach must filter them.
  • Ghostty has no split or tab-switch IPC, only +new-window and +new-tab measured (ghostty +help). Split layouts can't be rebuilt from outside after a reboot. kitty or WezTerm are the same design with full split IPC inferred.
  • In-band overlays (hints, which-key) take over the pane's screen for a moment and must restore it from a fresh snapshot. That's untested guess.
  • Browser keys: Ctrl+W/T/N reached the shell in an app window measured. Ctrl+Shift+I, Ctrl+L, F11 and Alt menus are untested guess. Hyprland or kanata can remap any that leak.
  • Two languages: the page is JS. Scittle or squint keep it Clojure without a build inferred, or keep the page a dumb renderer and put all logic in bb.
  • Chrome is a flatpak here. A Guix ungoogled-chromium or WebKitGTK window would make it reproducible. Each needs a check of its WebGL and latency guess.
  • Fidelity: xterm.js isn't Ghostty. Kitty keyboard protocol and graphics differ, which matters for pi and jjui inferred. ghostty-web is the way out.
  • Data connection reuse: Rex allows one data connection per client per block. A bridge must close the Rex stream when its page goes away; the spike didn't, and a second page got nothing measured.
