Guix, from the ground up

Fifteen short steps, each built only on the ones before. Every example is your own MacBook, checked on 25 November 2026, and every command only looks.

1. A program is a file that needs other files

A program is a file. It rarely works alone. It loads other files when it starts: libraries of shared code, and sometimes data or other programs.

Ask jq, the JSON tool, what it loads:

ldd $(readlink -f $(which jq))
libonig.so.5 => /gnu/store/3sgrw…-oniguruma-6.9.10/lib/…
libc.so.6    => /gnu/store/0mcy4…-glibc-2.41/lib/…
…

jq needs oniguruma, a library that matches patterns, and glibc, the C library almost every program needs. If either file is missing or wrong, jq does not start. The long /gnu/store/… folder names look odd. Step 3 explains them.

So: a program is a file plus a list of other files it needs to run.

2. Why installing things usually breaks

Most Linux systems put every program's libraries in the same shared folder, /usr/lib. A name there holds one file. There is one /usr/lib/libonig.so.5, full stop.

Now say app A was built for oniguruma 6.9 and app B wants 7.0. Installing 7.0 for B overwrites the one file A used. A breaks, and nothing warned you.

Upgrades add a second problem. An upgrade overwrites hundreds of files, one by one. Lose power halfway and you have half the old system and half the new. There is no undo, because the old files are gone.

So: the trouble is a shared folder where each name holds one file, and changes that overwrite files in place.

3. Folders that never change

Guix fixes both with one rule. Each program and each library gets its own folder under /gnu/store. Once a folder is written, nothing ever changes it. Guix may delete it much later, but never edits it. That folder of folders is the store.

ls /gnu/store | grep -- '-jq-1.8.2$'
0cs828z5in82ib1ml1rmv1vnima0j3p8-jq-1.8.2
dngb583q608v3acma2xd9smls2cyghpp-jq-1.8.2
x8g0a13kma26kca8f5a1w6f0n54jyp65-jq-1.8.2

Your store holds three copies of jq 1.8.2 side by side. Each name starts with a different 32-character code, so they never collide.

Look again at step 1. jq does not ask for “some libonig”. It names one exact folder, 3sgrw…-oniguruma-6.9.10. Nobody can swap that file under it, because that folder never changes.

So: each build of each thing lives in its own folder that never changes, and programs name those folders in full.

4. A name that is a fingerprint

Where does the code at the front of a name come from? Before Guix builds anything, it writes down exactly how: every input by its full store name (the compiler, the source code, oniguruma, glibc), the build script and its settings. That is the recipe. Guix calls it a derivation and saves it in the store as a .drv file.

head -c 400 $(guix build -d jq)
Derive([("out","/gnu/store/0cs828z5…-jq-1.8.2","","")],
       [("/gnu/store/1sfgckrz…-diffutils-3.12.drv",["out"]),
        ("/gnu/store/3bicy7zl…-sed-4.9.drv",["out"]), …

The recipe already names its result, 0cs828z5…-jq-1.8.2. That code is a hash of the recipe: a short fingerprint computed from every byte of it. Change one byte and the code comes out completely different.

Inputs are named by their store names, and each of those holds the hash of its own recipe. So jq's code covers its whole tree of inputs, all the way down.

That explains your three copies. Ask each which folders it points at:

guix gc --references /gnu/store/0cs828z5…-jq-1.8.2
/gnu/store/0mcy4…-glibc-2.41
/gnu/store/3sgrw…-oniguruma-6.9.10
…

The same command on the other two finds b34sh…-glibc-2.41, another build of the same glibc version, and nhphq…-glibc-2.44-57, a newer glibc. Same jq source, different inputs, so different recipes and different names.

So: a store name is a fingerprint of the whole recipe, so two different recipes never share a folder.

5. Building in a sealed room

A recipe is worth something only if it is complete. If the build script could quietly read /usr/lib or download a file, the result would depend on something the recipe leaves out.

So a background program, the Guix daemon, runs every build in a sealed room. Inside, the build:

  • sees only the inputs the recipe lists,
  • has no network, except to fetch source whose hash the recipe already holds,
  • runs as a throwaway user, and every file is dated 1970.

The build writes into the folder the recipe already named. When it ends, the daemon makes that folder read-only and scans it for store names written inside. Those names are its references, the list guix gc --references printed in step 4. That is how Guix knows jq needs glibc without anyone telling it.

So: the sealed room lets in only what the recipe lists, so the recipe really is everything that went in.

6. Download instead of build

The room is sealed, so the result depends only on the recipe. The same recipe built on another computer gives the same folder, nearly always bit for bit.guix challenge tests this by comparing your builds with the servers' builds.

The name is known before the build starts, because it comes from the recipe. So your daemon first asks a server: do you already have 0cs828z5…-jq-1.8.2? If so it downloads the finished folder, checks the server's signature, and puts it in the store. That download is a substitute, and a server that hands them out is a binary cache.

Your daemon asks three, in this order:From the daemon's own command line, ps -o args= -C guix-daemon. guix-builder, your Hetzner build machine on Tailscale; then bordeaux.guix.gnu.org; then ci.guix.gnu.org.

So: the name decides the result, so anyone who already built that name can hand you the folder.

7. Recipes written for people

A .drv lists hundreds of store names. Nobody writes that by hand. You write a package: a short description in Scheme, the language Guix itself is written in. Guix turns it into the .drv.

Your own kernel, trimmed, from /home/engstrand/guix/modules/engstrand/asahi/kernel.scm

(define %version "7.2.15")
(define %revision "1")
(define %hash "0w1kb68ki0fcdg7h9x6qqmbgmw2n2yq8wj1hcicp5gb8dipkk9g3")

(origin                         ; where the source comes from
  (method git-fetch)
  (uri (git-reference
        (url "https://github.com/AsahiLinux/linux")
        (commit tag)))          ; asahi-7.2.15-1
  (sha256 (base32 %hash)))      ; what the download must hash to

(package
  (inherit base)                ; start from Guix's own kernel
  (native-inputs … clang-19 rust rust-bindgen-cli …)
  (home-page "https://asahilinux.org"))

It says what a recipe says, in friendly words. The source comes with its hash, so the download is checked. Inputs are named by variable, such as rust, not by store name. Each input is a package too, so Guix walks the whole tree and writes a .drv for each.

Step 4 now tells you what a version bump does. Change %version and the recipe changes, so the name changes, so the new kernel lands in a new folder. The old kernel's folder is untouched.

One more kind of code appears in the file, starting with #~(. It does not run when Guix reads the file. Guix saves it into the recipe, and it runs later, inside the sealed room.Guix calls this a G-expression. Inside one, #$ drops in a value from outside, such as a store name.

So: a package is a recipe written for people, and Guix turns it into the exact .drv the daemon builds.

8. Fixing one library fast

Steps 4 and 7 have a cost. Change something low down and every name above it changes, and each new name is a new build.

Most days that is fine. Now say a security hole turns up in openssl, the library that encrypts network traffic for almost every program. Ask how much sits on top of it:

guix refresh -l openssl
Building the following 7653 packages would ensure
27385 dependent packages are rebuilt

Rebuilding 27,385 packages takes the build farms days. The fix should reach you today.

So Guix builds only the fixed openssl. Then, for each package that points at the old openssl, it copies the finished folder and swaps the old store name for the new one wherever it appears inside. Nothing is compiled. It is find-and-replace on bytes. This is a graft.

It works because of step 5. Guix already finds what a package needs by scanning it for store names, so it knows where every name sits.

The new name must be exactly as long as the old one, since shifting any byte in a compiled program breaks it. The hash part is always 32 characters, so the rest must match too: openssl-3.5.7 and openssl-3.5.9 are both 13.

One graft is live on your laptop. Your pinned Guix has this in its openssl file, trimmed:/home/engstrand/.config/guix/current/share/guile/site/3.0/gnu/packages/tls.scm lines 549 and 676

(define-public openssl-3.5
  (package
    (name "openssl")
    (version "3.5.7")
    (replacement openssl-3.5/fixed)   ; the graft
    …))

(define-public openssl-3.5/fixed
  (hidden-package
   (package
     (inherit openssl-3.5)
     (version "3.5.9") …)))

The replacement line is the whole switch. Everything is still built against 3.5.7, and Guix grafts 3.5.9 in its place. See both forms of mit-krb5, which uses openssl. --dry-run only prints the name, and --no-grafts turns grafting off:

guix build --dry-run --no-grafts mit-krb5
guix build --dry-run mit-krb5
/gnu/store/lbbq1g41dr994hh8yq95p7bc0p5qqdkw-mit-krb5-1.21
/gnu/store/3znk1rfg7qiqg0wkcxn3zinrc8ww5l8y-mit-krb5-1.21

Both are in your store. Ask each which openssl it points at:

guix gc --references /gnu/store/lbbq1g41…-mit-krb5-1.21 | grep openssl
guix gc --references /gnu/store/3znk1rfg…-mit-krb5-1.21 | grep openssl
/gnu/store/4xfdcm3ca7s72dcy59vg43v5ifpx0b1g-openssl-3.5.7
/gnu/store/xfzy3rq2lyi4h9jj342az01mc73mjc6y-openssl-3.5.9

The two copies of its TLS plugin, lib/krb5/plugins/tls/k5tls.so, are both 199,120 bytes. cmp -l finds 64 bytes that differ, all inside two names: openssl's, and mit-krb5's own, since the copy has a new name too.

Grafts climb. curl does not load openssl itself, but it uses mit-krb5, so curl gets a grafted copy too, x9b7p…-curl-8.21.0. Even your own kernel, mb9wq…-linux-asahi-7.2.15-1, is a grafted copy: it keeps a reference to rust, and rust leads down to openssl.

Where a graft is still to be made, Guix says so:

guix build --dry-run socat
The following graft would be made:
   /gnu/store/dpx6b83arq6z5s8an0nd79qiwn57hrsn-socat-1.7.4.4.drv

A graft is a recipe like any other. That .drv takes the normally built socat and the fixed openssl as inputs, and its job is to copy and swap, so step 6 holds: same inputs, same bytes.

What changes is the meaning. The grafted mit-krb5 was compiled against 3.5.7, and nobody compiled it against 3.5.9. That is safe only because 3.5.9 is a bug-fix release with the same interface.The Guix manual requires the two to be binary-compatible, with the same SONAME. The Guix developers decide when to graft, and keep it for small fixes like this one.

So: a graft gets a fix out today by copying each package above it and swapping one store name for another of the same length.

9. What a graft costs, and when it goes away

A graft is a stopgap. It has costs and limits, and it is meant to be replaced.

It costs time at install. Every grafted copy is a full copy, made and scanned on your laptop, because the caches hold only normal builds./home/engstrand/.config/guix/current/share/guile/site/3.0/guix/grafts.scm line 156 marks graft recipes #:local-build? #t and #:substitutable? #f. That is why make switch after make pull keeps printing applying … graft lines after the downloads end, even when guix-builder built everything ahead of time. The ungrafted folders stay in the store too, until step 12 cleans up.

It reaches only what Guix built:

Still holds the old opensslWhy
a binary from cargo build, pip, npm or NixGuix never built it, so never scans it
a program linked to openssl-3.5.7-staticit holds openssl's code, not a name to swap
a name inside a compressed filethe scan finds only names written plainly
anything built with --no-graftsright for debugging, wrong for daily use

The proper fix still comes. A change that would rebuild more than 300 packages goes to a separate branch, where the build farm rebuilds everything above it. There openssl becomes 3.5.9 for real and the replacement line goes. Once that branch is merged, a pull brings packages compiled against the fixed openssl. No copies, no swaps.

Is your graft still needed? Yes, on the Guix you run now. Your pinned commit, 704ad8c, still has the replacement line, so every package that uses openssl 3.5 gets 3.5.9 by graft, and nothing your machine runs has 3.5.7 in it. The graft carries real fixes: its commit, 66bdd5b0 of 30 September, lists 13 CVEs fixed between 3.5.7 and 3.5.9, the worst rated High. Removing it by hand on this commit would bring them back.openssl-3.0 (3.0.19, used only by ntp) and openssl-1.1 have no replacement.

On 24 November it accounted for 211 grafted copies on your machine. 35 load openssl directly, such as python, git, openssh, mit-krb5, qtbase, node and rust. The rest sit above those.Counted in T226 with guix gc -R, --references and --derivers.

Upstream has already rebuilt. Commit a310ed3e, “gnu: openssl: Ungraft.”, makes 3.5.9 the plain openssl and deletes openssl-3.5/fixed. It reached master on 21 November. After your next make pull and make switch you download packages built against 3.5.9, and nothing needs the 211 copies any more; step 12 shows how they go. guix weather after the pull shows whether the downloads are ready.

So: a graft costs time and reaches only what Guix built; a full rebuild replaces it, and yours arrives with the next pull.

10. One folder that makes the store look normal

Everything so far sits in folders with unreadable names, yet you just type jq. How does that find 0cs828z5…-jq-1.8.2?

Through a profile: a folder of links, each pointing into a store folder. Your shell's PATH includes ~/.guix-home/profile/bin:

readlink -f ~/.guix-home/profile/bin/jq
/gnu/store/0cs828z5in82ib1ml1rmv1vnima0j3p8-jq-1.8.2/bin/jq

That folder holds 283 links, one per command installed for you. It looks like one ordinary bin folder, but each entry leads to a different store folder.

Guix builds the profile from a recipe too. So it is a store folder itself, fwyn5…-profile, and it never changes either.

So: a profile is a folder of links that makes many store folders look like one ordinary system.

11. Upgrading by moving one arrow

If a profile never changes, how do you install or upgrade anything? Guix builds a new one beside the old, then moves one link to point at it. Each saved version is a generation. Your whole machine works this way:

readlink /run/current-system
readlink /var/guix/profiles/system-110-link
/var/guix/profiles/system-110-link
/gnu/store/k5rrnniwig0bmr49rjvp9x48h8kqcrb4-system

An upgrade builds the new system folder, adds system-110-link, then points /run/current-system at it. Moving one link happens all at once, so there is no half-upgraded moment.

A rollback moves the arrow back. Nothing is copied or repaired, because the old folder was never touched. sudo guix system roll-back does it, and so does the boot menu, which lists your old generations.

This saved you on 22 November (T216). Generation 107 was the first with your own kernel. It also carried a broken startup file for your login: camera-denoise, a program that starts when you log in, was missing one import. After your password, nothing started, and the login hung.

Nothing was repaired in place. At boot you picked generation 105 in the menu and had a working machine. Generations 108 and 109 fixed the bug, and you have since booted 109:

cat /proc/cmdline
readlink -f /run/booted-system /run/current-system

  gnu.system=/gnu/store/ybz6s…-system …

/gnu/store/k5rrnniw…-system   ← 110, the newest

You booted 109. This morning make switch built 110 and moved the arrow, so your programs already come from 110. A kernel changes only at boot, so 110's kernel waits for your next restart.guix system list-generations lists them all with dates; 110 is from 10:38 on 25 November.

So: an upgrade builds the new beside the old and moves one arrow, so a bad one costs a reboot, not a repair.

12. Deleting what no arrow reaches

Nothing in the store is overwritten, so the store only grows. Yours holds 42,213 folders and files.

Cleanup follows the arrows. Some links are roots: each generation link, /run/current-system, /run/booted-system and a few more. Guix keeps whatever a root points at, and everything that needs in turn, down through step 5's references. Deleting the rest is garbage collection.

guix gc --list-roots | wc -l
115

make gc first deletes old generation links, then runs guix gc. So deleting a generation is the moment you give up rolling back to it. While you run 109, /run/booted-system keeps it alive even after its link goes.

So: delete the arrows you no longer want, and the collector sweeps away whatever no arrow reaches.

13. One recipe for the whole machine

If one program is a recipe, why not the whole computer? That is Guix System. You describe the machine: kernel, bootloader, disks, users, what runs at startup. Guix turns it into recipes and builds one store folder:

ls /run/current-system
activate  boot  channels.scm  configuration.scm  etc  initrd
kernel  locale  parameters  profile  provenance

The kernel, the startup disk image (initrd), all of /etc and the system profile sit in one folder with one name. Guix Home is the same idea for your home folder: ~/.guix-home points at nlqx5…-home, which holds your profile, your config files and the script that starts things when you log in.

Your two descriptions are four lines each, /home/engstrand/guix/desktop/system.scm and /home/engstrand/guix/desktop/home.scm. Both hand over %familiar-config from /home/engstrand/guix/modules/engstrand/config.scm: one list of features from rde, a library of ready-made Guix settings, that makes both the system and the Home.

make switch is steps 4 to 11 for the whole machine. It builds the description into recipes, then builds, downloads or offloads them; then it adds the next generation link, moves the arrow, runs activate and adds a boot menu entry.

So: your whole computer is one recipe and one store folder, and make switch builds it, then moves the arrow.

14. What keeps running

A machine is more than files. Some programs must keep running: audio, networking, your bbh daemons. In the description, each such part is a service. A service adds something to the build: a config file, a user account, or a program to keep running.

Guix hands those programs to Shepherd, its service manager. One Shepherd runs the system as process 1. Guix Home starts another just for you:

herd status
Started:

Shepherd's list of services is a file built from a recipe, so it lives in the store too. That file is what broke in step 11: generation 107's file crashed while loading, so the login waited forever. Since then /home/engstrand/guix/desktop/build/home/check-shepherd.bb loads it after every build, before you switch.

So: services say what should run, Shepherd runs it, and its config is one more store folder.

Now see why pinning matters, from the bottom up. The commits fix the package files. The package files fix the recipes. The recipes fix every name. So: two commits plus your repo decide every recipe, every name, and so your whole machine.

The whole picture

Programs need other files (1). One shared folder makes them overwrite each other (2). So each build gets its own folder that never changes (3), named by a fingerprint of its full recipe (4). The recipe runs in a sealed room, so it is complete (5). A complete recipe gives the same result anywhere, so you can download instead of build (6). Packages are how people write recipes (7). A graft swaps in a low-level fix fast (8), until the full rebuild replaces it; your openssl graft goes with the next pull (9). Profiles make store folders look normal (10). New versions sit beside old ones and one arrow picks the live one, which is why T216 cost you only a reboot (11). Cleanup deletes what no arrow reaches (12). Your machine and Home are each one recipe (13), Shepherd keeps the running parts going (14), and the pinned channels decide all of it (15).
