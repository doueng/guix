Guix, from the ground up

Fifteen short steps. Each one uses only the steps before it. Every example comes from your own MacBook, and every command only looks.

1. A program is a file that needs other files

A program is a file. But it almost never works alone. It needs other files: libraries of shared code, data, other programs.

Take jq. Ask what it needs:

ldd $(readlink -f $(which jq))
libonig.so.5 => /gnu/store/3sgrw…-oniguruma-6.9.10/lib/…
libc.so.6    => /gnu/store/0mcy4…-glibc-2.41/lib/…

jq needs a regex library, oniguruma, and the C library, glibc. Without them it does not start. Ignore the odd /gnu/store/… folders for now. Step 3 explains them.

So: a program is a file plus a list of other files it needs.

2. Why installing things usually breaks

On most Linux systems, every program's files go into the same few shared folders. Libraries go in /usr/lib. There is exactly one /usr/lib/libonig.so.5.

Now take two programs. App A wants oniguruma 6.9. App B wants 7.0. There is one file with that name. Installing 7.0 for B overwrites the file A was using, and A breaks.

Upgrades make it worse. An upgrade overwrites hundreds of files one at a time. If the power dies halfway, you have half an old system and half a new one. And there is no undo, because the old files are gone.

So: the trouble is one shared folder where each name holds one file, and changes that overwrite in place.

3. A folder where nothing ever changes

Guix fixes this with one rule. Every program and library gets its own folder under /gnu/store, and once that folder is written, it never changes. Nothing edits it or overwrites it. Much later, Guix may delete it. That folder of folders is the store.

ls /gnu/store | grep -- '-jq-1.8.2$'
0cs828z5in82ib1ml1rmv1vnima0j3p8-jq-1.8.2
dngb583q608v3acma2xd9smls2cyghpp-jq-1.8.2
x8g0a13kma26kca8f5a1w6f0n54jyp65-jq-1.8.2

Three copies of jq 1.8.2 sit side by side, and none is in another's way. Each name starts with a 32-character code. The code keeps them apart.

Look back at step 1. jq does not look in /usr/lib. It points at one exact folder, 3sgrw…-oniguruma-6.9.10. Nothing can swap that file under it, because that folder never changes.

So: each version of each thing gets its own folder that never changes, and programs point at those folders by full name.

4. Where the code in the name comes from

Before Guix builds anything, it writes down a recipe: every input by its full store name (compiler, source code, oniguruma, glibc), the build script, and its settings. Guix calls a recipe a derivation and saves it as a .drv file in the store.

guix build -d jq
/gnu/store/yvn0aghzmw7l7b75byrkcmqxghvdx2vf-jq-1.8.2.drv
head -c 400 /gnu/store/yvn0aghzmw7l7b75byrkcmqxghvdx2vf-jq-1.8.2.drv
Derive([("out","/gnu/store/0cs828z5…-jq-1.8.2",…)],
       [("/gnu/store/1sfgckrz…-diffutils-3.12.drv",["out"]),
        ("/gnu/store/9qy0azyn…-oniguruma-6.9.10.drv",["out"]),
        ("/gnu/store/b6qd9vr6…-gcc-14.3.0.drv",["out"]), …

Now the key trick. The code at the front of 0cs828z5…-jq-1.8.2 is a hash of that recipe: a short fingerprint computed from every byte of it. Change one byte of the recipe and you get a completely different code.

The recipe names its inputs by their store names. Those names hold their own hashes, which came from their own recipes. So jq's hash covers everything below it, all the way down.

Your disk shows this. Ask each jq copy which folders it points at:

guix gc --references /gnu/store/0cs828z5in82ib1ml1rmv1vnima0j3p8-jq-1.8.2
guix gc --references /gnu/store/x8g0a13kma26kca8f5a1w6f0n54jyp65-jq-1.8.2

The first points at 0mcy4…-glibc-2.41, the second at nhphq…-glibc-2.44-57. Same jq, same version, built on a different glibc: a different recipe, so a different name. The third copy, dngb5…, uses glibc 2.41 too, but a different build of it, b34sh…. Something deep below changed, and the name changed with it.

So: a store name is a fingerprint of the full recipe, so two different recipes never share a folder.

5. Building in a sealed room

A recipe is only worth something if it is complete. If the build script could quietly read /usr/lib or download a file, the recipe would leave something out.

So a background program, the Guix daemon, runs every build in a sealed room:

  • it sees only the inputs the recipe lists,
  • it has no network, except to fetch source whose hash the recipe already holds,
  • it runs as a throwaway user with no home folder, and every file date is 1970.

The script writes into the folder whose name the recipe already fixed. When it ends, Guix makes the folder read-only. Then it scans the result for store names written inside it. Those names are the folder's references, the list guix gc --references printed in step 4. That is how Guix knows, without being told, that jq needs glibc.

So: the room holds only what the recipe lists, so the recipe really is everything that went in.

6. Same recipe, same result, so you can skip the build

The room is sealed, so the result depends only on the recipe. Build the same recipe on another computer and you get the same folder, nearly always bit for bit.guix challenge tests that claim by comparing your build with the caches' builds.

And the name of the result is known before the build, because it comes from the recipe. So your daemon first asks a server: do you already have 0cs828z5…-jq-1.8.2? If yes, it downloads the finished folder, checks the server's signature and puts it in the store. That download is a substitute, and a server that hands them out is a binary cache.

So: a result is decided by its name, so anyone who already built that name can hand it to you.

7. Recipes written for people

A .drv lists hundreds of store names. Nobody writes that by hand. You write a package instead: a short description in Scheme, the language Guix is written in. Guix turns it into the .drv.

Your own kernel from T212, trimmed, from /home/engstrand/guix/modules/engstrand/asahi/kernel.scm

(define %version "7.2.15")
(define %revision "1")
(define %hash "0w1kb68ki0fcdg7h9x6qqmbgmw2n2yq8wj1hcicp5gb8dipkk9g3")

(origin                              ; where the source comes from
  (method git-fetch)
  (uri (git-reference
        (url "https://github.com/AsahiLinux/linux")
        (commit "asahi-7.2.15-1")))
  (sha256 (base32 %hash)))           ; what the download must hash to

(package
  (inherit base)                     ; start from Guix's kernel package
  (native-inputs … clang-19 rust rust-bindgen-cli …)
  (synopsis "Linux for Apple Silicon Macs"))

A package says what a recipe says, in friendly words. The source, with its hash, so the download is checked. The inputs, by variable name such as rust, not by store name. Each input is a package too, so Guix walks the whole tree and writes a .drv for each.

Now step 4 tells you what a version bump does. Change %version and the recipe changes, so the name changes, so the new kernel lands in a new folder. The old kernel's folder stays, untouched.

The file has one more kind of code, starting with #~(. It does not run now. Guix saves it into the recipe, and it runs later inside the sealed room. Inside it, #$ drops in a value from outside, such as a store name.Guix calls this a G-expression. You only need: #~ means run this in the build room.

So: a package is a recipe written for people, and Guix turns it into the exact .drv the daemon builds.

8. Patching one library without rebuilding everything above it

Steps 4 and 7 have a cost. Change one thing low down and every name above it changes, and each new name means a new build.

Most days that is fine. Now say a security hole turns up in openssl, the library that encrypts network traffic for almost every program. Ask how much sits on top of it:

guix refresh -l openssl
Building the following 7653 packages would ensure
27385 dependent packages are rebuilt

27,385 packages take the build farms days, and the fix should reach you today.

So Guix builds only the fixed openssl. Then, for each package that points at the old openssl, it copies the finished folder and swaps the old store name for the new one wherever it is written inside. Nothing is compiled. It is find-and-replace on bytes. This is a graft.

It works because of step 5: Guix already finds what a package needs by scanning it for store names. A graft scans the copy for the old name and writes the new one in its place.

The new name must be exactly as long as the old one, since moving any byte in a compiled program breaks it. The hash part is always 32 characters, so the rest must match too. openssl-3.5.7 and openssl-3.5.9 are both 13.

One graft is live on your laptop. Your pinned Guix has this in gnu/packages/tls.scm, trimmed:The file is /home/engstrand/.config/guix/current/share/guile/site/3.0/gnu/packages/tls.scm line 554

(define-public openssl-3.5
  (package
    (name "openssl")
    (version "3.5.7")
    (replacement openssl-3.5/fixed)   ; the graft
    …))

(define-public openssl-3.5/fixed
  (hidden-package
   (package
     (inherit openssl-3.5)
     (version "3.5.9") …)))

The replacement line is the whole switch. Every package is still built against 3.5.7, and Guix grafts 3.5.9 in its place. See both forms of one package that uses openssl. --dry-run only prints, and --no-grafts turns grafting off:

guix build --dry-run --no-grafts mit-krb5
guix build --dry-run mit-krb5
/gnu/store/lbbq1g41dr994hh8yq95p7bc0p5qqdkw-mit-krb5-1.21
/gnu/store/3znk1rfg7qiqg0wkcxn3zinrc8ww5l8y-mit-krb5-1.21

Both are in your store. Ask each which openssl it points at:

guix gc --references /gnu/store/lbbq1g41…-mit-krb5-1.21 | grep openssl
guix gc --references /gnu/store/3znk1rfg…-mit-krb5-1.21 | grep openssl
/gnu/store/4xfdcm3ca7s72dcy59vg43v5ifpx0b1g-openssl-3.5.7
/gnu/store/xfzy3rq2lyi4h9jj342az01mc73mjc6y-openssl-3.5.9

Inside, the two copies of its TLS plugin, lib/krb5/plugins/tls/k5tls.so, are both 199,120 bytes. cmp -l finds 64 bytes that differ, all inside two names: openssl's, and mit-krb5's own, since the copy has a new name too.

Grafts climb. curl does not use openssl directly, but it uses mit-krb5, so curl gets a grafted copy too, x9b7p…-curl-8.21.0. Even your T212 kernel, mb9wq…-linux-asahi-7.2.15-1, is a grafted copy: it keeps a reference to rust, and rust leads down to openssl.

When a graft still has to be made, Guix says so:

guix build --dry-run socat
The following graft would be made:
   /gnu/store/dpx6b83arq6z5s8an0nd79qiwn57hrsn-socat-1.7.4.4.drv

Step 6 still holds, one level up. A graft is a recipe like any other: that .drv takes the normally built socat and the fixed openssl as inputs, and its job is to copy and swap. Same inputs, same swap, same bytes.

What changes is the meaning. The grafted mit-krb5 was compiled against 3.5.7, and nobody compiled it against 3.5.9. That is safe only because 3.5.9 is a bug-fix release with the same library interface.The Guix manual requires the two to be binary-compatible, with the same SONAME. The Guix developers choose grafts and use them only for small fixes like this one.

So: a graft gets a fix out today by copying each package above it and swapping one store name for another of the same length.

9. What a graft costs, and when it goes away

A graft is a stopgap. It has costs and limits, and it is meant to be replaced.

It costs time at install. Every grafted copy is a full copy, made and scanned on your laptop, because the caches only hold normal builds.guix/grafts.scm marks graft recipes #:local-build? #t and #:substitutable? #f. The manual says a graft usually takes under a minute for an average package. That is why make switch after make pull can keep printing applying … graft lines after the downloads finish, even when guix-builder built everything ahead of time. The ungrafted copies stay in the store too, until step 12 cleans up.

It reaches only what Guix built:

Holds old openssl after a graftWhy
a binary from cargo build, pip, npm or NixGuix never built it, so never scans it
a program linked to openssl-3.5.7-staticit holds openssl's code, not a name to swap
a name packed in a compressed filethe scan finds only names written plainly
anything built with --no-graftsright for debugging, wrong for daily use

Tools that care about the real build look past grafts: guix size measures the ungrafted package, and guix shell -C --no-grafts recreates a build environment exactly.

The proper fix still lands. A change that would rebuild more than 300 packages goes first to a separate branch, where the build farm rebuilds everything on top. There openssl becomes 3.5.9 for real and the replacement line is deleted. Once that branch is merged, your next make pull and make switch download packages compiled against the fixed openssl. No copies, no swaps.

Is this graft still needed? Yes, on the Guix you have now. A make pull removes it. Your pinned Guix, commit 704ad8c of 26 October, still has the replacement line, and on your laptop every package that uses openssl 3.5 gets 3.5.9 by graft. Nothing your machine uses has 3.5.7 in it at all.openssl-3.0 (3.0.19, used only by ntp) and openssl-1.1 have no replacement.

The graft carries real fixes. Its commit, 66bdd5b0 of 30 September, lists 13 CVEs fixed between 3.5.7 and 3.5.9, and OpenSSL rates the worst High. Removing it by hand while you stay on this commit would bring them back.

On 24 November it accounted for 211 grafted copies on your machine. 35 link openssl directly, such as python, git, openssh, mit-krb5, qtbase, node and rust. The rest sit above those.Counted in T226 with guix gc -R, --references and --derivers: a graft's .drv takes the plain build of the same name as an input.

The rebuild has already happened upstream. Commit a310ed3e, “gnu: openssl: Ungraft.” of 15 November, makes 3.5.9 the plain openssl and deletes openssl-3.5/fixed. It reached master on 21 November, with ungrafts for nss-certs, brotli, libpng, gstreamer and libgit2. After your next make pull and make switch, you download packages built against 3.5.9 and the 211 copies become garbage. Run guix weather after the pull to see coverage first.

So: a graft costs time and reaches only what Guix built; the full rebuild replaces it, and for openssl yours arrives with the next pull.

10. One folder that makes the store look like a normal system

Everything so far sits in folders with unreadable names. Yet you just type jq. How does that find 0cs828z5…-jq-1.8.2?

Through a profile: a folder of links, or shortcuts, each pointing into a store folder. Your shell's PATH includes ~/.guix-home/profile/bin:

ls -l ~/.guix-home/profile/bin/jq
jq -> /gnu/store/0cs828z5in82ib1ml1rmv1vnima0j3p8-jq-1.8.2/bin/jq

That folder holds 283 such links, one per command installed for you. It looks like one ordinary bin folder, but each entry points at a different store folder.

Guix builds the profile from a recipe too, so it is a store folder itself, fwyn5…-profile, and it never changes either.

So: a profile is one folder of links that makes many store folders look like one ordinary system.

11. Upgrading by moving one arrow

If a profile never changes, how do you install or upgrade anything? You build a new one beside the old one, then move one link to point at it. Each saved version is a generation. Your whole machine works this way:

readlink /run/current-system
readlink /var/guix/profiles/system-110-link
/var/guix/profiles/system-110-link
/gnu/store/k5rrnniwig0bmr49rjvp9x48h8kqcrb4-system

An upgrade builds the new system folder, adds system-110-link, then points system at it. Moving one link happens all at once, so there is no half-upgraded moment.

A rollback moves the arrow back. Nothing is copied or repaired, because the old folder was never touched. sudo guix system roll-back does it, and so does the boot menu, which lists your old generations.

This saved you on 22 November (T216). Generation 107 was the first with your own kernel from T212. It also carried a broken file for your login: camera-denoise, a program that starts when you log in, was missing one import. After you typed your password, nothing started, and the login hung.

Nothing was repaired in place. At boot you picked generation 105 in the menu and had a working machine. Generations 108 and 109 fixed the bug, and you have since booted 109:

12. Deleting what no arrow reaches

Nothing in the store is overwritten, so the store only grows. Yours holds 42,159 items, about 68 GB.

Cleanup follows the arrows. Some links are roots: each generation link, /run/current-system, /run/booted-system and a few more. Guix keeps anything a root points at, and everything that points at in turn, all the way down step 5's references. Deleting the rest is garbage collection.

guix gc --list-roots | wc -l
111

guix gc --requisites on a store folder lists it plus everything it needs, which is what one root keeps alive.

make gc first deletes old generation links, then runs guix gc. So deleting a generation is the moment you give up rolling back to it. While you run 109, /run/booted-system keeps it alive even if its link goes.

So: delete the arrows you no longer want, and the collector sweeps away whatever no arrow reaches.

13. One recipe for the whole machine

If one program is a recipe, why not the whole computer? That is Guix System. You describe the machine: kernel, bootloader, disks, users, what runs at startup. Guix turns it all into one recipe and builds one store folder:

ls /run/current-system
activate  boot  channels.scm  configuration.scm  etc  initrd
kernel  locale  parameters  profile  provenance

The kernel, the startup disk image (initrd), all of /etc and the system profile sit in one folder with one name. Guix Home is the same idea for your home folder: ~/.guix-home points at nlqx5…-home, which holds your profile, your config files and the script that starts things when you log in.

Your descriptions are tiny. /home/engstrand/guix/desktop/system.scm and /home/engstrand/guix/desktop/home.scm are four lines each. Both use %familiar-config in /home/engstrand/guix/modules/engstrand/config.scm, one list of features from rde, a library of ready-made Guix settings (desktop, shell, editor, kanata…), that makes both the system and the Home.

So: your whole computer is one recipe and one store folder, and make switch builds it, then moves the arrow.

14. What keeps running

A machine is more than files. Some programs must keep running: audio, networking, your bbh daemons. In the description, each such piece is a service. A service adds to the build: a config file, a user account, or a program to keep running.

The whole picture

Programs need other files (1). One shared folder makes them overwrite each other (2). So each build gets its own folder that never changes (3), named by a fingerprint of its full recipe (4). The recipe runs in a sealed room, so it is complete (5). Complete recipes give the same result anywhere, so you can download instead of build (6). Packages are how people write recipes (7). A graft swaps in a low-level fix fast (8), until the full rebuild replaces it (9). Profiles make store folders look normal (10). New versions sit beside old ones, and one arrow picks the live one, which is why T216 cost you only a reboot (11). Cleanup deletes what no arrow reaches (12). Your machine and Home are each one recipe (13), Shepherd keeps the running parts going (14), and the pinned channels decide all of it (15).
