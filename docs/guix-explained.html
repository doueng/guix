Guix, from the ground up

Sixteen short steps. Each one uses only the steps before it. Every example is from your own MacBook, and every command is safe to type: they only look.

1. A program is a file that needs other files

A program is a file. But it almost never works alone. It needs other files: libraries with shared code, data, other programs.

Take jq. Ask it what it needs:

ldd $(readlink -f $(which jq))

You get (trimmed):

libonig.so.5 => /gnu/store/3sgrw…-oniguruma-6.9.10/lib/libonig.so.5
libc.so.6    => /gnu/store/0mcy4…-glibc-2.41/lib/libc.so.6

So jq needs a regex library (oniguruma) and the C library (glibc). Without them, jq does not start. Ignore the odd /gnu/store/… folders for now. We will get there.

So: every program is a file plus a list of other files it needs.

2. Why installing things usually breaks

On a normal Linux, everybody's files go into the same few shared folders. Libraries go in /usr/lib. There is exactly one /usr/lib/libonig.so.5.

Now picture two programs. App A wants oniguruma 6.9. App B wants a newer one. There is one slot with that name. Installing the new one for B overwrites the file A was using. A breaks.

It gets worse. An upgrade copies hundreds of files one by one. If the power dies halfway, you have half an old system and half a new one. And there is no undo: the old files are gone, overwritten.

So: the trouble is one shared shelf where each name has room for only one thing, and changes happen in place.

3. The store: a folder where nothing ever changes

Guix fixes this with one rule. Everything goes into /gnu/store, each thing in its own folder, and once a folder is written, it never changes again. Not edited, not overwritten. Only, much later, maybe deleted.

Look at your store:

ls /gnu/store | grep -- '-jq-1.8.2$'
0cs828z5in82ib1ml1rmv1vnima0j3p8-jq-1.8.2
dngb583q608v3acma2xd9smls2cyghpp-jq-1.8.2
x8g0a13kma26kca8f5a1w6f0n54jyp65-jq-1.8.2

Three copies of jq 1.8.2, side by side, and none of them is in anybody's way. Each name starts with a 32-character code. That code is what keeps them apart.

And remember the ldd output from step 1? jq does not look in /usr/lib. It points at one exact folder: /gnu/store/3sgrw…-oniguruma-6.9.10. Nobody can swap that file under it, because that folder never changes.

So: every version of everything gets its own folder that never changes, and programs point at those folders by full name.

4. Where the code in the name comes from

Before Guix builds anything, it writes down a recipe. Guix calls it a derivation, and stores it as a .drv file. The recipe says, in full:

  • every input, named by its full store path (the compiler, the source code, oniguruma, glibc…),
  • the build script to run,
  • the settings it runs with.

See jq's recipe:

guix build -d jq
/gnu/store/yvn0aghzmw7l7b75byrkcmqxghvdx2vf-jq-1.8.2.drv

head -c 400 /gnu/store/yvn0aghzmw7l7b75byrkcmqxghvdx2vf-jq-1.8.2.drv
Derive([("out","/gnu/store/0cs828z5…-jq-1.8.2",…)],
       [("/gnu/store/1sfgckrz…-diffutils-3.12.drv",["out"]),
        ("/gnu/store/9qy0azyn…-oniguruma-6.9.10.drv",["out"]),
        ("/gnu/store/b6qd9vr6…-gcc-14.3.0.drv",["out"]), …

Now the key trick. The code at the front of 0cs828z5…-jq-1.8.2 is a hash of that recipe: a short fingerprint computed from all of it. Change one byte of the recipe and the fingerprint is completely different.

The recipe lists its inputs by their names, which contain their fingerprints, which came from their recipes. So the fingerprint covers everything, all the way down:

You can see this on your disk. Ask each jq copy what it points at:

guix gc --references /gnu/store/0cs828z5in82ib1ml1rmv1vnima0j3p8-jq-1.8.2
guix gc --references /gnu/store/x8g0a13kma26kca8f5a1w6f0n54jyp65-jq-1.8.2

The first points at 0mcy4…-glibc-2.41. The second points at nhphq…-glibc-2.44-57. Same jq, same version, built against a different glibc, so a different recipe, so a different name. The third copy, dngb5…, uses glibc 2.41 too, but a different build of it (b34sh…). Something deep below changed, and the name noticed.

So: the name is a fingerprint of the full recipe, so two different recipes can never land in the same folder.

5. Building: running the recipe in a sealed room

A recipe only means something if it is really complete. If the build script could quietly use /usr/lib or download something, the recipe would be lying.

So a background program, the Guix daemon, runs every build in a sealed room:

  • the only files it can see are the inputs the recipe lists,
  • no network (except to download source whose exact hash is already written in the recipe),
  • no home folder, a throwaway user, and file dates reset to 1970.

The script writes its result to the folder whose name was already worked out from the recipe. When it finishes, the folder is made read-only. Then Guix scans the result for other store names written inside it. That is how it knows, without being told, that jq needs glibc. It is exactly what guix gc --references printed above.

So: the room holds only what the recipe lists, so the recipe really is everything that went in.

6. Same recipe, same result: so you can skip the build

The room is sealed, so the result depends only on the recipe. Run the same recipe on another computer and you get the same thing, nearly always bit for bit. (guix challenge checks that claim.)

And here is the payoff. The name of the result is known before building, because it comes from the recipe. So before building, your daemon can ask a server: "Do you already have 0cs828z5…-jq-1.8.2?" If yes, it downloads the finished folder, checks the server's signature, and puts it in the store. That download is called a substitute. A server that hands them out is a binary cache.

Your daemon asks these, in this order (from its command line, ps -o args= -C guix-daemon):

  1. http://guix-builder.tailbf68ad.ts.net:8080, your own Hetzner build machine on Tailscale,
  2. https://bordeaux.guix.gnu.org, the Guix project's cache,
  3. https://substitutes.asahi-guix.org and https://ci.guix.gnu.org.

Try it:

guix weather jq

It says both guix-builder and bordeaux have jq: 100.0% substitutes available.

Some things nobody else has built. Your kernel uses your own config, so its recipe is yours alone and no public cache has its name. For those, the laptop offloads: it sends the recipe to guix-builder over SSH (listed in /etc/guix/machines.scm), which builds it in its own sealed room and sends back the result. The comment at the top of modules/engstrand/asahi/kernel.scm says just that: bump the version and build on guix-builder. make prebuild asks guix-builder to build your whole system ahead of time, so your next switch just downloads.

So: a result is decided by its name, so anyone who already built that name can just hand it to you.

7. Packages: recipes written for humans

A .drv lists hundreds of store paths. Nobody writes those by hand. You write a package instead: a short description in Scheme, the language Guix is written in. Guix turns it into the .drv for you.

Your own kernel from T212, trimmed, in /home/engstrand/guix/modules/engstrand/asahi/kernel.scm:

(define %version "7.2.15")
(define %revision "1")
(define %hash "0w1kb68ki0fcdg7h9x6qqmbgmw2n2yq8wj1hcicp5gb8dipkk9g3")

(origin                              ; where the source comes from
  (method git-fetch)
  (uri (git-reference
        (url "https://github.com/AsahiLinux/linux")
        (commit "asahi-7.2.15-1")))
  (sha256 (base32 %hash)))           ; what the download must hash to

(package
  (inherit base)                     ; start from Guix's kernel package
  (native-inputs … clang-19 rust rust-bindgen-cli …)
  (synopsis "Linux for Apple Silicon Macs"))

A package says what any recipe says, just in friendly words: the source (with its hash, so the download is checked), the inputs (by variable name, like rust, not by store path), and how to build. Each input is itself a package, so Guix walks down the whole tree and writes a .drv for each one.

Now step 4 tells you what a version bump does. Change %version: the recipe changes, so the name changes, so the new kernel goes into a new folder. The old kernel folder is still there, untouched.

One more piece of that file: the part starting with #~(. That is code that is not run now. It is saved into the recipe and runs later, inside the sealed room. Inside it, #$ drops in something from outside, such as a store path. Guix calls this a G-expression. You only need to know: #~ means "run this in the build room".

So: a package is a recipe written for people; Guix turns it into the exact .drv that the daemon builds.

8. Grafts: a quick patch without rebuilding everything

Steps 4 and 7 have a cost. Change one thing low down, and every name above it changes. Every name that changes means a new build.

Most days that is fine. Now picture a security hole in openssl, the library that does encryption for almost every program that talks to the network. Ask Guix how much sits on top of it:

guix refresh -l openssl
Building the following 7653 packages would ensure 27385 dependent packages are rebuilt

27,385 packages. The build farms need days for that, and the fix should reach you today. For glibc, which nearly every program uses, it would be the whole distribution.

The trick

Guix builds only the fixed library. Then, for each package that points at the old one, it makes a copy of the finished package and swaps the old library's store path for the new one, wherever that path is written inside. It does not compile anything. It is find-and-replace on bytes. Guix calls this a graft.

Remember step 5: Guix finds what a package needs by scanning it for store names. A graft uses the same fact the other way round. It scans the copy for the old name and writes the new one in its place.

Because it swaps bytes in place, the new name must be exactly as long as the old one. Move anything in a compiled program and it breaks. The code at the front is always 32 characters, so the rest must match too. openssl-3.5.7 and openssl-3.5.9 are both 13 characters, so that works.

One is live on your laptop right now

Your pinned Guix has this in gnu/packages/tls.scm (trimmed):

(define-public openssl-3.5
  (package
    (name "openssl")
    (version "3.5.7")
    (replacement openssl-3.5/fixed) ; graft
    …))

(define-public openssl-3.5/fixed
  (hidden-package
   (package
     (inherit openssl-3.5)
     (version "3.5.9") …)))

The replacement field is the whole switch. Every package still says it was built with openssl 3.5.7. Guix grafts 3.5.9 in its place. You can read the file at ~/.config/guix/current/share/guile/site/3.0/gnu/packages/tls.scm.

Ask for both versions of a package that uses openssl. --dry-run only prints, and --no-grafts turns grafting off:

guix build --dry-run --no-grafts mit-krb5     # as built
/gnu/store/lbbq1g41dr994hh8yq95p7bc0p5qqdkw-mit-krb5-1.21

guix build --dry-run mit-krb5                 # grafted copy
/gnu/store/3znk1rfg7qiqg0wkcxn3zinrc8ww5l8y-mit-krb5-1.21

Both are in your store. Ask each what it points at:

guix gc --references /gnu/store/lbbq1g41dr994hh8yq95p7bc0p5qqdkw-mit-krb5-1.21 | grep openssl
/gnu/store/4xfdcm3ca7s72dcy59vg43v5ifpx0b1g-openssl-3.5.7

guix gc --references /gnu/store/3znk1rfg7qiqg0wkcxn3zinrc8ww5l8y-mit-krb5-1.21 | grep openssl
/gnu/store/xfzy3rq2lyi4h9jj342az01mc73mjc6y-openssl-3.5.9

Now look inside one file, the TLS plugin lib/krb5/plugins/tls/k5tls.so. Both copies are 199,120 bytes. cmp -l finds 64 bytes that differ, and all of them sit inside two names: openssl's, and mit-krb5's own, since the copy has a new name too.

Grafts climb. curl does not use openssl directly, but it uses mit-krb5. So curl gets a grafted copy too (x9b7p…-curl-8.21.0), which points at the grafted mit-krb5. Even your own T212 kernel got one: it keeps a reference to rust, rust leads down to openssl, so mb9wq…-linux-asahi-7.2.15-1 is a grafted copy. Of the 1,471 items your system and Home need, 274 are grafted copies.

When a graft still has to be made, guix build says so. Try a package you do not have yet:

guix build --dry-run socat
The following graft would be made:
   /gnu/store/dpx6b83arq6z5s8an0nd79qiwn57hrsn-socat-1.7.4.4.drv

A real build then prints applying 1 graft for …socat-1.7.4.4.drv … while it works.

What happened to “same recipe, same result”?

It still holds, one level up. A graft is a recipe like any other. That .drv for socat lists two inputs: the socat that was built normally, and the fixed openssl. Its job is “copy this and swap these names”. Its name is a fingerprint of that recipe, and the same swap gives the same bytes every time.

What changes is the meaning. The grafted mit-krb5 was compiled against openssl 3.5.7, and no one ever compiled it against 3.5.9. That is only safe because 3.5.9 is a bug-fix release that keeps the same library interface (the manual says the two must be binary-compatible, with the same SONAME). Choosing grafts is the Guix developers' job, and they use them only for small fixes like this.

Two more things follow. The caches hold only the builds made without grafts; Guix never downloads a grafted copy and always makes it on your laptop (guix/grafts.scm marks graft recipes #:local-build? #t and #:substitutable? #f). And tools that care about the real build look past grafts: guix size measures the ungrafted package, and guix shell -C --no-grafts recreates a build environment exactly.

What grafts cost, and where they cannot reach

  • Time at install. Every grafted copy is a full copy, made and scanned on your laptop. The manual says usually under a minute for an average package. This is why a make switch after make pull can keep printing applying … graft lines after the downloads finish, even when guix-builder built everything ahead of time. The old, ungrafted copies stay in the store too, until garbage collection.
  • Only Guix-built things are fixed. A graft fixes what Guix built and knows about. Anything that got onto your disk some other way still has whatever openssl it brought: a binary you built with cargo build in your home folder, a pip or npm package, something installed with Nix.
  • Copied code is not a path. A program linked against openssl-3.5.7-static contains openssl's code itself, not a path to it. There is nothing to swap, so it keeps the old code.
  • Names must be written plainly. The scan finds names written as plain text (and in the wide forms some programs use). A name packed inside a compressed file would be missed.
  • You can turn it off. Anything built with --no-grafts skips the fix. That is right for debugging and wrong for daily use.

When grafts go away

A graft is a stopgap. The proper fix still lands. Changes that would rebuild more than 300 packages go to a separate branch first (it used to be called core-updates), where the build farm rebuilds everything on top. There, openssl becomes 3.5.9 for real and the replacement line is deleted. Once the branch is merged into master, your next make pull and make switch download normally built packages that were compiled against the fixed openssl. No copies, no swaps. The 274 grafted copies become ordinary garbage for step 12 to collect.

So: a graft gets a fix out today by copying each package and swapping one store name for another of the same length; the full rebuild follows later and replaces it.

9. Profiles: making store folders feel like a normal system

So far everything sits in folders with unreadable names. But you just type jq. How does that find 0cs828z5…-jq-1.8.2?

Through a profile: a folder full of links (shortcuts) that point into store folders. Your shell's PATH includes ~/.guix-home/profile/bin. Look at what is in it:

ls -l ~/.guix-home/profile/bin/jq
… jq -> /gnu/store/0cs828z5in82ib1ml1rmv1vnima0j3p8-jq-1.8.2/bin/jq

That folder has 283 such links: one for each command your Home gives you. To you it looks like one normal bin folder. Underneath, each entry points at a different store folder.

The profile is built by a recipe too, so it is a store folder itself (/gnu/store/plq4q…-profile), and it never changes either.

So: a profile is one folder of links that makes many store folders look like one ordinary system.

10. Generations and rollback: moving one arrow

If a profile never changes, how do you install or upgrade anything? You don't change it. You build a new profile next to the old one, and then move one link to point at the new one. Each saved version is a generation.

Your whole machine works this way. Follow the links:

readlink /run/current-system
/var/guix/profiles/system-109-link

readlink /var/guix/profiles/system-109-link
/gnu/store/ybz6s7a8wwbr7mm909c2mfzcchlsdnqa-system

Upgrading is: build the new system folder, add system-110-link, then flip system to point at it. Flipping one link happens all at once. There is no half-upgraded moment.

Rollback is: flip the arrow back. Nothing is copied or repaired, because the old folder was never touched. sudo guix system roll-back does it, and so does the boot menu, which lists your old generations.

So: upgrading builds the new beside the old and moves one arrow; rolling back moves the arrow back.

12. Garbage collection: deleting what no arrow reaches

Nothing in the store is ever overwritten, so the store only grows. Yours holds 41,963 items, about 67 GB.

Cleaning up follows the arrows. Some links are roots: each generation link, /run/current-system, /run/booted-system, and a few more. Anything a root points at is kept. So is everything that points at, all the way down (step 5's references). Everything else can go.

guix gc --list-roots | wc -l      # you have 125 roots
guix gc --requisites /gnu/store/0cs828z5in82ib1ml1rmv1vnima0j3p8-jq-1.8.2
                                  # jq plus everything it needs

make gc first deletes old generation links, then runs guix gc. So deleting a generation is the moment you give up rolling back to it. Generation 105 is safe for now: you booted it, so /run/booted-system keeps it alive.

So: delete the arrows you no longer want, and the collector sweeps away whatever no arrow reaches.

13. Guix System and Guix Home: one recipe for the whole machine

Now the big step, which is really a small one. If one program is a recipe, why not the whole computer?

That is Guix System. You describe the machine: kernel, bootloader, disks, users, what runs at startup. Guix turns all of it into one recipe and builds one store folder. Look inside the one you are on:

ls /run/current-system
activate  boot  channels.scm  configuration.scm  etc  initrd
kernel  locale  parameters  profile  provenance

The kernel, the startup disk image (initrd), all of /etc, the program profile: all inside one folder with one name. Guix Home is the same idea for your home folder. ~/.guix-home points at /gnu/store/znnhl…-home, which holds your profile, your config files and the script that starts things when you log in.

Your descriptions are tiny. /home/engstrand/guix/desktop/system.scm and desktop/home.scm are four lines each. Both use %familiar-config in modules/engstrand/config.scm, a list of rde features (desktop, shell, editor, kanata…). One feature list makes both the system and the home.

And make switch is just steps 4 to 10 for the whole machine:

  1. guix system build: turn the description into recipes and build them (or download them, or offload them),
  2. sudo guix system reconfigure: add the next system-N-link, move the arrow, run activate, add the new boot menu entry.
So: your whole computer is one recipe and one store folder, and make switch is build-then-move-the-arrow.

14. Services and Shepherd: what keeps running

A machine is not just files. Some programs must keep running: audio, networking, your bbh daemons. In Guix's description, each such piece is a service. A service adds things to the build: a config file, a user account, or a program to keep running.

The ones that run are handed to Shepherd, Guix's service manager. One Shepherd runs the system as process 1. Guix Home starts another one just for you. Ask yours:

herd status
Started:
 + bbh-super
 + camera-denoise
 + pipewire
 + …

Shepherd's list of services is a file built by a recipe, so it lives in the store like everything else. That is exactly what broke in T216: generation 107's Home Shepherd file crashed while loading, so your login waited forever for it. Since then, desktop/build/home/check-shepherd.bb loads that file after every build, before you switch.

So: services say what should run, Shepherd runs it, and its config is just another store folder.

15. Channels: where the recipes come from

Last question: where do packages like jq and rust come from? From channels: Git repositories full of package files. Yours are pinned in /home/engstrand/guix/channels.scm:

guix describe        # trimmed
  guix 704ad8c   https://codeberg.org/guix/guix
  rde  9300ace   https://git.sr.ht/~abcdw/rde

Plus your own modules/, which make adds with -L. Since T212 your kernel lives there, and the asahi-guix channel is gone.

make pull runs guix pull with that file. It fetches those exact commits, checks they are signed by the right people (the introduction lines), and builds a new guix command from them. That command is a profile with generations too: ~/.config/guix/current leads, link by link, to current-guix-9-link, your ninth pull.

Now see why pinning matters, from the bottom up. The commits fix the package files. The package files fix the recipes. The recipes fix every name. So the commits fix your entire system, down to the last byte. That is why guix-builder can build your system ahead of time and get exactly the names your laptop will ask for. Each system generation even records its channels: cat /run/current-system/channels.scm.

So: two commit IDs plus your repo decide every recipe, every name, and so your whole machine.

16. The whole picture

Programs need files (1). Sharing one folder breaks things (2). So every build gets its own folder that never changes (3), named by a fingerprint of its full recipe (4). The recipe is built in a sealed room, so it is honest (5). Honest recipes give the same result anywhere, so you can download instead of build (6). Packages are how people write recipes (7). A graft patches a low-level fix in fast by swapping store names, until the full rebuild arrives (8). Profiles make store folders feel normal (9). New versions sit beside old ones, and one arrow picks which is live (10), which is why T216 cost you only a reboot (11). Cleanup deletes what no arrow reaches (12). Your whole machine and home are one recipe (13), services and Shepherd keep the running parts (14), and the pinned channels decide all of it (15).
