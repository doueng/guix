Answer

Start with no Bombadil change at all. Add a small oilfm-tty test front end to oilfm. It runs the real FileManager view headless in gpui's TestApp (oilfm's ui-tests already does this), turns stdin bytes into gpui keystrokes, and prints the view model as text. Bombadil's existing terminal driver then tests it, the same way T174 tests the bbh Emacs UI. That is about 300 to 500 lines in oilfm plus a spec, about a day guess, with no Guix change: the packaged 0.7.10 binary is enough.

If you later want structured state or the real Wayland input path, the next step is a generic external stdio-JSON driver in Bombadil. Its state is whatever JSON the app's adapter sends, and its actions are keys, text, clicks and app-defined JSON. That is about 1,800 to 2,500 lines across about 20 files, 3 to 5 days guess. It is the shape the maintainer floated: "Maybe they should be third party projects and we expose a driver API in Bombadil" (issue #250) measured. Keep it as a fork until upstream agrees.

The accessibility route (AT-SPI) is blocked today. gpui gained AccessKit, including a Wayland adapter, on 2026-05-27 (zed PR #56065). That gpui needs Rust 1.95, while Guix ships 1.93 and oilfm pins gpui from 2026-03-30, before AccessKit measured. OCR is fragile and nobody upstream would want it inferred.

Guix: use a package variant, not a graft. Today the package is upstream's static release binary, so a patch-based variant first needs Bombadil packaged from source, which is the expensive part (579 crates, Zig 0.16 and ghostty). A fork's CI release asset needs only about 10 lines. A graft does nothing here: Bombadil is a leaf application with no dependents, and the change is a feature, not an ABI-compatible fix.

How Bombadil drives a target today

  • Two drivers, both compiled in. bombadil browser drives Chromium over CDP (its own lib/cdp crate, generated from the protocol). bombadil terminal (experimental) runs the program on a PTY and parses its output with libghostty-vt into a cell grid. measured lib/bombadil-cli/src/lib.rs, lib/bombadil-terminal/src/pty.rs
  • Extension point is the trait pair InterfaceDriver::new_session and InterfaceSession, with associated Action, ActionTemplate and State types, and next_event, apply, extract_snapshots, terminate and STALL_TIMEOUT. The runner, fuzzer, shrinker and LTL verifier are generic over it. measured lib/bombadil/src/driver.rs lines 41 to 178
  • A state is a driver-specific Rust struct (the terminal's is TerminalState: grid, scrollback, cursor, exit status, last action). The driver emits one after the UI goes quiet; the terminal driver waits for a quiescence timeout, capped at 1 s of draining. measured lib/bombadil-terminal/src/state.rs, driver.rs lines 42 to 52 and 465
  • Specs read state in TypeScript run by the boa JS engine. extract(state => …) returns a Cell, and properties are LTL formulas (always, eventually, within) over those cells. Each driver converts its state to a JS object (terminal_state_to_js) and ships a typed TS module, such as @antithesishq/bombadil/terminal. measured lib/bombadil/src/specification/terminal/index.ts, lib/bombadil-terminal/src/js.rs
  • Actions are enumerated by the spec. actions(() => templates) returns a weighted tree of templates, such as {TypeText: StringGenerator} or {Click: {row: Range, column: Range}}. The core picks a leaf and generates a concrete action. accepts lets --reproduce and shrinking check a recorded action against the templates offered at that state. Terminal actions are TypeText, Resize, Click, ScrollUp and ScrollDown. measured lib/bombadil-terminal/src/driver.rs lines 61 to 151, lib/bombadil/src/model.rs
  • Per-driver touch points outside the driver crate are a CLI subcommand (~550 lines for the terminal), a schema module (~300), a TS module and its defaults (~330), a trace envelope driver id (TraceDriver::Terminal = 1, Browser = 2), and trace writer and inspector rendering. measured lib/bombadil-trace/src/envelope.rs line 43, lib/bombadil-cli/src/terminal.rs, lib/bombadil-schema/src/terminal.rs
  • Size reference. The terminal driver crate is 2,465 lines today, and its first commit (#162) was 982 lines. The closed SwiftUI driver PR #254, which uses an in-app agent that serves an accessibility tree over a line protocol, was +4,006 lines in 48 files, about 1,250 of them Swift. measured

Does gpui expose AccessKit on Linux? Yes, upstream does: PR #56065 (merged 2026-05-27) adds accesskit_unix::Adapter to both the Wayland and X11 windows (59 lines in wayland/window.rs), plus element APIs .role(Role::…) and .aria_label(…). On Wayland a11y_update_window_bounds is a no-op, so AT-SPI screen coordinates are window-relative at best. oilfm's pin does not have it: the vendored crates contain no accesskit, and the pin (7f7520b, 2026-03-30) is 1,528 commits before the merge. Zed's toolchain at the merge is 1.95.0, against Guix's rust 1.93.0. Even after a bump, oilfm draws its buffer with custom elements, so each row would need roles and labels before AT-SPI saw anything useful inferred. measured

Spike: oilfm in a nested headless sway, driven by wtype

A guix shell with sway, wtype and grim (a 5.8 MB substitute download; nothing built) ran WLR_BACKENDS=headless WLR_RENDERER=pixman sway. Its config started the existing release oilfm on a temp dir. The spike typed into the nested WAYLAND_DISPLAY and captured frames with grim. Your Hyprland session was not touched.   • oilfm rendered fully under headless wlroots (some libEGL warnings, then a working software or GPU path), and j moved the cursor. measured
  • wtype g ? with no delay did not open help; wtype -s 300 'g?' did. A Shift modifier plus / typed /, not ?, because wtype sends keysyms through its own uploaded keymap. Input over the protocol is timing- and keymap-sensitive. measured

  • Without AccessKit, this black-box setup can act but cannot observe anything except pixels. The state has to come from inside the app, which is why b and d lead inferred.

Upstream or fork

  • The maintainers have not decided how alternative drivers should land. On mobile (#250) the maintainer wrote "We need to decide on an overall approach for these alternative drivers. Maybe they should be third party projects and we expose a driver API." The SwiftUI driver PR #254 was closed by its author on 2026-08-23 without comment. measured
  • So a gpui- or oilfm-specific driver would not be merged. A generic external-process driver (option b) is the one design that fits "expose a driver API": any toolkit, whether gpui, egui, SwiftUI or Android, just writes an adapter. Its odds are reasonable but not certain inferred.
  • Bombadil's gen-AI policy needs the issue, PR description, docs and commit messages written by a human, and generated code disclosed at the top of the PR. You would write the proposal text yourself. measured docs/development/gen-ai-policy.md
  • Until then, keep it as a fork, rebased on each release. The core traits have stayed stable while the terminal driver went from experimental to first-class (#183) inferred.

Guix: package variant, not graft

Today modules/engstrand/packages/bombadil.scm wraps upstream's static bombadil-aarch64-linux v0.7.10 with release-binary (copy-build-system, no compile) measured. That gives two ways to ship a changed Bombadil:

F1. Fork release asset (cheap)

Push the fork; upstream's release workflow already has a build-aarch64-linux job, so the fork's CI produces the same kind of static binary measured. The variant only swaps the origin:

(define-public bombadil/native
  (package
    (inherit bombadil)
    (version "0.7.10-native.1")
    (source
     (origin
       (method url-fetch)
       (uri "https://github.com/<you>/bombadil/releases/download/v0.7.10-native.1/bombadil-aarch64-linux")
       (sha256 (base32 "…"))))))

~10 lines, no local build. You trust GitHub's CI, as you already do for 0.7.10.

F2. From source + patches (what the brief describes)

(origin (inherit …) (patches (search-patches "bombadil-external-driver.patch"))) only works on a source package, which doesn't exist yet. Building Bombadil from source in Guix means:

  • 579 crates in Cargo.lock as cargo inputs measured
  • Zig 0.16 for libghostty-vt (Guix has zig 0.16.0) plus ghostty's Zig package cache fetched ahead of time; upstream's Nix does the same measured
  • trunk and wasm-bindgen-cli for the Inspect UI: guix show found neither. build.rs writes a placeholder page when lib/bombadil-inspect is absent, so a snippet can delete it measured

1-3 days guess, one heavy build offloaded to guix-builder. The patch then lives in the repo and the variant is exactly the brief's form.

Why not a graft. A graft tells Guix: "wherever a store item refers to package X, rewrite the reference to X′ without rebuilding". It is for security fixes to widely used libraries, such as openssl or glib. X′ must be a drop-in for X (same ABI, same file layout), and the point is to avoid rebuilding thousands of dependents. You can see it in this spike's own shell, where Guix printed applying 14 grafts for sway-1.12 for patched libraries under sway measured. Bombadil is the opposite case: nothing in your profile depends on it, so there is nothing to rewrite. The change adds a subcommand, so it is not a drop-in. And grafting a static binary does nothing, because there are no store references to rewrite inferred. The only graft-shaped case would be a security fix to a shared library a source-built Bombadil links, and that is not this inferred.

None of this is needed for step 1: option d uses the 0.7.10 binary that is already packaged.

Recommended plan

  1. oilfm-tty (0.5-1.5 days guess). Add a [[bin]] oilfm-tty behind ui-tests. It mounts a temp root, opens FileManager in TestApp, and maps stdin bytes to simulate_keystroke: printable keys, ESC to escape, CR to enter, and control bytes to ctrl-x. After run_until_parked it redraws a plain screen: the path line, a mode line, the buffer rows with a cursor marker, the confirm panel and a status line. It replaces the opener and the trash with test doubles (as view_tests.rs does with DirTrash). inferred
  2. Spec (0.5 day guess). Write oilfm.ts on the terminal driver, with weighted vim keys, :w, y, n and gR. Its properties: the screen never shows a panic; after a confirmed apply the listing matches disk (through a status line the adapter prints); a cancelled plan changes nothing; deletes stay in the trash double. Run it from a bb task modelled on desktop/build/bbh/test/bbh/bombadil.clj, with the same hermetic HOME and XDG.
  3. Decide on more after a few runs. If text screens are enough, stop there. If you want JSON state or the real Wayland input path, go to step 4.
  4. External driver (3-5 days guess). Open an issue upstream, in your own words, proposing a stdio-JSON driver. Build it in a fork as lib/bombadil-external. Its protocol is one line per message: {"state":…} from the app and {"action":…} to it, with templates Key, TypeText, Click and Custom(json). Copy the terminal crate's strategy, trace and CLI. The core needs no change, since FromGeneratedAction already has an identity impl for serde_json::Value measured. Ship it via F1, or F2 if you want the patch in the repo.
  5. Optional b' (+1-2 days guess). Put the same JSON adapter behind a debug socket in the real oilfm binary, run it in a nested headless sway, and send input with wtype -s delays or a native virtual-keyboard client.
  6. Revisit AT-SPI when Guix ships Rust 1.95 or later and gpui's a11y issues settle.
