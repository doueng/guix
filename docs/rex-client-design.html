A Rex client driven by Clojure: design and setup audit

T194, by W242 on 2026-11-17. Follows rex-vs-herdr.html (W229, W230), which decided whether to replace Herdr with Rex. This page designs the client and audits what it could replace.

Goal: turn the pasted design (a thin Rust GUI, Rex for sessions, libghostty for terminals, a babashka sidecar that owns commands and an Emacs-style M-x) into a concrete architecture; check its claims; settle UI-in-Clojure or not, and egui or GPUI; prototype stage 1; and say what in /home/engstrand/guix it would remove or merge.

Short answer.
  1. The pasted claims hold, with three corrections: the OSC 7501 states are idle, working, done, blocked, error (not finished or failed); keymaps are layers the client sends to client.keymap, not just a list to read; and agents only appear in Rex if they emit OSC 7501 themselves. measured
  2. You already own half of this design. Dusk, your desktop shell, is a GPUI program whose UI is described by a live babashka runtime over EDN lines, with a launcher, palette and which-key panel. leader.edn is already a cross-app command registry. Build the Rex client from Dusk's crates and protocol, not from scratch, and feed its registry from leader.edn. measured
  3. GPUI, not egui, because Dusk has already paid GPUI's Guix costs (fonts, Vulkan, a pinned Zed revision) and its EDN-to-GPUI renderer and runtime would be shared. egui would mean a second toolkit and a second protocol. inferred
  4. Open question: Clojure defines the panels (sidebar, lists, dialogs) as Dusk EDN trees, and all behaviour. Rust owns the terminal panes, pane layout, the key path and the minibuffer widget. That is the split Dusk already uses, plus a hard rule that nothing per-frame or per-key goes through bb. inferred
  5. Stage 1 works. A 149-line bb sidecar generated 95 M-x commands from a real Rex server's rex api list --json, filled session and block from context, rejected a bad enum by schema, prompted for missing arguments, and found a pane whose program reported blocked. measured
  6. Stage 0 works too. Dusk's pinned GPUI and libghostty-vt build together in one binary under Guix rust 1.96 and zig-0.17 on this machine, after bumping one locked crate (bitflags). measured
  7. Audit: remove Herdr and its pickers (about 680 lines plus Herdr branches elsewhere), merge keyleader's Herdr side, the pickers and the agent picker into the client's M-x; keep Hyprland, kanata, Emacs, bbh's Emacs surfaces, Dusk, the phone and the voice paths. Hyprland stays: the client replaces Herdr's tiling, not the compositor. inferred
  8. The go or wait call in the first page is unchanged: the Rex server still has no stable release or license. Stage 1 and a GPUI terminal spike are cheap, reusable and can run now. inferred

Tags: measured means I ran it or read it in code or docs, inferred means reasoned from what I read, guess means an estimate.

2. What you already have

The paste designs from zero. Three pieces of this repo already do much of it. measured

Dusk (/home/engstrand/guix/desktop/build/dusk) is your Wayland shell: about 3,760 lines of Rust on GPUI, pinned to Zed rev 7f7520b, plus a babashka runtime. bb sends a map of surface id to an EDN UI tree (dusk.ui: layer, row, column, box, stack, text, icon, button, input, progress); Rust re-renders the tree each frame and sends events back. It replaced Noctalia in October and draws the wallpaper, notifications (it owns org.freedesktop.Notifications), the volume and brightness OSD, the dmenu launcher, the command palette, the leader which-key panel and window hints. Hot reload took 71 ms. Its config is /home/engstrand/guix/desktop/configs/dusk/config.clj (332 lines).
leader.edn (/home/engstrand/guix/desktop/configs/keybindings/leader.edn) is already a command registry as data: 44 bindings with :keys, :label, groups, and an implementation per context (:herdr, :doom, :nvim, :idea, :desktop); 17 of them have a :herdr implementation. palette.edn lists Chrome and IntelliJ commands for the palette. keyleader (543 lines) runs them and keeps Hyprland's binds in step.
Emacs M-x through Dusk. palette.el sends Emacs's 6,661 commands to Dusk's palette; warm opening is 91 ms. The tuning notes say what matters: big catalogues cost in bb's EDN parse (20 ms before trimming) and in IPC, so filter in Rust and send the catalogue once.

So: the Rex client is Dusk's architecture with a terminal in it, and its commands are leader.edn's with a :rex context. That is the main design change from the paste.

3. Architecture

  • Three processes. The rex server (a Home service) owns sessions, PTYs, remote hosts and OSC 7501. The Rust client, working name rexmux, owns the window, panes, input and the minibuffer widget. A bb child owns commands, contexts, workflows, plugins and the contents of panels. inferred
  • Rust talks to Rex on one control WebSocket and one data WebSocket per visible pane, as in the W230 spike: tokio-tungstenite on the Unix socket, a libghostty-vt thread per pane as rexy does. The window and widgets are GPUI, with Dusk's fonts, style and EDN renderer moved into a shared crate. inferred
  • bb reads Rex directly for queries and events, with rex api call (21 ms per call measured) and one long-lived rex events --json (measured: it streamed program_status_changed as a program reported working then done). Later it can open its own socket: bb can open the Unix socket (measured), but has no WebSocket client for it, so that is about 100 lines of framing. measured
  • bb asks Rust to act by returning effects. bb runs side effects it can do itself (files, processes, rex calls that are not about this client). Anything that belongs to this client, such as its focus, its keymap, its UI, or a call that needs this connection's identity, is an effect. inferred
  • A separate process from the Dusk shell, built from the same crates. A terminal crash must not take down notifications and the wallpaper. inferred

4. IPC protocol

One EDN map per line on the child's stdin and stdout, the same framing and parser as Dusk (src/edn.rs, runtime.clj). Requests carry :id; replies echo it. Everything else is a notification. inferred

DirectionMessageMeaning
bb → Rust{:op :ready}Runtime loaded; Rust sends :hello.
Rust → bb{:op :hello :client-id .. :socket .. :api-revision 14}Who this client is, so bb can scope its own calls.
Rust → bb{:op :context :ctx {:session-id .. :window-id .. :block-id .. :program "pi" :mode nil :status {..}}}Sent on focus or program change, debounced. bb evaluates :when against it.
bb → Rust{:op :commands/changed :commands [{:id :agent/next-blocked :title .. :category .. :keys .. :doc ..}] :keymap {:name "mx" :bindings [..]}}The whole catalogue and its keymap layer, sent on load and on change, never per keystroke. Rust filters with nucleo and only shows those whose :when bb marked true for the current context.
Rust → bb{:op :commands/invoke :id 7 :command :rex/session.new_split :args {..} :ctx {..} :origin :mx}Run a command. Origin is mx, key, rex-do or panel.
bb → Rust{:op :reply :id 7 :prompt [{:name :direction :enum [..] :doc ..}] :partial {..}}Missing arguments: Rust prompts in the minibuffer, then invokes again with the answers. Completion of ids uses target.complete.
bb → Rust{:op :reply :id 7 :effects [[:rex/call ..] [:ui/message ..]]}Done: apply the effects in order and stop at the first failure.
bb → Rust{:op :reply :id 7 :error ".." :invalid [{:arg :direction :error ..}]}Schema or command error, shown in the echo area.
bb → Rust{:op :effects :effects [..]}Unprompted effects, from a workflow or a Rex event bb watched.
bb → Rust{:op :render :panels {:sidebar [:column ..]}}Dusk UI trees for panels. Same DSL as dusk.ui.
Rust → bb{:op :panel/event :panel :sidebar :handler 12 :value ..}A click or input in a panel, routed to the handler bb registered, as Dusk does.
Rust → bb{:op :effect/result :id 7 :results [..]}What the effects returned, for workflows that continue.
Rust → bb{:op :eval :id 9 :code ".."}describe-command, reloads and tests; nREPL stays opt-in.

This is the paste's commands/list, commands/invoke, state/changed and effect/apply, reshaped so the catalogue moves once and filtering stays in Rust.

6. Keys and prefix keys

Keys must never wait on bb. inferred

  1. bb compiles every :keys into one keymap layer named mx and the command ids into the actions list. Rust sends both to client.keymap as a defaults layer, so init.lua and recorded overrides sit above it, and Rex reports shadowed keys and unknown actions as diagnostics. One merged keymap, one conflict checker. measured that the API takes layers and actions; inferred that this layout suits us
  2. Rust keeps the merged result locally. A key press resolves in Rust: a bb command goes to :commands/invoke; client.key.forward goes to client.key (init.lua runs it); a server or block action goes to client.action; anything else is typed into the pane.
  3. Prefix keys: the server keeps no state between keys, so Rust holds the pending prefix, shows the continuations in a which-key panel (the Dusk leader-hint panel, moved in-window) and times out.
  4. Outside callers use Rex, not a private socket: rex -C rexmux do agent.next_blocked from Hyprland, keyleader or bbh, and client.perform from other clients. That replaces keyleader's direct Herdr socket calls. inferred from reference_cli.md line 113

8. Open question: should Clojure define the UI?

Recommendation: Clojure defines panels and all behaviour; Rust owns panes, layout, keys and the minibuffer widget. inferred

Clojure defines
  • The sidebar, agent list, session list, dialogs, help buffers: Dusk EDN trees, re-rendered on change, hot-reloaded.
  • What the minibuffer lists and prompts: commands, items, argument specs.
  • Commands, keymap layers, modes, workflows.
Rust owns
  • The terminal panes: cells, cursor, selection, scrollback, mouse, Kitty graphics later.
  • Pane tiling, taken from Rex's session.view, not from Clojure.
  • Key resolution and the minibuffer's text input, IME and fuzzy filtering.
  • The effect applier.

Why. Dusk already proved the declarative half here: one EDN tree per surface, stateless hot reload, a 3,760-line Rust side. But Dusk's trees are small and change on events; a terminal changes every frame, and a 20 ms bb round trip per keystroke would be felt. Rex already owns the layout, so a Clojure layout DSL would duplicate session.view. Defining panels in Rust instead would make every new panel a Rust rebuild of several minutes, which works against live extension. The split also matches the paste's own idea of high-level primitives, since Dusk's DSL is such a set.

12. Build order

The paste's order, adjusted for Dusk. Each stage ends with something usable or a decision. guess for durations

  1. Stage 0, done: native build check on Asahi. Dusk's GPUI pin plus libghostty-vt in one crate under Guix rust 1.96 and zig-0.17 (section 13).
  2. Stage 1, done as a prototype: the bb registry over rex api. Next: EDN framing, leader.edn as a source, keymap layer output, a test against the help document of each Rex revision.
  3. Stage 2, 1 to 2 weeks: split Dusk's renderer into a library crate; a GPUI window with a sidebar panel from bb, one pane and the minibuffer. Start with the pane drawn from session.view and a snapshot only.
  4. Stage 3, 2 to 3 weeks: live data streams per pane, client.key input, keymap layers and prefix keys, floating layers, resize and ownership.
  5. Stage 4, 1 to 2 weeks: agent workflows (next-blocked, send, broadcast, new-worktree, collect-results), the bbh resume script, then the audit's migrations with Herdr still installed as a fallback.

Stages 0 and 1 are worth doing before the Rex gate opens because both carry over: stage 0 tests Guix and Asahi, and the registry's leader.edn and keymap work helps whichever multiplexer wins. Stage 2 onward should wait for a stable, licensed Rex, as the first page says.
