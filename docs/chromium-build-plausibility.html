Building Chromium through Guix: plausibility

Goal. Decide whether to replace flatpak Google Chrome with a Chromium you build through Guix on guix-builder, carrying your own patches (keys, no address bar with vertical tabs, PGO, M-series tuning). Answer: not worth it now. Two of the four reasons for it are already handled or nearly handled without patches. The others would at best match what Google's build already ships. Meanwhile the builder can't hold the build, and you'd have to rebuild every week to keep up with security fixes. If you still want it, the phased plan at the end costs about 1 EUR of server time per build, but each build takes hours of your attention.

Labels: [M] measured here today, [I] inferred from sources (cited), [G] guess. Nothing was built and no server was created.

1. What Guix already has

  • [M] The guix channel packages ungoogled-chromium 156.0.8078.47-1 and a wrapper ungoogled-chromium/wayland in gnu/packages/chromium.scm. It sets no supported-systems, so aarch64 is allowed. The rde and asahi channels have no Chromium. You don't use nonguix.
  • [M] guix weather ungoogled-chromium --system=aarch64-linux: 0 of 1 available on bordeaux, ci and substitutes.asahi-guix.org. For x86_64 it is 100% (124 MiB of nars, 533 MiB installed). So on your laptop even the unpatched package means a full build.
  • [M] Your flatpak Chrome is 157.0.8103.38 (aarch64, flathub, updated 2026-11-04). Guix trails it by a major version.
  • [M] Build settings already in the package: is_official_build=true (which turns on ThinLTO, [I] https://source.chromium.org/chromium/chromium/src/+/main:build/config/compiler/compiler.gni ), chrome_pgo_phase=0 (no PGO), enable_widevine=false, safe_browsing_mode=0, symbol_level=0, rtc_use_pipewire=true, and on aarch64 use_vaapi=true use_v4l2_codec=true. It sets timeout to 40 h and max-silent-time to 2 h, with the comment that one core of a mid-range x86 machine needs more than 24 h.
  • [M] The package sets a native search path CHROMIUM_EXTENSION_DIRECTORY = share/chromium/extensions. A Guix package could therefore install vimium-cljs into the profile, with no Web Store involved.

Setup-specific options

  • -mcpu=apple-m1: a trap. Guix's package uses the unbundle toolchain for both host and target [M]. So -mcpu would also apply to build tools that run during the build, such as v8's mksnapshot and torque. The builder's Ampere Altra is an Armv8.2 Neoverse N1 chip, and M1 code that uses Armv8.4/8.5 instructions could stop it with SIGILL [I] https://www.hetzner.com/cloud/ . Use -mtune=apple-m1 instead, which only changes scheduling, set through CXXFLAGS/CFLAGS in the env phase. Expect 0 to 3% [G].
  • Wayland only: ozone_platform_x11=false ozone_platform="wayland" ozone_auto_platforms=false [I] https://chromium.googlesource.com/chromium/src/+/main/docs/ozone_overview.md . This saves a little build time and binary size. The risk is that X11-only code paths break the build in some release.
  • PipeWire: already on [M].
  • VA-API on Asahi: there is no VA-API driver for the M1's video decoder (AVD) yet [I] https://asahilinux.org/docs/platform/feature-support/overview/ , so video decodes in software in any build. [M] /dev/video0 exists, but that is most likely the camera [G].
  • Turning off more features: Guix already turns off remoting, VR, mDNS, reporting, enterprise components and tests [M]. Little remains that would shorten the build much.

3. What you lose leaving Google Chrome, and how to get it back

  • Widevine (Netflix, Spotify web, Disney+): Guix builds with enable_widevine=false [M]. You can rebuild with enable_widevine=true and add Asahi's widevine-installer, which extracts the ARM64 CDM from a ChromeOS image [I] https://github.com/AsahiLinux/widevine-installer . The CDM is proprietary and you'd maintain it by hand.
  • Google sync and sign-in: Google cut third-party Chromium builds off from sync in 2021 [I] https://blog.chromium.org/2021/01/limiting-private-api-availability-in.html , and ungoogled-chromium removes it as well. You can't get it back. Your bookmark push to second-brain reads Chrome's profile (modules/engstrand/features/second-brain.scm) [M] and would need the new profile path.
  • Chrome Web Store installs: ungoogled-chromium can't install from the store directly. Use the chromium-web-store helper extension [I] https://github.com/NeverDecaf/chromium-web-store , or ship extensions through CHROMIUM_EXTENSION_DIRECTORY [M], which suits vimium-cljs well.
  • Safe Browsing: off (safe_browsing_mode=0 [M]).
  • Automatic security updates: you would own the rebuild schedule. See section 5.

That comes from Guix's own comment (more than 24 h on one x86 core) [M] and from the usual reports of 2 to 4 h on 16-core desktops, scaled by about 2× for slower cloud vCPUs. Divide by the vCPU count and add about 1 h for the link. Phase 1 measures the real figure.
  • Resizing the CAX21 is worse than a separate server [I]: Hetzner's rescale keeps the 80 GB disk unless you also upgrade the disk, and an upgraded disk can't be scaled back down. Your make builder ACTION=create already provisions Guix through rescue (remote-builder-plan.html) [M], so a TYPE=cax41 variant plus a temporary entry in /etc/guix/machines.scm is most of the tooling.
  • PGO doubles it: an instrumented build, about 1 h of workloads on the laptop, then the optimized build. That is about 12 to 18 h on a CAX41 [G], around 1 EUR. Money doesn't matter here. The cost is wall time and attention.
  • Laptop: 15 GiB RAM with zram and 32 GB of free disk [M: same doc]. Don't build it there, because that risks the freezes earlyoom guards against.

5. Rebuild cadence and security

  • Chrome ships a major release every 4 weeks and security updates every week [I] https://chromereleases.googleblog.com/ . The browser is your biggest attack surface.
  • Guix already trails, 156 against your flatpak's 157 [M]. A variant built on Guix inherits that lag, plus your build time and the time to rebase patches. Building your own %chromium-version means writing your own Debian and ungoogled patch pins, so it becomes a fork of chromium.scm.
  • To keep up you'd rebuild weekly: about 52 builds a year at 6 to 9 h each. A PGO profile can be reused across point releases, with warnings about stale functions [I], so only major releases need the doubled build.

7. Recommendation and phased plan

Keep the flatpak Chrome. Let T185 finish. Build only if T185 shows that Chrome itself can't hide the address bar with vertical tabs, and if the next step, trying Vivaldi's settings, doesn't satisfy you either. Even then, PGO and -mtune are optional extras, not reasons to build.

  1. Phase 1, unpatched build and measurement (one evening): create a CAX41, run guix build ungoogled-chromium on it with --cores=16 and record wall time, peak RSS and peak disk. Then guix copy the result to guix-builder, delete the server, and live with it for a week. This answers whether Widevine and sync matter to you.
  2. Phase 2, patches: add a variant in a new module, modules/engstrand/packages/chromium.scm (sketch below). Use a phase that patches the already ungoogled tree rather than origin patches, so that iterating doesn't repack the source, about 1 GB of tarball [G]. Origin patches would work too, but they apply before domain substitution, so they must not touch URLs.
  3. Phase 3, PGO: a pgo-phase parameter on the variant. Build phase 1, run Speedometer 3, JetStream 2 and a list of your usual pages under LLVM_PROFILE_FILE on the laptop, merge, and commit the .profdata (tens of MB [G]) to local/ or the builder, not to git. Then build phase 2.
(define-public ungoogled-chromium/engstrand
  (package
    (inherit ungoogled-chromium)
    (name "ungoogled-chromium-engstrand")
    (arguments
     (substitute-keyword-arguments (package-arguments ungoogled-chromium)
       ((#:configure-flags flags)
        #~(append #$flags
                  '("ozone_platform_x11=false"
                    "ozone_platform=\"wayland\""
                    "ozone_auto_platforms=false")))
       ((#:phases phases)
        #~(modify-phases #$phases
            (add-after 'unpack 'apply-engstrand-patches
              (lambda _
                (for-each (lambda (p) (invoke "patch" "-p1" "--forward" "-i" p))
                          '#$(list (local-file "patches/chromium-hide-toolbar.patch")))))))))))

Stop conditions: if a patch fails to apply two releases running, or if security builds lag Chrome stable by more than a week, go back to the flatpak.
