Midjourney MCP for Pi: review and install

Outcome

The Midjourney MCP server and CLI by thenavidm are packaged in Guix Home and registered with Pi. pi mcp list shows midjourney: connected, 32 tools (codemode), and a Pi session called mcp__midjourney__whoami, which answered that the browser is not running and nobody is signed in. Nothing has touched Midjourney yet.

What it is

  • One TypeScript program, published on npm as @thenavidm/midjourney-mcp-cli 2.0.1. It is both an MCP server (midjourney-mcp) and a CLI (midjourney-cli), with 32 tools: imagine, vary, upscale, pan, zoom, animate, jobs, downloads, moodboards and explore.
  • MIT licence. Runtime dependencies: Slipway (Apache-2.0, same author), the MCP SDK, zod and ajv. That is 9 packages in total, with no install scripts.
  • Midjourney has no API, and the program needs no key or cookie. It starts its own Chrome profile in ~/.midjourney-mcp/chrome-profile, which you sign into once. It then calls midjourney.com's own /api/ endpoints with fetch() inside that page, over the Chrome DevTools protocol.

Security review

  • Network. The code contacts only the Midjourney origin (through the page), cdn.midjourney.com for downloads, and the local DevTools port. There is no telemetry, analytics or update check. Slipway fetches a URL only in its own developer check command, and runs a subprocess only in install <client>, which writes MCP client configs. This setup uses neither.
  • Build provenance. I compiled git tag v2.0.1 with tsc. The npm tarball's dist is byte-identical, excluding source maps, so the package uses the published tarball.
  • Risk 1: the DevTools port. While the controlled Chrome runs, any local process can drive your Midjourney session through its DevTools port. The default port is 9222. The wrappers move it to 127.0.0.1:9339, so the server never attaches to another Chrome.
  • Risk 2: spending. Slipway's guard asks a person through MCP elicitation. Pi does not support elicitation, so it falls back to confirm: true, which the model can set itself. An agent could therefore spend fast GPU time without asking you, and the default speed is fast. For that reason Pi's entry sets MIDJOURNEY_ALLOW_DESTRUCTIVE=0, which refuses paid and irreversible calls. I checked that imagine is refused under it.
  • Unofficial. Driving the web app's private API may break or go against Midjourney's terms. The tool paces its requests at 700 ms apart.

How it is installed

  • /home/engstrand/guix/modules/engstrand/packages/midjourney-mcp-cli.scm pins the npm tarball and each dependency by hash, and runs the program on Guix node 24. The wrappers point MIDJOURNEY_CHROME_PATH at a small launcher for the Flatpak Chrome (--filesystem=~/.midjourney-mcp) and set the port.
  • /home/engstrand/guix/modules/engstrand/features/development.scm adds it to the Home packages.
  • /home/engstrand/guix/desktop/pi/agent/mcp.json registers the server with codemode exposure. Stow links it to ~/.pi/agent/mcp.json.
  • No secrets: the login lives in the Chrome profile under ~/.midjourney-mcp, outside the repo.

To use it

  1. make home-apply installs the package and links mcp.json.
  2. midjourney-cli login opens the controlled Chrome; sign in to Midjourney there once.
  3. Read-only tools, such as whoami, list_jobs and download_job, then work from Pi. For Pi to generate, remove MIDJOURNEY_ALLOW_DESTRUCTIVE from mcp.json.
