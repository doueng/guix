How Ghostty plus Rex works (MUX=ghostty-rex)

How the MUX=ghostty-rex terminal works, from the code as of T208 and T210: the parts, what happens when you press a key, how output reaches the screen, and how to debug it. Use this page to understand it. The dev page is for changing it.

In short

Your terminal window is a plain Ghostty that only draws. Your shells and agents live in the Rex server, a separate daemon, so closing the window, reloading the client or switching multiplexers loses nothing. Between the two sit two processes: bb attach, a Babashka program that talks to Rex, reads your keys and decides what to draw, and rexg-render, a small C program on Ghostty's own terminal library that turns each pane's output into cells and composes the window. Herdr is still installed, and make mux MUX=herdr switches back.

The big picture

  • Ghostty is started with its own class and an extra config, /home/engstrand/.config/ghostty-rex/ghostty, which clears Ghostty's tab and split keys so every key reaches the client. Its only job is to show what rexg-render writes and to send keys and mouse reports back.
  • bb attach (desktop/build/ghostty-rex/src/rexg/) runs straight from the checkout, so an edit needs no build. One thread handles every change in order: keys, Rex replies and events, sidecar messages, renderer lines. After each batch it draws once.
  • The sidecar is rexmux's command layer (desktop/build/rexmux/sidecar/), loaded into the same bb process. It owns M-x, the leader keys, agent status and bbh. It starts one child, rex events --all --json, to follow agent reports.
  • rexg-render (csrc/rexg-render.c, about 580 lines of C) keeps one libghostty-vt terminal per visible pane. bb tells it the layout, the chrome text and the cursor, and it writes only changed cells to Ghostty.
  • The Rex server owns sessions, tabs, panes and their programs. bb talks to it over the socket through one control WebSocket (requests, replies, events) and one data WebSocket per visible pane.
Why two halves? Pane bytes never reach Ghostty itself. Rex's own terminal already answers a program's queries (cursor position, colours), so nothing answers twice. Ghostty's library does the parsing, and Babashka keeps all the logic editable without Rust or Zig. The cost is that Kitty graphics inside panes are not shown. The design is in /home/engstrand/guix/docs/rex-client-languages.html (option 1).

Cmd+Return to a usable window

  1. Hyprland. Cmd is Super. SUPER + RETURN runs ~/.local/bin/workspace-or-herdr-tab 1 (desktop/configs/hypr/hyprland.lua). Cmd+E, D and G do the same for tabs 2 to 4, and Cmd+B always opens a new window. Hyprland also starts one at login (startup.lua).
  2. Is a window open? workspace-or-herdr-tab reads the backend from /home/engstrand/.config/engstrand/mux (ghostty-rex) and looks for a window of class dev.engstrand.Rex. If one is focused, it runs rex -C ghostty-rex do mx.tab.select_1, and Rex asks the client to switch tabs. If one exists elsewhere, it focuses it. If none exists, it runs mux-terminal.
  3. Launch. mux-terminal runs desktop/bin/ghostty-rex, which execs ghostty --class=dev.engstrand.Rex --gtk-single-instance=false --config-file=~/.config/ghostty-rex/ghostty -e …/ghostty-rex attach.
  4. Inside Ghostty, ghostty-rex attach finds rexg-render: REXG_RENDER, else the Guix one on PATH, else the checkout's target/ build. A Hyprland notification says when it is missing. It then execs bb --config desktop/build/ghostty-rex/bb.edn attach.
  5. bb starts. It reads /home/engstrand/.config/ghostty-rex/config.edn (servers, shell fish, leader file, startup tabs) and starts rexg-render as a child. rexg-render switches Ghostty to the alternate screen, turns on mouse reports, bracketed paste and the Kitty keyboard protocol, and reports the size.
  6. Server. The socket is $XDG_RUNTIME_DIR/rex/server.sock. If it is missing, or a connection fails, bb runs rex server start. That command does nothing when a server already runs, and it replaces a socket a dead server left. The server is a daemon, so it outlives the window, as Herdr's does.
  7. Connect. bb opens the control WebSocket, says hello as client ghostty-rex and gets a welcome with its client ID. It registers its keymap and its commands, so rex -C ghostty-rex do … works, and asks for the session list.
  8. Pick the session. If main exists, bb attaches to it. If not, bb creates it from :startup: four tabs in ~/guix, shell (fish), bbh (emacs-bbh), pi and jjui, each a Rex block running its program in fish. Then it focuses tab 1.
  9. Revive after a reboot. When Rex restarts, it brings each pane back as your login shell, bash, without its program. For the startup session, bb asks each pane what runs in it. A bare shell gets a new block beside it running fish, or the tab's program (pi --continue for pi), with the same label and directory. Then the bare shell's block closes. Nothing is typed into the old shell, so no exec line shows (T210). The echo line says restored tab pi.
  10. Streams and sizes. For each visible pane, bb asks Rex for a data ticket (data.connect) and opens a data WebSocket. It takes ownership of the pane's size and tells Rex its size in cells, so programs lay out for the space they have. The first frame shows a snapshot of each pane.
Reconnect. If the control connection drops, the status line turns red with local not connected, reconnecting, and the bottom line says why and when the next try is. Tries come after 0.25 s, then double up to every 4 s, each one starting the local server if needed. When it answers, bb reattaches to the session it showed. You never need to kill the window.

A keypress

  • Hyprland keeps the Cmd chords for the desktop. Alt+Space is routed per window class by leader.edn's :apps: for dev.engstrand.Rex it is :pass, so Hyprland sends Alt+Space on to the window. In most other windows it opens the launcher.
  • Ghostty keeps Ctrl+Shift+C and V, Shift+Insert, font size (Ctrl+= and Ctrl+-) and config reload (Ctrl+Shift+Alt+R). Cmd+Left and Cmd+Right become Ctrl+A and Ctrl+E. Everything else goes through the Kitty keyboard protocol, so chords such as Ctrl+Enter or Alt+Space arrive whole.
  • Alt+Space is the only prefix (T208). It starts a sequence from leader.edn: w v splits right, t r renames the tab, u jumps to the next blocked agent, i opens the bbh inbox, Space opens M-x, and so on. Which-key lists what can follow, and Escape or Ctrl+G cancels. Ctrl+b is not a prefix here: it reaches fish or Emacs. Alt+x also opens M-x.
  • Bare Ctrl+h/j/k/l go through keyleader's term-nav. Vim, Emacs, pi and fzf keep the keys they use, and otherwise focus moves to the neighbouring pane.
  • Everything else is sent to Rex as client.key for the focused pane. Rex encodes it for that program's keyboard mode and writes it to the pane. Typing also leaves scrollback and clears a mouse selection.
  • Mouse. A click focuses a pane. A program that asked for mouse reports, such as Vim or jjui, gets them. Otherwise a drag selects and copies, the wheel scrolls into history, and a middle click pastes. Hold Shift to use Ghostty's own selection instead.

Output to the screen

  • Output from panes is never queued behind keys. Each stream's reader thread writes its bytes straight to rexg-render, tagged with the pane ID. Only Rex's own messages, a resize or a program exiting, go through bb's queue.
  • rexg-render does not choose where a pane goes. bb sends it the layout (l: pane, x, y, width, height), the chrome (v: tab bar, titles, status line, menus), and the cursor (c: in the focused pane, at a point, or hidden). It sends each only when it changed.
  • rexg-render reports back on stderr: the window size, each pane's mouse and scroll mode, errors, and the text of a pane for tiny fingers and mouse copies.
  • A pane that hides its cursor (ESC [ ?25 l) shows none, and a pane scrolled into history says ↑ history (type to return) in its title.

What it is
ATab bar. main is the Rex session's label, from :startup :label in config.edn. A session without a label shows its place in the session list, as session 2. Then the tabs, numbered and named, with the active one in brackets. Each tab names itself from its focused pane, as below, unless you named it. Cmd+Return, E, D and G pick 1 to 4.
BPane title rows. ▶ marks the focused pane, and ─ marks the others. Then what runs in the pane and its directory, fish ~/guix, with ~ for home and only the last two parts of a deep one (…/src/app); an ssh pane shows ssh and the host. … means Rex has not answered yet. An agent's pane adds its state icon and app: ● working, ○ idle, ✓ done, ! blocked (in red), ✗ error. Dividers │ separate tiled panes, and floating layers get a full frame.
CPane contents, drawn by rexg-render from that pane's terminal.
DStatus line. First the focused pane's program and directory, as on its title row. With more than one server in config.edn :servers, the current one's label (local, or a host's) comes first; with the one local server there is nothing to tell apart, so it is left out. agents counts panes that reported a status (OSC 7501). blocked counts those waiting for you. attention counts the blocked, failed and unseen finished ones, which Alt+Space U cycles through. It turns red when something is blocked or the server is down. Then it reads local not connected, reconnecting, or connecting to local at start. sidecar down shows only before the sidecar is ready.
EEcho line. The last message, such as Copied 42 characters, restored tab pi, Quit or an error. It also shows the M-x prompt, or the prefix you have typed so far (alt+space w-).

The window title is the session label, with ! 2 blocked added when agents wait, so Hyprland and the task switcher show it too.

How tabs name themselves

As in Herdr and tmux, a tab is named after what runs in it, and the name follows as that changes (T210). No Rex ID shows anywhere in the chrome; rex session list and rex -b still take them.

  1. Where the facts come from. When a session is shown, bb asks Rex about each of its panes: block.method process (the foreground program and its directory), title (the OSC 0 or 2 title a program set) and pwd (the directory a shell reported with OSC 7). After that Rex's events keep them current on the same connection: process_changed when a program starts or ends or the shell changes directory, title_changed and pwd_changed. Nothing polls.
  2. The name. A shell (fish, bash, zsh) is named by its directory's last part, ~ at home: guix. ssh is named by the host in the title the far side sets, else ssh. Any other program by its own name, cleaned up: .emacs-31.1-real reads emacs, -fish fish, emacsclient emacs. A script run by node, python or bb is named by the script, the app its agent reports (OSC 7501), or the command fish put in the title. Names are cut to 16 characters.
  3. Startup tabs. bbh, pi and jjui keep their config.edn label while their program runs, since bbh says more than emacs. Quit the program and the tab takes the shell's directory. The shell tab runs no program, so it always shows its directory. The labels stay in Rex, because a revive after a reboot finds the tabs by them.
  4. Your name wins. Alt+Space t r names the tab by hand; that name stays whatever runs, until you rename it with an empty name, which hands the tab back to its pane. Rex's own default label, Window and 8 hex digits, counts as no name.

Agent status and bbh

  1. Reporting. A program reports its state by printing OSC 7501 into its own terminal. For example, the bbh agent shell in Emacs prints ESC ]7501;state=working:app=bbh ESC \ (desktop/configs/doom/agent-shell.el). Rex stores the record on that block.
  2. Following. The sidecar reads every Rex event through rex events --all --json. When it starts, it also loads every record Rex already holds, so it agrees with Rex from the start. It ranks blocks blocked first, then error, then unseen done, and sends the list to the model. That list is what you see in the titles and the status line.
  3. Notifications. When an agent first becomes blocked, fails or finishes, the sidecar runs notify-send --app-name=ghostty-rex, for example bbh needs you. bbh's own notifications focus this window when the source is a pane, since they match the class dev.engstrand.Rex (bbh/super/notify.clj).
  4. Getting there. Alt+Space u focuses the next blocked agent, and Alt+Space U the next one wanting attention. Focusing a finished agent marks it seen.
  5. bbh from the window. Alt+Space i floats bbh inbox over the panes, and the layer closes when it exits. M-x bbh: tell the Router, or a thread as T12 … runs bbh say --from rex TEXT, which goes to the thread the text names, else to the Router. The bbh tab runs emacs-bbh, which is emacsclient -s bbh-super -t.

Cmd+Space

Cmd+Space runs ~/.local/bin/palette (T208). When the focused window is dev.engstrand.Rex, it asks Rex for what the client shows: rex client inspect ghostty-rex gives the session and the commands the client registered, session.view gives the focused pane, and block.method process gives the program running in it. The list then shows:

  1. the focused program's own entries, such as fish's or jjui's;
  2. the leader.edn rows the client offers, with their Alt+Space keys shown, so you learn them;
  3. every other M-x command;
  4. then the desktop's global entries.

Picking a Rex row runs rex -C ghostty-rex do ACTION. Rex forwards it to the client as a perform request, the client runs the command, and it replies. This is the same remote control that Cmd+Return and E/D/G use for tabs, and that rex -C ghostty-rex do mx.client.reload uses (mx.client.reload). It is also why two ghostty-rex windows make rex -C ghostty-rex ambiguous.

The switch. (define %terminal-mux 'ghostty-rex) in modules/engstrand/config.scm is the choice (herdr, rex or ghostty-rex). feature-familiar-terminal-mux (modules/engstrand/features/terminal-mux.scm) installs the packages above and writes the one word to ~/.config/engstrand/mux. Hyprland's keys.lua, mux-terminal, workspace-or-herdr-tab, the palette, keyleader and bbh's notify all read that word, through desktop/lib/mux.clj or their own copy. A MUX environment variable overrides it for one command.

make mux MUX=ghostty-rex   # edit config.scm, make home, hyprctl reload
make mux MUX=herdr         # back to Herdr
guix home roll-back        # also brings back the previous word

Rex sessions survive a switch, because Rex keeps them and the rexmux and ghostty-rex windows both show main. Herdr's sessions are its own.

The bb process keeps its PID across a reload, because the reload replaces it with exec. The renderer and the events follower get new PIDs. A [rex] <defunct> child under bb after a reload is the old events follower, which the new bb never reaps. It is harmless. inferred

Debug and recover

You seeWhat it means and what to do
Red status line, local not connected, reconnectingThe control connection to the Rex server dropped: the server stopped, crashed, or was replaced by a newer build. The client retries every 0.25 to 4 s and starts the server itself, then reattaches to the same session. If it stays red, run rex server status and read the log it names. A stuck socket is fixed by rex server start.
connecting to local that never endsThe first connection hasn't succeeded. Same checks. Also check that rex is on Hyprland's PATH, the Guix Home profile.
Notification: rexg-render is missingRun make home with %terminal-mux set to ghostty-rex, or make build NAME=ghostty-rex for a checkout build.
A tab shows bash, or lacks its programRevival runs only for the startup session, when a window opens. Close the window and press Cmd+B. A reload, or a window opened with --session, skips it.
An edit doesn't showbb code, config.edn and leader.edn: rex -C ghostty-rex do mx.client.reload (M-x Client: reload). C code: make home, then reload. The Ghostty config: Ctrl+Shift+Alt+R in the window.
Cmd+E, D or G or the launcher act oddlyrex client list. Two ghostty-rex clients make rex -C ambiguous, so close one window.
Window frozenrex -C ghostty-rex do mx.client.reload first. If that fails, run pkill -f 'ghostty-rex/bb.edn attach' (SIGTERM ends bb and rexg-render cleanly), then Cmd+Return. Your panes stay in Rex.

Logs

  • Client: it logs only when REXG_LOG is set, so start a window from a terminal: REXG_LOG=/tmp/rexg.log /home/engstrand/guix/desktop/bin/ghostty-rex. The log has keys, every request (out), lost with the reason, rex server start results, renderer lines and quit with its reason.
  • Server: one log per server under /home/engstrand/.local/state/rex/servers/, and rex server status prints the current one. Look for Rex server ready and stopped.
  • Bottom line: errors from Rex requests and pane streams (stream closed: …, pane ID: …) appear on the echo line.

make switch and make home

make switch reconfigures the system and reloads kanata. It does not touch the Rex server, the window or Guix Home. make home installs new rex, rexg-render and Ghostty builds, but running processes keep their old binaries. A new rexg-render takes effect at the next reload. A new Ghostty takes effect in a new window. A new Rex server takes effect only after the old server stops. That is when the red not connected line appears briefly. The client starts the new server, Rex restores the sessions, and step 9 above revives the startup tabs. Rex restores a session after any restart, clean or not, including a reboot.
