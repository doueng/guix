Result of the Emacs prototype

Built and kept (W191). make verify ONLY=bbh-bombadil drives the split Inbox in a capped emacs -nw on a throwaway churning controller. It checks 12 screen properties at about 7 screens/s. Within its first hour it found two real bugs, both now fixed with ERT tests: the thread list could hide the thread that needs you above its window, and C-c C-c opened org's Tags prompt and stalled the Inbox. After the fixes, two 10-minute runs passed. It also surfaced four smaller issues, reported to their owners. Full report: bombadil-inbox-report.html. measured
Extended to the Worker view (W192). make verify ONLY=bbh-bombadil now runs the Inbox, then the Router and Worker transcripts with their composer. A real controller drives real bbh acp sessions on a script model that streams in chunks, over 5 MB anonymized real transcripts, with injected turn-end errors (T163) and SIGKILLed Workers (T162). It found eight real bugs, all fixed with ERT tests, for example: a restart erased the half-typed draft; i stranded the read-only transcript and the thread list in insert state; a reader scrolled into a reply was pulled back as it streamed or rendered again; and text typed right after a send to the Router was erased. Every command plus its redisplay has a 1 s bound, stalls between commands too, and a 15 s watchdog catches hangs. In the final clean 10-minute run, scroll steps in the 5 MB transcript took a p95 of 26–45 ms and at most 121 ms, and the longest stall was 795 ms. One rare blank-rows case after re-entering the Router view stays open. Full report: bombadil-worker-report.html. measured

Verdict

oilfm: skip Bombadil. It cannot drive a native Wayland window. Also, the brief is out of date: oilfm is no longer Zig on zgui. T122 rewrote it in Rust on gpui. It already has proptest planner properties and a headless gpui TestApp that types keys and checks files on disk. The cheap win is a proptest random key sequence test on that harness, about half a day guess.
bbh Emacs UI: prototype, time-boxed to about 1.5 days guess. Bombadil's terminal driver ran emacs -nw on this machine at 76 states/s. The model-level rules (never waiting while working, an ask closes once) are already covered by T154/T170 properties and T66's TLA+. What is not covered is the screen: async bbh inbox refreshes racing real keystrokes through evil, and batch ERT never redisplays. That layer is exactly what Bombadil sees. Stop if a few hours of runs find nothing, or if flakiness from mid-redisplay samples swamps the signal.
Web inbox (T121): later, and only if the TTY prototype pays off. The browser driver gives default properties (no uncaught exceptions or console errors) for free and is the more mature driver. But Chromium is not on PATH here, and the web view mirrors the same model, so it adds less. Never point it at the live controller: it would click real answers.

What Bombadil is

Property-based testing for UIs, from Antithesis, MIT licensed, version 0.7.10 (repo commit 69a61bc, 2026-11-13). It's standalone: Antithesis is optional, an environment where it can also run. measured

QuestionAnswer
What it drivesTwo drivers. browser: anything with a DOM, through Chrome or Chromium over CDP. It can also attach to an existing Chrome or Electron app on a remote-debugging port. terminal (marked experimental): any program on a PTY (portable-pty), with the screen parsed by libghostty-vt. No native GUI driver, so nothing for Wayland or X11 windows. measured
How it exploresRandom weighted choice from action templates that your generators return for the current state (actions, weighted, map/filter/flatMap, .when). The terminal actions are TypeText (regex or charset generators), Resize, Click(row, column) and ScrollUp/Down. In the browser, JS coverage is instrumented and fed to the Antithesis fuzzer; there is no coverage guidance when running locally inferred. fuzz runs many short runs (experimental).
SpecsTypeScript modules that export properties and generators. extract(state => …) makes a Cell; properties are LTL formulas: always, next, eventually, now, .and/.or/.implies/not. Terminal state is grid (rows, cells, styles), scrollback, cursor, exitStatus and lastAction. Custom actions are browser-only. measured
RuntimeOne static Rust binary. It transpiles TS with oxc and runs it in the boa JS engine, so Node is not needed; npm only provides the type definitions. Specs see only the extracted state and cannot read files inferred from boa having no fs bindings.
DebuggingTraces, --reproduce (best effort), shrink (experimental), browser inspect web viewer. The terminal trace viewer is documented on main but not yet in 0.7.10. measured
aarch64 / GuixThe release ships bombadil-aarch64-linux, statically linked with musl (14 MB), and it runs on this Asahi kernel. There's no Guix package inferred. A tiny binary-download package or a pinned fetch in a bb task would do. There's also a Nix flake. measured

Smoke run on this machine

measured I downloaded the release binary to /tmp and ran a 20 s terminal test against emacs -Q -nw. The spec said the mode line names *scratch*, and the generators typed letters plus C-n/C-p/C-f/C-b/RET/DEL/C-g (never C-x).

  • Throughput 76.3 states/s, default quiescence 5 ms.
  • It flagged a violation after about 10 s, a state where the mode-line row was blank. The likely cause is a sample taken mid-redisplay or a grown echo area inferred. This is the main risk for Emacs: properties must tolerate transient frames, or --quiescence-timeout-ms must be raised.
  • terminal shrink reproduced the violation 2 of 3 times, then failed with “No such file or directory”. Shrinking is labeled experimental and was not usable in this run.

Spec and trace: /tmp/bombadil-spec/emacs.ts and /tmp/bombadil-spec/trace.bin (temporary).

oilfm

Brief correction measured. /home/engstrand/projects/oilfm is a Rust Cargo workspace on gpui (Zed). T122 commit ee1124d0 says “rewrite the GUI on gpui … drop vendored zgui”. The check is scripts/cargo test --workspace --features oilfm/ui-tests, not zig build test. Zig fuzzing therefore no longer applies; cargo-fuzz or proptest are the native tools.

Fit

  • Native Wayland window: Bombadil has no driver for it. A Wayland driver would mean ydotool plus screenshots and OCR, which is flaky and outside Bombadil.
  • Test mode on a TTY: oilfm-core's editor and session are GUI-free, so a small TUI front-end could expose them to the terminal driver. But that tests a front-end nobody uses, and the core is already reachable from Rust tests.
  • Port the planner to a web view: same objection, and more work.
  • What exists already measured: crates/oilfm-core/tests/plan_props.rs runs 512 proptest cases. Each one builds a random tree and random edits, plans, applies, and checks that the result equals the edited buffers. Deletes are exactly the confirmed ones, nothing outside the root and trash changes, a refused plan touches nothing, and a stale plan touches nothing. crates/oilfm/src/view_tests.rs drives the real view headlessly with simulate_keystroke and checks files on disk.

Plan (if wanted): about 0.5 day guess

  2. Check the invariants above after each key. proptest shrinks the sequence for free, which Bombadil's terminal shrink could not do here.

bbh Emacs UI

What is already covered

  • measured In /home/engstrand/guix/desktop/build/bbh/test/bbh/super_property_test.clj, random command sequences check “a Worker seen mid-turn is never shown as waiting”, that waiting agrees with the asks, and the ask lifecycle ranks (an ask is answered once, a closed ask refuses an answer).
  • T66 TLA+ (/home/engstrand/guix/desktop/build/bbh/verify/tla/Super.tla) checks StoppedAskWaits, TypedAnswerCloses, AnsweredAfterTaken and NoReplyWaitsOnFinished.
  • T154 harness_property_test.clj covers the journal, mailbox, checkpoint and transcript. T170 added a seeded ERT property for inbox rows (width and order) in agent-shell-test.el.
  • Emacs takes its status from the controller, which decides the :status of each row (bbh-super.el, the status glyph function). So “never waiting while working” is a model rule already checked, and the UI only has to render it faithfully.

The gap Bombadil fits

The screen layer. The inbox reloads by running bbh inbox asynchronously (make-process with a sentinel), and keys arrive through evil and keymaps meanwhile. Batch ERT never redisplays (the tty-scroll test says so). The existing TTY tests use script plus emacs -nw but feed keys with execute-kbd-macro. Those keys probably don't interleave with process output the way real typing does inferred. Bombadil types into a real PTY, waits for output, and checks temporal properties on what is drawn.

Seams that already exist measured

  • eng/bbh-inbox-bbh overrides the bbh command the inbox runs, so Emacs can be pointed at a test controller.
  • web_test.clj's start-super runs a controller in temp dirs with no-op launch, retire and release, and run-worker starts a Worker on it. A churn script on top can make fake Workers ask, note, go busy and finish.

Properties as Bombadil formulas inferred design

Your propertyScreen version
Status never shows waiting while workingalways: no row has ◐ and an open question, and no row in a waiting section (STOPPED, HOLDING-UP, WAITING) shows ◐. Bombadil cannot read controller state, so the fixture gives every ask a unique text to make the screen self-describing.
Answering an ask closes it exactly onceAfter a pick key (1–9 or .) on a row showing ask X, eventually X is gone, and from then on always X never shows again (unique texts make reappearance a bug).
C-n always sendsAfter C-n with a non-empty draft, eventually the draft is empty, and the echo area always lacks “is undefined”. Covers normal and insert state and an open completion popup (agent-shell.el binds a popup-aware C-n).
Navigation keeps pointIf the last action was not a motion or pick key, then next the selected thread id is unchanged unless that row disappeared, which catches async refresh jumps.

Prototype plan: about 1.5 days guess

  1. Fixture (3 h). A bb task that starts a temp controller as start-super does, then churns fake Workers on a timer (ask with unique text, note, busy and idle, finish). It prints the dir.
  2. Launcher (2 h). emacs -Q -nw that loads evil and bbh-super.el the way tty-scroll-test.el does, with eng/bbh-inbox-bbh pointed at the fixture, opening the split inbox.
  3. Spec (4 h). Extractors that parse rows (glyph, id, section header, ask text), the selected row, the evil state and the echo row. Weighted generators: j/k/TAB/RET/]t/1–9/./i plus text/C-n/Esc/gr. Never SPC q, C-x C-c, J (jjui) or D/archive on non-fixture rows. The four properties above, written to tolerate one transient frame, with --quiescence-timeout-ms around 30.
  4. Run and judge (3 h). Run 3 × 10 min, triage, and write up. Keep it only if it finds a real bug or runs clean and cheap. Then add a bb test:bombadil task and a checks.edn rule, with the binary pinned by hash. It stays out of make verify by default because it is slow.

Risks: the terminal driver is marked experimental, shrink failed here, and repro was 2 of 3. Emacs redraw timing needs the property tolerance above. Real Doom config is heavy, so test the bbh modules on -Q plus evil as the TTY tests do, which misses Doom keymap interactions.
