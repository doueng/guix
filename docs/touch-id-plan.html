Touch ID on your own M1 Air kernel: plan

Goal. You want Touch ID (login, sudo, lock screen) on this MacBook Air M1 (J313, T8103) under your own Guix kernel package from T212 (AsahiLinux asahi-7.2.15-1 plus kernel.config, built on guix-builder). This is the plan: how it works, who has it working, what the kernel and userspace need, what it costs in trust and risk, and a staged path with go or no-go points. Investigation only: no kernel change, nothing loaded, no reboot.

Short answer. It is possible, but not on your T212 kernel yet, and not safely on a Mac that still runs macOS. Upstream Asahi has nothing: SEP is WIP and Touch ID TBA on M1, and its kernel carries only a 375-line SEP boot stub. The only working stack is Aurora Silicon's apple_sep driver: 56 files and 42,584 new lines on Linux 7.3, plus SPI, mailbox, trusted-key and Rust API changes, about 10 libfprint and 4 fprintd patches, a PAM re-arm module and a root daemon. Aurora enrolled and matched on a J313 with your exact firmware, but nobody has seen a real PAM unlock on M1. The serious problem is that the driver always writes to the Secure Enclave storage file it shares with macOS. On M1, creating Linux's keybag rewrites a record that macOS also reads, and that cannot be undone. My recommendation is no-go for now. Do the read-only Stage 0 at any time. Revisit when one of the triggers in Tracking upstream fires, or if you are willing to treat macOS Touch ID as expendable.

1. The path from finger to sudo

  • Sensor. The Mesa sensor sits in the power button, on SPI bus 2 at 0x235108000, chip select 0, 8 MHz, powered by AP GPIO 108. Aurora worked out the pin group and the 120 MHz parent clock by measurement. Your running device tree has no spi@235108000 node at all, so Linux cannot see the sensor today measured (/proc/device-tree/soc lists spi@235100000, 235104000 and 23510c000 only).
  • Transport. Linux drives the SPI bus, but it only carries frames between the sensor and the enclave. The enclave authenticates the sensor (the SCRD endpoint) with the per-machine factory calibration apple/mesacal-j313.bin, which must be carved out of your own iBootSystemContainer. It is not redistributable inferred (mesa-fingerprint binding, extract-mesa-calibration.py).
  • SEP. On M1, iBoot puts the SEP to sleep before handing over, and the OS must boot sepOS again from a reserved region (TZ0, then IMG4). Your Asahi kernel already does this on every boot: the stub apple_sep driver is bound to 242400000.sep, with the sepfw carveout and the iboot-manifest and local-policy-manifest properties from m1n1 measured. After the boot, though, nothing talks to the enclave. The sepOS it boots is the 13.5 (22G74) one that matches your stub's asahi,os-fw-version = 13.5 and iBoot-8422.141.2. That is the exact combination Aurora's T8103 profile was written against measured (/proc/device-tree/chosen; profile.rs).
  • Endpoints. sepOS has twelve endpoints. Touch ID needs SBIO (biometrics), SCRD (credential/sensor authentication), SKS (key store, keybags) and xARM (secure storage), all over the ASC mailbox and a shared-memory window behind the SEP's DART. This is not RTKit: sepOS is its own OS inferred (Asahi docs hw/soc/sep.md).
  • Storage. The enclave keeps its anti-replay state in the xART gigalocker, a 6 MiB .gl file inside the 500 MB APFS iBootSystemContainer (nvme0n1p1 here). Every OS on the Mac shares it. The enclave asks the AP to read and write it, so Linux's driver has to parse APFS and write raw blocks. Prints and keys themselves never leave the enclave unencrypted. Linux keeps encrypted blobs in /var/lib: keybag, owner, user and master catacombs, the host-state store and the guard list inferred (XART-SAFETY.md, HOST-STATE.md).
  • Userspace. /dev/sep-bio (ioctl ABI v4 or v5), then the aurora libfprint driver, then fprintd over D-Bus, then pam_fprintd. The enclave does the matching and returns a result and a match token.

The OS identity gap on your boot chain

The T8103 profile takes the SEP OS identity, which picks the anti-replay lane, from /chosen/apfs-preboot-uuid. Only Aurora's m1n1 fork (aura, src/kboot.c line 1227) forwards it. Upstream m1n1 (5e3a756) does not, and your /chosen has no such property measured. Without it the driver refuses to enrol. So you would pass apple_sep.os_uuid_hi= and apple_sep.os_uuid_lo= on the kernel command line. Their value is your Linux stub's APFS volume-group UUID, which must not be macOS's and must never change afterwards (OS-IDENTITY.md). The other option is a small patch to the m1n1 you vendor in boot.scm. The command-line route keeps m1n1's store path, and so your known-good boot chain, unchanged inferred.

5. Enrolment

  • macOS prints do not carry over. They live in macOS's keybag, under macOS's OS identity and anti-replay lane. Linux gets its own identity, keybag and catacombs, and you enrol again under Linux inferred (OS-IDENTITY.md). Do not pin Linux to macOS's identity: enrolling in one would then invalidate the other.
  • Limits. ENROL_START requires a live identity count below three, so at most three fingers per Linux lane inferred (README line 109). The enclave enforces the lockout.
  • Flow. First boot with the driver creates Linux's identity keybag (the risky write, see section 7). fprintd-enroll then takes about a dozen touches. The driver saves the user and master catacombs at the end, and after a reboot Touch ID: restored N must appear before you trust it.
  • State to protect. The files /var/lib/aurora-sep* and /var/lib/fprint are root-only and tied to this machine. Back them up while the services are stopped. Never restore an old copy after the SEP has written: file rollback does not roll back the enclave's counters. That also rules out btrfs snapshot rollback of /var/lib.

6. Security: what you keep and what you lose

Keep (vs macOS)Lose or weaken
  • Matching, templates and the attempt counter stay inside the enclave. Linux never sees an image or a template.
  • Sensor-to-enclave traffic is authenticated, so a compromised AP cannot replay a captured finger to the enclave inferred.
  • Anti-replay counters in xART: deleted prints stay deleted.
  • Optional: SEP-sealed trusted keys (keyctl), which Aurora uses for LUKS and SSH.
  • The PAM decision runs on the AP. On macOS a match releases keys from the enclave. On Linux, sudo trusts a D-Bus answer from root-owned fprintd. Anyone with root, or a modified kernel, can fake a yes. Your boot is Asahi's permissive security mode, so the kernel itself is not measured inferred.
  • Match tokens come from Linux's CSPRNG, because the J313's SEP control entropy returned zeros measured (M1-SUPPORT.md line 28).
  • A fingerprint is a weaker factor than your password for sudo (coercion, lifted prints). macOS weighs this the same way. Keep the password for anything that changes the system.

New attack surface. About 43k lines of young, LLM-assisted ring-0 Rust and C that parse APFS and enclave replies measured. An ioctl ABI on /dev/sep-bio. A root daemon that receives your password to re-arm Touch ID. fprintd reading every input device. Raw block writes into a partition macOS owns. None of this code has had an outside review guess.

Aside: a possible bug in your current kernel

The build failure points to something that affects T212 today. Aurora's Documentation/rust/bindgen-layout-checks.rst says the following. With CONFIG_SCHEDSTATS=n, struct sched_statistics is an empty cacheline-aligned struct. Stock bindgen (0.73.2 and earlier) drops its alignment, which shifts task_struct fields after it, including mm, by 40 bytes on arm64 defconfig plus Asahi config. Rust then read a wrong pointer, and Asahi's RSS charge faulted. Your running kernel has SCHEDSTATS off and was built with Guix's bindgen 0.71.1 and --no-layout-tests measured. Asahi 7.2.15's rust/bindgen_parameters lacks Aurora's one-line fix, --opaque-type sched_statistics measured. If Aurora is right, your Rust GPU driver could misread task_struct inferred. I have not reproduced the fault. The cheap check is to set CONFIG_SCHEDSTATS=y in kernel.config, or carry that one-line patch. Treat it as a separate T212 follow-up.
