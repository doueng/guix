Hegel property testing for bbh: review

Verdict: skip the babashka migration, and maybe use Hegel for new Emacs Lisp properties. Hegel works on this machine. My spike drove it from both bb and batch Emacs. But bb cannot load a C library (it has no FFI), so every bb test would run a helper process I wrote and talk to it over a pipe. That adds a native binary to build and pin, adds 0.2 to 0.5 s to cheap properties, and ties the suite to a 0.x C ABI that shipped 22 releases in the last month. Shrinking was about as good as test.check. One stateful bug was missed in 2 of 3 runs because Hegel's lists are shorter by default. The clear gain is in Emacs, where the one random test has no shrinking at all. I have migrated nothing.

Labels: measured = I ran it on this M1 with bb 1.13.229 and Emacs batch. read = taken from Hegel's source or docs. inferred = my reasoning, not tested.

1. What Hegel is

  • Engine plus thin frontends (read). libhegel is a Rust library with a C ABI (hegel.h, 159 functions). It owns generation, shrinking, the example database and stateful rule selection. Each language frontend draws typed values through calls like hegel_generate_integer and hegel_new_collection, then reports the result with hegel_mark_complete (valid, invalid for an assume, overrun, or interesting for a failure). Docs: https://hegel.dev/explanation/how-hegel-works
  • No wire protocol any more (read). The old hegel-core was a Python server with a protocol. Its README says it is "no longer used" and asks users to migrate to the FFI library. So a bb client cannot just speak a protocol. It needs a bridge.
  • Frontends (read): Rust, Python, Go, C++, TypeScript, Java (JNA or FFM), OCaml and C#. There is none for Clojure or Emacs Lisp. The Java one needs a JVM with JNA or FFM, and bb has neither (measured: java.lang.foreign.Linker does not resolve in bb).
  • Shrinking (read): it shrinks the choice sequence, Hypothesis-style. Spans group draws so that, for example, a list element is deleted as a unit. Failures are grouped by an origin string, and each origin is treated as a separate bug.
  • Example database (read, measured): failures are stored per key in a directory and replayed first on the next run. A reproduce blob (base64) replays one exact case. In my spike, a rerun of a failing property took 2 cases instead of 730.
  • Stateful testing (read, not spiked): an engine-owned state machine with weighted rules, rule rejection, invariants and a step count (see examples/state_machine.c).
  • License and platforms (read): MIT. Prebuilt libhegel-linux-arm64.so ships with each release. 0.51.5 ran here after adding an rpath for libgcc_s (measured).
  • Guix (inferred): it can be packaged from source with cargo-build-system. The crate has 8 dependencies plus rustix, and needs Rust 1.86 or newer and edition 2024. A quicker route is a binary package fixed up with patchelf.
  • Maturity (read): 96 libhegel releases since 0.24.0 (2026-07-03), 22 of them in the last 30 days, and 28 minor bumps. Breaking ABI renames ship without shims, such as hegel_test_case_is_nondeterministic becoming hegel_test_case_should_capture.

3. The spike

All spike files are in /home/engstrand/.local/state/bbh/workflows/20261114-102612-099-investigation/evidence/spike

  • hegel-pipe.c (113 lines): a line-protocol bridge over libhegel. It handles start, next, integer, boolean, collection, span and complete.
  • hegel.clj (80 lines): a bb client with integer, elements, one-of, tuple, fmap, vector-of, such-that, assume and check.
  • hegel.el (65 lines): an Elisp client over make-process, with a hegel-deftest macro that wraps ert-deftest.
  • spike.clj: ports two real properties, spoken handle and random command sequences, and adds planted-bug variants.

Shrink quality is on par. Both libraries reach minimal or near-minimal inputs. The missed stateful bug comes from short default collections, not from a defect in Hegel (inferred). Fixing it needs a min_size or a port to Hegel's state-machine API. Either way the generator has to be redesigned, not just swapped.

4. Assessment

  1. babashka client: feasible with a bridge. That means about 120 lines of C for the bridge, about 200 for a production bb client, and a pinned libhegel. bb cannot load libhegel directly. A bb pod in Rust would also work, but it still runs as a separate process (inferred).
  2. Emacs client: feasible. It can use the same bridge over make-process (measured working in batch Emacs). An Emacs dynamic module would be faster (Emacs here was built with modules), but the build is heavier (inferred). It integrates with ERT through a hegel-deftest macro.
  3. What it buys: a failure database replayed across runs (bb has seed replay already), engine-owned stateful testing, and one engine for both bb and Elisp. In Emacs it also brings shrinking, which the tests lack today.
  4. What it costs: a native binary and a bridge to keep building, 0.2 to 0.5 s added to cheap properties under bb, an unstable 0.x ABI, generators retuned for each property, and a client library of our own to maintain, since there is no upstream Clojure or Elisp binding.

My pick: keep test.check for bb. If you want shrinking in Emacs, the smaller step is a small seed-and-retry shrinker in plain ERT (guess: about 20 lines). Revisit Hegel for Elisp once libhegel reaches 1.0 or ships a CLI or protocol mode. If you still want it now, the cheapest real gain is to port only the Elisp inbox property, with the bridge pinned to one libhegel release.
