Answer

Build level 1 in Babashka, with a small amount of level 2. Leave the daemon, the bootstrap and the 33k packages to Guix. A Clojure front end that talks to the real guix-daemon took about 100 lines here. It wrote a .drv, the daemon accepted it and built it, and the output landed at the store path the Clojure code had computed measured. From there your derivations can depend on any .drv Guix produces, so you keep all of Guix's packages and substitutes. You'd be writing glue in Clojure, not running a fork.
Jolt is promising but not ready to build on. It's Clojure compiled to Chez Scheme (not Guile). It is 5½ months old and mostly one author's work, and has no Linux aarch64 release. It did build and run here from source (with a patched Chez and two workarounds) and starts in 0.11 s, against Babashka's 0.01 s. It has no Unix-domain sockets and no SHA-256 built in, and Guix needs both on day one measured. Check again in 6–12 months. Its one real advantage is that it can be built from source, so in principle it could run inside builds. Babashka can't: you install a prebuilt GraalVM binary.
Levels 3 and 4 (your own daemon, a translated package collection) take person-years and mean maintaining a fork forever. The C++ daemon alone is 16,752 lines. Guix has 32,957 packages, and most of their build phases are Guile code that runs inside the build. Upstream has been working on a Guile daemon for years and it still isn't on master measured/inferred.

Levels of porting

Effort is for one person working evenings guess. Bar lengths are illustrative.

Level 1: a Clojure front end to the existing daemon

What: a guix.store library (RPCs including add-to-store with nar streaming, build-things, query-path-info, GC roots), guix.drv (ATerm read/write, hashing modulo inputs, fixed outputs), guix.nar and guix.base32. About 600–900 lines. The course's reference has the same parts in 578 lines of Guile (store 207, derivation 226, nar 145) measured.
Reusing Guix: get a package's .drv from guix build -d hello (or read Guix's .drv files) and list it as an input. Your derivations then sit on top of the whole collection and its substitutes inferred.
Risks: protocol drift (low: it's at 0x164 and keeps backwards compatibility). Builder code is whatever you can run in the sandbox, which today means bash, Guile, or a binary you copy into the store.
Gain: scripting the store from bbh/wf at bb speed, inspecting the store and deps graph from your REPL, and an understanding of Guix's core that you can test.

Level 2: a Clojure package and service DSL

2a, compile to Guix Scheme: EDN or Clojure macros print (package …) and (service …) forms into a channel module, and Guix does everything else. Gexps go across as quoted Guile forms. A few weeks gets a subset that covers your 54 modules in modules/engstrand measured/guess. Risks: two languages per bug, errors point at generated Scheme, and every Guix service record needs a mapping. The gain is small, since Guix's Scheme is already a Lisp DSL.
2b, compile straight to .drv: you'd reimplement lowering for the build systems you use (gnu-build-system first). The builder side can reuse Guix's Guile build modules as store inputs, or be Clojure, which needs a Clojure runtime in the store built from source. Jolt is the only candidate, and not yet. Byte-identical .drvs, the only way to get Guix's substitutes, would mean matching how Guix prints its builder scripts exactly. Expect your own builds instead inferred.

Level 3: full reimplementation including the daemon

That's 16.7k lines of C++ semantics (sandbox, users, locking, SQLite schema, GC, offload) plus about 20k lines of core Guile (store, derivations, gexp, packages, profiles, grafts…) measured. A daemon would run as root, and mistakes there are security holes. Guix's own Guile-daemon effort has run for years without landing inferred. JVM Clojure would be the sensible runtime for it. Gain: deep understanding, which the course already gives you at about 1,300 lines.

Level 4: translating the package collection

32,957 packages. The forms translate mechanically, but phases and snippets are Guile that runs in builds, and the bootstrap (commencement.scm) is Guile all the way down. Guix gets many commits a day guess, so the translation is stale within a week unless you re-run it on a schedule. And it still wouldn't give you substitutes unless the .drvs come out identical. Not worth doing.

How it relates to the course and bbh

  • Course (T191, /home/engstrand/projects/build-your-own-guix): its tester only runs ./byog as a process, so stages 01–11 and 13–17 work in any language (README) measured. Stages 12 (package language) and 18 (gexp) need a Lisp, and Clojure is one. A Clojure track of the course is level 1 plus a toy level 2, and stages 01–07 already check against real Guix values. That's the natural home for this work.
  • bbh/Babashka: level 1 as a bb library drops straight into bbh. For example, wf could query query-path-info/references, check a revision's derivation without guix repl, or build ad-hoc derivations inferred. The spike code is already bb.
  • Your Guix config: keep it in Scheme. Level 2a only pays off if a Clojure DSL removes real pain, and nothing in this investigation showed that pain guess.

Recommendation

  1. Build level 1 in Babashka as a Clojure track of the course: store client, drv, nar, base32, building the course's stages and checked against Guix's values. Estimate 1–3 weeks guess.
  2. Add a small level 2 on top: a defpackage macro that lowers to a .drv over Guix's own .drvs, with builders in bash or Guile. Stop there unless it turns out to be fun.
  3. Track Jolt, and re-run the probe when it ships an aarch64-linux binary, Unix sockets and a digest provider. Those are what would make it worth a look as a builder-side Clojure. Upstreaming a Guix package for it (patched Chez + seed) would be its own project.
  4. Don't do levels 3 or 4.
