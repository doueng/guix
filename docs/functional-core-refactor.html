Verdict

Most of the state is already a functional core. measured
  • bbh super: bbh.super.model is pure. decide turns a command into events and fold applies them. The state is a fold over the event log in super.db, which holds 24,984 events since 2 November. store/commit! is the only SQL. A property test drives random command sequences through it and checks Super.tla's rules.
  • wf: workflow/fold-event, replay and decide are pure. run-gates and attest! are the shell.
  • ghostty-rex: rexg.model is pure. Keys, Rex results and sidecar messages go in, and [m outs] comes back. The rexmux sidecar's deliver and handle return [state msgs].
What is still tangled is the layer that reacts to the world. inferred These loops read processes, files and sockets, then decide what to do and do it in the same function. That layer is reconcile!, dispatch!, launch-steps! and ensure-router! in bbh/super.clj, notify/tick!, voice/submit!, the handle! and :connect code in rexg/main.clj, and the sidecar commands that spawn inside :run. Their decisions are not in the pure model, so property tests and TLA+ do not cover them. Two of the three recent bugs came from this layer.
My opinion. guess Don't do a big refactor. The pure parts are already sound, and rewriting them buys little. Instead, take the decision out of each reactor into a pure plan function that returns effect data, and leave a dumb interpreter behind it. Do this one reactor at a time, starting with the ones behind real bugs: the cancel path (W262), the Rex reconnect, and sidecar spawning. Each step is small, keeps behavior, and adds a property test or a TLA+ action that matches the new code. Stop when what is left in the shell is IO with no if worth testing. Skip rexg-render, the SQL store, the jj, inbox and Emacs adapters, the web handlers and the sandbox.

The shape: observe, plan, perform

bbh super already has the inner loop: a command goes through decide, and the events it returns go through fold. What it lacks is an outer loop with the same discipline. Each reactor would split into three parts:

  1. observe! reads the world into a plain map and decides nothing. It may stay lazy, as emacs-up? is a delay today.
  2. plan is pure. From state, observations, now and policy it returns a vector of effects. All the conds live here.
  3. perform! is one case per effect kind. It contains no decisions. A failure becomes an event, or the next pass retries.

Effect vocabulary, bbh super

[:command {:id "cancelled-W262" :command :cancel-delivered! :args {...}}] ; commit via store, as run! does
[:job/stop job]                       ; process/stop-job!, then write <base>.exit 137
[:mailbox/send conv {:message-id m :text t :kind k}] then [:command :outbox-sent!]
[:mailbox/delete conv message]
[:session/open {:workspace :conversation :token-hash ...}]  ; token made in the shell, hash in the command
[:session/release w]   [:session/end agent]
[:wf/start w]  [:wf/close w]  [:jj/land w]  [:jj/advance w]  [:workspace/retire w]
[:notify/show n prev-handle]  [:notify/close handle]  [:views/changed]

bbh, area by area

1. Worker lifecycle: the cancel that never finished (W262)

What the event log shows measured
  • 14:01, seq 24246: W262's health is :needs-human. Job 1795269661329-245 is :unknown with pid nil: it "can no longer be identified as the process that started it".
  • 14:56, seq 24511 and 24513: cancel-requested, then outbox row o2357 sent and acked. The session took the cancel.
  • 15:06, seq 24522: timer-fired :cancelling W262. That was the 10-minute deadline from model/deadlines.
  • No worker-finished follows. At 15:17 the Router started T210 (W266) to work around "W262 is stuck cancelling".

Why it stuck inferred. The cancel can complete only in the shell, in reconcile!:

;; super.clj 675-683, today
(= :cancelling (:state w))
(let [blocked (filter #(#{:unknown :lost} (:state %)) jobs)
      running (filter #(= :running (:state %)) jobs)
      stopped? (every? true? (mapv process/stop-job! running))]
  (when (and (empty? blocked) stopped?)
    (doseq [j running] (spit (str (:base j) ".exit") "137\n"))
    (when (or (not agent) (not (model/cancel-owed? @state w)))
      (run! c :controller {:id (str "cancelled-" (:id w)) :command :cancel-delivered! ...})
      (promote! c))))

An :unknown job makes blocked non-empty, so the branch does nothing on every pass, and nothing records why. Super.tla models the guard as csig[w] /= "owed" \/ ended[w], without the job condition, and has no liveness rule that a cancel ends. The model checker passed while the code could wait forever. The person found out through the deadline timer. The deadline caught the hang, but it couldn't say what was blocking or offer a way out.

After: the decision moves into the model, where every outcome is named.

;; bbh.super.model, pure
(defn cancel-plan
  "Effects that move :cancelling Worker W on, from OBS (its :agent and :jobs)."
  [state w {:keys [agent jobs]}]
  (let [unknown (filterv #(#{:unknown :lost} (:state %)) jobs)
        running (filterv #(= :running (:state %)) jobs)]
    (cond
      (seq unknown)
      [[:command {:id (str "cancel-blocked-" (:id w) "-" (count unknown))
                  :command :cancel-blocked! :args {:worker (:id w) :jobs (mapv :id unknown)}}]]
      (seq running) (mapv #(vector :job/stop %) running)   ; next pass sees them gone
      (or (not agent) (not (cancel-owed? state w)))
      [[:command {:id (str "cancelled-" (:id w)) :command :cancel-delivered! :args {:worker (:id w)}}]
       [:promote]]
      :else [])))

;; bbh.super, the shell
(defn- perform! [c [kind x]]
  (case kind
    :command  (run! c :controller x)
    :job/stop (when (process/stop-job! x) (spit (str (:base x) ".exit") "137\n"))
    :promote  (promote! c)))

:cancel-blocked! folds into a :needs entry that the Inbox shows: "W262's cancel waits on job …245, which can no longer be identified; abandon it?". The person or the Router can answer with a :abandon-job! command. The TLA+ model gains a Blocked(w) variable and the liveness rule Cancelling(w) ~> (Finished(w) \/ NeedsPerson(w)). TLC would have reported the W262 hang as a counterexample before the fix inferred.

The same split applies to the rest of reconcile!: the health commit, the :starting to :running transition, and the relaunch after the restart grace. Together they make one (model/reconcile-plan state obs now policy). Generating the token stays in the shell. The plan asks for one with [:session/open ...], and the shell adds the hash to the :issue-token! command.

2. Outbox and inbox: dispatch!

The current version is safe: every step is a command with a fixed id, so a repeated pass is idempotent measured. What remains in the shell is the choice of rows: Router batching, summaries, acking when the file is gone, and dropping rows of finished Workers. That becomes (model/outbox-plan state {:mailbox-files #{...}}), which returns [:mailbox/send ...], [:command :outbox-acked!] and [:mailbox/delete ...]. You gain a property test for "a row of a finished Worker is never sent" and "the Router batch goes as one", without files. Medium value: no recent bug came from here.

3. Launch, promote, Router

launch-steps! is a sequence in which each step needs the previous step's result: the workspace path, then the wf run id, then the buffer. Plans of effect data can only express that as several passes, one effect each, with the result fed back as a command. :worker-prepared! already does this. So the split costs more here than it buys. I'd only move the decision "start the Router now?" into the model: no Router agent, grace window passed, Emacs up. Today that decision depends on (:router-tried c), an atom that a restart forgets inferred.

4. Event log, state, asks, workflows: leave them

These already follow the pattern. The one change worth making is to log raw observations as well as the results computed from them. health-observed (6,803 events) and machine-observed (4,695) already exist measured. If reconcile-plan's input were logged in a compact form, a bug report could replay a stuck Worker's exact pass. Keep the volume in mind: health is about 27% of all events. One option is to log observations only when the plan's output changes guess.

5. Notifications: notify/tick!

;; today: plan is pure, but tick! swaps atoms between show!/close! calls

  (when (= :burst (:key n)) (doseq [t ...] ((:close! effects) (@shown t)) (swap! shown dissoc t)))

;; after: one pure step, handles come back as events
(defn step [notifier state now policy overrides]
  {:notifier notifier' :effects [[:notify/close h] [:notify/show n prev-handle] ...] :due due})

The open question is which handle a show returns. The shell feeds it back as [:shown key handle]. This step is worth doing only when notification bugs come up. Today they don't.

6. Voice: submit!

The safety rules, such as "voice cannot approve", no picks on action or review asks, and the 60-second cursor window, are the most important logic in the file. Yet they sit inside pane/with-state-lock! next to socket calls and System/currentTimeMillis.

;; after: pure interpretation, in two phases because the thread is fetched by handle
(voice/resolve-target text {:selected sel :now now}) ;=> {:thread "T12" :words "option two send"}
(voice/interpret words thread-view sel)             ;=> {:do [[:pick "T12" 2 "a40"] [:send "T12"]]}
                                                    ;   or {:refuse "Voice cannot approve; press A ..."}

A generative test can then check that no utterance ever yields a pick on an :action or :review ask. It is a small change with a safety payoff.

7. Emacs, phone (web.clj), sandbox, inbox, workspace (jj), store

These are adapters: they translate, then call IO. A pure core would be a copy of their arguments. Leave them.

ghostty-rex, area by area

rexg.model (644 lines) is a pure port of rexmux's model.rs, so the Bombadil specs and Rexmux.tla describe it. main.clj (423 lines) is meant to be the shell. But its app atom holds a second, untested model: :conns :tags :streams :sizes :panes :text-reqs :next-req :last-draw :title. Its handle!, mouse! and :connect branches make decisions measured.

1. Reconnect, and 'local not connected'

The T210 mechanism found two causes measured:

  • (a) The shared test harness stopped the user's live Rex server, because rex server stop ignores REX_SERVER.
  • (b) The client never reconnected. On :closed it only echoed, so every later request said "local is not connected".

make switch itself did not stop Rex. T210 fixed (b), but the reconnect policy now lives in the shell:

;; main.clj 356-378, today (abridged)
:connect (let [local? (and (nil? address) (nil? (System/getenv "REX_SERVER")))]
           (when-not (get-in @app [:conns srv])
             (when (and local? (not (fs/exists? sock))) (start-local! log))
             (let [c (try (try!) (catch Exception e
                       (if local? (do (start-local! log) (try (try!) (catch Exception e2 (ex-message e2))))
                                  (ex-message e))))]
               (if (map? c) (do (swap! app assoc-in [:conns srv] c) (follow-events! srv)
                                (step! model/connected srv (:client-id c)))
                            (lost! srv (or c "no server"))))))
;; lost!: (step! model/disconnected ...) then (future (Thread/sleep in-ms) (put! [:connect srv]))

After: the connection becomes a state machine in the model, with :conn in :down, :connecting or :up. Every branch above becomes a returned out:

;; rexg.model, pure
(defn connect-failed [m srv why]
  (let [n (get-in m [:servers srv :attempt] 0)
        ms (retry-ms n)
        start? (and (local? m srv) (#{0 1} n))]        ; :env passed to new-model, no getenv
    (let [[m outs] (disconnected m srv why ms)]
      [m (cond-> outs start? (conj [:start-local-server srv])
                      true   (conj [:after ms [:connect srv]]))])))

(defn closed [m srv why] (connect-failed m srv why))   ; one path for both

;; rexg.main, the shell: no cond, results come back as events
:connect (put! (let [c (try (rex/connect! sock label on-msg) (catch Exception e (ex-message e)))]
                 (if (map? c) [:connected srv c] [:connect-failed srv c])))
:start-local-server (start-local! log)
:after (let [[ms ev] xs] (future (Thread/sleep ms) (put! ev)))

What this buys:

  • A unit test of "closed, failed three times, then connected" that reads like the bug report and runs in milliseconds, not in the 5-minute e2e.
  • Rexmux.tla can add Drop and Reconnect actions plus a liveness rule ServerUp ~> ClientAttached. Today the model covers streams, the link and agents, not loss of the control connection measured. This would have caught (b).
  • It does not catch (a), which came from an ambient address: the Rex CLI acted on the account's server instead of REX_SERVER. The fix there, passing -S everywhere, follows the same principle of making inputs explicit, but at the test harness, not in a core.

2. Command registry and spawning (PATH bugs)

Most registry commands already return effect vectors: :run (fn [ctx args] [[:layer/float {...}]]). The exceptions are the commands behind the T207 PATH bugs measured. They spawn while running:

;; rexmux/commands.clj 178-181, today
:run (fn [ctx _]
       (rex ctx :spawn (:server ctx) ["keyleader" "term-nav" d]
            {"REX_BLOCK" (:block-id ctx) "REX_SESSION" (:session-id ctx) "TERM_PROGRAM" "rex"})
       [])

;; after: data out; make-io's interpreter applies spawn-env and resolve-argv
:run (fn [ctx _]
       [[:spawn {:server (:server ctx) :argv ["keyleader" "term-nav" d]
                 :env {"REX_BLOCK" (:block-id ctx) "REX_SESSION" (:session-id ctx) "TERM_PROGRAM" "rex"}}]])

A test can then assert the exact argv and env every command produces. The one PATH rule, desktop/bin last via spawn-env and resolution against the child's PATH via resolve-argv, is applied in one interpreter and tested with a fake PATH. Ctrl+L or bbh say could no longer bypass it. In the same way, notify-attention! inside sidecar/deliver becomes an outgoing {:op :notify ...}, which makes deliver fully pure. The :eval op stays an intentional escape hatch.

Limits inferred: the root of the PATH bugs is that Hyprland's environment differs from a terminal's. A pure core cannot observe that. The e2e that runs the client with Hyprland's PATH (verify.clj) stays necessary.

3. Rex protocol bookkeeping

Request ids map to tags in (:tags @app), and renderer text requests map through :text-reqs and :next-req. Both are protocol state kept outside the model. Moving them into a pure rexg.link reducer, with outs like (request link srv method payload tag) => [link' id] and (response link srv id) => [link' tag], would let Rexmux.tla's rules EveryRequestAnswered and NoDuplicateReply be property-tested against the code that runs. Medium value.

4. Layout, screen, mouse

screen/render is pure. In main, draw! is a frame diff, which is fine as shell. mouse! (main 262-295), however, decides selection, wheel and click focus, and whether to pass the event to a program that wants mouse reports. That is UI logic of the kind Bombadil specs describe. As (model/mouse m geometry panes ev) => [m outs] it becomes unit-testable. Low to medium value.

5. Key dispatch

This is already pure: keys/read-input and model/key. The only leftover is two side rules in main's :key branch: scroll the focused pane to the bottom and drop the selection. They belong in model/key. It's a ten-minute change.

6. rexg-render (C)

It is the renderer, so it is the shell by definition. Its input is already a small framed protocol. Leave it.

Costs, risks, and where it is not worth it

  • Results that feed the next step. When an effect's result decides the next effect, as in launch (workspace, then wf run, then buffer) or connect (then attach), a plan needs one pass per step and the result fed back as an event. This is correct but indirect. Reading the code means following a loop instead of a let.
  • Staleness. A plan is computed from a snapshot. The shell must perform it under the same lock, or re-check, as attest! does with "the run moved while the gates ran". Commands with fixed ids keep this safe in bbh. In rexg everything runs on one thread, so it's free there.
  • Observation cost. A pure plan wants all its inputs up front. Today emacs-up? is lazy because checking costs a subprocess. Keep the observation lazy, or split observation by need.
  • Two vocabularies to keep in sync: the effect kinds and the interpreter's case. An unknown effect has to fail loudly, not hit nil as main's perform! does today.
  • Regression risk on a live system. bbh super runs every session, and a bad step stalls every Worker. Each step must keep command ids and event kinds unchanged, so the log stays replayable without upcasts.
  • The pattern can become a goal in itself. Building an effect monad or a generic interpreter framework would add code without catching bugs.

Where it is not worth it guess: rexg-render, store.clj, inbox.clj file ops, workspace.clj (jj), emacs.clj, web.clj handlers, sandbox.clj, the CLI entry points, and launch-steps!'s sequence. Also anything already pure: the model, wf decide, the registry's non-spawning commands, screen and keys. The pane byte path in rexg must stay out of any queue. It goes reader → renderer directly today, and that is right.
